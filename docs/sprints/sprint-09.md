- The bug is real and independently confirmed, read directly from INF-014's Outcome, not summarized secondhand: PostgresValidationRunRepository.create_run (services/validation-service/src/app/repositories/postgres_repository.py) calls session.refresh(run) after session.commit(). The per-transaction set_config('app.tenant_id', ...) scope set at the start of the transaction reverts at COMMIT by design (so it can't leak across pooled-connection reuse); refresh() issues a brand-new SELECT in a new transaction that never re-establishes that scope, so RLS correctly (if surprisingly) hides the row that transaction just inserted, and SQLAlchemy raises "could not refresh instance," surfacing to the caller as an HTTP 500. This was invisible before INF-014 because the app previously connected as the superuser naive_first, which Postgres exempts from RLS unconditionally - so this fail-closed behavior never triggered. The row itself is correctly persisted and correctly tenant-isolated (confirmed via direct superuser psql read in INF-014's own verification) - this is a response-construction bug, not a data-loss or isolation bug.
- The working precedent fix already exists in this codebase: services/gateway-api's PostgresTenantRepository.create_tenant / PostgresUserRepository.create_user (shipped in GW-012, Sprint 06) already avoid this exact pitfall, with an explicit code comment (per INF-014's Outcome quoting it directly): "Record built from the already-fully-populated object, not a post-commit session.refresh()... refreshing after commit() would issue a new SELECT in a new transaction... which RLS would then correctly, if surprisingly, block." validation-service's create_run did not follow this same pattern when it was written (VS-013, before INF-014 made RLS bypass-proof).
