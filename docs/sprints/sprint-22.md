# Sprint 22 - DB optimization, part 2 (the three previously-blocked tradeoff items now unblocked)

Sprint goal: the three DB-optimization backlog items that sat blocked on open user tradeoff decisions since Sprint 21 (identity.users email uniqueness, hypertable compression, and a continuous aggregate for dataset listing) are implemented and live-verified, closing out docs/product/backlog-db-optimization.md entirely except the already-resolved DBOPT-010 (Won't).

Backlog source: docs/product/backlog-db-optimization.md (DBOPT-005, DBOPT-008, DBOPT-009 - all three now unblocked by user decisions recorded this session; DBOPT-001/002/003/004/006/007 already done in Sprint 21, DBOPT-010 already closed "Won't (for now)").

Stories in scope (execution order):

1. DBOPT-005 - identity.users: unique index on email (gateway-api). First - Should priority (higher than the other two, both Could), no dependency on the other two items, and its migration shape is the simplest of the three. Sequencing note, not a silent reorder: the user's decision only resolves whether email should be unique going forward - it does not by itself confirm the real identity.users table (293 rows per Sprint 21's live UAT snapshot) is currently free of duplicate emails. A UNIQUE index/constraint migration will fail outright against real data if even one duplicate exists. This must be checked live before the migration is written, not discovered mid-migration - see risk note in the handoff.
2. DBOPT-009 - Continuous aggregate for list_datasets' per-source min/max/count (ingestion-service). Second - Could priority, independent of DBOPT-005 and DBOPT-008 (different schema, no shared table), and structurally the more contained of the two remaining Could items (one new materialized continuous aggregate + one refresh policy, no change to existing row-level query paths or write behavior). Sequenced before DBOPT-008 so the sprint banks a lower-risk win before the higher-risk compression item.
3. DBOPT-008 - Compression policy for old ingestion.price_ohlcv/onchain_metric/sentiment_score/validation.split_results hypertable chunks. Third - Could priority, sequenced last because it is the highest-risk item this sprint (touches write/backfill behavior on compressed chunks per the DBA's own documented tradeoff, and the user's decision attaches a hard requirement - a correctness-validating test against compressed-chunk queries, not just "compression enabled") and benefits from DBOPT-009's aggregate already existing so list_datasets-shaped access patterns can be exercised as part of the ingestion-side correctness validation.

Stories explicitly deferred: none - this sprint closes the remaining open backlog. (DBOPT-010 stays "Won't (for now)", untouched, not a deferral - already closed by the DBA per Sprint 21's own note.)

Definition of done for this sprint:
- All three migrations applied and verified against the real running Postgres/TimescaleDB container (same live-EXPLAIN/live-container verification standard as Sprint 21, not a config-file-only review).
- DBOPT-005: a live duplicate-email check run against the real identity.users table before the unique index/constraint migration is attempted; if duplicates are found, the migration is blocked and escalated back to the PM/user for a resolution decision (merge/rename/soft-delete) rather than silently dropped or forced through. If clean, CREATE UNIQUE INDEX confirmed live and get_user_by_email's existing scalar_one_or_none() behavior re-confirmed unchanged.
- DBOPT-008: compression policy enabled on all four listed hypertables' old chunks, plus a real test that queries data inside a compressed chunk and confirms correct results (not merely that compression is enabled) - per the user's explicit requirement, this is a hard acceptance criterion, not optional polish. Any write/backfill-path regression against compressed chunks (per the DBA's documented "against" tradeoff) is explicitly tested, not assumed away.
- DBOPT-009: continuous aggregate created and its refresh policy confirmed live; list_datasets' response shape confirmed unchanged from the caller's perspective (still source, min(event_time), max(event_time), count), with the accepted staleness window documented in the ingestion-service README rather than left implicit.
- Each touched service's existing test suite re-run with zero regressions.
- Each touched service's README updated where it documents schema/performance/consistency behavior (gateway-api for DBOPT-005; ingestion-service for DBOPT-008 and DBOPT-009, including the new eventual-consistency caveat on list_datasets).
