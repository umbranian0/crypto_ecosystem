## Must

### DBOPT-001 — `identity.api_keys`: no index on `key_hash`, the column every authenticated request's DB query filters on
**Status: Done (Sprint 21, ticket GW-025)** — `CREATE UNIQUE INDEX ix_api_keys_key_hash` shipped and live-verified. Small-table caveat disclosed: at the table's current 206-row size the planner still naturally chooses `Seq Scan`; forcing `SET enable_seqscan = off` confirmed the index is real and usable, and will be picked up automatically once table growth tips the planner's own cost estimate.
**Table/schema**: `identity.api_keys` (gateway-api).
**Query pattern**: `PostgresApiKeyRepository.get_by_hash` (`services/gateway-api/src/app/repositories/postgres_repository.py`) runs `SELECT ... FROM api_keys WHERE key_hash = :key_hash`. This is called from `app.dependencies.auth.get_authenticated_tenant` (`services/gateway-api/src/app/dependencies/auth.py`) — the FastAPI dependency that authenticates **every single request** that passes an API key to gateway-api, i.e. the hottest query path in the whole service. `get_by_hash` is also one of GW-003's two documented tenant-agnostic exceptions (it runs *before* a tenant is known, per the migration's RLS fallback clause), so this query can never be scoped to a small per-tenant slice first — it always searches the full `api_keys` table across all tenants.
**Evidence**: live `EXPLAIN (ANALYZE, BUFFERS)` against the real 197-row table: `Seq Scan on api_keys ... Filter: (key_hash = ...) Rows Removed by Filter: 196`. Currently 0.055ms because the table is small (197 rows across all tenants from this session's UAT), but it is a full-table sequential scan on the true hot path of the service — this scales linearly with total API keys issued platform-wide, not per-tenant, and will not stay this cheap.
**Migration shape**: `CREATE UNIQUE INDEX ix_api_keys_key_hash ON identity.api_keys (key_hash);` — unique because `get_by_hash`'s `scalar_one_or_none()` already assumes at most one row per hash (a SHA-256 digest of a distinct raw key is expected to be unique in practice); a unique index also gives Postgres a cheaper index-only-scan path than a plain non-unique btree.

### DBOPT-002 — `validation.runs`: RLS's `tenant_id` filter has no supporting index; `list_runs`/`count_runs` full-scan the whole table
**Status: Done (Sprint 21, ticket VS-025)** — `CREATE INDEX ix_runs_tenant_id_created_at` shipped and live-verified: both `list_runs`/`count_runs` moved from `Seq Scan` (1,950 rows removed by filter) to `Index Scan`/`Index Only Scan`, with `list_runs` now needing no separate `Sort` node. A clean, unambiguous win.
**Table/schema**: `validation.runs` (validation-service).
**Query pattern**: `PostgresValidationRunRepository.list_runs` — `SELECT * FROM runs WHERE tenant_id = :tenant_id ORDER BY created_at DESC LIMIT :limit OFFSET :offset` — and `.count_runs` — `SELECT count(*) FROM runs WHERE tenant_id = :tenant_id` (`services/validation-service/src/app/repositories/postgres_repository.py`). Both back `GET /runs` (list + pagination count). `runs`' only index today is the PK on `id`; the RLS policy's `USING (tenant_id = current_setting('app.tenant_id'))` clause and both of these `.where(Run.tenant_id == tenant_id)` calls have no index to use.
**Evidence**: live `EXPLAIN (ANALYZE, BUFFERS)` against the real 1,928-row table, scoped to a tenant with exactly 1 row: both `list_runs` and `count_runs` produce `Seq Scan on runs ... Filter: (tenant_id = ...) Rows Removed by Filter: 1927` — i.e. finding 1 row currently costs scanning all 1,928. This is the textbook "unindexed RLS filter becomes a full-table scan" trap called out in the DBA brief, caught live, not speculated.
**Migration shape**: `CREATE INDEX ix_runs_tenant_id_created_at ON validation.runs (tenant_id, created_at DESC);` — composite, tenant_id leading (serves the RLS filter and `count_runs` alone) and `created_at DESC` trailing (serves `list_runs`' `ORDER BY ... DESC` for free, no separate sort step).

### DBOPT-003 — `validation.split_results`: no index on `run_id`; `GET /runs/{id}/splits` scans every one of 108 hypertable chunks
**Status: Done (Sprint 21, ticket VS-026)** — `CREATE INDEX ix_split_results_tenant_run` shipped against the hypertable root and confirmed propagated to all 108/108 existing chunks. **Honest, disclosed finding**: Planning Time did not drop below the ~130ms baseline measured here, because `run_id` is not this hypertable's partitioning column (`test_start` is) — chunk exclusion cannot skip any chunk regardless of indexing, so a plan node is still built per chunk. This migration's real value is closing the RLS-`tenant_id` index gap and readying the table for `DBOPT-004`'s larger future chunks to actually benefit from it, not an immediate planning-time win on the current thin chunk layout.
**Table/schema**: `validation.split_results` (validation-service, TimescaleDB hypertable partitioned on `test_start`, INF-010).
**Query pattern**: `PostgresSplitResultRepository.get_splits` — `SELECT * FROM split_results WHERE run_id = :run_id AND tenant_id = :tenant_id ORDER BY split_index` — backs `GET /runs/{id}/splits`, the per-run drill-down every dashboard/report view of a run's splits uses. `split_results` currently has only its PK `(id, test_start)` and the automatic `test_start DESC` index TimescaleDB creates for its own partitioning column — neither helps a `run_id`/`tenant_id` filter, since `test_start` isn't part of this query's predicate at all.
**Evidence**: live `EXPLAIN (ANALYZE, BUFFERS)` against the real table (108 chunks, 552 rows total): the plan is an `Append` of 108 per-chunk `Seq Scan`s, each filtering on `run_id`/`tenant_id` with no index — **and Planning Time alone was 130ms**, dominated by evaluating chunk exclusion/plan construction across all 108 chunks, even though this query's actual predicate (`run_id`) can't be excluded on at the chunk level at all (it isn't the partitioning column). This is a real, measured cost on a query every completed run's results page depends on.
**Migration shape**: `CREATE INDEX ix_split_results_tenant_run ON validation.split_results (tenant_id, run_id);` issued against the hypertable's root table — Postgres/TimescaleDB propagates a root-level `CREATE INDEX` to all existing chunks automatically and to future chunks via the chunk template, so this is a single statement, not a per-chunk loop. This directly targets `get_splits`' predicate and doubles as the RLS-tenant_id-index this table was also missing.

### DBOPT-004 — All three ingestion hypertables (and `split_results`) were left at TimescaleDB's default 7-day `chunk_time_interval`, now producing hundreds of tiny chunks against 9–17 years of real backfilled history
**Status: Done (Sprint 21, split per-service into tickets VS-027 [`validation.split_results`] and INGEST-016 [`price_ohlcv`/`onchain_metric`/`sentiment_score`])** — all four hypertables retuned to a 90-day `chunk_time_interval`, live-verified via `timescaledb_information.dimensions`. **Forward-only effect confirmed empirically, not just documented**: `timescaledb_information.chunks` shows all four tables' pre-existing chunk counts (108 / 472 / 922 / 0) unchanged immediately after their respective migrations — existing undersized chunks are not retroactively resized or merged, exactly as flagged by the PM going into this sprint.
**Table/schema**: `ingestion.price_ohlcv`, `ingestion.onchain_metric`, `ingestion.sentiment_score` (ingestion-service), `validation.split_results` (validation-service).
**Query pattern**: this is not one query — it's a chunk-interval sizing problem that degrades *every* query against these hypertables, confirmed by the live evidence in DBOPT-003 and DBOPT-007 (both show query planning/execution cost scaling with total chunk count, not matching row count). `0003_convert_to_hypertables.py` (ingestion) and `0004_convert_split_results_to_hypertable.py` (validation) both call `create_hypertable(...)` without a `chunk_time_interval` argument, so every one of these tables uses Timescale's default, 7 days.
**Evidence — live, from `timescaledb_information.chunks`/`.dimensions`, not inferred**:
| hypertable | chunks | interval | span | rows | avg rows/chunk |
|---|---|---|---|---|---|
| `ingestion.price_ohlcv` | 472 | 7 days | 2017-08-17 → today | 121,895 | ~258 |
| `ingestion.onchain_metric` | 922 | 7 days | 2009-01-01 → today | 19,291 | ~21 |
| `validation.split_results` | 108 | 7 days | 1970-01-01 → 2026-08-06 | 552 | ~5 |

TimescaleDB's own sizing guidance targets chunks holding roughly 25% of available RAM (typically tens of millions of rows for small metric rows, certainly not tens or hundreds), with a rule of thumb of keeping the *total* chunk count low enough that recent chunks + their indexes fit comfortably in memory. `onchain_metric` averaging ~21 rows per chunk and `split_results` averaging ~5 are far past that — most of the 130ms planning time measured live in DBOPT-003 is TimescaleDB's planner walking all 108 `split_results` chunks to build the Append plan, not real work. This will get worse, not better, as more tenants' full-history backfills (`INGEST-013`) land, since new data keeps arriving at the *same* 7-day cadence while the historical backfill already used up hundreds of chunk-slots for years of thin data.
**Migration shape**: `SELECT set_chunk_time_interval('ingestion.price_ohlcv', INTERVAL '90 days');` (and similarly for `onchain_metric`, `sentiment_score`, `split_results` — interval chosen per table's actual event density; `price_ohlcv` at 1h candles is ~2,160 rows/90-day chunk per tenant/source, a much healthier chunk size than the current ~258/week). `set_chunk_time_interval` only affects **chunks created after** the call — existing undersized chunks are not automatically merged (see DBOPT-008's compression discussion for one way to reduce their count/footprint after the fact). This is schema-tuning only; no query surface or repository code changes.

### DBOPT-005 — `identity.users`: no index on `email`, the column the login-time lookup filters on
**Table/schema**: `identity.users` (gateway-api).
**Query pattern**: `PostgresUserRepository.get_user_by_email` — `SELECT ... FROM users WHERE email = :email` — GW-003's other documented tenant-agnostic exception (login-time resolution before a tenant is known), so like `api_keys.key_hash` this always scans across all tenants, not a pre-filtered per-tenant slice.
**Evidence**: live `EXPLAIN (ANALYZE, BUFFERS)` against the real 293-row table: `Seq Scan on users ... Filter: (email = ...) Rows Removed by Filter: 293`. Cheap today (0.03ms) for the same reason as DBOPT-001 — small table, but full-scan on a login-path query that grows with total users platform-wide.
**Migration shape**: `CREATE INDEX ix_users_email ON identity.users (email);` (or `UNIQUE`, see open question below).
**Open question for the user**: should `email` be `UNIQUE` at the DB level? `get_user_by_email` calls `.scalar_one_or_none()`, which already assumes at most one row per email, but nothing in `app.models.User` or the GW-003/GW-004 tickets enforces that today — a duplicate email across two tenants (or the same tenant) would silently break `scalar_one_or_none()` with a runtime error rather than a constraint violation at write time. This is a product/data-integrity decision (is email meant to be globally unique across tenants, or unique per-tenant?), not a DBA call — flagging rather than picking a side.

### DBOPT-006 — `ingestion.crawl_runs`: no index for `latest_crawl_run`'s per-tenant/source lookup
**Status: Done (Sprint 21, ticket INGEST-017)** — `CREATE INDEX ix_crawl_runs_tenant_source_fetched_at` shipped and live-verified. Same small-table caveat disclosed originally: the real table's 8 rows are too few for the planner to prefer the index naturally (`Seq Scan` persists); `SET enable_seqscan = off` confirmed the index is real, structurally correct, and usable.
**Table/schema**: `ingestion.crawl_runs` (ingestion-service).
**Query pattern**: `PostgresConnectorRecordRepository.latest_crawl_run` — `SELECT ... FROM crawl_runs WHERE tenant_id = :tenant_id AND source = :source ORDER BY fetched_at DESC LIMIT 1` — backs the connector/dataset status surface (last crawl outcome). `crawl_runs`' only index today is the PK on `id`.
**Evidence**: code-inferred, not live-EXPLAIN-verified — the real table has only 8 rows this session (too small for a sequential scan to show any measurable cost difference, so a live `EXPLAIN` here would show near-identical scan cost regardless of an index and wouldn't be meaningful evidence either way). The query shape itself (tenant/source filter + a sort + `LIMIT 1`, called once per connector per status check) is the same shape as DBOPT-002's `list_runs`, and `crawl_runs` will grow with every scheduled crawl run indefinitely (unlike `connector_credentials`, which is one row per tenant/source, ever).
**Migration shape**: `CREATE INDEX ix_crawl_runs_tenant_source_fetched_at ON ingestion.crawl_runs (tenant_id, source, fetched_at DESC);` — serves the exact filter+sort+limit shape and the RLS tenant_id filter as its leading column.

### DBOPT-007 — `ingestion.price_ohlcv`/`onchain_metric`/`sentiment_score`: `latest_fetched_at`'s per-tenant/source watermark check scans every hypertable chunk
**Status: Done (Sprint 21, ticket INGEST-018)** — composite `(tenant_id, source, fetched_at)` indexes shipped on all three hypertables' roots, confirmed propagated to all existing chunks (472/472 `price_ohlcv`, 922/922 `onchain_metric`). Live-verified win: `price_ohlcv`'s query plan moved from a 472-chunk `Append`/`Finalize Aggregate` (`Buffers: shared hit=2907`) to a `Merge Append` of per-chunk `Index Only Scan Backward`s (`Buffers: shared hit=472`). Honest caveat: `onchain_metric`'s own Planning Time remains high, driven by its 922-chunk count (`DBOPT-004`'s concern), not by this index — this index improves each chunk's own access path, it does not reduce how many chunks the planner must still visit.
**Table/schema**: `ingestion.price_ohlcv`, `ingestion.onchain_metric`, `ingestion.sentiment_score` (ingestion-service).
**Query pattern**: `PostgresConnectorRecordRepository.latest_fetched_at` — for each of the three models, `SELECT max(fetched_at) FROM <table> WHERE tenant_id = :tenant_id AND source = :source` — called by `connectors/base.py`'s incremental-fetch path to determine each crawl's watermark (i.e. on every scheduled crawl run, not just interactively). `fetched_at` is not part of any table's PK/index, and it is not the hypertable partitioning column (`open_time`/`timestamp`/`created_utc` are), so TimescaleDB's chunk exclusion cannot help this query at all — it must visit every chunk that could contain the tenant/source's rows.
**Evidence**: live `EXPLAIN (ANALYZE, BUFFERS)` for `price_ohlcv` scoped to the tenant with 79,127 rows: `Finalize Aggregate` over an `Append` of per-chunk `Partial Aggregate`s, one `Seq Scan` per chunk, touching all 472 chunks (`Buffers: shared hit=2907`), 24ms execution. Not slow in absolute terms yet, but this runs on every incremental crawl for every tenant/source pair, and its cost scales with total chunk count (DBOPT-004), not with how recent the tenant's actual last-fetched row is — the exact "chunk interval too small for real history depth" problem compounding a second, independent query pattern.
**Migration shape**: `CREATE INDEX ix_price_ohlcv_tenant_source_fetched_at ON ingestion.price_ohlcv (tenant_id, source, fetched_at);` (and the equivalent for `onchain_metric`, `sentiment_score`). With `fetched_at` as the trailing index column, `MAX(fetched_at)` for a given `(tenant_id, source)` becomes an index-only backward scan taking the first row, not a full aggregate over every matching row — this fixes the query independent of DBOPT-004's chunk-interval fix, and the two are complementary (fewer, bigger chunks reduces how many chunks the index still has to be consulted across).

### DBOPT-008 — Compression policy for old ingestion/validation hypertable chunks — open question, not decided here
**Table/schema**: `ingestion.price_ohlcv`, `ingestion.onchain_metric`, `ingestion.sentiment_score`, `validation.split_results`.
**Why this is on the table at all**: real data now spans 9–17 years (`price_ohlcv` from 2017, `onchain_metric` from 2009), and the vast majority of that history is write-once, read-rarely — a validation run's `dataset` reference (ADR-0005) slices a `{tenant, source, start, end}` range at submission time, but nothing about this platform's actual usage pattern re-reads, say, 2009–2015 on-chain data on a recurring basis. TimescaleDB native compression on old chunks (e.g. anything older than 90 days) would substantially shrink storage for that untouched tail.
**Evidence**: code-inferred (no compression policy exists today — confirmed absent from all four services' migrations) plus the real, measured volume numbers in DBOPT-004's table, which show the depth of history now actually sitting in these tables uncompressed.
**This is a genuine tradeoff, not a recommendation — flagging both sides rather than picking one**:
- **For**: compression on `timescale/timescaledb`-column-store chunks typically achieves 90%+ size reduction on OHLCV-shaped numeric time series; cheaper storage, smaller backups, and (counterintuitively) sometimes *faster* full-history scans since less I/O is needed per chunk.
- **Against**: a compressed chunk must be decompressed before any row-level write (so backfills/corrections into old date ranges get materially slower, and TimescaleDB by default blocks `INSERT`/`UPDATE` into compressed chunks unless a decompress step runs first); a validation run that legitimately requests a wide historical range (e.g. "the full 2009-2026 on-chain series," which `read_series` explicitly supports with `start`/`end` both `None`) would pay a real decompression cost on every such read, not just the first one, unless the compressed data is decompressed and cached.
**Open question for the user**: is there a real access pattern (a pilot client, a validation run) that reads multi-year-old ranges of `price_ohlcv`/`onchain_metric`, or is old data effectively write-once/never-read in practice today? That answer decides whether compression is a clear win or a real regression on some future query — this backlog does not assume either.

### DBOPT-009 — Continuous aggregate for `list_datasets`' per-source min/max/count — open question, not decided here
**Table/schema**: `ingestion.price_ohlcv`, `ingestion.onchain_metric`, `ingestion.sentiment_score`.
**Query pattern**: `PostgresConnectorRecordRepository.list_datasets` — for each table, `SELECT source, min(event_time), max(event_time), count(*) ... GROUP BY source` — backs the dataset-picker's list view (which sources exist, what range they cover), likely called on every visit to that UI surface, not just once per crawl.
**Evidence**: code-inferred; not separately live-EXPLAIN-verified beyond noting it shares `latest_fetched_at`'s scan shape (whole-table aggregate, all chunks visited, same as DBOPT-007) since `min`/`max`/`count` similarly can't use chunk exclusion on a `GROUP BY source` with no time predicate.
**This is a genuine tradeoff, flagged rather than decided**:
- **For**: a TimescaleDB continuous aggregate (materialized, incrementally refreshed) on `(tenant_id, source) -> min/max/count` would make `list_datasets` an index lookup against a tiny materialized table instead of a full scan, and the aggregation is naturally incremental (new rows only extend the range, they don't invalidate old buckets) — a good fit for continuous aggregates' refresh model.
- **Against**: a continuous aggregate has a real refresh lag (data ingested in the last refresh window won't show up in `list_datasets`' returned range/count until the next refresh policy run) — for a dataset picker, showing a slightly stale "as of N minutes ago" row count is probably fine, but it is a genuine behavior change from today's always-current `list_datasets`, and nobody has asked for eventual consistency here yet.
**Open question for the user**: is `list_datasets`' freshness (always exactly current row counts) load-bearing for any workflow (e.g. does a user submit a validation run immediately after a crawl and expect to see the just-ingested rows reflected in the picker), or would a few minutes of staleness be acceptable in exchange for a much cheaper query? Recommend deferring this one until `list_datasets` is actually called often enough in production to matter — DBOPT-007's simpler index likely closes most of the real gap for `latest_fetched_at`'s hotter, per-crawl call site first.

### DBOPT-010 — `reporting.reports`: no index beyond PK on `id`
**Table/schema**: `reporting.reports` (reporting-service).
**Why Won't, not Should**: checked directly — `PostgresReportRepository` has exactly two methods, `create_report` (INSERT) and `get_report` (`WHERE id = :id AND tenant_id = :tenant_id`, `id` already being the PK). There is no `list_reports`/`GET /reports` endpoint in this service today (confirmed: only `report_generation.py`/`report_retrieval.py` routers exist, both single-report by id). The RLS `tenant_id` filter on `get_report` is real but redundant with the PK-equality lookup already narrowing to at most one row — an unindexed `tenant_id` costs nothing extra here because Postgres never needs to scan for it once `id` has already resolved to zero-or-one rows. Table is also tiny (109 rows this session). Revisit the moment a `list_reports`/"my reports" endpoint is actually built — that is the concrete trigger, same "revisit on second real use" pattern this repo's own `backlog-infra.md` (INF-017) already applies elsewhere, not a permanent decline.
Depends on: none (blocked on a future `list_reports` endpoint existing, not on anything in this backlog)
