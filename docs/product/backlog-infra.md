## Scope

**Why this backlog exists now, stated plainly.** Implementation-plan.md section 6 trigger #4 ("create `infra/docker-compose.yml` + Postgres") is defined to fire "the same moment" as trigger #3 (`validation-service`). Trigger #3 fired several sprints ago — but trigger #4 did not actually fire alongside it. Both `validation-service` and `gateway-api` shipped instead on an interim, file-based SQLite backend, an explicit and disclosed judgment call recorded in both services' own backlogs (`backlog-validation-service.md` decision 2, `backlog-gateway-api.md` decision 2) and READMEs. `infra/README.md` has sat at "planned" since. This is not being written now because the trigger condition retroactively became true — it didn't fire on schedule, and this backlog does not pretend otherwise. It is being written because the platform owner has explicitly scheduled a debt sprint to build `infra/` now, specifically to unblock the Should stories that have been piling up waiting on it: `VS-013` (Postgres-backed validation-service repositories), `VS-014` (Redis Streams `run.completed` publisher), and `GW-012` (Postgres-backed identity repositories + RLS).

**In scope**: the three real infra pieces named in solution-design.md section 5's service table — `postgres` (`timescale/timescaledb` image), `minio`, `redis` — as `infra/docker-compose.yml` services; wiring the two services that actually exist as code (`validation-service`, `gateway-api`) into that same compose file as real, runnable containers; making Postgres and Redis concretely reachable with documented connection strings, so that `VS-013`, `VS-014`, and `GW-012` become buildable rather than perpetually blocked.

**Out of scope**: `ingestion-service`, `reporting-service`, `dashboard-web` — none of these exist as code yet (triggers #6–#8 haven't fired), and `infra/README.md`'s own standing rule is "don't add a compose file with services that don't exist as code." The solution-design.md section 5 table's `api`/`worker` rows are conceptual placeholders from before the module split in implementation-plan.md existed as code — they are **not** built here as a new generic container; `api` is superseded by the real `services/gateway-api` + `services/validation-service`, and `worker` (Prefect agent) has no concrete consumer yet (no flows are defined outside `validation-service`'s own synchronous request handling) so it is not stood up speculatively. Also out of scope: actually implementing `VS-013`/`VS-014`/`GW-012` (see decision 2 below), cloud/Heroku deployment (solution-design.md section 5.1 — a separate, later hosting decision, not this local-first Compose work), and TimescaleDB hypertable configuration (no query pattern needs it yet).

### Explicit scope decisions (per the instruction not to assume silently)

1. **This backlog's Must scope *does* include wiring `validation-service` and `gateway-api`'s Dockerfiles and Compose service definitions — `docker compose up` is expected to run the real services, not just the infra pieces around them.** Neither service has a `Dockerfile` yet (checked: `services/validation-service/Dockerfile` and `services/gateway-api/Dockerfile` don't exist; only `pyproject.toml` does). The alternative — infra ships Postgres/Redis/MinIO containers but the two real services still run manually outside Compose — would leave the debt sprint's own stated purpose unmet: `VS-013`/`GW-012`'s acceptance criteria ("point Alembic at a real DB", "swap the DI-wired repository, prove no call-site changes") are only concretely verifiable if the service and the database are reachable from the same environment. `infra/README.md`'s own "will hold" list already commits to `gateway-api`/`validation-service` as compose services. Deferring Dockerfile authorship to each service's own backlog would reproduce exactly the "planned but never built" gap this debt sprint exists to close. Note for the PM/Tech Lead: the `Dockerfile`s physically live under `services/validation-service/` and `services/gateway-api/` (implementation-plan.md section 3's repo layout assigns each service its own), but authorship here is about closing the compose-wiring gap, not about relitigating who owns runtime business logic in those directories — no story below touches either service's application code.
2. **This backlog's Must scope does *not* include `VS-013`, `VS-014`, or `GW-012` themselves.** Those are fully-specified Should stories already written, with their own acceptance criteria, inside `backlog-validation-service.md` and `backlog-gateway-api.md` — re-specifying them here would fork a single story across two backlogs, which implementation-plan.md section 9's DRY convention (and the cross-service "no service imports another service's internals" rule, by analogy) argues against. This backlog's job is narrower and prior: make the infra those three stories are blocked on actually exist and be reachable, so their own authors can execute them unmodified. Concretely, this backlog proves Postgres accepts each service's already-written Alembic migration (a connectivity/schema smoke test — see INF-005) without performing the DI swap, RLS policy authorship, or Redis-Streams publisher implementation those three stories still own. **Recommendation to the PM**: schedule `VS-013`, `VS-014`, and `GW-012` into the same debt sprint as this backlog — they are unblocked by it, not obsoleted by it, and none of their acceptance criteria are satisfied by infra work alone.
3. **`VS-014` is treated as unblocked by this backlog's Redis story (INF-002), even though implementation-plan.md section 6 nominally ties Redis Streams to trigger #7 (`reporting-service`), not trigger #4.** `VS-014`'s own scope is the *publisher* side only (`validation-service` writing to a stream) — it has no dependency on `reporting-service` existing as a subscriber to be implemented and tested; it only needs a real, reachable Redis instance to write to, which is what solution-design.md section 5's service table (and this backlog's INF-002) actually provides. The full pub/sub loop (a subscriber consuming what `VS-014` publishes) genuinely still waits on trigger #7 — that half is correctly out of scope here and not claimed as delivered.

## Stories

### INF-001 — PostgreSQL + TimescaleDB service in Docker Compose [Must]
**As** the Naive-First platform **I want** a `postgres` service (`timescale/timescaledb` image) defined in `infra/docker-compose.yml` **so that** `validation-service` and `gateway-api` have a real, reachable operational database instead of interim SQLite files.

Acceptance criteria:
- [ ] `infra/docker-compose.yml` defines a `postgres` service using the `timescale/timescaledb` image (matching solution-design.md section 5's table), with a fixed container port mapped to the host for local access from outside Compose (e.g. `psql`, a migration run from a service's own `.venv`).
- [ ] A named, persistent Docker volume is attached so data survives `docker compose down` (not `down -v`) — parity with the durability SQLite already provided ("state survives a process restart") that this backlog must not regress.
- [ ] Credentials and connection details are supplied via environment variables (not hardcoded in the compose file), documented in `infra/README.md` and a checked-in `.env.example`.
- [ ] `docker compose up postgres` starts successfully and accepts a plain `psql` connection using the documented credentials, verified manually as part of this story's Definition of Done.

Rationale for priority: this is the direct, named blocker for `VS-013` and `GW-012` — neither story is buildable without a real Postgres instance to target, and this is the trigger-#4 deliverable those two stories cite by name as their blocking dependency.
Depends on: none

### INF-014 — Non-superuser Postgres application role for `validation-service`/`gateway-api` [Must]
**As** the Naive-First platform **I want** `validation-service` and `gateway-api` to connect to Postgres as a dedicated, non-superuser, `NOSUPERUSER NOBYPASSRLS` application role — separate from whatever role owns/migrates the schemas — **so that** the RLS policies `VS-013` (`migrations/versions/0002_add_row_level_security.py`) and `GW-012` (`migrations/versions/0002_add_identity_rls.py`) already wrote, and already proved correct against a purpose-built ephemeral test role, are actually enforced against the credentials the running services use in practice, not just in test.

Context (why this is a real gap, not a hypothetical): INF-001 provisions exactly one Postgres role, `naive_first` (via the official image's `POSTGRES_USER` mechanism), and both services' `DATABASE_URL`s connect as it. That role is a Postgres superuser, and Postgres unconditionally exempts superusers from row-level security — `FORCE ROW LEVEL SECURITY` included, per both migrations' own docstrings, which document choosing `FORCE` specifically because "the app connects as the same role that owns these tables." Superuser exemption sits underneath `FORCE` and cannot be worked around by any RLS clause; the only fix is connecting as a role that isn't a superuser and doesn't have `BYPASSRLS`. Both services' own test suites already work around this correctly for verification purposes (`tests/test_postgres_repository.py` in each creates an ephemeral non-superuser role for its own assertions) — this story is what makes that the *real* runtime credential, not just the test one.

Acceptance criteria:
- [ ] A new Postgres role (e.g. `naive_first_app`) is created — via `infra/postgres-init/` (an additional numbered init script, consistent with `01-create-schemas.sql`'s existing convention) or an equivalent Compose-startup mechanism — with `LOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, and no `CREATEDB`/`CREATEROLE`.

### INF-015 — First-boot bootstrap script [Should]
**As** a developer or operator standing up this platform for the first time **I want** one command that brings up Compose, waits for Postgres to be healthy, and runs both services' `alembic upgrade head` against it **so that** first-time setup is not a hand-run, multi-terminal sequence reconstructed from `infra/README.md`'s prose (as INF-005's dev agent, and every Sprint 06 dev agent touching `VS-013`/`GW-012`, had to do by hand).

Context (what's manual today, confirmed by reading the actual current state): `docker compose up` (or `up -d`) starts the containers; `postgres`'s healthcheck (INF-009... actually landed as part of INF-001's compose file, `pg_isready`) means `depends_on: condition: service_healthy` already gates `validation-service`/`gateway-api` container start on Postgres being ready, but neither service runs its own migrations on container start — `infra/README.md`'s INF-005 section documents running `alembic upgrade head` by hand, from each service's own `.venv`, against the host-published Postgres port, and separately flags that this only works safely in a fixed order today because of the undocumented `alembic_version` collision (fixed by `VS-013`/`GW-012`'s schema-scoped version tables, per that same README section) — a fragility a bootstrap script should not silently inherit. After migrations, a usable tenant requires a third manual step, `scripts/provision_tenant.py`, run inside the `gateway-api` container per `infra/README.md`'s smoke-test section.

Acceptance criteria:
- [ ] A single script (e.g. `infra/bootstrap.sh` / `infra/bootstrap.ps1`, matching whichever shell convention the rest of `infra/` favors — this repo's other scripts are plain shell/PowerShell, not a new Python entrypoint, to avoid requiring a Python environment before any service's own `.venv` exists) runs, in order: `docker compose up -d` (or `--wait`, if the Compose version in use supports it) for `postgres`/`redis`; polls/waits on `postgres`'s healthcheck passing (reusing the existing `pg_isready` healthcheck INF-001 already defined, not a new ad hoc wait loop); then runs `alembic upgrade head` for `services/validation-service` and `services/gateway-api` each, against the real Compose Postgres, using the **migration-time** role (see INF-014 — post-INF-014, this is `naive_first`, not the new runtime-only role).
- [ ] The script fails loudly and stops (non-zero exit, clear error message naming which step failed) rather than continuing silently if any step fails — in particular, it must not mask the exact `alembic_version` collision INF-005 found; if that collision still exists (i.e. this script runs before `VS-013`/`GW-012`'s schema-scoped fix lands), the script's own ordering must not silently no-op the second service's migration.
- [ ] Then starts (or restarts, if not already up) `validation-service`/`gateway-api` themselves.
- [ ] `infra/README.md` is updated to lead with this script as the recommended first-boot path, with the existing hand-run sequence kept underneath as "what the script does, spelled out" (matching this backlog's own established documentation style of never deleting the manual explanation, only demoting it) rather than the primary instructions.
- [ ] **Tenant provisioning is explicitly NOT auto-run by this script — a deliberate call, not an oversight.** `provision_tenant.py`'s own docstring and `gateway-api`'s README both frame it as an operator decision (a real tenant name, custody of a raw API key that is shown exactly once and cannot be recovered) — silently minting a tenant and printing/discarding its one-time key inside an unattended bootstrap script would either lose that key permanently (if the script doesn't surface it clearly) or normalize treating a real credential-creation event as bootstrap noise. Rationale for priority: **Should**, not Must — every step it automates already works and is documented today (per `infra/README.md`'s INF-001–INF-005 sections); this story is a real usability improvement that removes tribal-knowledge risk for the next person who stands the stack up cold, but nothing currently in flight is blocked without it, unlike INF-001–INF-005's own Must stories.

### INF-017 — DB-backed operator/tenant configuration [Won't, for now — explicit judgment call]
**As** the Naive-First platform **I want** a database-backed settings/configuration mechanism for operator- or tenant-level behavior **so that** an operator could change platform behavior without a redeploy.

This story is written to record a deliberate **decline**, not to leave the request unaddressed — the platform owner explicitly asked that "user steps or configurations" be DB-backed, and that request deserves a real answer rather than either silent noncompliance or a settings table invented to look compliant.

**What was actually checked** (not assumed): every environment variable and hardcoded value currently in `infra/docker-compose.yml`, both services' `dependencies/*.py` DI wiring, and `gateway-api`'s `http_client.py` was read for this story. The inventory splits cleanly into two buckets:
1. **Bootstrap/infrastructure values** — `DATABASE_URL`, `REDIS_URL`, `VALIDATION_SERVICE_URL`, Postgres credentials, ports. These cannot be moved into the database, and this is a structural fact, not a preference: a service needs `DATABASE_URL` to know which database to connect to *before* it has made any database connection — moving that value into the database it describes is a literal chicken-and-egg problem, not a design choice this story could resolve either way. Same for `REDIS_URL` (needed before any Redis connection exists) and `VALIDATION_SERVICE_URL` (an inter-service network address, needed before any HTTP call can be made to look anything up). Flagging this explicitly per this story's own instruction: any story that proposed DB-backing these would create the exact bootstrap paradox it's meant to avoid, so none is written.
2. **Everything else found** — `gateway-api`'s downstream HTTP timeout (`http_client.py`, `_DOWNSTREAM_TIMEOUT_ENV_VAR`) is the one candidate that isn't a pure bootstrap value (it's a behavior knob, not a connection address) — but it is a single process-wide default read once at `httpx.Client` construction, not tenant-specific, and no operator workflow anywhere in this platform currently varies it (no per-tenant SLA tiers, no per-tenant rate limits, no per-tenant feature flags exist in either service's models or routers today — `identity.tenants` has no columns beyond `id`/`name`, `validation.runs` has no per-tenant behavior-selection field). Building a settings table for a knob nobody has asked to vary yet, for tenants that don't yet differ from each other in any stored way, is exactly the speculative-scaffolding pattern `libs/common`'s own README explicitly rules out ("don't pre-emptively move things here 'in case' another service needs them later — YAGNI; move on second real use") and this backlog has already declined the same pattern once before, explicitly, for TimescaleDB hypertables (INF-010's rationale: "doing this now would be speculative, per implementation-plan.md's own 'don't scaffold before something concrete needs it' principle").

**Decision: Won't, this backlog, for now.** There is currently no concrete, real operator- or tenant-level behavior difference anywhere in the running platform that a settings table would serve — inventing one (a generic `settings`/`config` table with no real reader) would add schema, migration surface, and a repository nobody calls, purely to satisfy the letter of the request rather than its intent. The honest answer to "should configuration live in the DB" is: **the platform doesn't have any configuration of the kind that claim is about yet** — what exists today is either infrastructure bootstrap values (bucket 1, structurally DB-incompatible) or a single non-tenant-specific timeout default (bucket 2, no real variation need). This is not a refusal of the underlying ask — the moment a real tenant- or operator-level behavior difference is needed (a per-tenant rate limit, a per-tenant feature flag, a per-tenant SLA timeout override), that is the concrete trigger for a real INF-01X story building exactly that, the same "revisit on second real use / on the trigger firing" pattern this backlog already applies to INF-008/INF-010/INF-011.

Rationale for priority: **Won't, this backlog** — same category as INF-010 (YAGNI, no current concrete need) rather than the "genuinely out of scope" category of INF-011/012/013; unlike those, this one has a stated, concrete trigger for revisiting (first real per-tenant/per-operator behavior difference) rather than an external trigger this backlog doesn't control.
Depends on: none (no dependency to revisit until a concrete need is identified)
