# Backlog — run submission safety (dashboard-web / validation-service)

Source: `CLAUDE.md` (positioning — nothing here implies prediction/trading-signal generation; this is a usability/safety fix to the audit-run submission flow), `docs/da-tese-ao-produto.md`, `docs/solution-design.md`, `docs/implementation-plan.md` (module boundaries — no story below has `dashboard-web` or `gateway-api` reimplement `validation-service`'s split-generation math, per the "no service imports another service's internals" rule), `services/dashboard-web/src/app/templates/run_new.html`, `services/dashboard-web/src/app/routers/runs.py` (`run_new_form`/`run_new_submit`, `_fetch_ingestion_datasets`, `DatasetSummaryResponse`), `services/validation-service/src/app/routers/runs.py` (`POST /runs`, `create_run`), `libs/naive_first_engine/src/naive_first_engine/splitting.py` (`generate_splits`, both `_generate_splits_by_position`/`_generate_splits_by_time`), `libs/naive_first_engine/src/naive_first_engine/protocol.py` (`run_validation_protocol`'s synchronous per-split loop), `services/gateway-api/src/app/dependencies/http_client.py` (`GATEWAY_API_DOWNSTREAM_TIMEOUT_SECONDS`, default 30.0s), `libs/common/src/naive_first_common/contracts.py` (`RunRequest`, `DatasetSummaryResponse`).

## Confirmed split-count formula (do not re-derive this differently in a future ticket)

`generate_splits`'s row-count (position-based) branch — the one every stored-dataset run in this incident used — produces one split per valid `train_start_pos` in `{0, step, 2*step, ...}` such that `train_start_pos + train_window + purge_gap + test_window <= n` (`n` = `row_count`, and `purge_gap` here is `request.purge_gap_hours` used verbatim as a **row-position offset**, not a calendar duration — see open question OQ-3 below on that naming mismatch). Closed form:

```
num_splits = floor((row_count - train_window - purge_gap_hours - test_window) / step) + 1   if the numerator >= 0
num_splits = 0                                                                                otherwise
```

Verified against the live incident: `row_count=79180, train_window=360, test_window=1540, step=2, purge_gap_hours=0` → `floor((79180-360-0-1540)/2)+1 = floor(77280/2)+1 = 38640+1 = 38641` splits — exactly the figure reported. `run_validation_protocol` (`libs/naive_first_engine/src/naive_first_engine/protocol.py`) then runs baseline fit/predict + full `MetricSet` (`mae`/`rmse`/`smape`/`mase`/`da`/`f1`/`oos_r2`) + a Diebold–Mariano test **synchronously, once per split, in a plain Python `for` loop with no cap, no early exit, and no cost estimate** before `POST /runs` (`services/validation-service/src/app/routers/runs.py::create_run`) returns — this is the exact code path that pegged CPU and left the run stuck showing `"pending"`.

## Scope

**In scope**: (1) `dashboard-web`'s `run_new.html`/`runs.py` — surfacing the selected stored dataset's real row count/date range and a live, client-side estimated-split-count as the user types, so they stop guessing blind; (2) a real server-side rejection of unreasonable split counts, added to `validation-service`'s `POST /runs` (the service that owns `generate_splits`/`run_validation_protocol` and can compute the true count before running anything) so the guardrail holds regardless of which client calls it — `dashboard-web`'s form, a pilot's own script hitting `gateway-api` directly, or `curl`.

**Out of scope**: making `POST /runs` asynchronous (background job + polling/webhook for completion) — that is a materially bigger architectural change (job queue, status polling contract, `gateway-api` timeout semantics all change) than "reject bad input before computing it," and nothing in the two problems described here requires it: a rejected 38,641-split request never starts computing regardless of whether computation is sync or async. Flagged as a candidate follow-up backlog, not built here. Also out of scope: retroactively fixing/killing the two runs currently stuck computing from today's incident (see OQ-1) and any change to `generate_splits`/`run_validation_protocol`'s own math (both stay exactly as read — this backlog only adds a check *before* they're invoked).

### Sequencing recommendation (stated once here, not repeated per story)

**RSS-004 (the guardrail) ships before RSS-001–003 (the dashboard UX epic), and is the higher priority of the two.** Rationale: the guardrail is a safety fix — it is the only story in this backlog that stops a request from pegging a service's CPU and producing an indistinguishable-from-broken stuck "pending" run, and it protects every caller (dashboard, `gateway-api` clients, `curl`), not just the dashboard's own users. The dashboard UX epic is a pure usability improvement layered on top of it — a user who sees a live "≈38,641 splits" estimate as they type is far less likely to submit that configuration in the first place, but a user who ignores or ships around that estimate (or calls the API directly) still needs RSS-004 to be the thing that actually stops them. RSS-001–003 have no architectural dependency on RSS-004 landing first and could ship independently/in parallel if the squad has capacity, but if only one lands this sprint, it must be RSS-004.

## Open questions for the user/PM before this goes to sequencing

- **OQ-1 (raised per the requester's own note):** the two runs from today's incident were left running rather than killed. If/when they finish or hard-fail-via-timeout, that gives one real, non-hypothetical data point for "how long does N splits actually take on this hardware" — worth capturing (e.g. as a one-line note in `validation-service/README.md` or this backlog) before RSS-004's threshold is finalized, rather than picking the threshold purely from the reasoning in RSS-004's own note below and then never revisiting it once real numbers exist.
- **OQ-2 (the threshold itself):** RSS-004 proposes a **provisional** cap of 500 splits (rationale in that story) precisely because no real per-split timing benchmark exists yet in this codebase — this number is a reasoned placeholder, not a measurement, and is called out as needing PM/Tech Lead confirmation (and revision once OQ-1's real data point exists) before implementation.
- **OQ-3 (naming mismatch, found while reading the code, not asked for but adjacent):** `RunRequest.purge_gap_hours` is passed into `ValidationConfig.purge_gap` and, in `generate_splits`'s row-count branch, used as a raw **row-position** offset (`test_start_pos = train_end_pos + purge_gap`), not a duration converted against the dataset's actual row spacing. For an hourly-spaced dataset those coincide; for any other cadence (e.g. minute-level on-chain data) the field name promises something the row-count code path doesn't do. This is a pre-existing naming/semantics gap, not something introduced by this backlog — flagging it here only because RSS-002's "live estimated split count" and RSS-004's split-count check both must use the same "`purge_gap_hours` as row offset" semantics `generate_splits` actually implements today, not the semantics its name implies, or the two guardrails (client estimate vs. server rejection) would disagree with each other on the same input. Recommend a separate, small documentation/rename ticket for the PM's backlog — not fixed here since fixing it is a behavior change to `generate_splits`'s public contract, outside this backlog's "add a check before invoking existing math" scope.

## Stories

### RSS-001 — Show the selected stored dataset's real row count and date range on the run form [Must]
**As** the dashboard-web run-submission form **I want** to display the actually-ingested row count and date range for whichever stored dataset the tenant selects **so that** the horizon/window/step fields below it are filled in with knowledge of the real dataset instead of blind.

Acceptance criteria:
- [ ] `run_new_form` (`services/dashboard-web/src/app/routers/runs.py`) passes the already-fetched `datasets` list (via the existing `_fetch_ingestion_datasets` call — DASH-108/111's `GET /ingestion/datasets` round trip) into `run_new.html` in a form the template's client-side JS can read per-option (e.g. `data-row-count`/`data-earliest`/`data-latest` attributes on each `<option>`), reusing the exact fields `DatasetSummaryResponse` already provides (`row_count`, `earliest_timestamp`, `latest_timestamp`) — no new backend field, no second `GET /ingestion/datasets` call.
- [ ] Selecting a source in the "Stored dataset" dropdown (`#dataset_reference_source`) updates a visible summary line (e.g. below the dropdown) showing that dataset's row count and `earliest_timestamp`–`latest_timestamp` range in plain text, without a page reload or additional server round-trip.
- [ ] If `dataset_reference_start`/`dataset_reference_end` are filled in (narrowing the range), the summary line's row-count figure is explicitly labeled as the *full source's* row count, not a recomputed count for the narrowed range (recomputing the true post-filter row count requires the server — see RSS-003) — the copy must not imply a precision the client doesn't have.
- [ ] No behavior changes to `run_new_submit`, `RunRequest` construction, or any existing dataset-reference mode (local file path / inline payload) — this story is additive display only in the stored-dataset fieldset.

Rationale for priority: prerequisite for RSS-002 (the live split-count estimate needs the row count already on the page) and the most direct fix for the requester's literal ask ("examples from that dataset"); zero risk to the existing submission path since it only reads data already being fetched.
Depends on: none

### RSS-002 — Live, client-side "approximately N splits" estimate as horizon/window/step fields are edited [Must]
**As** the dashboard-web run-submission form **I want** to show a live, continuously-updating estimated split count next to the horizon/purge-gap/train-window/test-window/step fields as the user types, computed from the selected dataset's row count already in the DOM (RSS-001) **so that** the user gets instant feedback on whether their configuration is reasonable before submitting, instead of discovering it only after the request hangs.

Acceptance criteria:
- [ ] The form's existing inline `<script>` block (the same one that already owns `checkReference()`) gains a `computeEstimatedSplits()` function implementing the exact formula confirmed in this backlog's header (`floor((row_count - train_window - purge_gap_hours - test_window) / step) + 1`, clamped to 0 when the numerator is negative), reading `row_count` from the selected `<option>`'s `data-row-count` attribute (RSS-001) and the four numeric fields' current values.
- [ ] The estimate re-renders on every `input` event on `horizon`... no — on every `input` event on `purge_gap_hours`, `train_window`, `test_window`, and `step` (not `horizon`, which `generate_splits` does not take as a parameter — confirmed by reading `generate_splits`'s signature), and on `change` of the dataset source dropdown, with no page reload and no server round-trip.
- [ ] When no stored dataset is selected (local file path or inline payload mode), the estimate area is hidden or shows an explicit "select a stored dataset to see an estimate" message, not a stale or fabricated number — this story does not attempt to estimate row count for the other two reference modes (a local file path's row count and an inline payload's row count are only known once loaded server-side, out of scope here).
- [ ] The story's copy/labeling is explicit that this is an **estimate for the whole selected source**, not the post-start/end-filter row count (same caveat as RSS-001, until RSS-003 exists) — no wording that could be read as a guaranteed final split count.
- [ ] This estimate is presented as an informational aid only — it must not block form submission by itself (that is RSS-004's job, server-side); this story adds no new client-side submission block beyond the existing `checkReference()` gate.

Rationale for priority: this is the concrete mechanism behind the requester's ask ("live client-side computation... updating in real time"); Must because it is the single highest-leverage UX change for preventing exactly today's incident from a well-intentioned user, but it is UX only — RSS-004 remains the actual safety backstop since this estimate can be ignored, miscalculated (e.g. a JS bug), or bypassed entirely by a non-dashboard caller.
Depends on: RSS-001

### RSS-003 — Server-computed exact split count when start/end narrows a stored dataset [Should]
**As** the dashboard-web run-submission form **I want** an exact, server-computed split count for a stored dataset once the user narrows it with a start/end date (not just the client-side estimate against the full source), **so that** the feedback the user sees before submitting is accurate rather than approximate whenever their query is more precise than "the whole source."

Acceptance criteria:
- [ ] A story-scoped decision, to be confirmed with the Tech Lead before build: whether this is served by a new lightweight `gateway-api`/`validation-service` endpoint (e.g. a dry-run "how many rows/splits would this reference + config produce" call) or is deferred until such an endpoint already exists for another reason — this story does not mandate a new service endpoint be built purely for this if the Tech Lead judges the cost disproportionate to the UX gain over RSS-001/002's whole-source approximation.
- [ ] If built: triggered on blur of `dataset_reference_start`/`dataset_reference_end` (not on every keystroke, to avoid a request per character), debounced, and clearly distinguished in the UI from RSS-002's live estimate (e.g. "estimate" vs. "exact for your selected range" labeling) so the user is never shown two silently-conflicting numbers with no explanation of which is authoritative.
- [ ] A transport failure or slow response degrades to RSS-002's client-side estimate remaining visible (same "form stays usable" precedent `_fetch_ingestion_datasets`'s degrade-to-empty-list behavior already sets) — this story must not make the form depend on a new round-trip succeeding in order to be submittable.

Rationale for priority: real improvement over RSS-001/002's "whole source only" approximation, but Should not Must — RSS-001/002 already solve the primary "stop guessing blind" problem for the common case (no date narrowing), and this story's own acceptance criteria explicitly allow deferring it pending a Tech Lead cost call, which is not true of any Must story in this backlog.
Depends on: RSS-001, RSS-002

### RSS-004 — Server-side split-count guardrail on `POST /runs` [Must]
**As** `validation-service` (the service that owns `generate_splits`/`run_validation_protocol` and is the one place every caller's request ultimately passes through — dashboard-web, a pilot's own script against `gateway-api`, or `curl`) **I want** to compute the exact split count a submitted configuration would produce and reject it with a `422` *before* calling `run_validation_protocol`, when that count exceeds a defined cap **so that** no request can peg the service's CPU and leave a run stuck indistinguishable-from-broken in `"pending"` the way today's 38,641-split submission did.

Acceptance criteria:
- [ ] `create_run` (`services/validation-service/src/app/routers/runs.py`) computes the split count using the exact formula confirmed in this backlog's header — either by calling `generate_splits` against the loaded series' index directly and taking `len(...)` (simplest, reuses the real implementation with zero risk of the check and the real math disagreeing) or the closed-form arithmetic, with a preference for calling the real function unless the Tech Lead determines the dataset load itself is expensive enough that a cheap arithmetic pre-check (using `row_count`, not a full load) is needed as a first, cheaper gate before an even-more-expensive full load. Either way, the computed count used for the check must be provably identical to what `run_validation_protocol` would actually produce for that same input — no independently-reimplemented approximation that could drift from `generate_splits`'s real behavior.
- [ ] When the computed split count exceeds the cap, `POST /runs` returns `422` with a message stating the actual computed split count and a concrete suggestion ("increase `step`" and/or "narrow the date range" and/or "reduce `train_window`/`test_window`"), before `run_repository.create_run` persists a `"pending"` row and before `run_validation_protocol` is invoked at all — no run record, no partial computation, no CPU spent on baselines/metrics/DM-test for a rejected request.
- [ ] The cap is a named constant (not a magic number inline) with an explicit rationale comment citing this backlog's OQ-1/OQ-2 provisional-value note, and is **provisionally set to 500 splits**, flagged as needing PM/Tech Lead confirmation before merge (see OQ-2) — not silently finalized by whoever implements the ticket.
- [ ] This is the sole enforcement point: the acceptance criteria explicitly do not rely on `dashboard-web`'s client-side estimate (RSS-002) or `gateway-api` doing a second, duplicate check — `gateway-api` continues to forward `POST /runs` and its body/response verbatim (per its existing `_call_downstream`/`422`-forwarding pattern already read in `runs.py`), so a `422` from this story reaches a `curl`/API caller exactly the same way a dashboard submission's `422` already does.
- [ ] A configuration that is rejected must never advance past this check regardless of `dataset_reference` mode (local path / inline / stored source) — the check runs after `DatasetSource.load` succeeds (so the real row count/index is known) but is proven, by a test, to run before any call to `run_validation_protocol` for at least one input shape per mode.
- [ ] Test coverage includes the literal incident input (`row_count=79180, train_window=360, test_window=1540, step=2, purge_gap_hours=0` → 38,641 splits) asserting `422`, plus a boundary case at exactly the cap (accepted) and cap+1 (rejected).

Rationale for priority: this is the actual safety fix — Must, and sequenced ahead of the dashboard UX epic (see "Sequencing recommendation" above) because it is the only story in this backlog that structurally prevents the incident regardless of which client sends the request, including ones that never render `run_new.html` at all.
Depends on: none architecturally (does not require RSS-001–003); OQ-1/OQ-2 should ideally be resolved (or explicitly deferred by the PM) before the cap value is finalized in code review.

### RSS-005 — Document the guardrail and its provisional threshold in `validation-service`'s README [Should]
**As** a future engineer picking up `validation-service` **I want** `services/validation-service/README.md` to state the split-count cap, its rationale, and that it is provisional pending real timing data (OQ-1) **so that** the next person to touch this code doesn't have to re-derive why the number is what it is, or silently "fix" it back out.

Acceptance criteria:
- [ ] README's contract/ownership section for `POST /runs` gains a short note: the cap's current value, the formula it's computed from (cross-referenced to `naive_first_engine.splitting.generate_splits`, not restated/duplicated), and a pointer to this backlog file for the OQ-1/OQ-2 rationale rather than re-explaining it inline (DRY, per implementation-plan.md section 9).
- [ ] If/when OQ-1's real timing data from today's two stuck runs becomes available, this is the file where it gets recorded (one line: observed duration for N splits) — the README doesn't need to be rewritten with a new cap by this story itself, only to have a place that data is expected to land.

Rationale for priority: not a safety-critical change itself (no runtime behavior), Should rather than Must, but directly required by this project's own standing rule that every ticket/sprint keeps READMEs/decision rationale current as part of the work, not a separate pass — and it's the natural home for OQ-1's eventual answer.
Depends on: RSS-004
