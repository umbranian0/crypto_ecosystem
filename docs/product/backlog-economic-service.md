## Override note (read this before the stories)

**Trigger #11 has NOT fired**, and this is a materially different kind of override than every other trigger override already recorded in this repo (`gateway-api` trigger #5, `dashboard-web` trigger #8, `ingestion-service` connectors trigger #6/#10). Those were all soft build-order triggers whose condition was simply "no pilot client yet" — a scheduling convenience, not a normative constraint. Trigger #11 is different in kind: `docs/implementation-plan.md` section 6 states it exists "per the ethical boundary in docs section 2.7," and `docs/da-tese-ao-produto.md` section 2.7 states plainly: *"Qualquer extensão para sinais de trading exige o módulo económico (custos, slippage) antes de qualquer alegação de rentabilidade"* and *"deixar claro... a distinção precisão estatística vs. lucro económico."* Section 2.3.5 states the module "só ativado depois de um modelo passar o subsistema 1." This is a business-honesty constraint tied directly to the platform's own core finding (section 1.4: no model beat Naive0 in a stable, significant way at any horizon; section 1.5: R² out-of-sample negative everywhere; the thesis explicitly never tested trading profit).

**What I checked, and what I found**, per the requester's explicit instruction to confirm this directly rather than assume:

1. **No model has ever beaten naive in a real run on this platform.** `services/validation-service/README.md`'s "Data model" section states plainly that `split_results.model_*`/`dm_*` currently map to the **`"naive_last"`** baseline — i.e. every run to date compares Naive0 against NaiveLast, not against any client-supplied predictive model. `VS-011`'s own regression test is described as reproducing "a construction-guaranteed NaiveLast-vs-Naive0 DM-verdict pattern" against the thesis's own published fixture constants — synthetic/regression-fixture data, not a live client audit.
2. **There is currently no mechanism anywhere in this platform for a client model to even be evaluated.** `docs/tickets/README.md`'s validation-service section lists `VS-017` ("client-supplied prediction baseline") as **deferred, not built** (Sprint 03's own deferral list: "VS-013–VS-017 deferred"). Until VS-017 ships, `validation-service` has no code path that ingests a client's predictions and produces a DM verdict against them at all — only Naive0 vs. NaiveLast.

This means the situation is stricter than "no model has passed the gate yet": **there is currently no gate to fail or pass**, because the capability the gate would check (a real client-model DM verdict) does not exist upstream. Any "real" eligibility check this backlog builds is therefore checking against a contract that `validation-service` doesn't yet implement — which is exactly why story ECON-004 makes mocking that upstream response, and never calling the real `validation-service` API, a hard architectural rule, not an implementation convenience.

**My own assessment, stated plainly rather than suppressed**: the ethical-boundary case for staying *fully* deferred (not even scaffolding) is a legitimate position, and I considered it before writing this backlog. I did not adopt it, for two reasons specific to what's actually authorized below: (1) every story here produces zero externally-observable capability — no endpoint in this scope can ever return a profitability number, by construction, because no real integration exists to feed it a real "eligible" result; the artifact this backlog produces is inert until two separate, independently-gated future events occur (VS-017 shipping *and* a real client model demonstrating stable outperformance). (2) The user has explicit authority to approve scaffolding-only work and did so explicitly, distinct from silently proceeding past the trigger. If either of those two conditions weren't true — if any story here could produce a reachable code path returning a number, or if this were being done without the user's explicit, informed sign-off on the ethical distinction — I would refuse to write it. I flag this here rather than deciding it unilaterally: **the requester should treat this paragraph as the thing to re-confirm, not the backlog's existence.**

## Explicit scope/dependency decisions

1. Trigger override recorded above, with the finding that VS-017 (the precondition for a real client-model DM verdict to even exist) is itself unbuilt — this is disclosed to the requester, not assumed away.
2. `economic.*` schema stores cost/slippage/turnover **assumption and simulation-input records** (fee schedules, slippage models, simulation configs) — never a table of computed profitability *outputs* tied to any real run, since no real run has earned the right to be simulated against yet (ECON-002's own design decision, stated again there).
3. Contracts (ECON-003) are kept **local** to `economic-service` for this backlog, not added to `libs/common`. Recommendation, not a final call (Tech Lead/dev-agent's to confirm): `libs/common`'s own DRY rule (implementation-plan.md section 9) is "extract on second duplication, cross-module goes to libs/* only when genuinely shared" — today exactly one module (`economic-service`) needs these shapes; `reporting-service` and `dashboard-web` don't render economic simulations yet (their own triggers, #7/#8, are about audit reports and run/split viewing, not economic output). Promoting to `libs/common` now would be speculative generality against a consumer that doesn't exist.
4. Mocked-upstream-only is a hard architectural rule for this backlog (ECON-004), not a temporary stub to be quietly upgraded by a later, differently-scoped ticket without its own explicit re-authorization.
5. The structural gate (ECON-005) is this backlog's actual deliverable; every other story exists to give it something to sit inside.

### ECON-002 — `economic.*` Postgres schema + Repository pattern for cost/slippage *inputs* [Must]
**As** `economic-service`'s own data-access layer, **I want** a schema and Repository interface for transaction-cost/slippage-model *assumption records* and *simulation configuration records* — never a table of computed profitability results tied to a real run — **so that** the schema itself cannot be used to store or retrieve a fabricated or premature profitability number, and so that schema-per-service (implementation-plan.md section 5) is respected from the first migration.

Design decision, stated explicitly per the prompt's requirement: this schema owns **inputs to a simulation** (fee tiers, slippage curve parameters, turnover assumptions, a `simulation_configs` record referencing which upstream run it would apply to) — it does **not** own an `economic_results`/`pnl`/`returns` table. A results table implies persisted profitability numbers exist to query, which begs the exact question this backlog exists to gate. If/when the gate (ECON-005) is ever satisfied for real, persisting a computed result is a new, separately-authorized story against this same schema — not assumed here.

Acceptance criteria:
- [ ] `economic` Postgres schema defined (SQLAlchemy models + Alembic migration, schema-qualified per `validation-service`'s `version_table_schema` precedent from the INF-005 finding — avoids the same cross-service `alembic_version` collision).
- [ ] Tables: `fee_schedules` (tenant_id, exchange/venue label, fee tiers), `slippage_models` (tenant_id, model kind, parameters), `simulation_configs` (tenant_id, references an upstream `validation_run_id` by opaque string/UUID — **not** a foreign key into `validation-service`'s schema, per "no service reads another service's DB schema directly," implementation-plan.md section 2). No table stores a computed return/P&L/profitability figure.
- [ ] Every table has `tenant_id` and is designed for the same RLS pattern `validation-service`/`gateway-api` already use (policy authored even if, per this repo's own precedent, enforcement against real non-superuser credentials is a later infra ticket — don't re-litigate INF-014's sequencing here, just don't regress it).
- [ ] `EconomicInputRepository`-style interfaces defined as `typing.Protocol` (mirroring VS-003's decision: no ABC, tenant_id-first parameter, plain dataclass record types, zero `sqlalchemy` import in the interface module) with an interim SQLite or Postgres-only implementation (implementer's choice, documented — this backlog doesn't require dual-backend support on day one the way `validation-service` grew into it).
- [ ] Tests: repository round-trip for each table, tenant-isolation test (two tenants, cross-tenant read returns nothing), and a schema-level test asserting no column/table name in `economic.*` matches a profitability-output naming pattern (e.g. `pnl`, `net_return`, `profit`) — a cheap, permanent regression guard against this design decision quietly eroding later.

Rationale for priority: this module's stated bounded context (implementation-plan.md section 2: "owns `economic.*` schema") is meaningless without it, and the "inputs not outputs" decision is itself part of the ethical boundary this backlog protects — Must, not Should, because deferring it risks a later ticket adding a results table without this same scrutiny.
Depends on: ECON-001

### ECON-003 — Contracts: cost/slippage parameters + simulation request shape [Must]
**As** `economic-service`'s API layer, **I want** Pydantic models for transaction-cost/slippage parameters and a simulation *request*, **so that** ECON-005's endpoint(s) have a typed, validated request shape and a typed *refusal* response shape that is structurally incapable of carrying a numeric profitability field.

Acceptance criteria:
- [ ] `SimulationRequest` Pydantic model: references an upstream run identifier, a `fee_schedule_id`/`slippage_model_id` (or inline parameters), and whatever config a simulation needs — no profitability field on the request (it's an input, not an echo).
- [ ] Two distinct, non-overlapping response models: `EligibleSimulationResult` (has numeric fields: cost-adjusted return, slippage-adjusted return, etc. — only ever constructible on the success path) and `NotEligibleForSimulation` (has **no** numeric return/profitability field at all — only a reason code/message and, where available, the upstream verdict that caused the refusal). This is enforced by them being genuinely separate Pydantic classes with disjoint field sets, not one class with optional/nullable numeric fields defaulting to `None`/`0` — a nullable-field design would let a serialization bug silently emit a `0.0` that reads as "no profit" instead of "not eligible," which is exactly the fabricated/placeholder-number failure mode this backlog exists to prevent.
- [ ] Kept local to `economic-service` (decision 3 above) — not added to `libs/common` in this backlog.
- [ ] Tests: `EligibleSimulationResult` and `NotEligibleForSimulation` fail Pydantic validation if constructed with the other's fields; a round-trip JSON-schema test confirms the two response types are distinguishable by shape alone (e.g. an API consumer's static type check can't accidentally read a profitability field off a refusal).

Rationale for priority: ECON-005's negative-test acceptance criterion (the backlog's own most important item) is only meaningful if the refusal type is structurally incapable of carrying a fabricated number — Must, load-bearing for ECON-005.
Depends on: ECON-001

### ECON-005 — The structural eligibility gate [Must]
**As** the validation engine's ethical boundary made real in code (not just documented), **I want** every endpoint capable of returning a computed profitability/return/net-P&L figure to run a runtime guard that refuses unless the upstream result it was given is both real (not `ECON-004`'s mock fixture) and already a documented Naive0-beating verdict per `validation-service`'s own DM-test output, **so that** it is structurally impossible for this scaffold to be extended into a real profitability claim by anyone who doesn't also re-authorize both preconditions.

This is the backlog's actual point. Acceptance criteria are written in detail, matching the "AC ties back to a verifiable behavior" bar this repo already applies to `naive_first_engine`'s own DM-test stories.

Acceptance criteria:
- [ ] One `POST /simulations` (or equivalent) endpoint exists, taking `ECON-003`'s `SimulationRequest`, and internally resolves an `UpstreamValidationResult` (via `ECON-004`'s mock client, per that story's hard rule) before doing anything else.
- [ ] A single, named guard function (e.g. `check_economic_eligibility(result: UpstreamValidationResult) -> EligibilityDecision`) is the **only** code path that may authorize calling the profitability-computation function. No route handler calls the computation function directly — it always goes through the guard first. This is checked structurally, not just behaviorally: a test that inspects the route handler's call graph (or, at minimum, asserts the computation function raises/is unreachable if invoked with a guard-refused input) proves this, not merely a happy-path integration test.
- [ ] The guard's refusal condition is the conjunction of two independently-checked facts, both required: (1) `result.source == "live"` (never `"mock_fixture"` — see ECON-004), and (2) `result.dm_verdict` indicates the client model beat Naive0 with statistical significance, per `validation-service`'s own DM-test output shape (`dm_statistic`/`dm_pvalue`/`dm_verdict`, Harvey-corrected per NFE-012/da-tese-ao-produto.md section 1.2 — the gate reads this verdict, it never recomputes or second-guesses the DM test itself, matching "no arbitrary code execution/duplication of validation logic" from this service's own README "does not own" boundary).
- [ ] On refusal, the endpoint returns a `4xx` (409 Conflict is the specific recommendation — the request is well-formed but the resource state doesn't permit the action — 422 is acceptable if the implementer documents why) with `ECON-003`'s `NotEligibleForSimulation` body: an explicit "not eligible for economic simulation" reason (distinguishing, where useful, "no real upstream result" from "upstream result exists but did not beat naive"), and **never** a `200` with a zero/null/placeholder numeric field.
- [ ] On success (both conditions true), the endpoint returns `200` with `EligibleSimulationResult`, computed by a pure function (Strategy-pattern-shaped per implementation-plan.md section 7, swappable cost/slippage models) that is only reachable through the guard.
- [ ] **The negative test is the single most important acceptance criterion in this entire backlog** — it must exist, and it must prove refusal, not merely assert an endpoint returns *some* 4xx:
  - [ ] Test 1: `ECON-004`'s real mock fixture (`source="mock_fixture"`) submitted → `409`/`422` `NotEligibleForSimulation`, response body contains no numeric field (asserted by iterating the actual parsed response JSON's keys/types, not just checking the status code).
  - [ ] Test 2: a hand-constructed `UpstreamValidationResult` with `source="live"` but a DM verdict indicating the model did **not** beat Naive0 (e.g. `dm_verdict="naive0_better"` or `p >= 0.05`) → same refusal shape as Test 1.
  - [ ] Test 3 (positive control, proving the gate isn't just always-refusing by accident): a hand-constructed `UpstreamValidationResult` with `source="live"` **and** a DM verdict indicating a real, significant, Harvey-corrected outperformance → `200` `EligibleSimulationResult` with a real computed numeric value. This case is only reachable via direct construction inside the test suite in this backlog's scope (per ECON-004, no code path in the running service can produce `source="live"` today) — the test docstring must say so explicitly, so a future reader doesn't mistake this for evidence the real integration exists.
  - [ ] Test 4: confirms that, as currently wired end-to-end through `ECON-004`'s mock-only client, **every real HTTP call to `POST /simulations` in this service, as actually deployed, returns the refusal shape** — i.e. the positive path (Test 3) is proven reachable in isolation, but never reachable through the service's real running configuration in this backlog's scope. This is the test that makes the override note's core claim ("this scaffold cannot return a profitability number today, structurally") independently verifiable rather than asserted.
- [ ] README documents the gate's exact two-condition logic in prose, cross-linking this ticket, so a future contributor reads the rule before touching the guard function.

Rationale for priority: this is the entire reason this backlog exists — Must, and deliberately the most heavily specified story in this document; every other story is a prerequisite for this one to be meaningful.
Depends on: ECON-002, ECON-003, ECON-004
