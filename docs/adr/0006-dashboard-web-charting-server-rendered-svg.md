# dashboard-web's charts are server-rendered inline SVG, not a client-side JS charting library

`run_detail.html` currently renders a completed run's per-split metrics only as a table (`GET /runs/{id}/splits`, `DASH-004`). Sprint 26's goal (`docs/product/backlog-run-analysis-visualization.md` RAV-002 model-vs-Naive0 error, RAV-003 DM-verdict visualization) needs two charts added on top of that same data, without any backend change and without reopening `CLAUDE.md`'s locked-in "local-first... server-rendered (FastAPI + HTMX/Jinja2) frontend" assumption. A grep across `services/dashboard-web` for `chart.js|plotly|d3|vega` (case-insensitive) confirmed no charting technology exists in this service today, so this was a real open decision, not a detail left implicit in RAV-002's own ticket.

**Decision**: charts are generated by a small, pure-Python module, `services/dashboard-web/src/app/charting.py` (functions taking already-fetched `SplitResultResponse` data and returning simple dataclasses/dicts of pre-computed pixel coordinates/dimensions), rendered into `<svg>` markup by Jinja2 partials (`_error_chart.html` for RAV-002, `_dm_verdict_chart.html` for RAV-003, included from `run_detail.html`). **No new dependency of any kind is introduced** — no client-side JS charting library (e.g. Chart.js, Plotly, D3), and no Python plotting/image library (e.g. matplotlib) either; plain string-built SVG via Jinja2, using only colors already defined in `style.css`, is sufficient for a handful of bars/markers.

This ADR answers the backlog's own four RAV-001 acceptance criteria explicitly:

1. **Approach named, both alternatives weighed.** Considered (a) a client-side JS charting library (e.g. Chart.js) rendering into a `<canvas>`/`<svg>` from JSON data fetched or embedded in the page, versus (b) server-rendered SVG/PNG with zero new JS. Chosen: (b), specifically inline SVG (not PNG — SVG stays text/markup, so it can be asserted against the same way the rest of this service's rendered HTML already is, and it scales without a rasterization step). (a) was rejected for the three reasons in "Rationale" below.
2. **Dependency stated.** No new frontend dependency is added (no `<script src=...>` for a charting library, no npm/CDN pin to track). No new Python library is added either (no `matplotlib`/`plotly`/etc. entry in `pyproject.toml`/lockfile) — the SVG markup is hand-built via the existing Jinja2 templating this service already uses for every other page.
3. **Architecture compatibility confirmed.** An inline `<svg>` block is just more server-rendered markup inside an existing Jinja2 template (`run_detail.html`, via two new `{% include %}`-style partials) — no SPA, no client-side routing, no JS build step, no framework. It is a strict continuation of this service's existing `FastAPI + Jinja2 + HTMX` pattern (`CLAUDE.md`'s locked-in assumption, `docs/solution-design.md` section 1), not a deviation from it.
4. **Silent on Epic B.** This decision is charting-*technology* only. It does not authorize, design, or otherwise touch Epic B (raw per-point predicted-vs-actual charting, RAV-006/RAV-007/RAV-008) — those tickets remain fully open on their own merits (data volume, axis/scale design, whether per-point series data even needs to leave `gateway-api`'s existing contract) and must not treat this ADR as a decision that per-point charting is also server-rendered SVG; that question is out of scope here and undecided by this ADR.

**Rationale**:

- **Testability matches this service's existing convention.** `dashboard-web` already has a documented precedent (`RSS-002`, see `services/dashboard-web/README.md`'s "Live split-count estimate" section) of avoiding a JS-execution test harness — this service's default test suite has no Selenium/browser-JS assertion path outside the separate `-m e2e` marker. Server-rendered SVG means RAV-002/RAV-003's "chart renders correct series values for a fixture set of splits" test criteria can be verified as a plain string/attribute assertion against the rendered HTML (`TestClient` + `response.text`), the same pattern every existing `tests/test_runs_*.py` file already uses — no new test infrastructure.
- **Palette risk named and avoided.** `docs/product/backlog-run-analysis-visualization.md` flags that an off-the-shelf charting library's default color scheme is the easy way to accidentally violate the no-green/red bull/bear rule (`CLAUDE.md`'s positioning constraint — statistical accuracy is never rendered as a trading-style win/loss signal). Hand-written SVG means every color value used by a chart is one of `style.css`'s existing variables (`--color-accent`, `--color-accent-2`, the existing `--color-status-*` triplet) chosen explicitly, never a library default that could silently reintroduce green/red semantics.
- **Zero new dependency.** Nothing to add to `pyproject.toml`/the lockfile, nothing to pin, no supply-chain surface added for what is a handful of bar charts and markers.
- **Confirmed HTMX/Jinja2-compatible.** An inline `<svg>` block is more server-rendered markup in an existing Jinja2 template — no client-side routing, no JS framework, no build step, nothing HTMX's swap model needs to treat specially.

The alternative — a client-side JS library — was rejected because it would introduce exactly the test-harness gap `RSS-002` already deliberately avoided (chart correctness would only be verifiable via browser-JS execution, not a `TestClient` string assertion), would import a library whose default palette this ticket would then have to override for every chart type rather than starting from `style.css`'s own approved variables, and would add a dependency (with its own supply-chain/version-pinning surface) for a rendering job plain SVG already handles at this data volume (a handful of splits per run).

**Consequence for future readers**: RAV-002/RAV-003 must both import their SVG-building logic from `app/charting.py` rather than each hand-rolling their own string-building (this ADR names the one shared module; per-ticket duplication of that logic would violate `docs/implementation-plan.md` section 9's DRY convention). Any future decision to add a real charting library (e.g. because Epic B's raw per-point volume outgrows what hand-built SVG can reasonably render) needs its own ADR — this decision is scoped to the handful-of-bars/markers case RAV-002/RAV-003 present, not a blanket ruling on all future charting needs in this service.
