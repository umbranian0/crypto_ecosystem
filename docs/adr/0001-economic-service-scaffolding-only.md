# `economic-service` is built now, but as inert scaffolding only

`implementation-plan.md`'s trigger #11 for `services/economic-service` says: "only once a specific client model has already demonstrated stable outperformance in `validation-service` — never before, per the ethical boundary in docs section 2.7." That trigger has not fired — no model has ever beaten Naive0 on this platform, and `VS-017` (the precondition for a real client-model DM verdict to even exist) isn't built yet. We built the service anyway, at explicit user request, but scoped it to scaffolding only: an inputs-only Postgres schema (no profitability-output table), typed contracts, a mock-only upstream integration (no real `httpx` call to `validation-service` anywhere in the code), and a structural, code-enforced eligibility gate (`ECON-005`) that makes it provably impossible for the shipped service to return a real profitability number today — verified by four required tests (a mock-fixture refusal, a live-but-not-significant refusal, an isolated positive control proving the gate isn't just always-refusing, and a proof that the positive path is unreachable through the real running service).

This is deliberately a different category of decision than every other trigger override in this repo (`gateway-api`, `dashboard-web`, `reporting-service`, `ingestion-service`'s connectors) — those are all scheduling conveniences ("no pilot client yet"). Trigger #11 is CLAUDE.md's own explicit business-honesty boundary, and the alternative — waiting for the trigger to fire before writing any code — was seriously considered and rejected only because every story in this scope produces zero externally-observable capability: the artifact is inert until two separate, independently-gated future events occur (`VS-017` shipping *and* a real client model demonstrating stable outperformance). If either of those weren't true, or if the user's authorization for scaffolding-only work hadn't been explicit and informed, this should not have been built.

**Consequence for future readers**: do not treat this service's existence as evidence the platform has, or is close to having, a profitable model. Any future ticket that would let this service actually call `validation-service` for real, or persist a real computed result, is a new, separately-authorized decision — not a natural extension of this one.
