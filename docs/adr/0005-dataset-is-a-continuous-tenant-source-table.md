# A dataset is a tenant's continuously-growing per-source table, not a discrete per-crawl-run snapshot

Before the per-tenant TimescaleDB migration, "dataset" was an ambiguous file/inline-JSON blob passed to `validation-service`'s `POST /runs` - `datasets(id, tenant_id, source, kind, raw_path, schema_version, ingested_at)` in `docs/solution-design.md` section 4's original sketch implied a row-per-snapshot model, one static, versioned artifact per ingest. That model stops making sense once ingestion connectors write directly into per-tenant, per-source TimescaleDB hypertables that grow indefinitely with every crawl (`docs/product/backlog-ingestion-pipeline-integration.md`'s Epic A) - there is no natural point at which a "snapshot" would be cut, and cutting one artificially (e.g. one row per crawl run) would multiply storage and force every consumer to know which snapshot is current.

The product owner locked in the alternative instead: a dataset is `{tenant_id, source}` itself - the ongoing table a tenant's connector appends to - and selecting a dataset for a validation run means selecting `{tenant, source}` plus a time-range slice **at submission time**, not picking a pre-cut snapshot from a list. `CONTEXT.md`'s "Dataset"/"Seed data" glossary entries record the terminology this decision produces; this ADR records the decision itself and its concrete downstream consequence for the HTTP contract: `ingestion-service`'s dataset-read endpoint must accept `start`/`end` parameters (`GET /datasets/{source}/series?start=...&end=...`) rather than returning "the dataset" unconditionally, and `validation-service`'s corresponding `DatasetSource` reference shape (`{"source": ..., "start": ..., "end": ...}`) carries the same range rather than a bare dataset id. See `docs/solution-design.md` section 8.1/8.3/8.4 for the schema and API design this produces.

The alternative considered - keep a `datasets` row-per-ingest-batch model and have `ingestion-service` periodically materialize one - was rejected because it reintroduces exactly the "which snapshot is current" staleness problem the continuous-table model avoids, and because it would require a second write path (append to the hypertable, then separately materialize a snapshot row) with no consumer that actually needs a frozen snapshot rather than "the data as of whenever I submitted my run."

**Consequence for future readers**: any future code that lists "a tenant's datasets" (e.g. a dashboard dropdown) is listing distinct `{tenant, source}` combinations, not distinct ingest events - a tenant with one Reddit crawl running daily for a year still has exactly one Reddit "dataset," now with a year of rows in it, not 365 datasets. A "crawl run" (one connector execution appending rows) remains a separate, distinct concept (`crawl_runs`, an event) and must not be conflated with "dataset" (the table) in any future ticket, contract, or UI copy.
