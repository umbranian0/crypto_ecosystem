# Tenant crawler credentials are encrypted at rest with an application-level Fernet key, not hashed or left plaintext

`docs/product/backlog-ingestion-pipeline-integration.md`'s `INGEST-004` originally accepted plaintext-at-rest for per-tenant Reddit crawler credentials (`REDDIT_CLIENT_ID`/`REDDIT_CLIENT_SECRET`), reasoning that unlike `gateway-api`'s API keys - which only ever need to be *compared*, so a one-way SHA-256 hash suffices - a Reddit client secret must be *used*, sent back to Reddit on every crawl, so it cannot be hashed the same way. That story flagged the plaintext posture as an open question rather than a final answer. The product owner has since resolved it: tenant-supplied crawler credentials must be encrypted at rest, not plaintext, and not a full secrets-manager integration (e.g. Vault/AWS Secrets Manager) - explicitly the smallest correct mechanism between "plaintext" and "external secrets infrastructure this platform has no other need for yet."

The chosen mechanism is application-level symmetric encryption via Python's `cryptography` library (`Fernet`, AES-128-CBC + HMAC), with the key held in a single environment variable (`INGESTION_CREDENTIAL_ENCRYPTION_KEY`) generated once via `Fernet.generate_key()` and printed by the bootstrap script the same way `provision_tenant.py`'s API key is one-time-revealed. Only the credential value columns in the new `ingestion.connector_credentials` table are encrypted; `tenant_id`/`source`/timestamps stay plaintext since RLS already scopes them and they carry no secret. Decryption happens only inside `ingestion-service`'s own connector code, in-process, immediately before calling Reddit's API - no endpoint, log line, or dashboard response ever returns a decrypted (or even ciphertext) value; every read-side view of a credential is a boolean "is it set" plus a timestamp.

The alternative of a full secrets-manager integration (Vault, AWS Secrets Manager, etc.) was rejected for this stage: it is real, justified infrastructure the moment a pilot client's compliance requirements demand it, but nothing today needs its rotation/audit/access-policy machinery, and introducing it now would be exactly the kind of premature complexity this platform's own engineering conventions (`implementation-plan.md` section 9, YAGNI) argue against. The alternative of leaving credentials plaintext (RLS/DB-access-boundary-protected only, `INGEST-004`'s original posture) was rejected because the product owner explicitly locked in encryption as a requirement, not a nice-to-have, once this question was raised for a decision.

**Consequence for future readers**: this is the platform's first symmetric application-managed key, a materially different trust surface from password hashing (one-way, no key to lose) and from RLS (enforced by Postgres, no key at all). Losing `INGESTION_CREDENTIAL_ENCRYPTION_KEY` makes every previously-stored credential permanently undecryptable - there is no recovery path other than a tenant re-entering their credentials. No key-rotation-with-re-encryption tooling is built as part of this decision; if that becomes a real operational need, it is a new, separately-scoped ticket, not an assumed extension of this one. Any future credential type this platform stores for a tenant (a second connector requiring OAuth secrets, for example) should reuse this same mechanism rather than inventing a third at-rest posture - see `docs/solution-design.md` section 8.5 for the concrete column/key-storage shape this decision produced.
