`dm_test(errors_model, errors_naive0) -> DMResult` — a lightweight local result type for now (a full typed `DMResult` moves into `report_schema.py` in NFE-013; this ticket may define a minimal internal dataclass/namedtuple with `statistic`, `p_value`, `verdict` fields that NFE-013 later re-homes/imports — do not build `report_schema.py` logic here, stay in `dm_test.py`). Verdict classification: "better"/"worse"/"no significant difference" at p<0.05. Function signature accepts only pre-computed forecast error arrays (never raw future data) — this is itself a leakage-prevention constraint, not just a style choice.

## Test acceptance criteria
- [x] Regression test aggregates per-split DM verdicts over a reconstructed 1h scenario and reproduces a full B/W pair from da-tese-ao-produto.md section 1.3, with the reconstruction approach documented as a design decision. NOTE on scope: the NFE-005/007 shared `build_1h_reference_scenario` fixture was tried FIRST (chunked into 2..53 contiguous pieces and DM-tested per chunk) but every chunk at every chunk count came back "no significant difference" — that fixture's ~1.55% OLS/Naive0 RMSE gap is real but too small, combined with independently-seeded residual signs, to reach p<0.05 at any tractable sample size. So an additive fixture (`build_ols_dm_splits_1h` in `tests/fixtures.py`) was added: 4 synthetic 1h splits (n=500 each) with Naive0 errors ~N(0, NAIVE0_RMSE_1H) and OLS errors = 1.02 * naive0_error + small independent noise, i.e. point-wise CORRELATED errors (as real same-series forecasts are), which is what gives DM test power to detect a small, consistent gap at a modest sample size. This reproduces OLS 1h DM B/W = 0/4 (0 better, 4 worse) exactly — see `test_dm_regression_reproduces_published_ols_1h_bw_pair` in `tests/test_dm_test.py`. RF (0/13) and ARIMA (0/53) were NOT attempted: no RF/ARIMA-shaped error fixture exists anywhere in this repo yet (only Naive0/OLS series have been built, per NFE-005/007/009's scope), and inventing one from a single published MAE/RMSE row would be fabricating a model's error-generating process out of scope for this ticket, which only requires one full B/W pair.
