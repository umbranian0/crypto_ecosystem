## Design

**Pattern**: none newly introduced. This is a same-shape extension of an existing FastAPI route/Jinja2
template pair — no Strategy/Repository/Adapter/Factory/Observer applies to a form-field addition;
Dependency Injection (`DownstreamHeadersDep`/`GatewayApiUrlDep`) is already in place and untouched.

**Files touched** (scoped to `services/dashboard-web` only, per the module-boundary rule):
- `services/dashboard-web/src/app/routers/runs.py`
- `services/dashboard-web/src/app/templates/run_new.html`
- `services/dashboard-web/tests/test_runs_submit.py` (new/extended tests, same file the existing
  `run_new`/`run_new_submit` tests already live in — no new test module)

**DRY check note** (grepped `runs.py` before writing this ticket): `run_new_submit` already has two
near-identical "build a `{"path": ...}` or `{"inline": json.loads(...)}` dict from a pair of raw form
strings, handling `json.JSONDecodeError`" code blocks in embryo — today only one exists explicitly
(`dataset_reference`'s path/inline branches, the first two arms of its `if/elif/elif/else` chain), but
adding a second, structurally identical instance for `client_prediction_reference` crosses the "extract on
second duplication" threshold (implementation-plan.md section 9). **Required implementation shape**:
extract a shared helper, e.g.

```python
def _parse_path_or_inline_reference(path_value: str, inline_value: str) -> dict | None:
    """Shared by dataset_reference's path/inline modes and the optional
    client_prediction_reference field (RPT-003) -- returns {"path": ...} or
    {"inline": <parsed JSON>}, or None if neither raw form string is filled in
    (caller decides whether that's an error: mandatory for dataset_reference,
    fine for the optional client_prediction_reference). Raises
    json.JSONDecodeError verbatim on invalid inline JSON; callers catch it
    themselves and redisplay their own field-specific error message -- this
    helper only extracts the shape-building step both fields already share,
    not the differing required/optional handling around it.
    """
    if path_value.strip():
        return {"path": path_value.strip()}
    if inline_value.strip():
        return {"inline": json.loads(inline_value)}
    return None
```

`dataset_reference`'s existing path/inline branches (its first two `if`/`elif` arms) are rewritten to call
this helper (catching `json.JSONDecodeError` where the existing `except json.JSONDecodeError:` block
already is — same `_INVALID_INLINE_JSON_ERROR`, unchanged text, unchanged status code, unchanged
redisplay shape), then fall through to the existing `elif dataset_reference_source.strip():` / `else:`
arms unchanged when the helper returns `None`. **This must not change `dataset_reference`'s own observable
behavior in any case** — same three modes, same precedence (path, then inline, then source, then error),
same error text, same 422 redisplay fields. The new `client_prediction_reference_path`/
`client_prediction_reference_inline` form fields call the same helper; when it returns `None` (both blank,
the expected common case), `client_prediction_reference` stays `None` — no "missing" error, since this
field is optional. A `json.JSONDecodeError` from the client-prediction call site is caught separately (its
own `except`, since it needs its own field-specific error message so a user with both a dataset inline
payload and a model-prediction inline payload on screen knows which one is broken) and redisplays the form
with a new, distinct message (do not reuse `_INVALID_INLINE_JSON_ERROR` verbatim — name the field it
refers to).

**Two-mode vs. three-mode scope call (Tech Lead's own disclosed judgment, per this sprint's explicit ask
not to default silently either way)**: **implementing two modes only — local file path and inline JSON —
not the third "stored dataset" mode `dataset_reference` itself grew under `DASH-108`.** Reasoning:
1. The backlog's (`docs/product/backlog-trust-and-admin-ops.md`) own acceptance criteria, quoted verbatim
   in the sprint plan, state "mirroring `dataset_reference`'s existing two-mode pattern (a local file path
   field and an inline-payload JSON textarea)" — this is the literal, already-approved scope text, not a
   paraphrase.
2. `docs/sprints/sprint-55.md`'s own "Design note the Tech Lead should weigh" section states the backlog
   text "scopes two modes only, and this sprint plan does not expand that" — the PM has already flagged
   this precise question and leaned two-mode; nothing discovered while reading the actual code changes that
   lean (the backend's `DatasetSourceDep` seam would accept a third/fourth mode transparently if the UI
   ever sent one, but nothing requires the UI to expose it now).
3. Adding a third mode here would require a second `<select>` sourced from `_fetch_ingestion_datasets`,
   plus start/end/field sub-inputs, effectively duplicating the "Stored dataset" fieldset a second time on
   the same page for a second field — a materially bigger, independently-reviewable UI surface, not a small
   extension. Nothing in `RPT-003`'s own rationale ("closing the single largest gap between what the
   backend already supports and what a real pilot client can reach") requires that: a tenant with model
   predictions overwhelmingly has them as a file or a pasted payload, not as something already sitting in
   `ingestion-service`'s own per-source table (that table is for the *target* series ingestion connects to,
   not for arbitrary client-computed model output).
4. This call is easily revisited later — the backend already supports it unconditionally, so a follow-on
   ticket adding the third mode to this one field is a pure, additive UI change with zero backend risk,
   exactly the shape `ONB-003`'s own "Won't, duplicate of RPT-003" entry already anticipates for a future
   upload affordance.

This is stated here for the record and repeated in the final report to the sprint requester — a genuine
scope judgment call, not a rubber-stamp of the PM's lean.

**Positioning note (form copy)**: the new fieldset's copy states only that the platform will compare the
supplied series against the mandatory naive baselines under the leakage-aware protocol (mirroring
`CLIENT_PREDICTION_AUDIT_DISCLAIMER`'s own framing) — it must not contain "improves," "corrects," or any
form of "certif-" (certify/certifies/certification) in any usage, affirmative or negated. (The full
disclaimer, including its own negated "does not certify the provenance" clause, already renders verbatim
on the run detail page today, per VS-017/VS-029 above, unchanged by this ticket — the new submission-form
copy does not need to restate that clause itself; it only needs to avoid overstating what submitting the
field does.) Extend `test_runs_submit.py`'s existing
`test_run_new_template_has_no_banned_positioning_words` banned tuple (currently `("optimal", "recommended",
"best")`) with `"improves"`, `"corrects"`, `"certif"` (the substring, catching every inflection) — this is
a strictly stronger version of the same existing test, applied to the whole template, not a new mechanism.

## Implementation acceptance criteria

- [x] `GET /runs/new` (`run_new_form`) needs no server-side logic change — the new fields are static form
  inputs like every other field on this page, no new downstream call.
- [x] `POST /runs/new` (`run_new_submit`) gains two new optional `Form(...)` parameters:
  `client_prediction_reference_path: str = Form("")` and `client_prediction_reference_inline: str =
  Form("")`, both added to the existing `values` dict (so a 422 redisplay repopulates them, same as every
  other field).
- [x] `_parse_path_or_inline_reference` (new shared helper, see Design) extracted and used by both
  `dataset_reference`'s existing path/inline arms (unchanged observable behavior) and the new
  `client_prediction_reference_path`/`_inline` fields.
- [x] `client_prediction_reference` is `None` when both new fields are blank (the common case, and the
  only case for every test/flow that predates this ticket) — no "field required" error is ever raised for
  it, since it is optional.
- [x] An invalid inline JSON payload in `client_prediction_reference_inline` redisplays `run_new.html` with
  a 422 status and a field-specific error message (distinct text from `_INVALID_INLINE_JSON_ERROR`, naming
  "your model's predictions" or equivalent) — the existing `dataset_reference_inline` error path/message is
  unchanged. (Message text: "Your model predictions inline payload must be valid JSON." — no apostrophe,
  deliberately, since `run_new.html` renders it through Jinja2's autoescaped `{{ error }}`.)
- [x] `RunRequest(...)` construction passes `client_prediction_reference=client_prediction_reference`
  (the parsed dict-or-`None`) alongside the existing fields — `None` when not supplied is what
  `model_dump()` already sends today (see Analysis), so this is the "only when supplied, `None` otherwise"
  behavior the backlog's AC calls for, verified by the regression test below.
- [x] `run_new.html` gains a new, clearly optional fieldset (e.g. `<legend>Your model's predictions
  (optional)</legend>`) mirroring the "Dataset reference" fieldset's path/inline structure exactly (one
  text input for a local file path, one textarea for inline JSON, the same "fill in at most one" framing),
  positioned after the existing "Stored dataset" fieldset and before the `horizon` field. Field names:
  `client_prediction_reference_path`, `client_prediction_reference_inline`.
- [x] The fieldset's own copy states plainly: leaving both fields blank evaluates Naive0/NaiveLast only
  (no behavior change from today); filling in either compares the supplied series against the mandatory
  naive baselines under the leakage-aware protocol. No positioning-banned word (see Design) appears
  anywhere in the new copy.
- [x] No existing field, default, tooltip, or validation rule on `run_new.html`/`run_new_submit` changes
  behavior for a submission that does not use the new fields.
