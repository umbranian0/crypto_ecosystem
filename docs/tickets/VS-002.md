# VS-002 — `validation` schema definition (`runs`, `split_results`)

**Status: done**

## Analysis
Story: VS-002 (Must), depends on VS-001 (done). Constraining docs: solution-design.md section 4 (exact field list, reproduced below), solution-design.md section 1 principle 3 ("every table tenant-scoped"), implementation-plan.md section 5 (schema-per-service, own Alembic env per service schema), backlog decision 2 (interim SQLite now, Postgres later — schema must be backend-agnostic).

solution-design.md section 4 field list (binding):
```
runs(id, tenant_id, dataset_id, horizon, purge_gap_hours,
     split_config, status, created_at, completed_at)

split_results(id, run_id, split_index, train_start, train_end,
              purge_start, purge_end, test_start, test_end,
              model_mae, model_rmse, model_da, model_f1,
              naive0_mae, naive0_rmse, ...,
              dm_statistic, dm_pvalue, dm_verdict)
```
`...` after `naive0_rmse` in the source doc is shorthand for "the rest of naive0's metric set" — this ticket must give `naive0_*` full parity with `model_*` (mae, rmse, da, f1) plus whatever else the engine's `MetricSet` produces that's worth keeping (see Design's field-mapping decision below); don't literally stop at `naive0_rmse`.

**Design decision this ticket must make and document (backlog doesn't spell it out, `naive_first_engine`'s README does not resolve it either)**: `naive_first_engine.protocol.run_validation_protocol` returns `SplitResult.baseline_results`, a dict keyed by baseline name (`"naive0"`, `"naive_last"`, plus any `extra_baselines`), each holding a `MetricSet` and an optional `DMResult`. The schema's `model_*`/`dm_*` columns need a single designated "the model" baseline to map from. Since VS-017 (client-supplied prediction baseline) is deferred and this sprint's `POST /runs` (VS-006) never passes `extra_baselines`, the only two baselines that will ever be present this sprint are `naive0` and `naive_last`. **Decision: `model_*` columns map to the `naive_last` baseline's `MetricSet` (the persistence-floor benchmark, paired with Naive0 per da-tese-ao-produto.md section 2.3.1), and `dm_statistic`/`dm_pvalue`/`dm_verdict` map to `naive_last`'s `DMResult`** (never `naive0`'s, which is always `None` — `run_validation_protocol` never DM-tests Naive0 against itself). `naive0_*` columns map to the `naive0` baseline's `MetricSet` directly. State this mapping in both `models.py`'s module docstring and the README once VS-006 wires it up, so a future contributor adding VS-017's client-model Strategy knows exactly which column stops being "naive_last" and starts being "the client model."

## Design
Pattern: none new (this is the schema/data-model layer the Repository pattern in VS-003 sits on top of). Files: `src/app/models.py` (new — SQLAlchemy 2.0 declarative models `Run`, `SplitResult`, both backend-agnostic so VS-004's SQLite and VS-013's future Postgres implementation share the exact same model classes, per this story's own AC3), `alembic.ini` (new, service root), `migrations/env.py`, `migrations/script.py.mako`, `migrations/versions/0001_create_validation_schema.py` (new — revision creating both tables against `models.Base.metadata`, written but not run against a live DB this sprint). DRY check: grep `src/app/` for any existing model/schema code first (none expected — VS-001 only scaffolded empty packages).

Field-for-field mapping, `runs`: `id` (PK, string — reuse the engine's `run_id` from `SplitResult.run_id` as the primary key rather than inventing a second ID, since `run_validation_protocol` already computes a deterministic one), `tenant_id`, `dataset_id` (the `DatasetSource` reference, stored as given), `horizon`, `purge_gap_hours`, `split_config` (JSON column: everything `ValidationConfig` needs beyond `horizon`/`purge_gap` — `train_window`, `test_window`, `step` — so the schema doesn't need a column per `ValidationConfig` field), `status` (`"running" | "completed" | "failed"`, VS-006/VS-012), `created_at`, `completed_at` (nullable until done), plus a `failure_reason` column (nullable text) that VS-012 needs and which solution-design.md's sketch doesn't list explicitly but VS-012's AC1 requires ("a stored error message/reason") — add it now rather than have VS-012 alter the schema later.

Field-for-field mapping, `split_results`: `id` (PK, surrogate — autoincrement or UUID, `report_schema.py`'s own docstring says this is deliberately not modeled in the engine's domain object, assigned at persistence time), `run_id` (FK to `runs.id`), `split_index`, `train_start/end`, `purge_start/end` (nullable — `SplitBoundaries.purge_start/end` are `pd.Timestamp | None`), `test_start/end`, `model_mae/rmse/da/f1`, `naive0_mae/rmse/da/f1`, `dm_statistic`, `dm_pvalue`, `dm_verdict` (string, one of `"better"|"worse"|"no significant difference"` per `dm_test.Verdict`), `tenant_id` (denormalized onto this table too, per AC2 — needed so `SplitResultRepository` methods can filter by tenant without a join back to `runs` on every query, and so a leaked/misrouted `run_id` can't be used to read another tenant's splits).
