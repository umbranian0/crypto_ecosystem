## Analysis

Story: OPS-003 (Should). Acceptance criteria (backlog): a documented policy (automated — e.g.
`dependabot.yml`/Renovate once CI exists to gate its PRs — or explicitly manual, e.g. "reviewed once
per sprint") for how each of the five modules' dependencies get reviewed for updates; the policy
explicitly states whether `services/ingestion-service/requirements.txt`'s unpinned floors move to a
lockfile or stay as-is — a real, named inconsistency this story must decide on, not silently resolve
either way without stating it; the policy is referenced from each of the five modules' own READMEs,
not left in one place a future contributor has to already know to look for.

Evidence (re-confirmed at ticket-breakdown time): `libs/common/uv.lock`, `services/validation-service/uv.lock`,
`services/gateway-api/uv.lock` exist; `libs/naive_first_engine/pyproject.toml` and
`services/ingestion-service/requirements.txt` declare only floors, no lockfile at all for the former
and no lockfile mechanism for the latter. No `.github/dependabot.yml`/Renovate config/documented
manual cadence exists anywhere (glob confirms zero matches for both, still true).

## Design

No `implementation-plan.md` section 7 pattern applies — this is a documentation/policy deliverable,
not code.

**Decision (this ticket, not left open): manual cadence, not automated Dependabot, for this sprint.**
Rationale to record in the doc: OPS-001's CI now exists (satisfies the "viable" precondition), but
standing up Dependabot today would generate PRs against a platform with no live pilot client and no
incident on record — same YAGNI reasoning `backlog-operability.md` itself already applies to
OPS-006/OPS-007. A manual, once-per-sprint reviewed cadence is cheaper to reverse later (turn
Dependabot on) than to stand up and then have to tune noise out of. This is a policy decision the Tech
Lead makes explicitly in the doc, not left for the dev agent to invent.

**Decision (this ticket, not left open): `services/ingestion-service/requirements.txt`'s unpinned
floors stay as-is for this sprint**, not moved to a lockfile. Rationale to record in the doc: moving
it to a lockfile (`uv`/`pip-tools`) is real, useful work, but it means also giving the module a
`pyproject.toml`/`uv`-managed structure — a change explicitly out of scope this session (the session
constraint that set up `services/ingestion-service`'s current `requirements.txt` + hand-built `.venv`
was deliberate, specifically to unblock its new test suite, not a placeholder awaiting an immediate
follow-up). Flag it as a named, tracked gap (a candidate story for a future sprint), not silently
left unaddressed.

Files touched: a new short doc, `docs/dependency-upgrade-policy.md` (root `docs/`, since this is a
cross-cutting policy, not any one module's own concern — same placement precedent as
`docs/implementation-plan.md` itself), plus one new line in each of the five modules' READMEs
pointing at it.

DRY check: grepped `docs/` for any existing dependency-policy doc — none exists. This is greenfield;
no existing content to extend.
