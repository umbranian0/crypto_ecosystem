Status: **done, with one finding reported (unresolved cross-service alembic_version collision)**

## Analysis

Confirmed independent of ARCH-001/002: both services' `migrations/env.py` build their own engine
via `engine_from_config(...)` against `app.models.Base.metadata` — a separate code path from the
runtime engine-builder ARCH-001 extracts. This story only proves the migration *source* is
executable against real infra; it does not implement VS-013/GW-012's repository classes or RLS.

- With `DATABASE_URL` pointed at the Compose Postgres instance (targeting the `validation` schema
  for validation-service, `identity` for gateway-api — this is where the schema-targeting change
  from binding decision #4 is actually exercised for the first time, even though authoring that
  `env.py` change is VS-013/GW-012's scope, not this ticket's; INF-005 runs against whatever those
  two tickets ship, in the phase-4 sequencing sense — practically, INF-005 is executed against
  Postgres using the pre-existing `public`-schema migrations first to prove basic connectivity,
  and re-verified once VS-013/GW-012's schema-targeting lands, per sprint-06.md's own Phase
  2→Phase 4 ordering note that INF-005 proves migrations run against Postgres "at all", not that
  schema-targeting already works).
- `alembic upgrade head` run from `services/validation-service/` succeeds, creates `runs`/
  `split_results` tables with all columns from `0001_create_validation_schema.py`.
- Same for `services/gateway-api/` and `0001_create_identity_schema.py`.
- Both services' schemas coexist in the same Postgres instance without collision.
- Does not implement VS-013/GW-012's repository classes or RLS policies (out of scope, per
  backlog-infra.md scope decision 2).

## Outcome

Both migrations were run from the host (each service's own `.venv`, not inside a container)
against the real Compose `postgres` container at `localhost:5432`, with
`DATABASE_URL=postgresql://naive_first:naive_first_dev_password@localhost:5432/naive_first`. Both
succeeded individually, creating the expected tables with correct columns (including `tenant_id`
on `runs`/`split_results`). Neither service's `.venv` had a Postgres driver installed
(`psycopg2-binary` was pip-installed into both to unblock the run — neither `pyproject.toml`
declares one, since neither app currently talks to Postgres).

**Real finding, reported not hidden:** running both `alembic upgrade head` commands back-to-back
against the same database is currently unsafe and was reproduced as order-independent. Both
migrations hardcode `revision = '0001'` / `down_revision = None`, and both `env.py`s use the
default (unscoped) `public.alembic_version` table. Whichever service migrates second sees
`version_num = '0001'` already stamped, and Alembic — matching purely on that string, with no
awareness it came from a different script directory — treats the DB as already at head for that
service too. Its `upgrade()` silently never runs; no error, no warning. Confirmed via `alembic
current`/`alembic history` and by checking table presence after each ordering.

This is exactly the gap the ticket's Design section flags: real coexistence without collision
needs the `validation`/`identity` schema-targeting (and, implicitly, schema-scoped
`alembic_version` tracking) that VS-013/GW-012 own — not in this ticket's scope to fix. To still
produce a full 5-table verification snapshot, `alembic_version` (bookkeeping only, no data tables)
was manually dropped between the two runs via `psql` — a diagnostic workaround for this ticket's
verification purpose, not a resolution.
