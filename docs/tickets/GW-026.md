## Analysis

Story: DBOPT-005 (`docs/product/backlog-db-optimization.md`). `PostgresUserRepository.get_user_by_email`
(`services/gateway-api/src/app/repositories/postgres_repository.py`) runs
`SELECT ... FROM users WHERE email = :email`, called from the login-time resolution path — GW-003's
other documented tenant-agnostic exception (resolves identity before a tenant is known, alongside
`get_by_hash`), so like `api_keys.key_hash` it always scans the full table across all tenants, never a
pre-filtered per-tenant slice.

Live-verified by the DBA (`docs/product/backlog-db-optimization.md` DBOPT-005): `EXPLAIN (ANALYZE,
BUFFERS)` on the real 293-row table showed `Seq Scan on users ... Filter: (email = ...) Rows Removed by
Filter: 293`. Cheap today only because the table is small platform-wide, not per-tenant — same
constraint class as DBOPT-001/GW-025.

**Binding user decision** (recorded ahead of Sprint 22, restated in the DBA backlog): `email` is meant
to be globally unique across tenants, not merely per-tenant — so this resolves to a `UNIQUE` index, not
a plain non-unique btree, matching `get_user_by_email`'s existing `scalar_one_or_none()` assumption of
at most one row per email.

## Implementation acceptance criteria

- New Alembic migration adds `CREATE UNIQUE INDEX ix_users_email ON identity.users (email);` — unique,
  per the user's explicit decision that email is globally unique, and matching `get_user_by_email`'s
  `scalar_one_or_none()` assumption.
- Migration is Postgres-only-guarded (same idiom as `0002_add_identity_rls.py`/`0003_add_api_keys_key_hash_index.py`)
  so `alembic upgrade head` against a `sqlite:///` `DATABASE_URL`
  (`tests/test_models.py::test_alembic_upgrade_head_creates_matching_schema`) still no-ops cleanly, not
  errors.
- `downgrade()` drops the index (`DROP INDEX IF EXISTS ix_users_email`), Postgres-guarded the same way.
- Zero changes to `src/app/repositories/postgres_repository.py`, `src/app/dependencies/auth.py`, or any
  route/business-logic file — schema-only. `get_user_by_email`'s query text is unchanged; the migration
  only makes the existing query's plan cheaper and adds the uniqueness guarantee at the DB level.
