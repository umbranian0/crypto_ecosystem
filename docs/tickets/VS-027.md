## Analysis

Story: DBOPT-004 (`docs/product/backlog-db-optimization.md`), `validation.split_results` portion only.
`0004_convert_split_results_to_hypertable.py` called `create_hypertable(...)` without a
`chunk_time_interval` argument, so it uses TimescaleDB's default 7-day interval. Live-verified by the
DBA via `timescaledb_information.chunks`/`.dimensions`: 108 chunks, 7-day interval, spanning
1970-01-01 → 2026-08-06, 552 rows total — an average of ~5 rows per chunk, far below TimescaleDB's own
sizing guidance (chunks should hold a meaningful fraction of available RAM, not single-digit rows).
This is a real, measured contributor to VS-026's own 130ms planning-time finding — most of that time is
the planner walking all 108 chunks to build the `Append` plan, not real work.

**Binding constraint from the PM, must not be contradicted anywhere in this ticket's migration or
docs**: `set_chunk_time_interval` only affects chunks created **after** the call. Existing undersized
chunks are not retroactively merged or resized. This ticket's migration docstring, README addition, and
any test assertions must state this explicitly — do not imply or test for existing chunks shrinking in
count after this migration runs.

## Implementation acceptance criteria

- New Alembic migration issues `SELECT set_chunk_time_interval('validation.split_results', INTERVAL
  '90 days');` — the DBA's stated interval choice, scaled up from the current default 7 days given
  `split_results`' thin per-chunk row density.
- Postgres-only-guarded, same idiom as `0004`/`0006`.
- Migration docstring **explicitly states** the forward-only-effect caveat (does not affect existing
  chunks) — copy the wording precedent from this repo's own `0004_convert_split_results_to_hypertable.py`
  downgrade-caveat style (explicit, not implied).
- `downgrade()` reverts to the original 7-day interval via a second `set_chunk_time_interval` call
  (also forward-only, same caveat applies and must be stated) — there being no
  "undo chunk interval" primitive beyond re-setting the value going forward, matching
  `0004`'s own precedent of a documented, non-destructive downgrade rather than attempting a rebuild.
- Zero changes to `src/app/repositories/`, routers, or any query code — this is schema-tuning only.
