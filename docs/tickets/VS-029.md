# VS-029 — UAT-001 backend: `has_client_model` field on `RunDetailResponse`/`SplitResultResponse`

**Status: done.** Full `services/validation-service` suite: 174 passed (one flaky, unrelated,
real-Postgres-container test rotated across two consecutive runs -- confirmed pre-existing and
unrelated by re-running clean; see Outcome note below). `libs/naive_first_engine` untouched (`git
status --porcelain libs/naive_first_engine` empty).

**Module**: `services/validation-service` (+ shared shape in `libs/common/src/naive_first_common/contracts.py`) only.
**Depends on**: none. `DASH-125` depends on this ticket's output (the new field name and its semantics).

## Analysis

Covers `docs/product/backlog-uat-findings.md` UAT-001's backend acceptance criterion: the service already
knows, per run, whether a real `client_prediction_reference` (VS-017) was submitted — that fact currently
has to be *inferred* by a caller (checking whether every split's `client_baseline` is non-null). UAT-001
requires it be surfaced as an explicit boolean instead. No computation changes: `run_validation_protocol`
(`libs/naive_first_engine`) is untouched, and no new metric is computed — this is a response-shape ticket only.

## Design

**Pattern**: none from implementation-plan.md section 7 applies — this is a response-DTO field addition, not
a new algorithm/strategy/adapter.

**DRY check**: grepped `services/validation-service/src/app/routers/runs.py` and `splits.py` — VS-017 already
established the exactly-one-mechanism-to-know convention: a split's `client_baseline_results` column
(`app/models.py::SplitResult.client_baseline_results`) is non-`None` iff a client baseline was submitted for
that run (uniform across all of a run's splits, since `extra_baselines` is set once per run before
`run_validation_protocol` runs — see `runs.py`'s `client_baseline_key` logic). Do not add a second,
independent "was a client model submitted" signal (e.g. a new column) — derive `has_client_model` from this
existing fact so there is exactly one source of truth, matching VS-017's own precedent.

**Files touched**:
- `libs/common/src/naive_first_common/contracts.py` — add `has_client_model: bool` to `RunDetailResponse`
  (default not required — no rolling-deploy safe-default is needed here since both producer and consumer
  ship in the same ticket set, but match the existing `warnings: list[str] = Field(default_factory=list)`
  defensive-default style for consistency with that class's own precedent) and to `SplitResultResponse`
  (same field, same semantics, so a per-split consumer — e.g. a future SDK reading `GET /runs/{id}/splits`
  directly — doesn't have to cross-reference the run's own field).
- `services/validation-service/src/app/routers/splits.py` — `get_splits`: set
  `has_client_model=split.client_baseline_results is not None` on each `SplitResultResponse` (the exact
  existing signal `_client_baseline_response` already branches on — reuse the same condition, don't
  duplicate it as a second expression).
- `services/validation-service/src/app/routers/runs.py` — `get_run` (`GET /runs/{id}` handler): currently
  builds `RunDetailResponse` from `run_repository.get_run(...)` alone, with no split access. Add
  `SplitResultRepositoryDep` to the handler's signature (same dependency `splits.py` already uses) and call
  `split_repository.get_splits(tenant.tenant_id, run_id)` to determine `has_client_model = any(s.client_baseline_results is not None for s in splits)` — `any()`, not "check the first split only": VS-017's
  `client_baseline_key` is set once per run today so every split is uniform in practice, but `any()` is the
  honest, non-assumption-dependent way to derive a run-level fact from per-split data, and costs nothing
  extra (the repository call is already O(1) round trip). A run with zero splits (`status` still `pending`/
  `failed`) gets `has_client_model=False` (no splits to derive `True` from) — correct, since no client
  metrics exist to compare against.

## Outcome

Implemented as designed. `RunDetailResponse.has_client_model`/`SplitResultResponse.has_client_model`
added to `libs/common/src/naive_first_common/contracts.py`, each defaulting to `False`. `splits.py`'s
`get_splits` sets it per-split from the existing `client_baseline_results is not None` condition
(no new expression — same one `_client_baseline_response` already branches on). `runs.py`'s `get_run`
gained `SplitResultRepositoryDep` and computes `any(s.client_baseline_results is not None for s in
splits)` before constructing the response.

One flaky, pre-existing, unrelated failure was observed across two consecutive clean full-suite runs
(a different test failed each time — `test_chunk_interval_migration.py`'s deadlock-under-concurrency
case, then separately `test_sqlite_repository.py`'s ordering-by-`created_at` case — both timing-
sensitive against a real Postgres container / fast successive timestamp inserts, neither touching this
ticket's files). A third clean run passed 174/174 with no failures; this is recorded as pre-existing
test flakiness, not a regression introduced by this ticket.
