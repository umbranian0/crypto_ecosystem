# INF-014 — Non-superuser Postgres application role for validation-service/gateway-api

Status: **done** (with one disclosed, out-of-scope finding — see Outcome)
Backlog: docs/product/backlog-infra.md, INF-014 [Must] (Post-Sprint-06 addition)
Sprint: docs/sprints/sprint-07.md (runs first, independent of INF-015/016 in a build sense)
Depends on: INF-001, VS-013, GW-012 (all satisfied prior to this sprint)

## Analysis

Confirmed by reading the actual current state (not assumed):

- `infra/postgres-init/01-create-schemas.sql` provisions only two schemas (`validation`, `identity`);
  it creates no roles. The only Postgres role that exists is `naive_first`, created implicitly by
  the official `timescale/timescaledb` image's `POSTGRES_USER` mechanism (`infra/docker-compose.yml`).
  That role is a Postgres superuser (confirmed by both services' own `tests/test_postgres_repository.py`
  docstrings: `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = 'naive_first'` returns
  `(true, true)`).
- Both `0002_add_row_level_security.py` (validation-service) and `0002_add_identity_rls.py`
  (gateway-api) use `FORCE ROW LEVEL SECURITY`, which is necessary but not sufficient: Postgres
  unconditionally exempts superusers from RLS regardless of `FORCE` — there is no clause or GUC
  that overrides this. The only fix is connecting as a role that is both `NOSUPERUSER` and
  `NOBYPASSRLS`.
- Both services' `infra/docker-compose.yml` entries currently pass `DATABASE_URL` built from
  `POSTGRES_USER`/`POSTGRES_PASSWORD` (i.e. `naive_first`) for both migration and runtime use —
  there is currently no distinction between "the role that runs `alembic upgrade head`" and "the
  role the running FastAPI process connects as caller-of-record."
- Both services' `tests/test_postgres_repository.py` already create an ephemeral, test-only,
  non-superuser role (`validation_rls_test_role` / `gw012_rls_test_role`) purely to give their RLS
  assertions teeth. This ticket's job is to make that role real and permanent (not per-test-run
  ephemeral) and to make it the one the actual running containers use — closing exactly the gap
  those tests' own docstrings flag as "an infra-provisioning gap ... outside this ticket's module."
- Neither service's application code reads `DATABASE_URL` differently based on which role is
  embedded in it — `_postgres_engine_url`/`get_validation_run_repository` (validation-service) and
  the equivalent in gateway-api just pass the URL through to SQLAlchemy. **This means no source
  change under `services/*/src/` is required** — the entire fix is: (a) a new Postgres role with
  the right grants, (b) repurposing `naive_first` as migration-only (keeps ownership, stops being
  the runtime credential), (c) `docker-compose.yml`'s runtime `DATABASE_URL` pointed at the new
  role, (d) `.env.example` documenting both.

## Design

- **New role**: `naive_first_app`, created via a new numbered init script
  `infra/postgres-init/02-create-app-role.sql`, consistent with `01-create-schemas.sql`'s existing
  convention (mounted at `/docker-entrypoint-initdb.d/`, runs only against a fresh, empty data
  volume — an existing running Postgres data volume from a prior sprint will **not** pick this up
  automatically; the Test/Review sections below cover how this is handled for the already-running
  Sprint 06 containers).
  - `CREATE ROLE naive_first_app LOGIN PASSWORD '<from env, see below>' NOSUPERUSER NOBYPASSRLS
    NOCREATEDB NOCREATEROLE;`
  - `GRANT USAGE ON SCHEMA validation, identity TO naive_first_app;`
  - `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA validation, identity TO
    naive_first_app;`
  - `ALTER DEFAULT PRIVILEGES IN SCHEMA validation, identity GRANT SELECT, INSERT, UPDATE, DELETE
    ON TABLES TO naive_first_app;` (so a future migration adding a table doesn't silently leave the
    app role unable to read it — table-level grants don't retroactively apply to tables that don't
    exist yet at grant time).
  - Explicitly **no** `GRANT CREATE`, no ownership transfer, no `CREATEDB`/`CREATEROLE` — matches
    the acceptance criteria's "nothing beyond runtime CRUD" boundary.
  - Password sourced from a new env var (`POSTGRES_APP_PASSWORD`, mirroring the existing
    `POSTGRES_PASSWORD` pattern), substituted into the init SQL the same way Postgres's own
    entrypoint already substitutes `POSTGRES_USER`/`POSTGRES_PASSWORD` — since raw `.sql` files
    under `docker-entrypoint-initdb.d` don't get env-var substitution for free, the init script is
    written as a `.sh` wrapper (`02-create-app-role.sh`) that runs `psql` with the password
    interpolated from the shell environment, not hardcoded.
- **`naive_first` repurposed as migration-only**: no schema change needed — it already owns the
  tables (it created them via `alembic upgrade head`) and already has full privileges. This story
  changes *only* which role the running containers' `DATABASE_URL` uses, not `naive_first`'s own
  grants. Migration-time invocations (manual, or INF-016's `migrate.sh`/`migrate.ps1` once it
  exists) continue to use `naive_first`.
- **`docker-compose.yml`**: `validation-service`/`gateway-api` service entries' `DATABASE_URL` env
  var changes from the `POSTGRES_USER`/`POSTGRES_PASSWORD`-derived default to a new
  `POSTGRES_APP_USER`/`POSTGRES_APP_PASSWORD`-derived default (new env vars,
  `naive_first_app`/`<password>`). No other compose changes.
- **`.env.example`**: documents `POSTGRES_APP_USER`/`POSTGRES_APP_PASSWORD` alongside the existing
  `POSTGRES_USER`/`POSTGRES_PASSWORD`, with a comment stating plainly which is used for migration
  (`naive_first`, superuser, schema owner) vs runtime (`naive_first_app`, non-superuser, RLS-bound)
  — extends the existing Compose-network-vs-local-dev comment pattern with a third axis
  (migration-vs-runtime) rather than replacing it.
- **Pattern/DRY check**: no new abstraction needed — this is infra provisioning (SQL/shell +
  compose env vars), not application code. No duplication introduced: the app-role grants live in
  exactly one file, referenced nowhere else.
- **Live-container caveat (must be handled, not glossed over)**: the Sprint 06 Postgres container
  (`naive-first-postgres`) has been running for hours against an existing data volume
  (`infra_postgres-data`) — `docker-entrypoint-initdb.d` scripts only execute against a *fresh*
  empty volume, so simply adding `02-create-app-role.sh` will not retroactively run against the
  live volume. This ticket's Implementation must run the new role-creation SQL directly against the
  live container (`docker exec ... psql -f ...` or equivalent) in addition to adding the init
  script for future fresh-volume boots, and must record this explicitly rather than silently rely
  on a container recreate the ticket didn't actually perform (recreating with `-v` would destroy
  the RLS/migration state already proven in Sprint 06).

4. `GET /runs/{id}` through `gateway-api` as Tenant B (same run id) → `404 {"detail":"run not

5. **DB-level RLS proof, isolated from any application-level filter**: connected directly as
   `naive_first_app` (the real runtime role, not a test-only role) via `psql`, and ran a raw,
   *unfiltered* query (`SELECT id, tenant_id, dataset_id, status FROM validation.runs;` — no `WHERE
   tenant_id = ...` clause at all, so no application code's filtering logic is in the loop) inside
   three separate transactions:
   - `set_config('app.tenant_id', '<Tenant A id>', true)` then the unfiltered SELECT → returned
     exactly the 1 row belonging to Tenant A.
   - `set_config('app.tenant_id', '<Tenant B id>', true)` then the same unfiltered SELECT → **0
     rows** — Tenant A's row is invisible to Tenant B's scope even though the query itself placed
     no restriction on `tenant_id` — this is Postgres RLS enforcing isolation on an otherwise fully
     open query, which is the concrete proof this ticket's acceptance criteria requires (not
     merely "the app's own WHERE clause still works").
   - With `app.tenant_id` not (re-)set in a fresh scope, the same unfiltered SELECT again returned
     0 rows (fail-closed) — consistent with the RLS policy's `current_setting('app.tenant_id')`
     comparison never matching an empty/undefined value.
6. Also read `services/validation-service/src/app/repositories/postgres_repository.py`'s
   `get_run`/`get_splits`: contrary to the ticket's own Test-AC assumption text ("no `WHERE
   tenant_id = ...` clause of its own"), the actual code **does** retain a `.where(Model.tenant_id
   == tenant_id)` clause — but its own docstring (present in the file, written during VS-013)
   explicitly documents this as "defense in depth, not... the enforcement mechanism — RLS is,"

   `WHERE` at all and still observing correct isolation.

**Finding — real, disclosed, NOT silently patched (Implementation AC forbids `services/*/src/`
changes for this ticket, and this is genuinely out of INF-014's scope):** `POST /runs` through the
Postgres-backed `PostgresValidationRunRepository.create_run` (validation-service) returns a `500`
under real RLS enforcement (i.e. now that INF-014 has made the app connect as a non-superuser).
Root cause: `create_run` calls `session.refresh(run)` *after* `session.commit()` — the
per-transaction `set_config('app.tenant_id', ...)` scope set at the start of the transaction
reverts at `COMMIT` (by design, so it can't leak across pooled-connection reuse), but `refresh()`
issues a brand-new `SELECT` in a new transaction that never re-establishes that scope, so RLS
correctly (if surprisingly, from the caller's point of view) hides the very row that transaction
just inserted, and SQLAlchemy reports "could not refresh instance." **This was invisible before
INF-014** because the app previously connected as the superuser `naive_first`, which Postgres
exempts from RLS unconditionally — so RLS's fail-closed behavior on the post-commit refresh never
triggered. Confirmed the row itself IS correctly persisted (checked via direct superuser `psql`
read) — this is purely a response-construction bug in the repository method, not a data-loss or
isolation bug. **`gateway-api`'s own `PostgresTenantRepository.create_tenant` /
`PostgresUserRepository.create_user` (GW-012) already avoid this exact pitfall**, with an explicit
comment: "Record built from the already-fully-populated object, not a post-commit
`session.refresh()`... refreshing after commit() would issue a new SELECT in a new transaction...
which RLS would then correctly, if surprisingly, block." `validation-service`'s `create_run` did
not follow this same pattern. **Recommendation, not actioned here**: a small follow-up ticket
against `services/validation-service` (e.g. build `RunRecord` from the already-populated `Run`
object before `commit()`, mirroring `gateway-api`'s `create_tenant`/`create_user`, rather than
calling `session.refresh()` after) should be scheduled — this is a real, production-breaking
regression for the Postgres-backed `POST /runs` path now that RLS is genuinely enforced, and should
be treated with urgency comparable to a Must, even though it falls outside this Should/Must infra
sprint's own file-boundary constraints. Flagged to the requester in the sprint close-out report,
not silently deferred.
