## Light-compute ceiling — exact numeric caps (non-negotiable, per sprint-41.md)

- **Dataset window**: exactly **3,000 hourly rows** (seeded, deterministic — `numpy.random.default_rng`
  with a fixed seed, documented in the fixture's docstring). This matches the "on the order of a few
  thousand hourly rows" scale `naive_first_engine`'s own regression suite already exercises.
- **`ValidationConfig`**: `train_window=500`, `test_window=50`, `step=250`, `purge_gap=6` (the larger of
  the two horizons, applied uniformly to both runs for simplicity — never less than either horizon).
  This yields roughly 9-10 splits per horizon run (`(3000 - 500 - 50 - 6) / 250 ≈ 9.8`), ~18-20 splits
  total across both horizon runs — bounded, not the full walk-forward sweep a real deployment would use.
- **LightGBM hyperparameters, fixed, no search**: `n_estimators=50`, `max_depth=4`, `num_leaves=15`,
  `learning_rate=0.1`, `min_child_samples=10`, `n_jobs=1`, `random_state=42`, `verbose=-1`. No
  `GridSearchCV`/`RandomizedSearchCV`/Optuna or any other hyperparameter-search loop anywhere in this
  ticket's code.
- **CPU-only**: plain `pip`-installable `lightgbm` (CPU build); no `device="gpu"`, no cloud training call.
- **Horizons**: exactly `1` and `6` — no `24` or other horizon in this ticket's run.
- **Expected runtime ceiling**: the dev agent must time its own full pytest run (dataset generation +
  both horizon runs' full split loop, fit/predict/DM-test) and report the wall-clock seconds in its
  final message. If the actual measured time trends toward the 10-minute mark or beyond, the dev agent
  must scale `step` up (fewer splits) or the dataset window down further and re-measure — not proceed
  and only flag it. Target: **under 5 minutes** for the full new test file alone.

### Correction — Tech Lead review found a same-row target-leakage bug (fixed)

Tech Lead review caught a real bug in the dev agent's original `_make_features` (in
`research/models/gradient_boosting.py`): it called `rolling_mean_return(returns, 5)` and
`rolling_volatility(returns, 5)` directly on `returns` and used the result as a feature for predicting
`returns` at that *same row*. `pandas.Series.rolling(window)` is inclusive of the current row by
construction — `rolling_mean(5)[t] = mean(returns[t-4..t])` — so the feature at row t partially contained
the exact target value (`returns[t]`) it was predicting. This is same-row contamination in how
`gradient_boosting.py` combined `research/features.py`'s functions into a supervised frame, not a bug in
`research/features.py` itself (MR-002's `rolling_mean_return`/`rolling_volatility`/`lagged_returns` are
correct as documented for their intended, caller-shifts-if-needed use, and were left unmodified). It
explains the suspiciously one-sided pre-fix verdict counts above (6/10 and 7/10 "better", zero "worse")
— a strong signal of leakage, not a genuine finding, and those numbers must not be read as real results.

**Fix**: `_make_features` now applies an additional `.shift(1)` to both rolling-derived columns before
use — `rolling_mean_return(returns, 5).shift(1)` / `rolling_volatility(returns, 5).shift(1)` — so the
feature at row t only ever uses `returns[t-5..t-1]`, matching `lagged_returns`'s own already-correct
`shift(lag)` (lag>=1) convention. `research/features.py` itself was not modified. The extra leading NaN
this produces is already absorbed by `predict`'s existing `.dropna()` (train) / `.fillna(0.0)` (test)
handling — no other code change was needed.

- Full `research/tests/` suite (10 tests, including MR-002's `test_features.py`): 10 passed in 1.62s.
