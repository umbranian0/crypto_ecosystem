# LC-010 — Extract the tenant-scoped-transaction helper into `libs/common`

**Sprint**: 18. **Module**: `libs/common` (+ small call-site edits in `gateway-api`/`validation-service`).
**Status**: todo. **Priority**: Must. **Depends on**: none (parallel with `INGEST-002`/`INGEST-011`).
**Blocks**: `INGEST-003` (must be the third consumer from day one, not a fourth hand-rolled copy).

## Analysis

Story: backlog `LC-010`. Two services (`gateway-api`'s `_set_tenant_scope`, `validation-service`'s
`_tenant_scoped_session`) already independently implement
`SELECT set_config('app.tenant_id', :tenant_id, true)` as the first statement of every transaction.
`ingestion-service` is about to become a third. `implementation-plan.md` section 9's DRY rule ("if two
services seem to need the same logic, that logic belongs in a lib") — two existing copies plus a third
about to be written is the textbook second-duplication trigger this rule exists for.

## Design

No section-7 pattern renamed here — this is plain DRY extraction, not a new pattern. File touched:
`libs/common/src/naive_first_common/db.py` (already home to `build_engine`, ARCH-001 — one function
added to an existing file, not a new module, since it's the same "DB helper" concern).

**DRY check (grep first)**: `grep -rn "set_config('app.tenant_id'" services/` — confirmed exactly two
call sites today: `services/gateway-api/src/app/repositories/postgres_repository.py`'s
`_set_tenant_scope(session, tenant_id)` and `services/validation-service/src/app/repositories/
postgres_repository.py`'s `_tenant_scoped_session(engine, tenant_id) -> Session`. The two existing
signatures differ (one takes an existing `Session`, one builds and returns one) — the shared function
must support both call shapes without forcing either service to restructure its `with Session(...)`
blocks.

## Implementation acceptance criteria

- [ ] `naive_first_common.db` gains `tenant_scope(session: Session, tenant_id: str) -> None` — issues
  exactly `SELECT set_config('app.tenant_id', :tenant_id, true)` via `session.execute(text(...), ...)`,
  byte-identical SQL/params to both existing private functions.
- [ ] `gateway-api`'s `_set_tenant_scope` becomes a thin call to `naive_first_common.db.tenant_scope`
  (or is removed and call sites import the shared function directly — dev agent's choice, but no
  parallel implementation left behind).
- [ ] `validation-service`'s `_tenant_scoped_session` keeps its own `(engine, tenant_id) -> Session`
  signature (callers rely on it returning a `Session`) but its body now calls
  `naive_first_common.db.tenant_scope(session, tenant_id)` instead of issuing the `SELECT set_config`
  statement itself.
- [ ] Zero behavior change: same SQL, same parameter binding, same per-transaction (not per-connection)
  scoping semantics.

## Test acceptance criteria

- [ ] `libs/common`'s own test suite gains a unit test for `tenant_scope` (fake/mock `Session`, assert
  `execute` called with the exact SQL text and `{"tenant_id": ...}` params).
- [ ] `gateway-api`'s and `validation-service`'s **existing** test suites (including
  `validation-service`'s pooled-connection-reuse-does-not-leak test and `gateway-api`'s equivalent) are
  re-run unchanged against the new call sites and still pass — this is the proof the extraction changed
  no behavior, not a new test to write.
