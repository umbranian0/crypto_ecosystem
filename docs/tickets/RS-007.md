## Analysis

Covers backlog RS-007: `GET /health` checks real connectivity to this service's own Postgres schema,
matching OPS-005-01/02's precedent -- not a hardcoded `ok`.

## Design

- Files touched: `src/app/main.py` (add route), `src/app/dependencies/repositories.py` (add
  `get_health_check_engine`, same seam validation-service uses), `tests/test_health.py` (new).
- **DRY check note**: reuse `naive_first_common.db.build_engine`/the memoized-by-URL provider
  already established by RS-002, not a third derivation of engine construction. Mirror
  `services/validation-service/src/app/dependencies/repositories.py`'s `get_health_check_engine`
  and `src/app/main.py`'s `/health` handler shape exactly (same `SELECT 1`, same response shapes).
- Redis connectivity (RS-006's subscriber) is explicitly out of scope for this check, same stance
  validation-service's own `/health` docs take for its Redis producer side.

## Outcome

Implemented `GET /health` in `src/app/main.py`, mirroring validation-service's `/health`
(OPS-005-01) handler shape exactly: `Depends(HealthCheckEngineDep)`, `with engine.connect() as
conn: conn.execute(text("SELECT 1"))`, `200 {"status": "ok"}` on success, `503
{"status": "unhealthy", "detail": "database unreachable"}` (fixed generic string) on any exception
from `connect()`/`execute()`.

Added `get_health_check_engine()` to `src/app/dependencies/repositories.py`, reusing the existing
`_database_url()`/`_postgres_engine_url()`/`_get_engine()` (memoized-by-URL) helpers that
`get_report_repository()` already uses -- no second/third derivation of the DB URL or engine
construction, per the ticket's DRY check note. Unlike validation-service, this service has no
SQLite fallback branch (backlog decision 4, Postgres-only), so the provider is a straight-line
resolve-URL-then-memoized-engine call.

Files changed:
- `services/reporting-service/src/app/main.py` -- added the `/health` route (imports
  `JSONResponse`, `text`, `HealthCheckEngineDep`).
- `services/reporting-service/src/app/dependencies/repositories.py` -- added
  `get_health_check_engine()` and `HealthCheckEngineDep`.
- `services/reporting-service/tests/test_health.py` -- new. Three tests: healthy path (fake engine
  that connects/executes cleanly -> 200), connect-raises path (-> 503, fixed detail string, asserts
  `"password"`/tenant-role name absent from the response body), execute-raises path (same
  assertions, covering the case where `connect()` succeeds but the `SELECT 1` itself fails).
- `services/reporting-service/README.md` -- Status line and Contract paragraph updated to document
  `GET /health` (RS-007 -- done), matching validation-service's own OPS-005-01 documentation
  pattern, and explicitly noting Redis connectivity is out of scope.

Test run (uv run pytest, full `services/reporting-service` suite, run from a temp copy outside the
OneDrive-synced tree per this session's environment workaround, `../../libs/common` kept at the
same relative position, real Postgres reachable at localhost:5432): **28 passed** (25 pre-existing +
3 new in `test_health.py`), 0 failed. `uv.lock` was not modified (diffed identical against the repo
copy -- no new dependency needed, as expected).

No deviations from the ticket's Design section. All Implementation/Test/Documentation acceptance
criteria met. Review acceptance criteria left unchecked for the Tech Lead's own verification pass,
per protocol.
