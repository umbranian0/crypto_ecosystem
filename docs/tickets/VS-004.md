# VS-004 — Interim in-memory/SQLite-backed repository implementation

**Status: done**

## Analysis
Story: VS-004 (Must), depends on VS-003. Constraining docs: backlog decision 2 (interim SQLite now, Postgres later, purely a DI swap), this service's README ("schema-per-service can later become DB-per-service without touching call sites"). This is one of the two tickets (with VS-012) the role definition calls out for special scrutiny: tenant-isolation tests must be real, not rubber-stamped.

## Design
Pattern: Repository (concrete implementation of VS-003's interfaces). Files: `src/app/repositories/sqlite_repository.py` (new — `SQLiteValidationRunRepository`, `SQLiteSplitResultRepository`, both backed by VS-002's `models.py` SQLAlchemy models against a file-based SQLite engine, so state survives a process restart per AC1), `src/app/dependencies/repositories.py` (edit — wire the DI provider stubs from VS-003 to construct these concrete classes, e.g. reading a DB path from an env var/settings with a sane local default like `./validation.db`). DRY check: grep `src/app/repositories/` for existing SQLite/session-handling code before writing (VS-002's `tests/test_models.py` may already have engine-construction boilerplate worth factoring into a shared `src/app/db.py` helper if duplicated a second time — check).

Every query method (`get_run`, `update_run_status`, `get_splits`) filters by `tenant_id` in the `WHERE` clause itself (application-level filtering, since this is SQLite — row-level security is VS-013's Postgres-only concern) — never "fetch by id, then check tenant_id in Python," which would be an easy-to-regress pattern once someone forgets the check.

## Implementation acceptance criteria
- [x] `SQLiteValidationRunRepository` and `SQLiteSplitResultRepository` implement VS-003's interfaces against SQLite (file-based), using VS-002's schema.
- [x] Swappable purely via DI: `src/app/dependencies/repositories.py`'s provider functions are the only place a concrete class is referenced; no router/business-logic code imports `sqlite_repository` directly.
- [x] Every read/update query filters by `tenant_id` at the query level, not via post-fetch filtering in Python.

## Test acceptance criteria — tenant isolation is the load-bearing part of this ticket
- [x] `tests/test_sqlite_repository.py`: unit tests exercise both repositories directly — create run, update status, append splits, fetch splits.
- [x] **A dedicated tenant-isolation test, written so it would fail if isolation broke**: create a run for `tenant_a`, create a *different* run for `tenant_b`. Assert `get_run(tenant_b, tenant_a_run_id)` returns `None` (not `tenant_a`'s row). Assert `get_splits(tenant_b, tenant_a_run_id)` returns an empty list, not `tenant_a`'s splits. Do the same in the other direction (`tenant_a` querying `tenant_b`'s run). This must use two genuinely different `tenant_id` values and genuinely assert the *absence* of the other tenant's data — not merely assert that querying with the correct tenant_id works.
- [x] Run via `.venv\Scripts\python.exe -m pytest -q`, confirm pass, paste output.

## Review acceptance criteria
- **Tech Lead personally reads the tenant-isolation test body** (not just the pass/fail result) to confirm it actually creates two distinct tenants' data and asserts cross-tenant queries return nothing — per the role definition's explicit instruction not to rubber-stamp this. Tech Lead also reads `sqlite_repository.py`'s query methods to confirm `tenant_id` is in the SQL `WHERE` clause (e.g. via SQLAlchemy's `.where(Model.tenant_id == tenant_id)`), not filtered after fetching.

## Documentation acceptance criteria
- [x] `services/validation-service/README.md` states explicitly that this SQLite repository is an interim storage backend pending `infra/docker-compose.yml` + Postgres (VS-013, blocked on trigger #4), named explicitly so a future contributor doesn't mistake it for final design.
