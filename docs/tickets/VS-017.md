   NaN-becomes-JSON-`null`-on-the-wire behavior already affected the *existing* top-level

## Analysis

Story: accept a client-supplied prediction column and run it through the same leakage-aware protocol
as the naive baselines, via a Strategy implementation of `naive_first_engine`'s `Baseline` interface,
so a client model can eventually be scored against Naive0/NaiveLast without a special-cased code path.
Acceptance criteria (verbatim, including the review's added fourth criterion):
- A wrapper class implements the same `Baseline` interface (`predict(train, test) -> Series`)
  `Naive0`/`NaiveLast` already implement, backed by a client-supplied prediction series.
- `POST /runs` optionally accepts a client-prediction reference alongside the mandatory naive
  baselines — naive baselines are never optional/skippable (VS-019).
- No new execution path runs arbitrary client code (VS-018) — this is "client submits predictions,"
  not "client submits a model."
- Any report/response surface built on this states explicitly that the platform audits the
  *comparison*, not the *provenance*, of the client's predictions.

**This is a genuinely new capability, not hygiene** (per the hardening-wave review's own extra
scrutiny) — it does not touch the leakage-aware split/purge-gap protocol (client predictions apply
only to already-defined test windows) and does not introduce client code execution. The one thing this
ticket must get right, structurally not just by convention: naive baselines cannot become skippable as
a side effect of adding this feature.

## Design

**Pattern**: Strategy (implementation-plan.md section 7) — `naive_first_engine.baselines.Baseline` is
already the interface (`predict(train, test) -> Series`), and `naive_first_engine.protocol.ValidationConfig`
already has an `extra_baselines: list[Baseline]` field, wired through `run_validation_protocol` (read
`libs/naive_first_engine/src/naive_first_engine/protocol.py` directly — `_baseline_key`,
`config.extra_baselines` loop, lines ~72 and ~128 as of this ticket). **This extension point already
exists and needs zero changes to `naive_first_engine` itself** — this ticket is entirely
`validation-service`-side: a new `Baseline` implementation plus wiring it into `POST /runs`'s existing
`ValidationConfig` construction.

**New wrapper class**: `ClientPredictionBaseline` (new file,
`services/validation-service/src/app/client_baseline.py`), implementing `Baseline.predict(train,
test) -> pd.Series`. It is constructed with a pre-loaded `pd.Series` of client predictions (loaded via
the *existing* `DatasetSource` interface — reuse `DatasetSourceDep`, do not invent a second dataset-
loading mechanism for client predictions; a client-prediction reference is structurally the same shape
as a dataset reference, just used differently). `predict(train, test)` looks up `test.index` in the
pre-loaded client series and returns exactly those values, raising a clear `ValueError` (not a silent
`NaN`-fill) if any `test.index` timestamp is missing from the client series — this is what "no
arbitrary client code execution" means concretely: the wrapper only ever indexes into
already-materialized data, it never calls back into anything client-supplied at prediction time.

**Persistence**: `split_results`' existing columns (`model_*`, `naive0_*`, `dm_*`) are fixed to the two
mandatory baselines and must not be repurposed for a third baseline's numbers (that would silently
break the existing "model_* means naive_last" documented contract other tickets/reports already rely
on). Add one new nullable column, `split_results.client_baseline_results` (`JSON`/`Text`, SQLAlchemy
`JSON` type on Postgres, TEXT-serialized-JSON fallback on SQLite consistent with how this codebase
already handles JSON-ish columns like `runs.split_config` — read `app/models.py` first and match its
existing JSON-column pattern exactly, do not invent a new one), storing `{"key": <baseline key from
_baseline_key>, "metrics": {...same 7 fields as model_*/naive0_*...}, "dm_statistic": ..., "dm_pvalue":
..., "dm_verdict": ...}` per split, `NULL` when no client baseline was supplied for that run. This is a
new migration (both SQLite `create_all` via `models.py`'s declarative change, and a new Postgres
Alembic migration file).

**`POST /runs` request/response**: `naive_first_common.contracts.RunRequest` gains one new **optional**
field, `client_prediction_reference: dict | None = None` (same shape as `dataset_reference` — a
`DatasetSource`-compatible reference). When present, `runs.py`'s handler: loads it via
`dataset_source.load(...)` (same `DatasetSourceDep`), constructs `ClientPredictionBaseline(series)`,
passes `ValidationConfig(..., extra_baselines=[ClientPredictionBaseline(series)])`. When absent,
`extra_baselines=[]` — byte-identical to today's behavior, confirming naive baselines are never
affected either way. `GET /runs/{id}/splits`' response model gains an optional
`client_baseline: ClientBaselineResult | None` field (new Pydantic model, mirroring the existing
`model_*`/`naive0_*` field group's shape but nested rather than flattened, to avoid a fifth
near-duplicate set of 10 top-level fields) populated from the new column when non-null.

**Positioning disclaimer (the review's added AC)**: `GET /runs/{id}/splits`' response gains a
service-level constant string (e.g. a module-level `CLIENT_PREDICTION_AUDIT_DISCLAIMER` in
`app/client_baseline.py`, imported by `runs.py`/`splits.py`) returned in the response whenever any
split's `client_baseline` field is non-null — e.g. as a top-level field on `RunListResponse`'s sibling
detail responses, or as a fixed field embedded in `ClientBaselineResult` itself (simplest: put it on
`ClientBaselineResult`, since it's per-run-with-a-client-baseline, not global) — exact wording: "This
platform validates the comparison between the client-supplied prediction series and the naive
baselines (Naive0/NaiveLast), computed honestly under the leakage-aware protocol. It does not certify
the provenance of the client's own predictions — a client-supplied series could itself have been
produced with knowledge of test-period outcomes, and that is the client's own leakage, not this
platform's." This exact framing (or a materially equivalent one covering both clauses) must appear
verbatim in the response body, not only in prose documentation.

**DRY check performed**: `Baseline` interface and `extra_baselines` plumbing already exist in
`naive_first_engine` (zero duplication needed there). `DatasetSource`/`DatasetSourceDep` already
exist and are reused, not duplicated, for loading the client-prediction series. `runs.py`'s existing
try/except failure-handling structure (VS-012) wraps the new load/predict call automatically since it
sits inside the same `try` block as `dataset_source.load`/`run_validation_protocol` — no new
error-handling path needed.
