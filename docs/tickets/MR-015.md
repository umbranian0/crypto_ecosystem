## The leakage guard (binding, must be implemented exactly this way)

For a fixed `window` (≤ 24), `GRUSequenceBaseline.predict(train, test)` must construct, for every row
whose target is being predicted (whether in `train`'s own internal train/val split for fitting, or in
`test` for inference), an input tensor built exclusively from the `window` values immediately preceding
that row — i.e. for target row at position `i` (0-indexed within the full `pd.concat([train, test])`
time-ordered context), the input window is `values[i-window:i]`, never including `values[i]` itself.
Concretely:

1. Build windows for fitting using `train` only: for each valid position `i` in `train` (`i >= window`),
   `X[i] = train.values[i-window:i]`, `y[i] = train.values[i]`. The first `window` rows of `train` have no
   valid window and are dropped (`.dropna()`-equivalent row-drop, not zero-padding that could look like a
   real value).
2. For `test`, each target row's window may span the boundary into `train`'s own tail (this is legitimate
   train-fold information, available before `test` starts, same convention `RegimeHMMBaseline` already
   uses for its lagged state routing) — i.e. row 0 of `test`'s window is `train.values[-window:]`, row 1's
   window is `train.values[-window+1:]` + `test.values[:1]`, etc. At no point does any row's window include
   that same row's own value.
3. Any normalization/scaling of the input values (if used) is fit on `train`'s own values only (e.g.
   `StandardScaler().fit(train.values.reshape(-1, 1))`), then applied to both `train`- and `test`-derived
   windows — never fit on `test` or on `train`+`test` combined.
4. A fresh `torch.nn.GRU`-based model and optimizer are constructed and trained (≤ 20 epochs) inside every
   `predict()` call — no instance-level state persisted across calls, same structural invariant every
   other `research/models/*.py` baseline already enforces.
5. `torch.manual_seed(42)` (or equivalent fixed seed) set inside `predict()` for determinism, matching
   `RegimeHMMBaseline`'s `random_state=42` precedent — not a correctness requirement of the leakage guard
   itself, but required for reproducible ticket-outcome numbers.

**Unit test requirement (binding)**: `test_gru_sequence.py` must include a test that constructs a
synthetic series where each timestep has a distinguishable, unique value (e.g. `pd.Series(range(N))` or
similarly monotonic/unique), calls the window-construction helper directly (not the full `predict()`, so
the test isolates the boundary logic precisely), and asserts for every constructed window that (a) the
window's own values are exactly `values[i-window:i]` (b) `values[i]` (the target) is never present anywhere
in the window array, and (c) deliberately breaking the boundary by one position (i.e. constructing
`values[i-window+1:i+1]`, which DOES include `values[i]`) is shown, in the same test, to make the "target
present in window" assertion fail — either by asserting the correct implementation's output differs from
this deliberately-broken slice, or by directly asserting `values[i] not in window` where `values` are
unique enough that this is a genuine, non-trivial check (not something that would pass by accident on
e.g. an all-zeros series). A test that only asserts "predict returns a Series of the right length" does
not satisfy this AC.

## Compute-ceiling scoping decision for MR-015 (binding, Tech-Lead-fixed, not the dev agent's to vary)

- **Hidden size**: 16 (well under the ≤32 cap, leaves headroom if runtime pressure appears).
- **Epochs**: 10 (well under the ≤20 cap).
- **Sequence window**: 12 timesteps (well under the ≤24 cap).
- **Architecture**: single-layer `torch.nn.GRU(input_size=1, hidden_size=16, num_layers=1,
  batch_first=True)` followed by a `torch.nn.Linear(16, 1)` head on the final hidden state. No
  bidirectionality, no attention, no dropout (dataset/window too small to need regularization at this
  scale, and dropout would add nondeterminism the dev agent would then have to control for).
  Optimizer: `torch.optim.Adam(lr=1e-3)`. Loss: `torch.nn.MSELoss()`. `torch.set_num_threads` left at
  default; `device="cpu"` hardcoded (`torch.device("cpu")`), no CUDA check performed at all (not even a
  conditional) — this is CPU-only by construction, not by a runtime branch that could silently pick CUDA
  on a different machine.
- **Data/window/config reused verbatim from MR-012/MR-013**: tenant `271d391dd7bf4213b3e5fb8ea6636563`,
  source `binance_price_btcusdt_1h`, `start="2024-08-08T09:00:00"`, `end="2026-08-07T09:00:00"`, 17,496
  returns after `.pct_change().dropna()`. `ValidationConfig(train_window=500, test_window=50, step=250)`,
  `purge_gap=6` for horizon=1/6, `purge_gap=24` for horizon=24. Expect ~68 splits per horizon (MR-012/
  MR-013's actual measured count) — dev agent reports the actual count, not this estimate.
- **If runtime approaches/exceeds 5 minutes for the full 3-horizon test file**: narrow, in this order,
  reporting the narrowing in the ticket Outcome: (1) epochs 10→5, (2) hidden size 16→8, (3) window 12→8.
  Never loosen the 5-minute ceiling itself, never narrow the purge gap.
