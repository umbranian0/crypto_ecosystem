# LC-003 — FastAPI `Depends()`-based tenant context resolver (interim: explicit-field extraction)

**Status: done**

## Analysis
Story: LC-003 (Must), depends on LC-002 (`TenantContext` must exist as the return type). Constraining docs: docs/product/backlog-libs-common.md LC-003 acceptance criteria — a `Depends()`-compatible callable (`get_tenant_context`), interim extraction from an explicit already-present request source, single swappable resolution seam (for LC-009's future gateway-api-based resolution, not this sprint), missing/empty `tenant_id` rejected before any route handler body runs. **Binding sprint note (sprint-04.md, non-negotiable): the rejection status is 401 Unauthorized specifically, not 400** — for consistency with what `gateway-api`'s real auth will eventually return once it exists (trigger #5).

## Design
Pattern: Dependency Injection (implementation-plan.md section 7 — "used for DB sessions, tenant context, and repository instances"). Files: `libs/common/src/naive_first_common/tenant_context.py` (edit — add `get_tenant_context` alongside `TenantContext`, same module since the resolver's whole job is "extract + validate → construct `TenantContext`", matching LC-002's ticket rationale that the resolver's job stays narrow), `libs/common/src/naive_first_common/__init__.py` (edit — export `get_tenant_context`).
DRY check: grep `libs/common/src/naive_first_common/` — only `tenant_context.py` (LC-002) exists; nothing to deduplicate.

**Extraction source**: an `X-Tenant-Id` HTTP header (FastAPI `Header(default=None, alias="X-Tenant-Id")` parameter on the resolver function itself) — this is the "explicit source already present on the request" the story asks for, and headers are the natural interim seam for a value that will later come from a verified JWT/API-key's claims (LC-009) without changing where downstream code looks for it (a header today, an auth-context-derived value tomorrow, same `Depends()` call site).

**Swappable seam (binding, per AC3)**: the raw extraction step is a single small internal function, `_extract_tenant_id(x_tenant_id: str | None) -> str | None`, called by `get_tenant_context`. `get_tenant_context` itself does: call `_extract_tenant_id` → if `None`/empty/whitespace-only, raise `HTTPException(401, ...)` → else construct and return `TenantContext(tenant_id=...)` (re-raising `TenantContext`'s own `ValidationError` as the same 401, so the two fail-closed layers — LC-002's construction-time check and LC-003's request-level check — agree on the outward-facing status). When LC-009 swaps the resolution strategy later, only `_extract_tenant_id`'s body (or the header parameter) changes — `get_tenant_context`'s signature and its `Depends()` call sites stay identical, mirroring the Repository-swap precedent (validation-service backlog decision 2).

**Failure mode**: `HTTPException(status_code=401, detail="missing or empty tenant context")` — raised inside the dependency function itself, which FastAPI evaluates before the route handler body runs (this is what "fails closed before the handler" means mechanically — no code change needed elsewhere to get this property, it's inherent to how FastAPI resolves `Depends()` params before calling the endpoint function).

## Implementation acceptance criteria
- [x] `get_tenant_context` exists as a callable usable as `tenant: TenantContext = Depends(get_tenant_context)` in any FastAPI route handler.
- [x] Resolution extracts `tenant_id` from the `X-Tenant-Id` request header — no JWT decoding, no API-key lookup, no network/DB call.
- [x] The raw-extraction step is a single, separately named internal function (`_extract_tenant_id`) that is the sole seam a future swap (LC-009) needs to touch — `get_tenant_context`'s own signature is unaffected by that future swap.
- [x] Missing header, empty-string header value, or whitespace-only header value all raise `HTTPException(status_code=401, ...)` — not 400, not 500, not a silently-empty `TenantContext` — before any route handler body would run.
