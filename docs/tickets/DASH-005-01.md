**What in the docs constrains this ticket, read directly this session, not assumed**:
- `services/gateway-api/README.md`'s Contract section (`GET /runs`, GW-016 entry): the real response
  is `RunListResponse = {items: list[RunSummaryResponse], limit: int, offset: int, total: int}`.
  `RunSummaryResponse = {id, dataset_id, horizon, status, created_at, completed_at}`, imported from
  `naive_first_common.contracts` (ARCH-003) — **`RunListResponse` itself is NOT in
  `naive_first_common.contracts`** — gateway-api's own README states it explicitly: "`RunListResponse`
  is this router's own local envelope, mirroring validation-service's own envelope field names since
  it's pass-through." Do not attempt to import `RunListResponse` from `naive_first_common.contracts` —
  it does not exist there and importing it will fail. `RunSummaryResponse` is the only piece of this
  shape that is shared; `dashboard-web` must define its own local envelope model (or work with the
  parsed dict directly) for `items`/`limit`/`offset`/`total`, mirroring gateway-api's own convention of
  a router-local envelope wrapping a shared item model.
- `limit`/`offset` are forwarded by `gateway-api` to `validation-service` **unmodified** — an
  out-of-range value's `422` is `validation-service`'s own response, passed through as-is. This ticket
  does not add "next page" controls (the backlog's own AC list doesn't require one, and inventing
  pagination UI now would need to respect this un-clamped constraint for no acceptance-criteria
  benefit) — a plain, single-page render of whatever `gateway-api` returns for the default
  `limit`/`offset` is sufficient this ticket. If the incoming dashboard-web request itself carries
  `limit`/`offset` query params, forward them unmodified to `gateway-api` (do not invent defaults that
  diverge from what `gateway-api`/`validation-service` themselves default to) and forward a `422`
  through generically, same spirit as this router's existing `error.html` failure path.
- CLAUDE.md positioning: no language implying price prediction or a trading signal anywhere in the new
  template — "runs" / "validation runs" / "benchmark comparison" framing only, matching
  `run_detail.html`'s existing convention.

## Design

Pattern: **Dependency Injection only** (implementation-plan.md section 7) — same as DASH-004/006, no
Strategy/Factory/Adapter applies to a read-only list view.

File touched: `services/dashboard-web/src/app/routers/runs.py` only (add a new `GET /runs` handler to
the existing router module — do not create a second router file; this keeps all of DASH-004/005/006's
run-related routes in one place, matching the existing module's own docstring convention). Also:
`services/dashboard-web/src/app/templates/runs_list.html` (new template).

**DRY check note (grepped `services/dashboard-web/src/app/routers/runs.py` and
`app/dependencies/downstream.py` before writing, not assumed)**:
- Reuse `DownstreamHeadersDep`/`GatewayApiUrlDep` (DASH-003) — no hand-rolled header/env-var read.
- Reuse `_call_downstream` (already generalized in this file by DASH-006 to take any bound `httpx.Client`
  method) for the outbound `client.get("/runs", ...)` call — do not write a third near-identical
  try/except for transport-failure translation.
- Reuse the existing `502`/`504` → `error.html` ("results currently unavailable") pattern from
  `run_detail`/`run_new_submit` in this same file — do not write a fourth copy of that branch; consider
  extracting a shared helper only if this ticket's own new code would otherwise be the *third*
  duplicate of that exact branch (it would be the third occurrence across `run_new_submit`/
  `run_detail`/this new route — extract a small `_render_error_for_status(request, status_code)`
  helper in this same file rather than copy-pasting a third block, per implementation-plan.md section
  9's "extract on second duplication" rule — this is in fact past that threshold already).
- Reuse `RunSummaryResponse` from `naive_first_common.contracts` for each item — do not redefine its
  fields locally.
- New route registered in this file; no change needed to `run_new`'s "before `/runs/{run_id}`"
  ordering comment, since `/runs` (no path param) does not collide with `/runs/new` or
  `/runs/{run_id}`, but place it near the top of the router for readability, matching existing route
  grouping.

**Template**: `runs_list.html` extends `base.html` (matching `run_detail.html`/`run_new.html`'s own
pattern). One `<table>` row per run: `id` (rendered as a link `<a href="/runs/{{ run.id }}">`), status,
dataset_id, horizon, created_at, completed_at. Empty-list case renders a plain "no runs yet" message
(no error, no fabricated row). Positioning: no "prediction"/"forecast"/"signal"/"recommendation"
language anywhere in this template, mirroring `run_detail.html`'s existing test convention
(`test_run_detail_template_has_no_banned_positioning_words`) — this ticket should add the equivalent
test for `runs_list.html`.

## Implementation acceptance criteria

- [x] `GET /runs` (`src/app/routers/runs.py`) is gated behind `headers: DownstreamHeadersDep`/
  `base_url: GatewayApiUrlDep` (DASH-003), same as every other authenticated route in this service.
- [x] Calls `gateway-api`'s real `GET /runs`, parses the response as `{"items": [...], "limit": ...,
  "offset": ..., "total": ...}` with each item validated via `RunSummaryResponse` (imported, not
  redefined).
- [x] Renders `runs_list.html`: one row per run (id linking to `/runs/{id}`, status, dataset_id,
  horizon, created_at, completed_at), in the order `gateway-api`/`validation-service` returned them
  (no client-side re-sort) — `created_at DESC` is already the server's own ordering.
- [x] Zero runs renders a plain empty-state message, not an error.
- [x] A transport-level failure or a `502`/`504` forwarded from `gateway-api` renders the existing
  `error.html` with the same fixed "results currently unavailable" string DASH-004/006 already use —
  no new error template, no leaked hostname/status/exception text.
- [x] No client-side pagination, sorting, local record-keeping, or scraping of any other page is
  introduced anywhere in this ticket's diff.
- [x] No language implying price prediction or a trading signal anywhere in `runs_list.html`.
