- Constrains solution: implementation-plan.md section 7 (this is a genuinely new Strategy implementation —

  `StackingEnsembleBaseline` is itself a new `Baseline`-protocol implementation (registered the same way
  via `config.extra_baselines`), internally composing `LightGBMBaseline`/`RegimeHMMBaseline` as its own
  private base learners. No `naive_first_engine` change.
- File touched (new): `research/models/stacking_ensemble.py`.
- File touched (new): `research/tests/test_stacking_ensemble.py` — unit tests (incl. the leakage-guard
  test) plus the MR-013 real-data run at 1h/6h/24h.
- **DRY check (dev agent must state this explicitly)**: grep `research/models/` before writing anything —
  reuse `research/models/gradient_boosting.py::LightGBMBaseline` and
  `research/models/regime_hmm.py::RegimeHMMBaseline` directly (import, zero changes to either file); reuse

  scalar predictions, not on raw features.

## The leakage guard (binding, must be implemented exactly this way)

`StackingEnsembleBaseline.predict(train, test)` must, within a single call:

1. Split `train` itself into a base-fit portion and a meta-fit (holdout) portion, in time order (e.g. the
   first ~80% of `train` fits the base models, the last ~20% is held out — no random/shuffled split, per
   CLAUDE.md's "no random/non-time-ordered splits" rule).
2. Fit fresh `LightGBMBaseline`/`RegimeHMMBaseline` instances on the base-fit portion only, then call
   `.predict(base_fit_portion, meta_fit_holdout_portion)` on each to get each base model's **out-of-sample**
   predictions on the holdout portion (never predictions the base models produced on rows they were
   trained on).
3. Fit the meta-learner (`sklearn.linear_model.Ridge` or `LinearRegression`) on those two out-of-sample
   prediction columns vs. the holdout portion's actual target values.
4. Re-instantiate and refit fresh `LightGBMBaseline`/`RegimeHMMBaseline` on the **full** `train` (not just
   the base-fit portion) to produce the final base predictions on `test` — this maximizes the base models'
   own training data for the actual out-of-sample `test` prediction, while the meta-learner itself was
   fit only on genuinely held-out predictions. This mirrors standard stacking practice (meta-learner
   trained on out-of-fold predictions; base learners refit on full training data for final inference).
5. Apply the fitted meta-learner to the two base models' `test`-set predictions to produce the ensemble's
   final `test` predictions.

**Unit test requirement (binding)**: `test_stacking_ensemble.py` must include a test that would fail if the
meta-learner were instead fit on the base models' in-sample training predictions — e.g. construct a
synthetic series where a base model's in-sample fit is near-perfect (overfit) but its true out-of-sample
error is large, and assert the meta-learner's fitted coefficients/behavior reflect the base model's real
(holdout) performance, not its in-sample performance. A test that merely asserts "the meta-learner has
coefficients" or "predict returns a Series" does not satisfy this AC — it must actually exercise the
in-sample-vs-holdout distinction.

**Tech Lead personally traced the leakage guard's control flow** in `stacking_ensemble.py` (not just the
dev agent's docstring claim): `_split_train_chronologically` splits by position (`train.iloc[:split_at]` /
`train.iloc[split_at:]`), never shuffled; `Ridge().fit()` receives only `meta_features`/`meta_target` built
from `LightGBMBaseline().predict(base_fit_portion, meta_fit_holdout_portion)` and
`RegimeHMMBaseline().predict(base_fit_portion, meta_fit_holdout_portion)` — genuinely out-of-sample
predictions on rows the base models were never fit on — never the base-fit portion's own in-sample
predictions; fresh `LightGBMBaseline()`/`RegimeHMMBaseline()` instances are constructed both for the
holdout step and the final full-`train` refit step producing `test` predictions; nothing is stored on
`self`.

**Tech Lead personally read the leakage-guard unit test's logic** and confirms it would genuinely fail
against a naively-in-sample-fit implementation:
`test_meta_learner_fits_on_holdout_out_of_sample_predictions_not_in_sample` monkeypatches both base models
with `_FakeMemorizingBaseModel` (returns exact true values for rows it was "trained" on, a constant `0.0`
for genuinely unseen rows) and `Ridge` with `_SpyRidge` (records the exact `X`/`y` passed to `.fit()`).
Asserts: (1) `len(fit_y)` equals the holdout portion's length, not the (larger) base-fit portion's; (2)
`fit_X`'s columns are all `0.0` (the fake's out-of-sample constant), never the memorized in-sample values,
and not close to `fit_y`; (3) `fit_y`'s index matches the holdout portion's index exactly. A naive
in-sample-fit bug (calling `.predict(base_fit_portion, base_fit_portion)`) would produce a `y` of the wrong
(larger) length, wrong index, and `X` bit-identical to the target — each assertion independently catches
that failure mode. This is not a trivial "meta-learner has coefficients" check.

Both base models confirmed genuinely re-instantiated per `predict()` call
(`test_base_models_are_reinstantiated_per_predict_call` — 8 fresh instances tracked across 2 calls, held
alive to rule out CPython address-recycling false positives; no `_lgbm`/`_hmm`/`_meta_learner` instance
attribute exists on the ensemble). `LightGBMBaseline`/`RegimeHMMBaseline`'s own `predict()` methods called
unmodified (zero diff in either file).
