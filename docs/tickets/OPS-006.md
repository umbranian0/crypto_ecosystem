## Analysis

Story: adopt a structured logging convention with a request/tenant-correlation id, threaded through
both FastAPI services, so a `gateway-api` request proxied into `validation-service` can be correlated
across both services' logs. Acceptance criteria (verbatim):
- A structured logging convention (e.g. `structlog`, or stdlib `logging` + JSON formatter) is adopted
  as the documented standard for both FastAPI services.
- A correlation/request id is generated (or read from an inbound header) at the start of each request
  and attached to every log line via middleware/context var — not passed explicitly through every
  function call.
- `gateway-api`'s proxying to `validation-service` forwards the same correlation id as a header.
- The existing single log call in `events.py` is migrated to the new convention.
- Does not stand up a log-aggregation backend (OPS-007's still-declined scope).

**Non-negotiable care condition**: this is the precondition GW-014 (Round 3) builds on — it must be
fully landed and verified before GW-014 starts, not merely "alongside" it, given the same-service
file-collision risk with GW-010/GW-014 identified in the sprint file.

## Design

**Pattern**: Dependency Injection (implementation-plan.md section 7) is the natural mechanism for the
correlation id — FastAPI middleware setting a context var, read by a shared logging helper, mirrors
the existing DI-seam convention both services already use (`Depends()` for repositories/tenant
context). No new pattern beyond that is warranted; this is observability plumbing, not a new
extension point.

**Shared logic, cross-service DRY (implementation-plan.md section 9)**: the correlation-id
generation/context-var/logging-setup logic is identical in shape for both services (same middleware
signature, same JSON log format). Per section 9's explicit rule ("cross-module duplication gets
pulled into a `libs/*` package, never copy-pasted across service boundaries"), this logic belongs in
`libs/common`, not written twice. Add a new module `libs/common/src/naive_first_common/logging.py`
exposing:
- `configure_structured_logging() -> None` — stdlib `logging` configured with a JSON formatter (do
  not add a new third-party dependency like `structlog` unless the codebase already has one; check
  `pyproject.toml` for both services first — as of this ticket neither declares `structlog`, so use
  stdlib `logging` + a small JSON `Formatter` subclass to avoid adding a new dependency for a Could
  story).
- `correlation_id_var: contextvars.ContextVar[str]` — the context var holding the current request's
  correlation id.
- `CorrelationIdMiddleware` (a `starlette`/FastAPI middleware class) — reads `X-Correlation-Id` from
  the inbound request if present, otherwise generates one (`uuid4().hex`), sets it on
  `correlation_id_var`, and attaches it as a response header too (useful for debugging from the
  client side).
- A `logging.Filter` (or a `LoggerAdapter` factory) that injects `correlation_id_var`'s current value
  into every log record's `extra` so the JSON formatter always includes it, even for log calls that
  don't explicitly pass it.

**Files touched**:
- `libs/common/src/naive_first_common/logging.py` (new).
- `libs/common/src/naive_first_common/__init__.py` — export the new public names (mirrors how
  `TenantContext`/`get_tenant_context` are already exported).
- `libs/common/tests/test_logging.py` (new).
- `services/gateway-api/src/app/main.py` — register `CorrelationIdMiddleware`, call
  `configure_structured_logging()` at import time.
- `services/gateway-api/src/app/dependencies/routing.py` — `build_downstream_headers` gains the
  correlation-id header (read from `correlation_id_var`) alongside the existing `X-Tenant-Id`.
- `services/validation-service/src/app/main.py` — same middleware registration.
- `services/validation-service/src/app/events.py` — migrate `InProcessLogEventPublisher.publish`'s
  existing `logger.info(...)` call to use the new convention (this is the acceptance criteria's
  explicit "the existing single log call... is migrated... not left as the one pre-existing
  exception").
- `libs/common/README.md`, `services/gateway-api/README.md`, `services/validation-service/README.md`.

**DRY check performed**: grepped both services for `logging`/`logger`/`structlog` (matches the
backlog entry's own stated evidence: only `events.py`'s one call, plus Alembic's own generated
boilerplate in both `migrations/env.py` files, which is not application code and is out of scope).
`build_downstream_headers` (GW-007) is the existing, single header-building seam in `gateway-api` —
extend it, do not add a second header-construction function elsewhere in the router layer.

## Implementation acceptance criteria

- [x] `libs/common/src/naive_first_common/logging.py` implements `configure_structured_logging()`,
  `correlation_id_var`, `CorrelationIdMiddleware` as described above. JSON log lines include at
  minimum: `timestamp`, `level`, `logger` (module name), `message`, `correlation_id` (empty string, not
  `"None"`, when unset — consistent with `RedisStreamsEventPublisher`'s existing `None -> ""` field
  convention in `events.py`, reused for consistency, not reinvented).
- [x] `CorrelationIdMiddleware`: reads `X-Correlation-Id` from the inbound request when present
  (non-empty), otherwise generates `uuid4().hex`; sets `correlation_id_var`; resets it after the
  request completes (use `contextvars.Token` reset in a `finally`, so one request's id can never leak
  into a subsequent request handled by a reused worker thread/task); also sets the response header
  `X-Correlation-Id` to the same value.
- [x] `gateway-api`'s `app.main` registers `CorrelationIdMiddleware` and calls
  `configure_structured_logging()` at module import time (before `app = FastAPI(...)`, matching where
  `validation-service` will do the same).
- [x] `validation-service`'s `app.main` does the same.
- [x] `gateway-api`'s `build_downstream_headers(tenant: TenantContext) -> dict[str, str]` gains a
  second header, `X-Correlation-Id: correlation_id_var.get()`, alongside the existing `X-Tenant-Id` —
  read `dependencies/routing.py` first; extend the existing function, do not add a second
  header-building helper.
- [x] `events.py`'s `InProcessLogEventPublisher.publish` uses the new convention (either by relying on
  `configure_structured_logging()`'s global logging setup so its existing `logger.info(...)` call
  automatically gets JSON-formatted + correlation-id-tagged, or by switching to a `LoggerAdapter` —
  whichever requires the least code change while genuinely being "the new convention," not a second
  parallel shape). Its existing `.published` in-memory list behavior (used by tests) is unchanged.
- [x] No log-aggregation backend, shipper, or external sink is added anywhere in this ticket's diff.
- [x] No third-party logging dependency (`structlog`, `python-json-logger`, etc.) added to any
  `pyproject.toml` unless a design review genuinely justifies it over stdlib `logging` — default is
  stdlib-only per the Design section above.
