# VS-034 — Fix: flaky `GET /runs` ordering test (`created_at` tie-break missing)

Sprint: none (out-of-band bug fix, flagged by QA during a later sprint's validation pass; module
untouched by the MR-*/AI-* sprints that were running at the time). Backlog: none — regression-style
fix to already-shipped VS-022 code, not a new story.
Status: **done** (Tech Lead, 2026-09-16).

**Outcome**: fixed as designed — `id` descending added as the secondary sort key to `list_runs` on
both `sqlite_repository.py` and `postgres_repository.py`; `interfaces.py` docstrings updated;
`tests/test_runs_list_endpoint.py` gained a deterministic tie-break regression test
(`test_tied_created_at_breaks_ties_by_id_descending_deterministically`, using a monkeypatched fixed
`datetime.utcnow()` so all seeded rows collide on `created_at` by construction, not by luck). One
additional pre-existing latent issue was found and fixed within this same ticket's scope during
implementation: `test_limit_and_offset_paginate_correctly_across_a_seeded_set_larger_than_one_page`
(25 rapidly-seeded runs) also implicitly depended on real-clock `created_at` staying strictly
increasing across all 25 `create_run` calls — an assumption the ordering contract never actually
guaranteed, and one the new `id`-based tie-break could deterministically violate on a real collision.
Fixed the same way (a monkeypatched, strictly-increasing fake clock for that test, no production code
change), rather than leaving a second latent flake behind. Full `services/validation-service` suite
(224 tests) re-run by the Tech Lead 3/3 clean (no failures) after both fixes landed; the dev agent
separately ran it 5/5 clean after the second fix. `services/validation-service/README.md`'s VS-022
bullet updated. `docs/tickets/README.md`'s out-of-band bug-fix section added.

## Analysis

QA flagged `tests/test_runs_list_endpoint.py::test_tenant_with_three_runs_sees_exactly_its_own_in_created_at_desc_order`
as an intermittent failure. Root cause, confirmed by reading the code (not assumed):

- `ValidationRunRepository.list_runs` (both `sqlite_repository.py` and `postgres_repository.py`)
  orders solely by `Run.created_at.desc()` (`interfaces.py`'s VS-022 "ordering is the repository's
  job" decision, correctly implemented for the single-column case) — with **no secondary/tie-break
  key**.
- `create_run` stamps `created_at=datetime.utcnow()` (both repos). `utcnow()`'s effective resolution
  combined with how fast a test loop can call `create_run` three times in a row means two or more
  seeded runs can legitimately get an identical (or, on some platforms, coarsely-truncated-to-equal)
  `created_at` value. When that happens, `ORDER BY created_at DESC` alone has no defined tie-break —
  SQLite/Postgres are both free to return equally-ranked rows in whatever order their query plan
  happens to produce (frequently, but not reliably, insertion order), which is exactly the kind of
  undefined behavior that produces a test that "usually" passes.
- This is a genuine ordering-determinism bug, not merely a test artifact: the same non-determinism is
  live in production `GET /runs` pagination — two runs created within the same clock tick can appear
  in inconsistent relative order across repeated calls, or (worse) a page boundary can inconsistently
  include/exclude a tied row across two calls with the same `limit`/`offset`.
- Fix must be a **real query-level tie-break**, not a test-side `sleep()`/retry hack (that would hide
  the same bug in production, just make the test stop noticing it).

**Chosen fix**: add `Run.id` as a secondary, descending sort key: `.order_by(Run.created_at.desc(),
Run.id.desc())`. `id` is unique (primary key) and always populated at `create_run` time (`uuid4().hex`,
same file, a few lines above `list_runs`), so this fully removes any possibility of a tied, ambiguous
ordering regardless of backend — SQL guarantees a total order once every row differs on at least one
sort key. No schema change, no migration: `id` already exists as an indexed primary key on both
backends.

**Alternative considered and rejected**: adding a new monotonic `sequence`/autoincrement column.
Rejected as disproportionate to the bug — it would require a migration on both repos plus a model
change for a problem `id` (already a unique per-row key on both backends) already solves. `id` being a
random `uuid4().hex` rather than a monotonic counter means the secondary sort does not reconstruct
"true" sub-second creation order for tied rows (an arbitrary-but-fixed order is used instead) — this is
acceptable because the only property `GET /runs`'s contract actually promises (`README.md`'s VS-022
section: "ordered `created_at` descending") is a stable, deterministic total order, not sub-second
creation-order fidelity that `created_at`'s own storage resolution can't provide either way.

## Design

**Pattern**: none new from implementation-plan.md section 7 — this is a one-line fix within the
existing Repository pattern seam (`ValidationRunRepository.list_runs`), consistent with VS-022's own
"ordering is the repository's job" decision in `interfaces.py`.

**Files touched** (all `services/validation-service/`, no other module):
- `src/app/repositories/sqlite_repository.py` — `list_runs`'s `.order_by(Run.created_at.desc())` →
  `.order_by(Run.created_at.desc(), Run.id.desc())`.
- `src/app/repositories/postgres_repository.py` — identical one-line change, same method.
- `src/app/repositories/interfaces.py` — `list_runs`'s docstring (and the VS-022 module-docstring
  paragraph describing the ordering decision) updated to state the tie-break explicitly: "ordered by
  `created_at` descending, with `id` descending as a deterministic tie-break for rows sharing the same
  `created_at`."
- `tests/test_runs_list_endpoint.py` — extend with a new test that reproduces the tie-break
  deterministically (see Test section below), rather than relying on real-clock timing to sometimes
  hit the collision.

**DRY check performed**: grepped `order_by(Run.created_at` — exactly the two call sites above (one
per backend), both changed identically; no third hand-written ordering clause exists elsewhere
(`get_splits`'s `SplitResult.split_index` ordering is a separate, already-unique column, out of
scope).
