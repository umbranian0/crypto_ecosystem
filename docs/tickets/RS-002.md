## Analysis

Covers backlog RS-002s acceptance criteria in full: a `reporting.reports` table (`id`, `tenant_id`,
`run_id`, `report_kind`, `generated_at`, `content`, `status`) behind a `ReportRepository` Protocol,
tenant-isolated via real Postgres RLS -- matching this platforms multi-tenancy-from-day-one
guarantee (solution-design.md section 1, principle 3) and the RLS-as-hard-requirement precedent
VS-013/GW-012 already set for every other tenant-scoped table.

## Design

- **Pattern**: Repository (implementation-plan.md section 7) -- keeps Postgres specifics out of
  business logic.
- Files touched (all under `services/reporting-service/`, disjoint from RS-003s `renderers/`+
  `templates/`): `src/app/repositories/interfaces.py` (new), `src/app/models.py` (new),
  `src/app/repositories/postgres_repository.py` (new), `src/app/dependencies/repositories.py` (new),
  `migrations/env.py` + `migrations/versions/0001_*.py` + `0002_*.py` (new), `alembic.ini` (new),
  `tests/test_postgres_repository.py` (new).
- **DRY check note (mandatory before writing code)**: read
  `services/validation-service/src/app/repositories/interfaces.py`,
  `src/app/repositories/postgres_repository.py`, `migrations/env.py`, and
  `migrations/versions/0002_add_row_level_security.py` directly (VS-013s shipped code, not just its
  ticket text). Reuse the exact same mechanism: `Protocol` interface, `@dataclass(frozen=True)`
  record type with zero `sqlalchemy` import in `interfaces.py`, `naive_first_common.db.build_engine`
  (ARCH-001) + the memoized-by-URL provider (ARCH-002) -- no per-request `create_engine`,
  `SELECT set_config('app.tenant_id', :tenant_id, true)` as the first statement of every transaction
  (VS-013s corrected syntax, NOT the invalid literal `SET LOCAL ... = :param`),
  `migrations/env.py`s `search_path`/`version_table_schema` conditional-on-postgres pattern
  targeting the `reporting` schema specifically (INF-005s proven cross-service `alembic_version`
  collision applies here exactly as it did to `validation`/`identity`). Do not re-derive any of this
  from scratch -- copy the proven shape, adapt table/schema names only.
- `ReportRepository` Protocol (`typing.Protocol`, first param after `self` is always `tenant_id`):
  `create_report(tenant_id, run_id, report_kind, content, status) -> ReportRecord`,
  `get_report(tenant_id, report_id) -> ReportRecord | None`.
- `src/app/models.py`: SQLAlchemy 2.0 declarative `reports` table (`id`, `tenant_id`, `run_id`,
  `report_kind`, `generated_at`, `content` text, `status`), shared by the Alembic migration and the
  repository layer -- no duplicate schema definition (implementation-plan.md section 9 DRY rule).
- RLS migration: `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` +
  `CREATE POLICY tenant_isolation ON reports USING (tenant_id = current_setting('app.tenant_id'))`,
  both DDL statements conditional on `op.get_bind().dialect.name == "postgresql"` (a SQLite-target
  migration test would otherwise break, same reason VS-013 guards this).
- DI wiring (`dependencies/repositories.py`): `get_report_repository` provider, Postgres-only per
  backlog decision 4 (no SQLite fallback branch -- this is a deliberate scope decision, not an
  oversight; do not add one).

## Implementation acceptance criteria

- [x] `src/app/repositories/interfaces.py` declares `ReportRepository` as a `typing.Protocol`, first
      param after `self` is always `tenant_id`, returns a plain `@dataclass(frozen=True)`
      `ReportRecord`, zero `sqlalchemy` import in this file.
- [x] `src/app/models.py` defines the `reports` table via SQLAlchemy 2.0 declarative, shared by the
      Alembic migration and the repository layer -- no duplicate schema definition.
- [x] `PostgresReportRepository` implements the interface using `naive_first_common.db.build_engine`
      (ARCH-001) + the memoized-by-URL provider (ARCH-002) -- no per-request `create_engine` call.
- [x] Alembic migration enables and forces RLS on `reports` (`ENABLE ROW LEVEL SECURITY` +
      `FORCE ROW LEVEL SECURITY` +
      `CREATE POLICY tenant_isolation ON reports USING (tenant_id = current_setting('app.tenant_id'))`),
      matching VS-013s exact mechanism.
- [x] Every transaction the repository opens sets `app.tenant_id` first via
      `SELECT set_config('app.tenant_id', :tenant_id, true)` before any query.
- [x] `migrations/env.py` targets the `reporting` schema specifically (`search_path` +
      `version_table_schema="reporting"`), conditional on `connection.dialect.name == "postgresql"`.
- [x] A test proves RLS actually blocks cross-tenant reads at the database level: a raw, unfiltered
      `SELECT tenant_id, id FROM reports` (no `WHERE tenant_id = ...`) run as a dedicated
      non-superuser role after scoping `app.tenant_id` to tenant A, asserting tenant Bs row is
      absent -- run as a real non-superuser role (`naive_first_app` if reachable in this
      environment, else an ephemeral dedicated test role created/dropped by the test fixture,
      matching GW-012s fallback precedent), never a superuser/`BYPASSRLS` role.
- [x] Full test suite passes against real Postgres (skip-guarded if unreachable, matching
      `tests/test_postgres_repository.py`s precedent in validation-service/gateway-api).

**One real gap found and fixed by the Tech Lead, not by the dev agent**: `reporting` schema/`reports`
table had never actually been migrated onto the real, live Postgres container (the `naive_first`
role's `alembic upgrade head` had never been run for this brand-new service) -- so the first full
test run (`3 failed, 8 passed, 1 error`) failed on `UndefinedTable: relation "reports" does not
exist` for the CRUD/RLS tests, purely because the schema didn't exist yet in the real database, not
a code defect. Fixed by personally running `DATABASE_URL=postgresql+psycopg://naive_first:...
uv run alembic upgrade head` against the live `naive-first-postgres` container, then confirming via
a direct `information_schema.tables` query that `reporting.reports` and `reporting.alembic_version`
now exist (`identity`/`validation`/`reporting` all present, `public` absent, matching every other
service's own schema-per-service convention). Also granted `naive_first_app` `USAGE`/`SELECT` on the
`reporting` schema/table (the RLS test fixture's own idempotent `GRANT` statements handle this
going forward, matching the test file's own documented rationale) since `infra/postgres-init` only
ever provisioned `naive_first_app` for `validation`/`identity`, not yet `reporting` -- flagged here
as a real, disclosed infra gap for a future `INF-0NN` ticket (this service is not yet wired into
`infra/docker-compose.yml` at all, RS-GAP, so this grant is currently test-fixture-scoped, not a
production wiring gap yet).

**Second finding**: initial Postgres-connection latency in this environment was extremely high
(~20 minutes for a 5-test/12-test suite) -- root-caused to the same IPv6-loopback DNS-resolution
quirk on `localhost` this repo's own Sprint 09 outcome notes already document for
`validation-service`'s Postgres tests. Worked around identically: setting the standard libpq
`PGCONNECT_TIMEOUT` environment variable (no code or test-file change) brought the same suite down
to under a minute.
