# DH-008 — Surface the selected dataset's sampling interval and horizon-unit meaning on the run-submission form

**Sprint**: 30. **Module**: `services/dashboard-web` only. **Status**: todo. **Priority**: Must.
**Depends on**: none. Sequenced after DH-005 in this sprint (both touch `run_new.html`, different
regions — land DH-005 first so this ticket starts from a committed baseline, per the sprint plan).

## Analysis

Backlog DH-008 (Must), finding #8: the Horizon field's tooltip on `run_new.html` says only "How many
steps ahead to validate against, e.g. 1 for one-step-ahead. Must be at least 1." — it names no unit and
no dataset-frequency dependence, even though ADR-0007 already established `horizon` is
dataset-sampling-interval-relative, not a fixed platform unit. This is presentation-only per the
backlog's own scope statement — no backend field, no new endpoint, no change to `POST /runs`'s payload
or to `naive_first_engine`/`validation-service`'s handling of `horizon`. CLAUDE.md's positioning rule
applies directly to the copy: no wording may imply which horizon/unit is "better," this is a
units-clarity fix only (that framing is DH-006's territory, not in this sprint).

## Design

**Pattern**: none newly invoked — this extends the existing `data-tooltip`/`field-hint` presentation
pattern `run_new.html` already uses elsewhere (RSS-001's stored-dataset summary, RSS-002's estimator).

**Files touched** (scoped to `services/dashboard-web` only):
- `services/dashboard-web/src/app/templates/run_new.html` — the Horizon field's `<label>`/
  `data-tooltip` block (around line 97-104) and a new `field-hint`-styled element next to it.

**DRY check note** (grepped `run_new.html` before writing this ticket): reuses the same
`data-tooltip`/`field-hint` CSS classes and `.dataset-info-panel`-style show/hide pattern the stored-
dataset context summary (RSS-001) already established for reading `dataset.source`/`data-row-count`
off the DOM when a stored dataset is selected — no new client-side data-fetch mechanism, no new CSS
class family invented for this ticket.

## Implementation acceptance criteria

- [ ] When a stored (`ingestion-service`) dataset is selected via `dataset_reference_source`, a
  `field-hint`-styled element next to the Horizon label states the dataset's known sampling interval
  and restates `horizon`'s meaning in that unit — e.g. "This dataset (`binance_price_btcusdt_1h`) is
  sampled hourly, so `horizon: 24` here means 24 hours ahead, not 24 days." The interval is derived
  client-side from `dataset.source`'s existing naming convention (per ADR-0007 finding (a)/(c); today
  only the one hourly connector exists) — no new backend field/endpoint added to compute it.
- [ ] The Horizon field's existing `data-tooltip` text is updated to state, regardless of whether a
  stored dataset is selected, that `horizon` is a count of the dataset's own sampling steps, not a
  fixed hour/day unit, with a pointer to the hint element below once a dataset is selected.
- [ ] For local-file-path/inline-payload modes (interval not known client-side), the hint element
  states plainly that the interval is whatever the submitted data's own timestamp spacing turns out to
  be — no false silence, no fabricated interval.
- [ ] The hint text includes a plain-text pointer to `/runs/horizon-summary` and states in one clause
  that that page presents horizon in fixed days assuming hourly sampling (reciprocal to
  `horizon_summary.html`'s existing ADR-0007 link in the other direction).
- [ ] No new backend field, no new endpoint, no change to `POST /runs`'s accepted payload.
- [ ] Copy contains no claim about which unit/horizon length is "better" or "recommended" — banned-word
  discipline (no "optimal," "recommended," "best") applies the same way it does to every other
  positioning-sensitive template in this service.
