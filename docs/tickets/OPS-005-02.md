# OPS-005-02 — Deepen gateway-api's `/health` to check real DB connectivity

Status: **done**
Backlog: docs/product/backlog-operability.md, OPS-005 [Should]
Sprint: docs/sprints/sprint-08.md, runs in parallel with OPS-001 and OPS-005-01
Depends on: none

## Analysis

Story: OPS-005 (Should), scoped here to `gateway-api`'s half of the story (`OPS-005-01` covers
`validation-service`'s half — same story, split into two tickets because each touches exactly one
service's own file, per the Tech Lead's "a ticket spanning two modules should be two tickets" rule).

Evidence: `services/gateway-api/src/app/main.py:25-27` is byte-identical to `validation-service`'s:
```python
@app.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok"}
```
Same failure mode: unconditionally healthy even with a dead Postgres connection.

Constraining docs: same as OPS-005-01 — distinct from `INF-009` (Compose startup ordering, not this
story's concern). `gateway-api` has no Redis dependency (that's `validation-service`'s `run.completed`
publisher path); this ticket checks only `gateway-api`'s own Postgres/SQLite repository backend, not
Redis.

Acceptance criteria (backlog, this service's half): `/health` performs a lightweight real check
against the active repository backend; returns a non-`200`/distinguishable-failure body when the
check fails; stays cheap; preserves the existing `200 {"status":"ok"}` shape in the healthy case; a
test proves the failure case using this service's existing dependency-override/fake pattern.

## Design

No new `implementation-plan.md` section 7 pattern — reuses the existing DI seam
(`app.dependencies.repositories`).

File touched: `services/gateway-api/src/app/main.py` (the `/health` handler) and
`services/gateway-api/src/app/dependencies/repositories.py` (a new, small DI provider — see DRY
check). New test file: `services/gateway-api/tests/test_health.py`.

DRY check: grepped `services/gateway-api/src/app/dependencies/repositories.py` — it already has
`_get_engine(url: str) -> Engine` (ARCH-002, memoized by URL) and `_select_backend(...)`, which the
three existing repository providers (`get_tenant_repository`/`get_user_repository`/
`get_api_key_repository`) all call to resolve the correct URL (SQLite path or `DATABASE_URL`). Do
**not** duplicate that URL-resolution logic in `main.py` — add one new small provider,
`get_health_check_engine() -> Engine`, in `dependencies/repositories.py` that resolves the URL the
same way `_select_backend` does (reuse `_database_url()`/`_is_postgres_url()`/`_postgres_engine_url()`/
`_db_path()`/`_get_engine()` directly — do not re-derive the URL a second way) and expose it via a
`HealthCheckEngineDep` `Annotated[Engine, Depends(...)]` alias alongside the existing
`TenantRepositoryDep`/`UserRepositoryDep`/`ApiKeyRepositoryDep` aliases, so `main.py`'s `/health`
handler takes the engine via `Depends()` like the rest of this service, and tests can override it with
`app.dependency_overrides` exactly like the rest of the suite already does.

Check design: identical shape to OPS-005-01 — `SELECT 1` via `engine.connect()` in a `try`/`except`.
Success: unchanged `{"status": "ok"}` (`200`). Failure: `{"status": "unhealthy", "detail": "database
unreachable"}` (`503`), no raw exception text/connection string/credential in the body — same
generic-string decision as OPS-005-01, kept consistent across both services since a future poller
should see the same failure shape from either service (DRY-in-spirit across the two tickets' design,
even though the code itself is per-service, per implementation-plan.md's own boundary rule: no
service imports another service's code, so this is a parallel implementation, not a shared one).

## Implementation acceptance criteria

- [x] `dependencies/repositories.py` gains a `get_health_check_engine() -> Engine` provider that
      reuses the existing URL-resolution helpers (no re-derivation of the DB URL, same pattern as
      `_select_backend`) and a `HealthCheckEngineDep` `Annotated[Engine, Depends(...)]` alias,
      matching the existing alias convention in this module.
- [x] `main.py`'s `/health` handler takes `engine: HealthCheckEngineDep`, runs a cheap connectivity
      probe (`SELECT 1` via `engine.connect()`), and returns `{"status": "ok"}` (`200`) on success or
      `{"status": "unhealthy", "detail": "database unreachable"}` (`503`) on any connection/execution
      exception — no raw exception text, connection string, or credential ever appears in the
      response body.
- [x] The healthy-case response shape (`200 {"status": "ok"}`) is byte-identical to today's — additive
      change only.

## Outcome

Implemented as designed: `get_health_check_engine()`/`HealthCheckEngineDep` added to
`dependencies/repositories.py`, reusing `_database_url()`/`_is_postgres_url()`/`_postgres_engine_url()`/
`_db_path()`/`_get_engine()` with no second URL derivation. `main.py`'s `/health` now takes
`HealthCheckEngineDep`, runs `SELECT 1`, returns `200 {"status": "ok"}` on success (byte-identical to
before) or `503 {"status": "unhealthy", "detail": "database unreachable"}` on failure. One deviation
from a literal reading of the design note: `_select_backend` itself returns *repository instances*, not
an `Engine`, so `get_health_check_engine` reimplements just the Postgres/SQLite branch (mirroring
`validation-service`'s own OPS-005-01 `get_health_check_engine`) rather than calling `_select_backend`
directly -- it still calls the same underlying helper functions in the same order, so no URL-resolution
logic is duplicated, only the outer branch shape differs because the return type differs.
`tests/test_health.py` added (2 tests, non-tautological failure case). README.md gains a "Health check
(OPS-005-02)" note. Full suite: 68 passed (66 baseline + 2 new), zero regressions.
