## Analysis

Covers backlog RS-006: subscribe to validation-service's real `run.completed` Redis Streams event
and automatically generate a `"validation_audit"` report on receipt -- the module's stated
"triggered by run.completed" contract (implementation-plan.md section 2).

**Read `services/validation-service/README.md`'s "Event publishing" section directly before writing
any code** -- the exact wire format is already documented there (VS-014's shipped contract):
`XADD run.completed run_id=... tenant_id=... status=... completed_at=<ISO-8601>`, flattened string
fields, stream key IS the event name, not a nested JSON blob. Do not reinvent or assume a different
shape.

## Design

- **Pattern**: Observer/pub-sub (implementation-plan.md section 7) -- this is the concrete instance
  the pattern table names explicitly ("`run.completed` -> `reporting-service`").
- Files touched: `src/app/subscriber.py` (new, standalone-runnable module,
  `python -m app.subscriber` per the backlog's own AC), `tests/test_subscriber.py` (new
  Redis-integration test, skip-guarded).
- **Mandatory DRY requirement (this ticket's single highest-stakes AC)**: the subscriber MUST call
  RS-004's own `generate_validation_audit_report` function (`src/app/generation.py`, RS-004's
  binding decision) with the event's `run_id`/`tenant_id` -- fetch from validation-service -> render
  via RS-003's Factory -> persist via RS-002's repository. **Do not write a second copy of this
  sequence.** Read `src/app/generation.py` first; if RS-004 did not actually extract this into a
  reusable function (check before assuming), flag this back rather than duplicating the logic
  inline -- this is exactly the kind of gap the Tech Lead will check the diff for.
- Consumes via `XREAD`/consumer-group semantics against `REDIS_URL` (mirrors `DATABASE_URL`'s
  convention, same env var name VS-014 already established for validation-service's producer side).
- A malformed or partially-missing event (e.g. missing `tenant_id`) is logged and skipped, not
  crashed on -- the subscriber loop must not die on one bad message (structural, not just a
  try/except around the whole loop body silently swallowing everything -- log the specific field
  that was missing).
- Only `status == "completed"` events trigger generation; even though VS-012's structural guarantee
  means `run.completed` is only ever published for a completed run, this subscriber re-checks
  `status` on the fetched run detail (from `GET /runs/{id}`) before rendering, as defense in depth --
  do not trust the event payload's own `status` field blindly for this check, re-verify against the
  freshly fetched `RunDetailResponse`.
- Not wired into `infra/docker-compose.yml` this ticket (RS-GAP) -- the subscriber process exists
  and is documented as runnable standalone.

## Outcome

Built `src/app/subscriber.py` (new) and `tests/test_subscriber.py` (new); updated
`services/reporting-service/README.md` (Design notes + Contract sections) to document RS-006.

**Implementation**: `subscriber.py` consumes the `run.completed` Redis Stream via `XREADGROUP`
consumer-group semantics (group `reporting-service`, a fresh group starts at `id="$"` so it only
sees entries published after the subscriber starts, deliberately not replaying the stream's full
history since it's shared with validation-service's own VS-014 producer-side tests). `handle_event`
validates the three required fields (`run_id`/`tenant_id`/`status`) are present and non-empty,
logging the specific missing field name(s) and returning early on a malformed event -- no bare
`except Exception` anywhere in the module; the only `try/except` blocks are narrowly scoped
(`httpx.ConnectError`/`httpx.TimeoutException` around the defense-in-depth `GET /runs/{id}` call,
`app.generation.GenerationError` around the `generate_validation_audit_report` call, and
`redis.exceptions.ResponseError` filtered on `"BUSYGROUP"` around consumer-group creation). Only
`status == "completed"` events proceed past the payload check; before calling
`generate_validation_audit_report`, the subscriber issues its own extra `GET /runs/{id}` (via the
same injected `httpx.Client`) and re-checks the *freshly fetched* `RunDetailResponse`'s `status`
field -- not the event payload's `status` -- aborting generation if they disagree (defense in
depth). `generate_validation_audit_report` (imported directly from `app.generation`, the exact
object `app.routers.report_generation` also imports -- proven by
`test_subscriber_imports_the_same_generation_function_as_the_route_handler`) is called unmodified
with no second fetch-render-persist sequence written anywhere in this diff. Entrypoint:
`python -m app.subscriber` (`if __name__ == "__main__":` calling `main()`, which wires
`get_redis_client()` (new, reads `REDIS_URL`, default `redis://localhost:6379/0`) +
`get_validation_service_client()` + `get_report_repository()` (both RS-004/RS-002's existing DI
providers, reused unmodified) into `run_subscriber(..., max_events=None)` for an unbounded blocking
loop). Not wired into `infra/docker-compose.yml` (RS-GAP), as scoped.

**Deviation from the ticket's literal `XREAD` wording**: implemented with `XREADGROUP` (consumer
groups), not a bare `XREAD`, per the ticket's own Design section ("consumer-group semantics") and
Implementation AC1's own wording ("via `XREAD`/consumer-group semantics") -- consumer groups are
what make `XACK`-based at-least-once delivery meaningful for a single long-running subscriber
process; this is the documented intended reading, not a scope expansion.

`localhost:6379` (not skipped -- confirmed by actually observing `PASSED`, not `SKIPPED`, in the run
