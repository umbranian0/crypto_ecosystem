# RSS-002 — Live, client-side "approximately N splits" estimate

**Status: done (browser click-through verification blocked by the same environment constraints as RSS-001, see Review notes — code/formula/test verification complete)**

## Analysis
Story: RSS-002 (Must, `docs/product/backlog-run-submission-safety.md`). Depends on RSS-001 — reads the
`data-row-count` attribute RSS-001 adds to the dataset `<option>` elements; must not start until RSS-001
is merged and verified (real dependency, not a priority artifact).

Constraining acceptance criteria, read directly from the backlog entry, not summarized from memory:
- `computeEstimatedSplits()` implements the **exact** row-offset formula
  `floor((row_count - train_window - purge_gap_hours - test_window) / step) + 1`, clamped to `0` when
  the numerator is negative — this is `naive_first_engine.splitting.generate_splits`'s row-count
  (position-based) branch closed form, confirmed against the library source
  (`_generate_splits_by_position`) by this sprint's own planning read, not re-derived independently here.
  **Must use `purge_gap_hours` as a literal row-position offset** (the semantics `generate_splits`
  actually implements today), not a calendar-hour conversion — the `purge_gap_hours` naming mismatch
  (OQ-3) is explicitly out of scope this sprint; RSS-004's server check uses the same row-offset
  semantics, so this client formula must agree with it on every input or the two guardrails would
  silently disagree.
- Re-renders on `input` of `purge_gap_hours`, `train_window`, `test_window`, `step` (**not** `horizon` —
  `generate_splits` does not take horizon as a parameter) and on `change` of the dataset source dropdown.
- When no stored dataset is selected (path/inline mode), the estimate area shows an explicit "select a
  stored dataset to see an estimate" message — never a stale or fabricated number.
- Copy is explicit this is an estimate for the whole selected source, not the post-filter row count
  (same caveat RSS-001 established for its summary line).
- Informational only — does not block form submission; adds no new client-side gate beyond the existing
  `checkReference()`.

## Design
Pattern: none new — client-side JS only, no backend/pattern from implementation-plan.md section 7
applies. File touched: `services/dashboard-web/src/app/templates/run_new.html` only (same file RSS-001
touched — this ticket runs strictly after RSS-001 is merged, not in parallel, to avoid two agents editing
the same `<script>` block at once).

**DRY check (performed before writing this ticket)**: the formula must be written once, as
`computeEstimatedSplits()`, in the same inline `<script>` block `checkReference()` already lives in —
not a second `<script>` tag, not duplicated inline at each event-listener call site. Grepped for any
existing JS split-count logic in this template/service — none exists; this is the first client-side
implementation of the formula, and it must be the *only* one (a future ticket needing the same formula
elsewhere in this service should import/reuse this function, not re-derive it a third time).
