# VS-007 — `GET /runs/{id}` endpoint

**Status: done**

## Analysis
Story: VS-007 (Must), depends on VS-006. Constraining docs: solution-design.md section 1 principle 3 (tenant-isolation-by-default: `404`, never `403` or leaked data), this service's README contract list.

## Design
Pattern: none new (same DI seam as VS-006). Files: `src/app/routers/runs.py` (edit — add `GET /runs/{id}` handler to the same router VS-006 created; same file, so this ticket must run **after** VS-006 completes, not in parallel with it, to avoid two agents editing `runs.py` at once). DRY check: reuse VS-006's repository `Depends()` providers, don't re-declare them.

**Tenant resolution for this interim design**: since VS-010 (resolved tenant context) is blocked, `GET /runs/{id}` accepts `tenant_id` as an explicit query parameter (same interim pattern as VS-006's request body field) — document this consistently with VS-006's own caveat.

**Tenant isolation (AC2, load-bearing)**: `ValidationRunRepository.get_run(tenant_id, run_id)` (VS-004) already returns `None` for a cross-tenant lookup — this handler's job is to translate that `None` into `404` for *both* "wrong tenant" and "doesn't exist at all," never distinguishing the two in the response (a `403` or a differently-shaped error for "exists but wrong tenant" would itself leak that the run exists — explicitly disallowed).

## Implementation acceptance criteria
- [x] `GET /runs/{id}?tenant_id=...` returns `id`, `tenant_id`, `dataset_id`, `horizon`, `purge_gap_hours`, `split_config`, `status`, `created_at`, `completed_at` — the full `runs` row.
- [x] A run belonging to a different tenant than the query param returns `404` (relies on VS-004's `get_run` returning `None` cross-tenant — this handler must not "helpfully" fall back to any other lookup path).
- [x] A nonexistent run ID returns `404` with a clear JSON error body, not a `500`.
