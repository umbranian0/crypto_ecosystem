# DH-003 — Detect and block same-timestamp-different-value conflicts, never auto-resolved

**Sprint**: 30. **Module**: `services/validation-service` only. **Status**: done. **Priority**: Must.
**Depends on**: DH-002 (its check must run on the already-deduped series so an exact duplicate never
reaches this check).

## Analysis

Backlog DH-003 (Must), finding #4: two rows sharing a timestamp but disagreeing on value is entirely
unhandled today — `pd.Series` accepts a non-unique `DatetimeIndex` without complaint, and nothing
downstream would ever surface it. Per CLAUDE.md's no-silent-inference rule and the backlog's own
"Leakage/honesty check," this is a hard failure, never an auto-resolution (not "keep first," not
"average," not "keep last") — which of two contradictory readings is correct is a genuine judgment call
about the user's own data, the same category of decision DH-090/091/092 already declined to make
silently.

## Design

**Pattern**: reuses the existing `DatasetSourceError` exception path every other malformed-input case
in this module already raises through — no new error-handling mechanism.

**Files touched** (scoped to `services/validation-service/src/app/dataset_source.py` only):
- `_build_series`, immediately after DH-002's dedup step: check `index.duplicated(keep=False)` on the
  deduped series (any timestamp still appearing more than once, by construction now guaranteed to
  differ in value, since exact duplicates were already removed by DH-002). If any such timestamp
  exists, raise `DatasetSourceError` naming the timestamp and both (or all) differing values — not just
  a count.
- No change needed to `runs.py::create_run` — the existing `try: series = dataset_source.load(...)
  except Exception as exc:` branch (RSS-004's load-failure handling, unchanged since VS-012) already
  turns any `DatasetSourceError` into `status="failed"`, `failure_reason=str(exc)`. Confirm at
  implementation time that this pre-existing branch fires correctly for a `DatasetSourceError` raised
  from inside the now-`LoadedSeries`-returning `.load()` — the exception must propagate before any
  `LoadedSeries` is constructed/returned, not get swallowed by the DH-001 unpacking logic.

**DRY check note** (grepped `dataset_source.py` before writing this ticket): reuses the existing
`DatasetSourceError` type and message-construction style already used throughout this file (e.g.
`"CSV row must have 2 columns, got {row!r}"`) — no new exception type, no new error-surfacing mechanism
in `runs.py`.
