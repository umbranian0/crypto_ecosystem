## Analysis

No new backend aggregation endpoint is authorized unless this ticket's own investigation concludes
client-side aggregation of `GET /runs`'s already-returned `RunSummaryResponse` list is insufficient.
`RunSummaryResponse` (`libs/common/src/naive_first_common/contracts.py`) already carries
`dataset_id`/`horizon`/`status`/`created_at`/`completed_at` per run — grouping by
`(dataset_id, horizon)` is possible entirely client-side from the existing `GET /runs` response,
same call `runs_list`/`runs_horizon_summary` already make. Per-run metric values for the chosen
metric require each selected run's own `GET /runs/{id}/splits` call (already-existing endpoint,
called once per selected run — bounded by the tenant's own run count, not a new N+1 concern beyond
what a tenant would see by opening each run individually).

**Investigation finding (binding on Design below)**: client-side aggregation of the two already-
existing endpoints (`GET /runs`, `GET /runs/{id}/splits`) is sufficient for this story's scope — no
new backend endpoint or field is introduced. If, during implementation, a real N+1 performance
problem surfaces at realistic tenant/run volumes, document it in this ticket's own implementation
notes rather than silently inventing a new endpoint outside this ticket's stated scope.

## Design

**Pattern**: none from implementation-plan.md section 7 applies — read-only rendering addition, DI
(`DownstreamHeadersDep`/`GatewayApiUrlDep`) already in place and reused, not reinvented.

**Files touched** (scoped to `services/dashboard-web` only):
- `services/dashboard-web/src/app/routers/runs.py` — new route, e.g. `GET /runs/trend`, registered
  near `runs_horizon_summary` (same "literal segment before path-param route" ordering rule already
  documented in this file's own module docstring — must precede `GET /runs/{run_id}`). Calls
  `GET /runs` (reusing the existing `_call_downstream`/`_render_error_for_status` helpers, no new
  transport-failure handling), groups the parsed `RunSummaryResponse` list by
  `(dataset_id, horizon)` for the selector, and — once a tenant picks a group and a metric — calls
  `GET /runs/{id}/splits` for each `completed` run in that group (skip `running`/`failed` runs, same
  reasoning `runs_horizon_summary` already applies: a non-completed run is not evidence of anything
  yet) and passes the per-run split lists through a new `app.charting.build_trend_chart` function.
- `services/dashboard-web/src/app/charting.py` — new pure function `build_trend_chart(runs:
  list[tuple[RunSummaryResponse, list[SplitResultResponse]]], metric: str) -> TrendChartData`,
  reusing RAV-004's metric registry for the value lookup (import, don't re-derive) — plots one point/
  bar per run (e.g. mean of the chosen metric across that run's own splits, or per-split if that
  reads more honestly — dev's call, document which was chosen and why) for `model` and `naive0`
  series across the selected runs, same status-neutral two-series convention `build_error_chart`
  already established.
- `services/dashboard-web/src/app/templates/runs_list.html` or a new adjacent template (e.g.
  `runs_trend.html`, dev's call per the story's own "extends the existing list view or adds an
  adjacent page" framing) — the group selector (dataset/horizon dropdown) and the resulting chart.
- `services/dashboard-web/src/app/static/style.css` — no new colors; reuses
  `--color-accent`/`--color-accent-2`, same as every other chart in this backlog.

**DRY check**: reuses RAV-002's `Bar`-style geometry dataclass shape and RAV-004's metric registry
rather than a third bar-geometry implementation or a fourth metric-name-to-attribute mapping; reuses
`_call_downstream`/`_render_error_for_status` (already 3+ call sites in this file) rather than a
fourth near-identical try/except.
