## Analysis
Story: VS-006 (Must), depends on VS-004, VS-005 (both complete by this point). Constraining docs: this is the literal trigger condition for the service (implementation-plan.md section 6, trigger #3). ## Design
Pattern: Dependency Injection (repositories + `DatasetSource` injected via `Depends()`, per VS-003's seam). Files: `src/app/routers/runs.py` (new — `POST /runs` handler + its Pydantic request/response models), `src/app/dependencies/repositories.py` (edit — add a `DatasetSource` provider alongside the repository providers), `src/app/main.py` (edit — mount the new router). DRY check: grep `src/app/routers/` (empty from VS-001) and `src/app/` broadly for any existing request-validation or protocol-invocation code before writing.

**Config validation before execution (AC2)**: mirror the constraints `naive_first_engine.splitting.generate_splits` implicitly relies on for a sane result (read `splitting.py` first — it does not raise on bad input, it just silently produces zero splits, which is *not* an acceptable "success"): `horizon >= 1`, `purge_gap_hours >= 0`, `train_window > 0`, `test_window > 0`, `step > 0`. Enforce these as Pydantic field validators/constraints on the request model so FastAPI returns `422` automatically — do not let a bad config reach `run_validation_protocol` and silently produce an empty `list[SplitResult]` that then gets persisted as a "successful" zero-split run.

**Request shape**: `tenant_id: str` (interim explicit field, decision 1), `dataset_reference: dict` (passed through to `DatasetSource.load` — VS-005), `horizon: int`, `purge_gap_hours: int`, `train_window: int`, `test_window: int`, `step: int` (the last three needed by `ValidationConfig` beyond horizon/purge gap — stored in `runs.split_config` per VS-002's design).

**Handler flow (fixed order, must match exactly)**:
1. Validate request (Pydantic, `422` on failure — before touching `DatasetSource` or any repository).
2. `DatasetSource.load(dataset_reference)` → `pd.Series`. Exceptions here are VS-012's concern (this ticket should leave a clear seam, not necessarily the full failure-handling implementation — see VS-012's own ticket for the persisted-failure behavior; VS-006 must not let such an exception produce a bare unhandled `500`, at minimum).
3. Build `ValidationConfig(train_window=..., test_window=..., step=..., purge_gap=purge_gap_hours, horizon=horizon)`.
4. `ValidationRunRepository.create_run(...)` — persist the `runs` row with `status="running"` (or `"completed"`, if synchronous execution finishes within the same request — this interim design is synchronous, document that choice, no Prefect/worker orchestration exists yet per backlog AC5).
5. `results = run_validation_protocol(series, config)` — called **exactly as exposed by the library**, no wrapping that changes argument order, no reimplementing any piece of split/baseline/metrics/DM-test inside this service.
6. Map each `SplitResult` in `results` to a `split_results` row per VS-002's `model_*` = naive_last / `naive0_*` = naive0 / `dm_*` = naive_last's `DMResult` mapping decision; persist via `SplitResultRepository.add_splits(...)`.
7. `ValidationRunRepository.update_run_status(tenant_id, run_id, status="completed", completed_at=now)`.
8. Return `{"id": run_id, "status": "completed"}` (or `"running"`, matching whichever status was chosen in step 4 — must be internally consistent).

VS-009's `run.completed` publish call is **not** part of this ticket's own acceptance criteria (VS-009 adds it) — but leave the handler's success path (after step 7) as the obvious, single place VS-009 will add one call, rather than scattering "done" logic across multiple branches.

## Implementation acceptance criteria
- [x] `POST /runs` accepts `tenant_id`, a `DatasetSource`-resolvable dataset reference, and a `ValidationConfig`-matching config (horizon, purge gap, train/test window, step at minimum).
- [x] Invalid config (non-positive horizon/windows/step, negative purge gap) returns `422` before any execution starts — verified by a test that confirms `run_validation_protocol` is never invoked for such a request (e.g. via a mock/spy).
- [x] `naive_first_engine.protocol.run_validation_protocol` is invoked exactly as-is (import + direct call, no subclassing/wrapping that changes its behavior or argument order).
- [x] Results persisted: one `runs` row, one `split_results` row per split, via VS-003/004's repositories.
- [x] Endpoint returns the created run's `id` and status.

Deviation note: the request also requires an explicit `dataset_id: str` field (not listed in the Design section's Request shape paragraph). `runs.dataset_id`/`ValidationRunRepository.create_run`'s `dataset_id` parameter are both non-nullable, and no `datasets` registry table exists in this sprint's schema for the handler to derive an id from (`solution-design.md` section 4's `datasets` table is out of `validation-service`'s bounded context). Treated this the same way backlog decision 1 treats `tenant_id`: an interim explicit field on the request, documented in `runs.py`'s module docstring and the README Contract entry.
