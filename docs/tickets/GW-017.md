## Analysis

Story: a Locust-based load-test suite driving `gateway-api`'s key endpoints (auth, `POST /runs`,
`GET /runs/{id}`, `GET /runs/{id}/splits`) against a real running Compose stack, so request
latency/throughput/error-rate behavior is observable before a real pilot client generates it. No
formal implementation-plan.md trigger authorizes this — explicit disclosed override, already
acknowledged in the backlog entry itself. Acceptance criteria (verbatim):
- `services/gateway-api/loadtest/locustfile.py` defines Locust user tasks covering authenticated
  `GET /runs/{id}`, `GET /runs/{id}/splits`, `POST /runs` (against a seeded/interim dataset reference
  so runs actually execute), and at least one deliberately-invalid-auth request path.
- README section documents how to run it against the real Compose stack (host/port, provisioning a
  test tenant/key via GW-005's script, recommended user-count/spawn-rate starting points).
- No hard performance SLA/threshold is asserted or gated on — observability tooling, not a pass/fail
  gate.
- `POST /runs`'s synchronous, potentially-long-running execution is called out explicitly as a known
  factor affecting its numbers differently from the two GET endpoints.
- Cross-referenced (one line) from `docs/product/backlog-validation-service.md`.

**Care condition**: none beyond the item's own acceptance criteria (the hardening-wave review found
none needed) — keep the "not a pass/fail gate" framing.

## Implementation acceptance criteria

- [x] `services/gateway-api/pyproject.toml` gains `locust` as a dev-only dependency (a
  `[dependency-groups] dev` entry, or a separate `loadtest` optional group — do not add it to the
  service's runtime `dependencies`, since Locust is a test tool, not something the running app needs).
- [x] `services/gateway-api/loadtest/locustfile.py` defines a `HttpUser` (or subclass) with tasks:
  - `GET /runs/{id}` — using an id known to exist (seed one at test start via a `POST /runs` call in
    `on_start`, or accept a `RUN_ID` env var — document whichever choice is made).
  - `GET /runs/{id}/splits` — same run id.
  - `POST /runs` — using a small, deterministic inline `dataset_reference` payload (mirroring the
    smoke-test payload already documented in `infra/README.md`'s "Full-stack smoke test" section —
    reuse that exact shape, don't invent a new one) so runs actually execute end-to-end, not just hit
    a 4xx early-exit.
  - At least one task issuing a request with a deliberately invalid/missing API key, to observe `401`
    behavior under load (a distinct task, not folded into the other three).
  - Authentication for the valid-path tasks reads the API key from an env var (e.g. `LOCUST_API_KEY`)
    set by the operator after running `provision_tenant.py` — never hardcoded, never auto-provisioned
    by the locustfile itself (this is a test client, not a fixture-provisioning tool; keep those
    concerns separate).
- [x] No `locust.wait_time`/task weighting or any other constraint that would imply a hard SLA
  assertion — this is a request-stats generator for a human to read, not a CI gate. No
  `--exit-code-on-error` / custom failure-threshold flag is baked into the locustfile or documented as
  a CI-invoked command.
