## Analysis

Covers backlog RS-004: `POST /reports/generate`, resolving tenant via `X-Tenant-Id`, so a report can
be produced synchronously/deterministically for testing/demo ahead of RS-006's async path.

## Design

- Files touched: `src/app/routers/report_generation.py` (new -- deliberately its own module, not
  named `reports.py`, so RS-005's `GET /reports/{id}` can live in its own disjoint file and both
  tickets can run in parallel with zero file overlap, matching validation-service's VS-007/VS-008
  precedent of splitting `runs.py`/`splits.py` for the same reason), `src/app/dependencies/http_client.py` (new,
  mirrors gateway-api's GW-008 `ValidationServiceClientDep` shape), `src/app/main.py` (mount
  router), `src/app/generation.py` (new -- **the shared generation function RS-006 must reuse, see
  below**), `tests/test_generate_endpoint.py` (new).
- **DRY check note**: grep `services/gateway-api/src/app/routers/runs.py` and
  `src/app/dependencies/http_client.py` (GW-008/GW-009) before writing -- reuse the exact same
  `httpx.Client` provider shape (base-URL env var + timeout env var,
  `_call_downstream`-style transport-failure wrapper translating `httpx.ConnectError`/
  `httpx.TimeoutException` into `502`/`504`) rather than inventing a second one. Base URL env var:
  `VALIDATION_SERVICE_URL` (same name gateway-api already uses, since this is the same kind of
  internal-hostname call, scope decision 5).
- **Binding decision (mandatory, feeds RS-006 directly)**: the actual generation sequence (fetch
  `GET /runs/{id}` + `GET /runs/{id}/splits` from validation-service -> render via RS-003's Factory
  with `kind="validation_audit"` -> persist via RS-002's `ReportRepository`) MUST live in one named,
  reusable function (e.g. `generate_validation_audit_report(tenant_id, run_id, client, renderer,
  repository) -> ReportRecord`) in its own module (`src/app/generation.py`), not inlined in the
  route handler. `POST /reports/generate`'s handler calls this function and does nothing else
  business-logic-wise. RS-006's subscriber will import and call this exact same function -- do not
  let this ticket leave the sequence as router-handler-local code, or RS-006 will be forced to
  duplicate it (implementation-plan.md section 9 DRY rule, explicitly flagged in the sprint's own
  Handoff notes).
- Resolves tenant via `Depends(naive_first_common.get_tenant_context)` -- no local
  reimplementation.
- A `run_id` that does not exist for the resolved tenant (validation-service's `404`, cross-tenant
  or nonexistent, both collapsed) passes through as this endpoint's own `404` -- no distinction
  shown, matching validation-service's own non-disclosure stance forwarded one hop further (same
  pattern GW-008 already uses for its own proxy).
- A `"failed"`-status run still generates a status-only report (RS-003's renderer already handles
  this) -- not rejected by this endpoint.
