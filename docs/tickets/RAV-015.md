# RAV-015 — Inline predicted-vs-actual chart per split on `run_detail`

**Status: done.**

**Module**: `services/dashboard-web` only.
**Story**: `RAV-015`, `docs/product/backlog-run-analysis-visualization.md` Epic D.
**Depends on**: none (Epic B's prerequisite backend capability — `build_predicted_vs_actual_chart`,
`GET /runs/{run_id}/splits/{split_index}/points` — is already live, confirmed by sprint-60.md's own
verification). Safe to implement independently/in parallel with `RAV-011`–`014`: touches a different
function (`run_detail`, `routers/runs.py` lines 1183+) and a different template (`run_detail.html`), not
`runs_list`/`runs_list.html`.
**Sprint**: 60 (`docs/sprints/sprint-60.md`). Sequenced last in the plan's narrative order, but has no
ordering dependency on `RAV-011`–`014` and may be dispatched to a dev agent in parallel with them.

## Analysis

`run_detail.html` line 115 today renders a plain text link per split row:
`<a href="/runs/{{ run.id }}/splits/{{ split.split_index }}/points-chart">Actual vs. predicted
value</a>`, sending a tenant to a separate page (`split_points_chart.html`, via `run_split_points_chart`,
`routers/runs.py` line 1131/1132) to see that split's predicted-vs-actual chart. This ticket renders that
same chart **inline**, in `run_detail.html` itself, so a tenant auditing a run's splits sees it directly
alongside that split's row instead of navigating away per split.

The chart-building logic (`build_predicted_vs_actual_chart`, `charting.py` line 926) and its template
partial (`_predicted_vs_actual_chart.html`) already exist and are already correct (Epic B, shipped) —
this ticket **reuses them exactly as-is**, wiring them into `run_detail` instead of (or in addition to)
`split_points_chart.html`. No new chart-building code, no second implementation of point-series geometry.

**N+1 awareness (binding AC, must be stated explicitly, not left implicit)**: `run_detail` already caps
what it renders at `MAX_RENDERED_SPLITS = 500` (`routers/runs.py` line 532/1229-1230) — `rendered_splits`
is already the bounded list every other per-split feature on this page (the metrics table, `RAV-002`'s
error chart inputs) iterates over. This ticket adds **exactly one** new downstream call per rendered
split (`GET /runs/{run_id}/splits/{split_index}/points`) — i.e. up to 500 calls for the largest allowed
run, the same existing cap, not a new unbounded pattern. This ticket does not change `MAX_RENDERED_SPLITS`
or add any new cap — it is bound by the cap that already exists.

**Known, disclosed, out-of-scope limitation carried forward unchanged (do not "fix" it in this
ticket)**: the points endpoint's `limit` query param defaults to 20 (gateway-api/validation-service's
existing `Query(default=20)`), and the existing standalone `run_split_points_chart` route already makes
an unparameterized call relying on that default (per `services/dashboard-web/README.md`'s own "RAV-008/
DASH-129" section: *"no DASH-122-style paging loop was added, since this ticket's own acceptance criteria
don't call for one"*). A split whose test window has more than 20 points will show only the first 20 in
both the standalone page today and this ticket's new inline chart — a pre-existing limitation, not
introduced or worsened by this ticket, and not this ticket's scope to fix (flag it in the Tech Lead's
final report, do not silently patch it here).

## Design

**Design pattern**: none new — this is a read-only rendering ticket, same DI-only pattern
`run_detail`/`run_split_points_chart` already use.

**Files touched** (scoped to `dashboard-web`):
- `services/dashboard-web/src/app/templates/run_detail.html` — line 115's link replaced; new inline
  chart markup added.
- `services/dashboard-web/src/app/routers/runs.py` — `run_detail` (lines 1183+) fetches per-split points
  for each rendered split.
- `services/dashboard-web/src/app/templates/_predicted_vs_actual_chart.html` — reused as-is via
  `{% include %}`, **do not fork/copy it**. If it needs a small parameterization (e.g. a unique anchor id
  per split when included multiple times on one page — it previously only ever appeared once, on
  `split_points_chart.html`), extend it in place (e.g. read `split_index` from the already-passed
  template variable, which this partial already does) rather than creating a second, diverging copy for
  `run_detail.html`'s multi-split context. Verify by reading the partial in full before editing — it
  already parameterizes everything by `split_index`/`points_chart`/`model_column_label`, so it likely
  needs zero changes to be `{% include %}`-ed once per split in a loop.

**DRY check note (mandatory, grepped `routers/runs.py`/`charting.py` before writing this design)**:
`build_predicted_vs_actual_chart(points)` and `PredictedVsActualChartData` (both `charting.py`) are the
one existing implementation — reuse verbatim, do not write a second point-series geometry function.
`run_split_points_chart`'s existing per-split points-fetch call (`client.get(f"/runs/{run_id}/splits/
{split.split_index}/points", headers=headers)`) is the pattern to repeat in a loop over
`rendered_splits`, not reinvent.

**Route wiring** (`run_detail`, inside the existing `with httpx.Client(...) as client:` block, after
`splits`/`rendered_splits` are computed): for each split in `rendered_splits`, fetch its points and build
its chart:
```python
split_points_charts: dict[int, PredictedVsActualChartData] = {}
for split in rendered_splits:
    points_response, points_transport_status = _call_downstream(
        client.get, f"/runs/{run_id}/splits/{split.split_index}/points", headers=headers
    )
    if points_transport_status is not None or points_response.status_code in (502, 504):
        # Degrade this one split's chart to "no data" rather than failing the
        # whole page -- same "don't block the page over one secondary call"
        # stance RAV-012 takes for runs_list's summary call. A genuine
        # transport failure on one split's points must not prevent every
        # other split's table row / chart from rendering.
        split_points_charts[split.split_index] = PredictedVsActualChartData(
            width=..., height=..., plot_bottom=..., has_data=False
        )
        continue
    points = (
        [SplitPointResponse(**item) for item in points_response.json()["items"]]
        if points_response.status_code == 200
        else []
    )
    split_points_charts[split.split_index] = build_predicted_vs_actual_chart(points)
```
Pass `split_points_charts` into the template context. State this degrade-per-split decision explicitly in
a code comment (mirrors `RAV-012`'s equivalent decision for `runs_list`, applied here per-split instead
of per-page) — a dev must not instead propagate a transport failure into `_render_error_for_status` for
the whole page, since that would make one flaky split's points call break the entire run detail view.

**Template**: replace `run_detail.html` line 115's `<td>` link with either (a) a short in-row anchor
link to an in-page id (`<a href="#split-{{ split.split_index }}-points-chart">View chart below</a>`) if
the per-split chart is rendered in a new section after the main table, or (b) the chart included directly
in that split's own row/section if the layout allows — **dev's call between (a) and (b)**, both satisfy
the AC's "in that split's own row/section" wording; (a) is likely simpler given the existing table's
already-wide column count (21 columns) makes embedding an SVG inside a `<td>` visually awkward. Whichever
layout is chosen, iterate `rendered_splits` once (not `splits`) and `{% include
"_predicted_vs_actual_chart.html" %}` per split, passing that split's own `points_chart`/`split_index`
into the include's context (Jinja2 `{% include %}` with an explicit `with context` or passed variables —
confirm which mechanism the existing single-use call in `split_points_chart.html` relies on and match
it).

**Standalone route**: sprint-60.md recommends **keeping** `/runs/{run_id}/splits/{split_index}/points-
chart` (shareable/printable single-split view) — this ticket does not remove it. If kept unchanged, no
extra work is required (it already uses the shared partial/function). State the keep/remove decision
explicitly in this ticket's Outcome section either way (Tech Lead's final call, per the AC).
