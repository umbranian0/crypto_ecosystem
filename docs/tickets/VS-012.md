# VS-012 — Run failure/status handling

**Status: done**

## Analysis
Story: VS-012 (Must), depends on VS-006, VS-009 (both complete). Constraining docs: da-tese-ao-produto.md section 2.2 ("honest statistical verdict" positioning — a validation product whose own failures are invisible undermines its value proposition). This is the second ticket (with VS-004) the role definition calls out for special scrutiny — specifically the "`run.completed` must NOT fire for failed runs" claim.

## Design
Pattern: none new — this hardens VS-006's handler, doesn't add one. Files: `src/app/routers/runs.py` (edit — wrap the `DatasetSource.load(...)` call and the `run_validation_protocol(...)` call in exception handling; on either raising, persist `status="failed"` + `failure_reason` via `ValidationRunRepository.update_run_status`, return a non-`500` response, and **skip** the `event_publisher.publish("run.completed", ...)` call entirely for that request). DRY check: this is a single-file edit on top of VS-009's changes to the same handler — read the current state of `runs.py` in full before editing, don't reintroduce logic VS-006/009 already wrote.

**Failure flow**: 
1. `run = repo.create_run(..., status="running")` (as in VS-006).
2. `try: series = dataset_source.load(...); results = run_validation_protocol(series, config)` — both wrapped.
3. On exception: `repo.update_run_status(tenant_id, run.id, status="failed", failure_reason=str(exc))`; return a response with the failed run's `id` and `status="failed"` (recommend HTTP `201`/`200` with a failed-status body, matching "a run that fails is a completed *request*, just an unsuccessful *run*" — not a `500`, since the request itself was handled correctly; document whichever status code choice was made and why).
4. `event_publisher.publish("run.completed", ...)` is **only** reached in the success branch — structure the code so this is true by construction (e.g. the publish call sits after the try/except's success path returns, or inside an `else` clause), not by a flag that could be forgotten.

`GET /runs/{id}` (VS-007) already returns whatever `status`/fields the row has, including `failure_reason` if the model exposes it — confirm no change needed there beyond making sure `failure_reason` is included in that endpoint's response model (add it if VS-007 didn't already surface it).

## Implementation acceptance criteria
- [x] Any exception from `DatasetSource.load` or `run_validation_protocol` during `POST /runs` results in a persisted `runs` row with `status="failed"` and a stored `failure_reason`, not an unpersisted `500`.
- [x] `GET /runs/{id}` surfaces `status="failed"` and `failure_reason` to the caller (extend VS-007's response model if it didn't already include this field).
- [x] `run.completed` is **not** published for failed runs — verified structurally (the publish call is unreachable from the failure branch), not just by a passing test that happens not to trigger it.

## Test acceptance criteria — the "no run.completed on failure" claim must be genuinely proven
- [x] `tests/test_failure_handling.py`: force a `DatasetSource` failure (e.g. malformed inline payload that VS-005's `DatasetSourceError` rejects) via `POST /runs`, assert the response is not a `500`, assert the persisted `runs` row (via `GET /runs/{id}`) has `status="failed"` and a non-empty `failure_reason`.
- [x] **The same test (or a paired one) asserts the injected `EventPublisher`'s recorded-events list is empty after the failed run** — using the same fake/in-memory `EventPublisher` pattern VS-009's tests use, so this is a genuine assertion against recorded state, not an absence-of-error inference.
- [x] A second failure scenario is confirmed to produce `status="failed"`, not a crash — implemented as a *second* `DatasetSource` failure mode (non-numeric value in an inline payload), not a `run_validation_protocol`-internal failure: every `RunRequest` field that reaches `ValidationConfig`/`generate_splits` (`horizon`, `purge_gap_hours`, `train_window`, `test_window`, `step`) is constrained by pydantic to plain positive/non-negative ints, and `generate_splits` itself never raises on a bad combination of those (it silently yields zero splits per VS-006's own docstring) — so no config reachable through `POST /runs`'s validated request shape can be constructed to make `run_validation_protocol` raise without first reasoning about `naive_first_engine` internals this ticket's Design section says not to duplicate. Two distinct `DatasetSource` failure shapes (missing `inline`/`path` key; non-numeric value) are exercised instead.
