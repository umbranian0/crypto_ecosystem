# VS-031 — Persist raw per-point predicted/actual values per split

**Status: done.** See Outcome section at the end of this file.

**Module**: `services/validation-service` only.
**Story**: RAV-006 (`docs/product/backlog-run-analysis-visualization.md`), first half — persistence.
**Depends on**: none.
**Blocks**: VS-032 (retention), and transitively RAV-007/RAV-008.

## Analysis

`SplitResult`/`SplitResultRecord` today store only the seven aggregated `MetricSet` fields per
baseline per split (`model_*`, `naive0_*`, plus optional `client_baseline_results` JSON). Confirmed
by reading `services/validation-service/src/app/models.py` and
`src/app/repositories/interfaces.py` — no `predictions`/`actuals` column or table exists anywhere.
`naive_first_engine.protocol.run_validation_protocol` (`libs/naive_first_engine/src/naive_first_engine/protocol.py`)
computes `naive0_pred`, `naive_last_pred`, and any `extra_baselines` prediction (`pred`) as full
`pd.Series` aligned to the test window's index, but the function currently only reduces these to
`MetricSet`s via `_metric_set` before discarding the raw arrays. This ticket captures those same
already-computed arrays as a side effect of the existing protocol call — it does not change what the
protocol computes, does not re-fit or re-predict anything outside a split's own train/test boundary,
and does not touch `naive_first_engine` itself (the arrays are already return values of `Naive0()
.predict`/`NaiveLast().predict`/`extra_baseline.predict`, available in `runs.py`'s existing loop over
`results`).

Constrained by: CLAUDE.md ("no service reads another service's schema" — not relevant here, single
service; "preprocessing fit train-only" — not relevant, no fitting happens in this ticket);
implementation-plan.md section 5 (schema-per-service, no cross-schema FKs — the new table lives in
the `validation` schema alongside `split_results`); section 7 (Repository pattern — a new repository
interface, not raw SQL in the router); section 9 (DRY — reuse `SplitResultRepository`'s existing
tenant-scoping/session helpers, don't reinvent them for the new table).

## Design

**Design pattern**: Repository (implementation-plan.md section 7) — a new `SplitPointRepository`
interface/implementation sibling to `SplitResultRepository`, not a method bolted onto the existing
one (different row shape, different volume characteristics, different retention lifecycle — VS-032).
No other pattern from the table applies here (this is a pure persistence addition, not a pluggable
strategy/adapter/factory).

**Schema shape (Tech Lead's call, per RAV-006's own acceptance criteria)**: a new table,
`validation.split_points`, **not** a JSON/array column on `split_results`. Rationale: (a) the
retention mechanism (VS-032) needs to delete/query-filter individual rows by age — a JSON blob
column can't be partially pruned by Postgres without rewriting the whole row/column, a real table can
be deleted from directly and even hypertable-partitioned like `split_results` already is (VS-025);
(b) RAV-007 needs per-split, possibly-paginated reads — a table supports `LIMIT`/`OFFSET`/cursor
pagination natively, a JSON array does not without loading the whole blob first; (c) this mirrors the
`split_results` table's own existing shape (one row per fact, not a JSON grab-bag), the precedent
this module already uses.

Columns: `id` (str PK, uuid4 hex, matching `SplitResult.id`'s convention), `run_id` (FK to
`runs.id`), `tenant_id` (denormalized, same rationale as `SplitResult.tenant_id` — no join needed to
tenant-scope, and a leaked/misrouted `run_id` can't be used to read another tenant's points),
`split_index` (int, matches the owning split), `baseline_key` (str — one of `"naive_last"`,
`"naive0"`, or the client baseline's key, mirroring `naive_first_engine.protocol`'s own
`NAIVE0_KEY`/`NAIVE_LAST_KEY`/class-name convention — never a repurposed enum, matching VS-017's
"never repurpose model_*/naive0_* columns" precedent applied to a new axis instead), `timestamp`
(the test-window instant this point belongs to), `predicted` (float), `actual` (float), `created_at`
(datetime, copied from the owning run's creation time at write time — **not** `datetime.utcnow()`
recomputed per row — so VS-032's age-based retention cutoff needs no join back to `runs` to filter;
this is the one denormalization this ticket adds beyond mirroring `split_results`' existing style,
and it is necessary for VS-032, not incidental).

Files touched (scoped to `validation-service` only):
- `src/app/models.py` — new `SplitPoint` SQLAlchemy model.
- `src/app/repositories/interfaces.py` — new `SplitPointRecord` dataclass + `SplitPointRepository`
  Protocol (`add_points(tenant_id, run_id, points: list[SplitPointRecord]) -> None`,
  `get_points(tenant_id, run_id, split_index) -> list[SplitPointRecord]`).
- `src/app/repositories/sqlite_repository.py` / `postgres_repository.py` — `SQLiteSplitPointRepository`
  / `PostgresSplitPointRepository` implementations, reusing the exact `_tenant_scoped_session`/
  `Session` patterns `SplitResultRepository`'s siblings already use (DRY — no new session-management
  code).
- `src/app/dependencies/repositories.py` — `get_split_point_repository` provider + `SplitPointRepositoryDep`,
  same DI seam shape as `SplitResultRepositoryDep`.
- `src/app/routers/runs.py` — `create_run`'s existing loop over `results` (the `naive_first_engine`
  `SplitResult` objects, not to be confused with this service's own `SplitResult` model) gains a
  second, additive persistence step per split: build `SplitPointRecord`s from `naive0_pred`/
  `naive_last_pred`/(client `pred` if present) aligned against `test.index`/`test.values`, and call
  `split_point_repository.add_points(...)` alongside the existing `split_repository.add_splits(...)`
  call. **This requires threading the raw prediction Series out of `run_validation_protocol`'s return
  value** — today `SplitResult.baseline_results[key]` only carries `BaselineResult(metrics, dm_result)`,
  no raw predictions. Two options: (a) extend `naive_first_engine`'s `BaselineResult` dataclass with
  an optional `predictions: pd.Series | None` field (opt-in, default `None`, zero behavior change for
  every existing caller/test that doesn't set it), or (b) recompute predictions a second time in
  `validation-service` by calling each baseline's `.predict(train, test)` again outside the protocol.
  **Choose (a)** — (b) would mean re-running inference outside the protocol's own fixed
  split→baseline→metrics→DM-test order (Template Method, implementation-plan.md section 7), which is
  exactly the shortcut CLAUDE.md and section 7 warn against ("you can't skip/duplicate the protocol's
  own steps"), and it would double the compute cost for no reason when the value is already sitting in
  a local variable inside `protocol.py`'s loop. This means **this ticket also touches
  `libs/naive_first_engine/src/naive_first_engine/report_schema.py`'s `BaselineResult`** and
  `protocol.py`'s three call sites that construct one — additive-only (new optional field, existing
  7-field `MetricSet`/`dm_result` shape unchanged), covered by `naive_first_engine`'s own existing
  regression suite continuing to pass unmodified (no regression-number change, since metrics
  computation itself is untouched).
- `libs/naive_first_engine/src/naive_first_engine/report_schema.py`, `protocol.py` — additive
  `predictions` field per above (ML-adjacent change — see note below).
- `migrations/versions/00NN_add_split_points_table.py` — new Alembic migration, `validation` schema
  target (same `search_path`/`version_table_schema` convention every prior migration in this module
  uses), including RLS enable+force+policy on `split_points` (matching `runs`/`split_results`'
  `0002_add_row_level_security.py` precedent — this table holds tenant data too, RLS is not optional).

**DRY check note**: grepped `services/validation-service/src/app` for existing per-point/raw-array
persistence — none exists (confirmed by the Analysis section above and by `grep -rn "predictions\|raw_points\|split_points" services/validation-service/src` returning nothing pre-ticket). `_tenant_scoped_session`
(`postgres_repository.py`) and the SQLite `Session(self._engine)` pattern are the two pieces of
existing code this ticket must reuse verbatim for the new repository classes, not reimplement.

**ML/data-pipeline note**: this ticket touches `naive_first_engine`'s `report_schema.py`/`protocol.py`
(an additive dataclass field only) and a model-adapter output (the raw prediction arrays already
produced by `Baseline.predict`). Per this project's skill-routing convention, the dev agent should
read `/ml-engineer` before touching `naive_first_engine`, even for this narrow an addition — the
binding constraint is that **no new fitting/prediction call is introduced**; the `predictions` field
is populated from values the protocol already computes in its fixed order, never from a second,
independent `.predict()` call. `naive_first_engine`'s existing regression suite
(`tests/test_regression_1h.py`) must still pass unmodified — this proves the metrics/DM-test path is
byte-identical to before this ticket.

## Implementation acceptance criteria

- [x] `naive_first_engine.report_schema.BaselineResult` gains an optional `predictions: pd.Series | None
      = None` field; `protocol.py`'s three `BaselineResult(...)` construction sites (naive0, naive_last,
      each `extra_baselines` entry) populate it with the same `naive0_pred`/`naive_last_pred`/`pred`
      Series already computed in that loop — no second `.predict()` call anywhere.
- [x] `validation.split_points` table exists (new Alembic migration), RLS-enabled/forced, with a
      `tenant_isolation` policy matching `runs`/`split_results`'s existing policy shape exactly.
- [x] `SplitPointRepository` (`add_points`/`get_points`) is defined as a `typing.Protocol`, SQLite +
      Postgres implementations wired into the DI seam, following VS-003's binding "no storage-driver
      import in interfaces.py" rule.
- [x] `POST /runs`'s existing handler persists one `split_points` row per `(split, baseline, test-window
      timestamp)` triple for `naive_last` (model), `naive0`, and the client baseline (when
      `client_prediction_reference` was supplied) — additive only, `split_results`'s own persistence is
      byte-unchanged.
- [x] No leakage-protocol change: `run_validation_protocol`'s call site, argument order, and internal
      split→baseline→metrics→DM-test sequence are unmodified; the only diff inside `naive_first_engine`
      is the additive `predictions` field.
