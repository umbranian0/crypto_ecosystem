# ADMIN-003-02 — Crawl-status panel: render `failure_detail` when a crawl failed (dashboard-web)

**Status: done.** Implemented, tested (422 passed / 0 failed / 8 deselected, personally re-run by the
Tech Lead), Tech-Lead-reviewed. **Tech Lead fix applied during Review**: the dev agent correctly
identified and did not silently work around a pre-existing, unrelated test bug --
`test_crawl_progress.py::test_crawl_progress_column_has_no_banned_positioning_words_in_panel_template`
(`DASH-118`) did a naive substring match for `"eta"` against the whole template file, which
false-positived once this ticket's mandated field name `entry.failure_detail` (containing `"eta"` as a
substring of `"detail"`) landed in `_crawl_status_panel.html`. The Tech Lead applied the dev's own
suggested minimal fix directly (a one-line, mechanical, well-reasoned test-only change, not a
re-delegation-worthy scope): `test_crawl_progress.py`'s banned-word checks now use a word-boundary
regex (`\bWORD\b`) instead of a bare substring test, preserving the test's real intent (catch a
standalone "ETA"/positioning word) while no longer false-positiving on "detail"/"metadata"/etc. Full
`services/dashboard-web` suite re-run after the fix: 422 passed, 0 failed, 8 deselected.

## Design

**Pattern**: none applies — static server-side templating over an already-fetched dict, same shape as
`_crawl_status_panel.html`'s existing `entry.progress_display` cell.

**Files touched** (scoped to `services/dashboard-web` only):
- `services/dashboard-web/src/app/templates/_crawl_status_panel.html` — the status `<td>` (line 60)
  becomes:
  ```html
  <td>
      {{ entry.status }}
      {% if entry.status == "failed" and entry.failure_detail %}
      <br><span class="failure-detail">{{ entry.failure_detail }}</span>
      {% endif %}
  </td>
  ```
  Gated on **both** `entry.status == "failed"` **and** a truthy `entry.failure_detail` (defensive: a
  pre-`ADMIN-003-01` row, or any row where the backend legitimately has no value, must not render an
  empty/`None` line) — matches the AC's own "renders `failure_detail` when present, next to the existing
  status badge" wording exactly. No other `<td>` in this table changes; Progress/Trigger columns are
  untouched (AC's own explicit constraint).
- `services/dashboard-web/src/app/routers/operator.py` — **no change**. Confirmed in Analysis: the
  existing `**status_response.json()}` spread already forwards `failure_detail` once `ingestion-service`
  emits it; touching this file would be an unnecessary, undocumented edit outside this ticket's stated
  scope.

**DRY check note** (grepped before writing this ticket): no existing "render an optional detail line
under a status cell" markup exists anywhere in this template to reuse or duplicate — this is a new,
single conditional, not a copy of existing markup.
