# MDF-004-01 — Analysis: does `naive_first_engine`'s public interface need to change for multi-column candidate-model input?

**Module**: `libs/naive_first_engine` (analysis output as a new ADR; code change only if the analysis concludes
one is warranted, additive-only, same module).
**Sprint**: 38 (`docs/sprints/sprint-38.md`). **Story**: MDF-004 [Must, high scrutiny].
**Status**: done — Tech Lead reviewed, ADR-0010 accepted, `libs/naive_first_engine` suite 99 passed (95
pre-existing + 4 new), zero-line diff confirmed on `baselines.py`/`splitting.py`/`dm_test.py`/
`report_schema.py`/`protocol.py`.

## Analysis

Covers MDF-004's full acceptance criteria (`docs/product/backlog-multimodal-dataset-fusion.md` lines 190-211).
MDF-003 (`services/validation-service/src/app/feature_dataset.py`, shipped Sprint 36) assembles an aligned,
multi-column `pd.DataFrame` (`FeatureDatasetAssembler.assemble()`), fold-scaled by `FeatureFoldScaler`, but
**does not** call any candidate model with it — no such call site exists anywhere in the codebase today. The
existing `Baseline` Strategy protocol (`libs/naive_first_engine/src/naive_first_engine/baselines.py:16-31`,
`predict(train: pd.Series, test: pd.Series) -> pd.Series`) is consumed today only by `Naive0`, `NaiveLast`, and
(implicitly, by producing the error Series `dm_test.py` consumes) any future client-model adapter running
inside the same univariate walk-forward loop (`protocol.py`'s `run_validation_protocol`, a Template Method).

Constraints from the docs, binding on this analysis:
- CLAUDE.md: "No service imports another service's code — only `libs/*` are shared" and the leakage rule
  ("preprocessing... fit on the training fold only, per split — never globally").
- implementation-plan.md section 7: Strategy pattern is why `Baseline` exists in the first place — any new
  interface must fit that same rationale (interchangeable algorithms, uniform call site) or explain why it
  doesn't apply.
- implementation-plan.md section 9 (DRY): grep `libs/naive_first_engine` and `protocol.py` first — state
  explicitly what is reused (the `Split` boundaries from `splitting.generate_splits`, `dm_test.py`,
  `report_schema.py`'s typed results) vs. what, if anything, is new.
- Sprint-38 high-scrutiny flag: any interface change must be **additive** (kept alongside `Baseline`, not a
  modification to it), must not alter `Naive0`/`NaiveLast`/`dm_test.py`'s existing behavior or test results,
  and the full existing regression suite (1h/6h/24h) must pass **unmodified** (not edited to pass).

## Design

- Deliverable: `docs/adr/0010-multimodal-candidate-model-interface.md` (next free ADR number, confirmed by
  `ls docs/adr/` — 0001 through 0009 exist). Follow the existing ADR format/frontmatter used by
  ADR-0007/0008/0009 (read one of those first for the exact section headings this repo uses: status, context,
  decision, consequences, etc.).
- The ADR must answer, explicitly, in its own "Decision" section:
  1. Does `Baseline.predict(train: pd.Series, test: pd.Series) -> pd.Series` change? (Expected answer, per the
     sprint plan's own steer: **no** — it currently governs only naive baselines and DM-test error Series,
     not a candidate model's own inference call, so there is no forcing reason to touch it.)
  2. Is a new, additive interface needed for "a candidate model that consumes a multi-column feature
     `DataFrame` and emits a `pd.Series` of predictions on the same target"? If yes, specify its exact
     signature, its file location (must stay inside `libs/naive_first_engine`, not `validation-service` — this
     is core-IP, not a service-side concern per implementation-plan.md section 2/5), and how it composes with
     `generate_splits`'s `Split` boundaries and `protocol.py`'s Template Method call sequence without
     duplicating either.
  3. Confirms explicitly (with a code/test reference, not just an assertion) that `generate_splits`'s purge-gap
     logic (`splitting.py`) applies identically regardless of whether the model side is univariate or
     multivariate — the purge gap is keyed off the target/test-fold *time index* boundary
     (`train_end`/`test_start`), not column count, so nothing about a wider feature `DataFrame` changes
     `_generate_splits_by_position`/`_generate_splits_by_time`'s behavior. State this as a design fact and back
     it with a short new/existing test proving `generate_splits` is called identically (same `Split` objects)
     whether the caller later feeds a `Series` or a `DataFrame` to whatever consumes the split boundaries — the
     splitter itself never sees model input at all, only the index.
  4. If a new interface is added: the DRY check confirms it does not duplicate `Baseline`'s docstring
     leakage-safety argument (pre-sliced train/test making it structurally impossible to read past `train_end`)
     — the new interface must carry the equivalent structural guarantee for a `DataFrame` input, not merely
     inherit the argument by reference.
