## Design — placement decision (documented decision, satisfies AC1)

**Decision: the check lives in `services/validation-service`, not `libs/naive_first_engine`.**

Reasoning against `libs/naive_first_engine/README.md`'s "Owns/Does not own" section:
- `naive_first_engine` **owns**: "the validation algorithm only... dataset-agnostic" — `splitting.py`,
  `baselines.py`, `metrics.py`, `dm_test.py`, `protocol.py` have no concept of what a value *means*
  (price vs. return vs. any other unit); they operate on whatever numeric series they're given. Teaching
  the engine to distinguish "this looks like a price level" vs. "this looks like a return" would be new
  domain semantics the library was explicitly never scoped to carry, and would break its own stated
  design goal of being pip-installable/open-coreable standalone on arbitrary series.
- `naive_first_engine` explicitly **does not own** "dataset storage" or dataset semantics — that's
  `validation-service`'s/`ingestion-service`'s territory (README's own words). Whether a submitted series
  is a price level or a return is a *dataset content* question, the same category of question
  `validation-service` already answers today in `dataset_source.py` (DH-001 reordering, DH-002 dedup,
  DH-003 conflict detection) and in `runs.py` (RSS-004 split-count guardrail, DH-005 zero-split
  guardrail) — all input-validation, all before `run_validation_protocol` is ever invoked.
- Placing it inside `naive_first_engine` would also force a signature change to accept some kind of
  "series kind" flag on `generate_splits`/`run_validation_protocol`, which AC4 explicitly forbids.
  Placing it in `validation-service` needs no engine change at all.
- This mirrors the exact precedent already set by DH-005 (a `422` guardrail computed from the loaded
  series before `run_validation_protocol` runs and before any `runs` row is persisted) — reusing an
  established pattern, not inventing a new one. A short decision note in this ticket is sufficient; this
  does not warrant a full ADR (no cross-module architecture change, no new external contract, single
  file/module affected, directly precedented by DH-005/RSS-004 already living in the same file).

## Design — implementation

Pattern: no new design pattern from implementation-plan.md section 7 is needed — this is a guardrail
function in the existing input-validation chain, same shape as RSS-004/DH-005 (plain function + `422`
`HTTPException`), not a Strategy/Adapter/Factory.

Files touched (scoped to `services/validation-service` only):
- `services/validation-service/src/app/level_detection.py` (new) — pure function(s), no I/O, no
  dependency beyond `pandas`/`numpy` (both already transitively available via `naive_first_engine`'s own
  `pandas`/`numpy`/`scipy` dependency — no new `pyproject.toml` entry needed; confirmed by grep below).
- `services/validation-service/src/app/routers/runs.py` — one new guardrail call, inserted after the
  DH-005 zero-split check and before `_persist_new_run` (same "no run row, zero engine calls" property
  RSS-004/DH-005 already have for a rejected request).

**DRY check (grep first)**: `grep -rn "autocorr\|adfuller\|is_stationary\|price_level" services/validation-service/src` — expected empty (confirmed before implementation; no existing detection logic to reuse or duplicate). No `statsmodels` dependency exists in `pyproject.toml` today (grepped) — deliberately not adding one; see heuristic choice below.

**Heuristic choice (not a formal ADF test)**: a full Augmented Dickey-Fuller test requires `statsmodels`
(new dependency) and produces a p-value whose pass/fail threshold is itself a judgment call, and is prone
to being flaky/ambiguous on the short synthetic series unit tests use. Instead: a deterministic,
dependency-free heuristic combining two classic signatures of a non-differenced, trending price level
vs. a returns series:
1. **Lag-1 autocorrelation** of the raw series close to 1 (price levels move by small increments
   relative to their own level, so consecutive values are highly correlated; returns are close to i.i.d.
   noise around a fixed mean, so lag-1 autocorrelation is low).
2. **Mean far from zero relative to spread** (`abs(mean) / std`): a returns series (fractional/log
   returns) is centered near 0 by construction; a price level series is not.
Both conditions must hold (AND, not OR) to flag as price-level-like — avoids over-flagging a returns
series that happens to have a slight, non-price-level trend. Thresholds (`lag1_autocorr > 0.90` and
`abs(mean)/std > 1.0`) are conservative-by-design, documented as such in the module docstring, same
"disclosed, not silently tuned" convention as `MAX_SPLIT_COUNT`/`DEFAULT_PURGE_GAP`.

**No auto-transform**: the check rejects (`422`), it does not silently difference/transform the series
into returns on the caller's behalf. This matches this module's own established "no silent inference"
convention (DH-003's hard-block-not-auto-resolve precedent, cited in that ticket's own reasoning) —
auto-converting the caller's own submitted data without being asked is a bigger silent-inference risk
than requiring an explicit resubmission with a returns-shaped dataset/field.

## Outcome

**Dev agent's original findings**: implementation matched the Design section exactly (placement,
ordering, heuristic, thresholds, no auto-transform, no `naive_first_engine`/`statsmodels` change).
Applying the ticket's own specified thresholds (`lag1_autocorr > 0.90 AND abs(mean)/std > 1.0`) against
this repo's *existing* test fixtures surfaced a real conflict: several pre-existing tests across the
suite used monotonic or piecewise-near-constant filler series (e.g. `pd.Series(range(n))` in
`test_split_count_guardrail.py`'s `_FakeDatasetSource`, or `test_regression_api.py`'s own
DM-verdict-pattern construction) as generic placeholder data for testing unrelated concerns (tenant
isolation, split-count math, event publishing, DM-verdict wiring) — not intended to represent a real
price/return series, but which the heuristic correctly (per its own definition) flagged as price-level-
like anyway. 19 previously-passing tests failed: `test_client_baseline_endpoint.py` (5),
`test_events.py` (2), `test_ingestion_dataset_source_tenant_forwarding.py` (1), `test_regression_api.py`
(1, the DM-verdict test), `test_runs_endpoint.py` (6), `test_split_count_guardrail.py` (1),
`test_splits_endpoint.py` (3). The dev agent correctly declined to choose between retuning thresholds,
fixing fixtures, or accepting the failures unilaterally, and flagged the decision back to the Tech Lead.

**Tech Lead decision and resolution**: option (b)/(c) from the dev agent's own framing — fix the
fixtures, do not retune the thresholds (retuning was never this dev agent's or this Tech Lead pass's
call to make unilaterally; the thresholds are a documented Design-section decision). Personally
inspected every one of the 19 failures: in all 6 affected files, the filler value generator was
`[float(i) for i in range(n)]` (or the `pd.Series(range(row_count))` equivalent) — a monotonic ramp with
lag-1 autocorrelation ≈1 and a mean far from 0 relative to its spread, i.e. textbook price-level shape,
used purely as cheap placeholder data for tests that assert on split counts, tenant isolation,
dedup/reorder warnings, or event-publishing — none of which read the *values* themselves. Replaced with
a deterministic (fixed-seed), zero-centered, low-autocorrelation `numpy` noise generator in
`test_runs_endpoint.py`, `test_events.py`, `test_client_baseline_endpoint.py`,
`test_split_count_guardrail.py`, `test_ingestion_dataset_source_tenant_forwarding.py`, and
`test_splits_endpoint.py` (the last of these needed its `_inline_dataset`/`_series` helpers to share a
seed, since that file's own round-trip assertion requires both to encode the same underlying series).
`test_regression_api.py`'s DM-verdict test needed a different, narrower fix: its train segment was
centered on `_DM_L` for its *entire* length, when only the segment's last element is actually read by
`NaiveLast.predict`; zero-centering the rest of the segment (keeping the pinned last point) dropped the
*global* submitted series' `abs(mean)/std` back under 1.0 without changing any per-split DM-verdict
math any existing assertion depends on. No `level_detection.py` threshold was touched. Full suite
re-run by the Tech Lead: `services/validation-service` **169 passed, 0 failed**;
`libs/naive_first_engine` **95 passed**; `check_doc_sync.py` clean;
`generate_splits`/`dm_test`/`Baseline` signature grep identical before/after.
