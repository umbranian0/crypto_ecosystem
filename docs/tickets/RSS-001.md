# RSS-001 — Show the selected stored dataset's real row count and date range on the run form

**Status: done (browser click-through verification blocked by environment constraints, see Review notes — code/test verification complete)**

## Analysis
Story: RSS-001 (Must, `docs/product/backlog-run-submission-safety.md`), no dependency on RSS-004 or any
other story — architecturally independent (`dashboard-web`, disjoint files from RSS-004's
`validation-service` change), runs in parallel with RSS-004 per `docs/sprints/sprint-25.md`.

Constraining acceptance criteria, read directly from the backlog entry, not summarized from memory:
- `run_new_form` (`services/dashboard-web/src/app/routers/runs.py`) already fetches `datasets` via
  `_fetch_ingestion_datasets` (DASH-108/111) and already passes it to `run_new.html`, which already
  renders each dataset's `row_count`/date range inside the `<option>` **text** (see
  `run_new.html` line 58: `{{ dataset.source }} ({{ dataset_macros.date_range(dataset) }}, {{
  dataset.row_count }} rows)`). This ticket's actual gap is that this data is not machine-readable
  per-option (no `data-row-count`/`data-earliest`/`data-latest` attributes) and there is no visible
  summary line below the dropdown that updates on selection — both are needed by RSS-002's live
  estimate. **No new backend field and no second `GET /ingestion/datasets` call** — reuse the exact
  `DatasetSummaryResponse` fields (`row_count`, `earliest_timestamp`, `latest_timestamp`) already
  flowing into the template.
- Selecting a source updates a visible summary line (row count + earliest–latest range) with no page
  reload/server round-trip.
- If `dataset_reference_start`/`dataset_reference_end` are filled in, the summary line's row-count figure
  is explicitly labeled as the *full source's* row count, not a recomputed narrowed count (RSS-003's
  territory, not this ticket's).
- No behavior change to `run_new_submit`, `RunRequest` construction, or the local-path/inline modes —
  additive display only in the stored-dataset fieldset.

## Design
Pattern: none new — Dependency Injection is already this service's only applicable pattern
(implementation-plan.md section 7's table; this service persists nothing of its own, so Repository does
not apply). File(s) touched, scoped to `dashboard-web` only:
- `services/dashboard-web/src/app/templates/run_new.html` — add `data-row-count`, `data-earliest`,
  `data-latest` attributes to each `<option>` in the `#dataset_reference_source` dropdown (reusing the
  exact `dataset.row_count`/`dataset.earliest_timestamp`/`dataset.latest_timestamp` fields the template
  already has in scope — no new template context variable); add a summary `<p>`/`<span>` element below
  the dropdown (empty/hidden by default) plus inline `<script>` logic (in the same `<script>` block
  `checkReference()` already lives in, not a second `<script>` tag) that reads the selected `<option>`'s
  dataset attributes on `change` and renders the summary line, explicitly labeled "full source" when
  `dataset_reference_start`/`dataset_reference_end` have a value.
- `services/dashboard-web/src/app/routers/runs.py` — **no change expected**: `run_new_form` already
  passes `datasets` (the full `DatasetSummaryResponse` list) to the template; if the dev agent finds any
  field is not already present on the template context, that is the only permitted router-level edit
  (adding a missing pass-through, never a new endpoint call).

**DRY check (performed before writing this ticket)**: grepped `run_new.html` and confirmed `date_range`
macro (`_dataset_macros.html`) already produces the "earliest to latest" phrase used in the `<option>`
text — the new summary line should reuse the same wording convention (not invent a second date-range
phrasing), though it must be computed client-side from the `data-*` attributes since the summary updates
without a server round-trip, not by re-rendering the Jinja macro. Grepped `runs.py` — no existing
per-source summary logic to duplicate.
