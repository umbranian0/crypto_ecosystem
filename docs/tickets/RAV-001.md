## Analysis

`run_detail.html` currently renders a completed run's per-split metrics only as a table
(`GET /runs/{id}/splits`, DASH-004). Sprint 26's goal needs two charts added on top of that same
data (RAV-002 model-vs-Naive0 error, RAV-003 DM-verdict visualization) without any backend change.
Before either chart ticket starts, this repo needs one documented decision on *how* a chart gets
rendered inside a locked-in server-rendered FastAPI + Jinja2/HTMX architecture — CLAUDE.md's
"local-first... server-rendered (FastAPI + HTMX/Jinja2) frontend" assumption is binding and rules
out a SPA/client-side-routing rewrite. A grep across `services/dashboard-web` for
`chart.js|plotly|d3|vega` (case-insensitive) confirms no charting technology exists in this service
today — this is a real open decision, not a detail to leave implicit in RAV-002's ticket.

Acceptance criteria from the backlog (all four must be explicitly answered in the written decision):
1. Names the chosen approach and explicitly weighs (a) a client-side JS library (e.g. Chart.js) vs.
   (b) server-rendered SVG/PNG with zero new JS.
2. States whether a new frontend dependency is introduced (name + pinning convention) or, if
   server-rendered, names the Python library used (or states that none is needed).
3. Confirms compatibility with the locked-in FastAPI + Jinja2/HTMX architecture (no SPA, no
   client-side routing).
4. Is silent on/does not touch Epic B (raw per-point predicted/actual charting, RAV-006/007/008) —
   this decision is charting-technology only.

## Design

**Decided direction (Tech Lead call, to be written up and justified by this ticket, not
re-litigated)**: server-rendered inline SVG, generated by a small new pure-Python module
`services/dashboard-web/src/app/charting.py` (functions that take already-fetched
`SplitResultResponse` data and return simple dataclasses/dicts of pre-computed pixel
coordinates/dimensions), rendered into `<svg>` markup by two new Jinja2 partials
(`_error_chart.html` for RAV-002, `_dm_verdict_chart.html` for RAV-003, included from
`run_detail.html`). **No new dependency of any kind** — no Chart.js/Plotly/D3 script tag, no Python
plotting library (matplotlib/etc. would be a heavy, image-rendering dependency for what is a
handful of bars/markers; plain string-built SVG via Jinja2 is sufficient and keeps the "zero new
JS" property CLAUDE.md's architecture assumption prefers).

Rationale (write this into the decision doc, don't just assert it):
- **Testability matches this service's existing convention.** `dashboard-web` already has a
  documented precedent (RSS-002, `services/dashboard-web/README.md` "Live split-count estimate"
  section) of avoiding a JS-execution test harness — this service's default test suite has no
  Selenium/browser-JS assertion path outside the separate `-m e2e` marker. Server-rendered SVG
  means RAV-002/RAV-003's "chart renders correct series values for a fixture set of splits" test
  criteria can be verified as a plain string/attribute assertion against the rendered HTML
  (`TestClient` + `response.text`), the same pattern every existing `tests/test_runs_*.py` file
  already uses — no new test infrastructure.
- **Palette risk named and avoided.** The backlog explicitly flags that "an off-the-shelf charting
  library's default color scheme is the easy way to accidentally violate" the no-green/red
  bull/bear rule. Hand-written SVG means every color value is one of `style.css`'s existing
  variables (`--color-accent`, `--color-accent-2`, the existing `--color-status-*` triplet) chosen
  explicitly by this ticket — never a library default.
- **Zero new dependency** — nothing to add to `pyproject.toml`/lockfile, nothing to pin, no supply
  chain surface added for a handful of bar charts.
- **Confirmed HTMX/Jinja2-compatible**: an inline `<svg>` block is just more server-rendered markup
  in an existing Jinja2 template — no client-side routing, no JS framework, no build step.
