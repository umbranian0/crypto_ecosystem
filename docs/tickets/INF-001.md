# INF-001 — PostgreSQL + TimescaleDB service in Docker Compose

Status: **done**
Backlog: docs/product/backlog-infra.md, INF-001 [Must]
Sprint: docs/sprints/sprint-06.md, Phase 1 / Track B
Depends on: none

## Analysis

`infra/` currently holds only a "planned" README, no compose file. `validation-service` and
`gateway-api` both run on interim SQLite; VS-013/GW-012 are blocked until a real Postgres exists
and is reachable. `implementation-plan.md` section 5 specifies a single Postgres + TimescaleDB
instance for the pilot phase, schema-per-service.

## Design

- **Binding decision (grooming, #4)**: INF-001 provisions **ONE** Postgres database with **TWO**
  schemas (`CREATE SCHEMA validation`, `CREATE SCHEMA identity`) — not two separate databases.
  This ticket's job is the container + one database + init step that creates both schemas (or a
  documented init script doing so); VS-013/GW-012 own pointing their own Alembic `env.py` at
  their respective schema (that is new scope tracked on those two tickets, not here).
- `infra/docker-compose.yml` (new file) defines a `postgres` service using the
  `timescale/timescaledb` image (matches solution-design.md section 5), fixed host port mapping
  (e.g. `5432:5432`), named volume for the data directory, credentials via env vars sourced from
  `.env`/`.env.example`.
- An init mechanism (either a mounted `initdb` SQL script under
  `infra/postgres-init/*.sql`, run automatically by the official Postgres/Timescale image's
  `/docker-entrypoint-initdb.d/` convention, or documented manual step) creates the `validation`
  and `identity` schemas inside the one database on first startup.
- Pattern: infra-as-compose-config, no application code touched — matches this backlog's own
  explicit scope boundary (decision 1: Dockerfiles/compose only, no VS-013/GW-012 logic here).
- DRY check: n/a (first infra file in the repo).

## Outcome

Implemented as specified in Design. `infra/docker-compose.yml` was created fresh with a single
`postgres` service (`timescale/timescaledb:latest-pg16`, port `5432:5432`, named volume
`postgres-data`, credentials via `${POSTGRES_USER}`/`${POSTGRES_PASSWORD}`/`${POSTGRES_DB}` env
vars with dev-only defaults, no hardcoded secrets). A parallel agent (INF-002) added a `redis`
service to the same file concurrently; both blocks coexist without conflict.

Schema creation is handled by `infra/postgres-init/01-create-schemas.sql`, mounted to
`/docker-entrypoint-initdb.d/`, running `CREATE SCHEMA IF NOT EXISTS validation;` and
`CREATE SCHEMA IF NOT EXISTS identity;` — one database, two schemas, per the binding grooming
decision.

`.env.example` was added at `infra/.env.example` (chose `infra/` over repo root since the compose
file lives there and Compose resolves the project directory — and therefore its `.env` — from the
compose file's location, confirmed empirically with `docker compose -f infra/docker-compose.yml
config`). It was extended additively by the INF-002 agent with `REDIS_URL`; my `POSTGRES_*`
block was untouched.

Real verification performed (see final report to Tech Lead for full command output):
- `docker compose -f infra/docker-compose.yml up -d postgres` — image pulled, container
  `naive-first-postgres` came up and reported `healthy`.
- `docker exec naive-first-postgres psql -U naive_first -d naive_first -c '\dn'` — returned
  `identity`, `public`, `validation` (3 rows). Both required schemas present.
- `SELECT version();` confirmed PostgreSQL 16.14 (Timescale image) reachable and responsive.

Container left running (not torn down) since INF-002/INF-003 need postgres+redis up together.

Unmet: none of the Implementation/Test/Documentation ACs. The "Review acceptance criteria" section
is explicitly scoped to the Tech Lead's personal verification and is left unchecked for them to
perform independently.
