## Analysis

`gateway-api` currently only has `SQLiteTenantRepository`/`SQLiteUserRepository`/
`SQLiteApiKeyRepository` (GW-004) behind GW-003's interfaces. This ticket adds Postgres-backed
implementations with RLS, same shape as VS-013.

## Design

- **Binding decisions carried from grooming**: `psycopg` v3 synchronous driver (#3);
  `naive_first_common.db.build_engine` + ARCH-002's memoized-by-URL engine provider (#1/#2);
  Alembic `migrations/env.py` targets the `identity` schema via `search_path` AND
  `version_table_schema="identity"`, new scope beyond INF-005 (#4) — **UPGRADED FROM SHOULD TO
  HARD REQUIREMENT**: INF-005 empirically reproduced a real collision running both services'
  current public-schema, version_table_schema-less migrations back-to-back against the same
  Postgres database — whichever runs second finds `public.alembic_version` already stamped and
  silently skips its own `upgrade()` with no error. `version_table_schema="identity"` is
  required, not optional polish, or this service's migration will silently no-op against a real
  shared database the moment VS-013's migration has already run against it.
- **Binding decision (grooming, #8) — the subtlest cross-story interaction in this sprint**: RLS
  uses a per-transaction `SET LOCAL app.tenant_id` session variable (via a SQLAlchemy
  session-begin/`before_cursor_execute` hook), **NOT per-tenant Postgres roles**. This hook MUST
  be added at the same seam ARCH-002 introduces (the shared, now-pooled engine/session factory) —
  a connection recycled from one tenant's request must not leak `SET LOCAL` state into another
  tenant's request. Concretely: use SQLAlchemy's `Engine`-level `@event.listens_for(engine,
  "checkout")` or a session-scoped `begin()` hook that issues `SET LOCAL app.tenant_id = :id`
  as the first statement of every transaction — never a connection-level `SET` (non-`LOCAL`,
  which persists beyond the transaction and would leak across pooled reuse) and never set only
  once at engine-creation time.
- New `PostgresTenantRepository`/`PostgresUserRepository`/`PostgresApiKeyRepository` behind
  GW-003's existing interfaces — no call-site changes anywhere else in the service.
- RLS policies (`CREATE POLICY`) scope every tenant-scoped query to `tenant_id` via
  `current_setting('app.tenant_id')`, added via a new Alembic migration for `tenants`, `users`,
  `api_keys`. `get_by_hash`/`get_user_by_email` are GW-003's documented tenant-agnostic exceptions
  — these two methods must NOT be blocked by RLS (they resolve identity before a tenant is known);
  handle via a policy that also permits the no-tenant-set lookup path for exactly these two query
  shapes, or by running those two specific queries outside the tenant-scoped policy context,
  documented explicitly since this is the one place RLS must NOT apply as bluntly as VS-013's.
- GW-002's Alembic migrations (already written against the schema) point at the real Postgres
  `identity` schema as part of this story.

## Implementation acceptance criteria

- [x] `PostgresTenantRepository`/`PostgresUserRepository`/`PostgresApiKeyRepository` implement
      GW-003's interfaces — no call-site changes anywhere else in the service.
- [x] Uses `naive_first_common.db.build_engine` + ARCH-002's memoized-by-URL provider.
- [x] `migrations/env.py` targets the `identity` schema via BOTH `search_path` (table creation)
      AND `version_table_schema="identity"` (`alembic_version` tracking) — hard requirement per
      INF-005's reproduced collision, not optional.
- [x] RLS policies (`CREATE POLICY`) added for `tenants`/`users`/`api_keys`, scoping to
      `current_setting('app.tenant_id')`, with `get_by_hash`/`get_user_by_email` correctly exempt
      (documented, not accidentally broken).
- [x] `SET LOCAL app.tenant_id` fires on every transaction via an engine/session-level hook (event
      listener on session-begin or connection-checkout), not a one-time connection-level `SET`.
      Implemented as a per-`Session(engine)` hook (each repository method opens its own `Session`
      and calls `_set_tenant_scope` as its first statement), not a SQLAlchemy `"checkout"` event
      listener — the Design section itself flagged `"checkout"` as one option but noted the
      per-transaction/session-`begin()` alternative; `"checkout"` fires before any per-request
      tenant_id is known (it only sees the raw pooled connection), so it structurally cannot carry
      the value this hook needs. See Outcome for how this was proven non-tautologically.
- [x] GW-004's SQLite implementation retained, unmodified in behavior. `sqlite_repository.py` was
      not touched; `tests/test_sqlite_repository.py` and `tests/test_repository_engine_memoization.py`
      (sqlite-only) pass unmodified.

## Outcome

Implemented, self-reviewed, and tested against a real Postgres instance (`localhost:5432`,
database `naive_first`, user `naive_first` — same credentials `infra/.env.example` documents for
Compose). Files touched: `services/gateway-api/migrations/env.py`,
`services/gateway-api/migrations/versions/0002_add_identity_rls.py` (new),
`services/gateway-api/src/app/repositories/postgres_repository.py` (new),
`services/gateway-api/src/app/dependencies/repositories.py`, `services/gateway-api/pyproject.toml`,
`services/gateway-api/tests/test_postgres_repository.py` (new), `services/gateway-api/README.md`.

**Three real bugs found and fixed during Test/Self-review, not assumed away:**
1. `migrations/env.py`'s original `search_path` fix executed `connection.execute(text("SET
   search_path ..."))` before `context.configure(...)`, which SQLAlchemy 2.0 Core implicitly
   "autobegins" as a transaction; without an explicit `connection.commit()`, closing the
   connection at the end of `run_migrations_online`'s `with` block silently rolled back *every*
   DDL statement the migration ran, even though Alembic itself reported success. First
   `alembic upgrade head` run against real Postgres produced zero tables/policies despite a clean
   "success" log — caught by manually inspecting `pg_class`/`pg_policies` after the run rather than
   trusting the log output.
2. `postgres_repository.py`'s `create_tenant`/`create_user`/`create_key` originally called
   `session.refresh(...)` after `session.commit()`, matching `sqlite_repository.py`'s pattern.
   Against Postgres with RLS enabled, this issued a second SELECT in a *new* transaction that
   `_set_tenant_scope` had not (yet) run against, which RLS then correctly blocked, surfacing as
   `InvalidRequestError: Could not refresh instance`. This is itself indirect proof the
   per-transaction scoping is real (a stale/leaked scope would have made the bug invisible). Fixed
   by building the returned record from the already-fully-populated in-memory object before
   `commit()`, removing the need for any post-commit round trip.
3. **Empirically discovered, not anticipated in the Design section**: Postgres does not revert a
   custom GUC like `app.tenant_id` to `NULL` when its `SET LOCAL`/`set_config(..., true)` scope
   ends — it reverts to `''` (empty string), but only once that GUC has been referenced at all on
   the session/connection (pooled connections make this the common case, not an edge case). The
   original RLS policy's `current_setting('app.tenant_id', true) IS NULL` fallback (for
   `get_by_hash`/`get_user_by_email`) was therefore silently broken the moment a connection had
   handled any prior tenant-scoped transaction — caught by the pooled-connection-reuse test itself
   (which is exactly the scenario this ticket cares about). Fixed by normalizing with
   `NULLIF(current_setting('app.tenant_id', true), '') IS NULL` in the RLS policy, and adjusting
   the leak-detection test's assertion to treat both `NULL` and `''` as "correctly cleared" while
   still failing on an actual leaked tenant id.

**Infra caveat flagged, not fixed here (out of this ticket's module)**: the `naive_first` Postgres
role this repo's infra provisions (`infra/docker-compose.yml`/`infra/.env.example`, via the
official Postgres image's `POSTGRES_USER` mechanism) is a **superuser** —
`SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = 'naive_first'` returns `(true, true)`.
Postgres superusers bypass RLS unconditionally, `FORCE ROW LEVEL SECURITY` included, so this
service's own repository code, run with the credentials `infra/` actually hands it today, would
never be blocked by RLS regardless of how correct migration 0002's policies are — RLS enforcement
against the *real* deployed infra is currently unverifiable and, as configured, ineffective. This
isn't a gap in the migration or `postgres_repository.py`; it's that INF-001 never provisioned a
second, non-superuser application role. Worked around *for this ticket's own tests only* by having
`tests/test_postgres_repository.py` create an ephemeral, test-scoped, `NOSUPERUSER NOBYPASSRLS`
role (dropped at teardown) so the RLS-proving tests are real proof rather than trivially passing
via superuser bypass. Recommend a follow-up infra ticket to provision a properly-scoped
application role and update `GATEWAY_API_DATABASE_URL` (and validation-service's equivalent, same
underlying gap) to use it instead of the superuser credentials.

Everything else in the Test acceptance criteria was directly verified against the real database,
not assumed: table/policy existence and `FORCE ROW LEVEL SECURITY` were checked via `psql` queries
against `pg_class`/`pg_policies`/`pg_roles`, not just alembic's own "success" log (see bug #1
above for why that log alone isn't trustworthy here); the pooled-connection-reuse property was
checked by asserting `pg_backend_pid()` equality across sequential `Session`s, not merely assumed
from `pool_size=1`.
