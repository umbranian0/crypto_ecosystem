## Analysis

Story: DBOPT-003 (`docs/product/backlog-db-optimization.md`). `PostgresSplitResultRepository.get_splits`
(`SELECT * FROM split_results WHERE run_id = :run_id AND tenant_id = :tenant_id ORDER BY split_index`)
backs `GET /runs/{id}/splits` (VS-008), the per-run drill-down every completed run's results page uses.
`split_results` is a TimescaleDB hypertable (INF-010, partitioned on `test_start`) with only its PK
`(id, test_start)` and TimescaleDB's own automatic `test_start` partitioning index — neither helps a
`run_id`/`tenant_id` filter, since `test_start` isn't part of this query's predicate.

Live-verified by the DBA: against the real table (108 chunks, 552 rows), the plan is an `Append` of 108
per-chunk `Seq Scan`s, and **Planning Time alone was 130ms** — chunk exclusion cannot help at all here
since `run_id` isn't the partitioning column, so every chunk's plan must still be built.

**Version-specific constraint the PM flagged**: the DBA's migration shape assumes a root-table
`CREATE INDEX` on a hypertable auto-propagates to all existing chunks and to future chunks via the
chunk template. Confirmed live by the Tech Lead before this ticket was written: the real running
container is `timescale/timescaledb:latest-pg16`, TimescaleDB extension version `2.29.1`, Postgres
`16.14` — root-level `CREATE INDEX` propagation to existing/future chunks has been standard TimescaleDB
behavior since well before 2.x. **This dev agent must still verify this live** (Test/Review AC below),
not rely solely on the Tech Lead's pre-ticket check, since the running container could differ by the
time this ticket executes.

**Live `EXPLAIN (ANALYZE, BUFFERS)`**, real query shape, real `run_id`/`tenant_id` with 68 real splits (`run_id=9a5ff274bf4c4269b5bd6f33bab8675b`, `tenant_id=b6b28f394c2249e28aa62d516d7b0081`), against the real 108-chunk table, 3 runs each side:

- **Before** (`0005`, no index): `Append` of 108 unindexed `Seq Scan`s, as the DBA's own finding described. Planning Time: 188-193 ms across 3 runs. Execution Time: ~4.2 ms.
- **After** (`0006`, index present): `Append` of 108 chunks, of which only 1 chunk (`_hyper_3_2_chunk`, the one holding the largest number of this run's rows) used an `Index Scan` on the new per-chunk index (`_hyper_3_2_chunk_ix_split_results_tenant_run`); the remaining 107 chunks still used `Seq Scan` -- the planner correctly judged a sequential scan cheaper than an index lookup on chunks holding only 1-16 rows each. Planning Time: 206-223 ms across 3 runs. Execution Time: ~4.0 ms.

**Honest finding, not fudged**: Planning Time did **not** drop below the DBA's ~130 ms baseline -- it stayed roughly flat to slightly *higher* after the index was added (188-193 ms before vs. 206-223 ms after, both already above the DBA's originally-measured 130 ms, and this repo's own current run showing higher-than-DBA's-baseline Planning Time even in the "before" state). Root cause: `run_id` is not `split_results`' partitioning column (`test_start` is), so TimescaleDB's chunk-exclusion planner cannot skip any of the 108 chunks either way -- a plan node must still be built per chunk regardless of whether an index exists on it, and with each chunk holding only a handful of rows, adding a second candidate access path (index vs. seq scan) per chunk gives the planner slightly *more* work to do during planning, not less. Execution Time was already negligible (~4 ms) before this migration and remains so after -- this migration does not meaningfully change end-to-end query latency on the *current* data volume; its value is prospective (as chunks grow rows, e.g. beyond real production data volumes, the per-chunk `Index Scan` path this migration now makes available will increasingly win over `Seq Scan`) and it also closes the missing RLS-`tenant_id` index gap described in the ticket's Implementation AC. This finding should be weighed by the Tech Lead against the ticket's Review AC wording ("materially lower Planning Time"), since the live data does not show that on this dataset.

**Chunk-propagation proof**: queried `timescaledb_information.chunks` joined against `pg_indexes` directly (not trusting the migration's success alone) -- `validation.split_results` has exactly 108 chunks, and **all 108** have a matching `<chunk>_ix_split_results_tenant_run`-named index with `tenant_id`/`run_id` in its definition. Sampled 10 of those chunk relations explicitly by name (e.g. `_hyper_3_1409_chunk` through `_hyper_3_1418_chunk`) and confirmed each individually via `pg_indexes`. These chunks all pre-date this migration (they are exactly the same 108 chunks the DBA's original live measurement found), so this is genuine proof of propagation to pre-existing chunks, not just future ones.
