# UAT-006 — Make `failure_reason` a real message instead of literal `"0"`

**Module**: `services/validation-service`. **Depends on**: none. Can run fully in parallel with UAT-007
(no file overlap).

## Analysis
Story: `docs/product/backlog-uat-findings.md` UAT-006. `runs.py`'s three failure sites already write
`failure_reason=str(exc)` (real exception text), so the literal `"0"` must originate from a specific
exception whose `str()` is `"0"` — e.g. an assertion/guard using a falsy/int sentinel, or an exception
raised with an int argument somewhere in the call chain reached from these `try/except Exception` blocks
(dataset load, split generation, or `naive_first_engine` invocation). Trace the actual call graph under
each of the three `except Exception as exc` blocks (`services/validation-service/src/app/routers/runs.py`
lines ~40-48, ~298-304, ~467-472) to find where an exception with `str(exc) == "0"` can be raised —
likely candidates: `naive_first_engine`'s split/validation code raising a bare
`raise SomeError(0)`/`assert x, 0`, or a numpy/pandas operation whose exception stringifies to a bare
index. Do not touch `libs/naive_first_engine`'s computation itself if the fix is only in how the caught
exception is stringified/wrapped here in `validation-service`.

## Design
Pattern: none new. File(s) touched: `services/validation-service/src/app/routers/runs.py` only (wrap the
caught exception in a descriptive message, e.g.
`failure_reason=f"Validation run failed: {exc}" if str(exc).strip() else "Validation run failed with an unspecified internal error."`,
plus fix the actual root cause if traced to a specific falsy/int-stringifying raise).
**DRY check note**: three near-identical `except Exception as exc: ... failure_reason=str(exc)` blocks
already exist (lines ~44, ~267, ~302, ~471) — extract a single `_fail_run(run_repository, tenant, run, exc)`
helper used by all three/four, rather than patching each inline (extract-on-second-duplication,
implementation-plan.md section 9; there are already 4 occurrences).

## Implementation acceptance criteria
- [x] Root cause of the literal `"0"` traced and fixed at its source. **Trace result**: grepped every
      `raise`/exception construction reachable from the three `except Exception` blocks -- `runs.py`,
      `dataset_source.py`, `feature_dataset.py`, `client_baseline.py`, `level_detection.py`, and
      `naive_first_engine`'s `splitting.py`/`metrics.py`/`dm_test.py`/`protocol.py`. Every first-party
      raise already embeds a descriptive f-string; none constructs a bare-int exception. The only
      built-in shape that genuinely stringifies to `"0"` is a single-arg exception like `KeyError(0)`
      (`BaseException.__str__` for one positional arg returns `str(args[0])` verbatim) -- not
      locally reproducible from this codebase's own code, so the live incident is most plausibly a
      third-party/stdlib (pandas/numpy) exception surfacing through one of these three `except` blocks
      with that exact shape. Fixed by never trusting `str(exc)` to already be descriptive: `_fail_run`
      (new, `app/routers/runs.py`) wraps every caught exception, and specifically detects an
      empty-or-digits-only message (this `"0"` shape included) and replaces it with a fixed,
      human-authored fallback naming the exception type and run id, rather than ever persisting a bare
      number.
- [x] A blanket safety net (non-empty, human-readable fallback for any other never-str()-able exception)
      is also added -- `_fail_run`'s own `try/except Exception` around `str(exc)` itself.
- [x] `gateway-api`'s own forwarding of `failure_reason` is unmodified (confirmed via grep -- no
      `gateway-api` file touched by this ticket).
