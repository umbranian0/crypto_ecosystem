# GW-002 — `identity` schema definition (`tenants`, `users`, `api_keys`)

**Status: done**

## Analysis
Story: GW-002 (Must), depends on GW-001 (done). Constraining docs: solution-design.md section 4 (schema sketch), backlog decision 2 (interim SQLite now, mirroring VS-004's precedent; Postgres is GW-012, Should, blocked on trigger #4), backlog AC (`api_keys` stores only `key_hash`, raw key never persisted). Precedent to follow exactly: `services/validation-service/src/app/models.py` (SQLAlchemy 2.0 declarative `Base`, backend-agnostic types, one schema shared by SQLite now/Postgres later) and its Alembic migration under `migrations/`.

## Design
Pattern: none new — this is the schema-per-service convention (implementation-plan.md section 5) made concrete, same as VS-002. Files: `src/app/models.py` (new — `Tenant`, `User`, `ApiKey` SQLAlchemy models sharing one `Base`), `alembic.ini` (new, copy validation-service's, `script_location = %(here)s/migrations`, default `sqlalchemy.url = sqlite:///gateway.db`), `migrations/env.py` (new, copy validation-service's, `target_metadata = Base.metadata` from `app.models`, `DATABASE_URL` env override), `migrations/script.py.mako` (new, copy validation-service's verbatim), `migrations/versions/0001_create_identity_schema.py` (new, hand-written or `alembic revision --autogenerate` equivalent, mirroring VS-002's `0001_create_validation_schema.py` style).

DRY check: grep `src/app/` before writing — only `__init__.py`/`main.py` exist from GW-001, nothing to reuse yet. Reuse validation-service's `models.py`/`alembic.ini`/`migrations/env.py` as *structural* templates (same tool, same pattern) — do not import them, this service owns its own schema file per "no service reads another service's schema" (CLAUDE.md).

Schema (binding, solution-design.md section 4 field-for-field):
- `tenants(id, name, created_at)` — `id: str` (uuid4 hex PK, mirrors `Run.id`'s PK precedent), `name: str not null`, `created_at: datetime not null`.
- `users(id, tenant_id, email, role, ...)` — `id: str` PK, `tenant_id: str not null` (FK to `tenants.id`), `email: str not null`, `role: str not null`, `created_at: datetime not null`. (`...` in the backlog AC covers no further mandatory field this sprint — GW-011's JWT login, Should/deferred, is the only consumer that would need a password/credential field, and this ticket does not invent one ahead of that story per "don't add unrequested fields.")
- `api_keys(id, tenant_id, key_hash, created_at, revoked_at)` — `id: str` PK, `tenant_id: str not null` (FK to `tenants.id`), `key_hash: str not null` (SHA-256 hex digest, this sprint's binding hashing decision — GW-002 only defines the column, GW-005/006 do the hashing), `created_at: datetime not null`, `revoked_at: datetime | None` (revocation is a flag, not a delete — GW-004/GW-010 need this). **No `key_plaintext`/`raw_key` column of any kind exists anywhere in this model** — the raw key is never persisted, per backlog AC3.

`users`/`api_keys` both denormalize `tenant_id` directly on the row (same rationale as `SplitResult.tenant_id` in validation-service: lets repositories filter by tenant without a join, and stops a leaked/misrouted id from reaching cross-tenant data). `tenants` creation is the one exception (a tenant doesn't have an id to scope by yet, per GW-003's own note) — this is a schema-level fact this ticket must reflect (no `tenant_id` column on `tenants` itself, obviously) but is otherwise a GW-003 concern.
