## Analysis

Confirmed by reading the actual current state: first-time setup today is a hand-run, multi-terminal
sequence reconstructed from `infra/README.md`'s prose — `docker compose up -d`, wait for Postgres
healthy (already gated by `depends_on: condition: service_healthy` for the two app services, but
migrations are not run automatically on container start), then `alembic upgrade head` by hand for
each service (order-sensitive before VS-013/GW-012's schema-scoped `alembic_version` fix, no longer
order-sensitive now that both `env.py`s target their own schema — confirmed by reading both
`env.py`s directly), then `provision_tenant.py` by hand inside the `gateway-api` container.

INF-016 now exists (sequenced immediately before this ticket) and owns the exact
`alembic upgrade head` invocation (interpreter, `DATABASE_URL` construction, working directory).
This ticket's script must call INF-016's `infra/migrate.sh both` / `infra/migrate.ps1 -Service both`
for its own migration step, not re-derive that invocation — per INF-016's own ticket text and
sprint-07.md's binding sequencing decision.

## Design

- Two scripts, `infra/bootstrap.sh` (bash) and `infra/bootstrap.ps1` (PowerShell), matching the
  repo's existing shell/PowerShell convention (no new Python entrypoint required before any
  service's own `.venv` exists).
- Steps, in order, each failing loudly (non-zero exit, clear message naming the failed step) rather
  than continuing silently:
  1. `docker compose -f infra/docker-compose.yml up -d postgres redis` (brings up the two
     infra-only pieces first).
  2. Poll/wait on `postgres`'s existing healthcheck passing (reuse the container's own
     `pg_isready`-based healthcheck via `docker compose ps --format ... postgres` / `docker inspect
     --format '{{.State.Health.Status}}' naive-first-postgres` in a bounded retry loop — not a new
     ad hoc `sleep`/port-probe).
  3. Call `infra/migrate.sh both` (or `infra/migrate.ps1 -Service both` on Windows) for the
     migration step — **not** a duplicated `alembic upgrade head` invocation. If this step fails
     (including the historical `alembic_version` collision INF-005 found, in case this script is
     ever run against migration sources that predate VS-013/GW-012's fix), the bootstrap script
     stops here with a clear, non-zero-exit error naming which service's migration failed — it must
     not silently continue to start the app containers against a partially-migrated database.
  4. `docker compose -f infra/docker-compose.yml up -d --build validation-service gateway-api`
     (starts, or restarts if already up, both app containers).
  5. Print `provision_tenant.py`'s exact invocation command as the final "next step" — does **not**
     auto-run it. This is a deliberate, explicit design choice (per the backlog's own reasoning):
     tenant provisioning mints a real, one-time-visible credential; an unattended script either
     loses that key permanently or normalizes treating credential creation as bootstrap noise.
- **Pattern/DRY check**: this script owns orchestration only (compose up, health-wait, ordering,
  final app container start/restart) — it delegates the one piece of logic that would otherwise be
  duplicated (the migration invocation) to INF-016's script. No other duplication introduced.
- **Role note**: per sprint-07.md's sequencing decision, this script references INF-014's final,
  concrete role names directly (no env-var abstraction) — but since the migration step is delegated
  entirely to INF-016's script (which itself already hardcodes the migration-time role,
  `naive_first`), this script has no direct role-name coupling of its own beyond documenting, in a
  comment, that migrations run as the migration-time role while the app containers it starts in
  step 4 connect at runtime as `naive_first_app` (INF-014) via `docker-compose.yml`'s own env-var
  wiring — nothing in this script's own body needs to name either role explicitly.

## Outcome

**Built**: `infra/bootstrap.sh` and `infra/bootstrap.ps1`, matching the five-step design above.
Both are pure orchestration — `docker compose up -d postgres redis`, a bounded (`30` attempts,
`2`s apart, `60`s total) `docker inspect --format '{{.State.Health.Status}}' naive-first-postgres`
poll loop, a delegated call to `infra/migrate.sh both` / `infra/migrate.ps1 -Service both` (no
re-derived `alembic upgrade head` invocation — grep confirms the only occurrences of the string
`alembic` in either script are in each script's own header comment, describing what step 3
delegates to; neither script ever invokes `alembic`/`python -m alembic` itself), `docker compose up
-d --build
validation-service gateway-api`, then a printed (never executed) `provision_tenant.py` command.
Each step is wrapped so a non-zero exit from that step's own command triggers a `fail`/`Fail-Step`
helper that prints `ERROR: bootstrap failed at step: <step name>` and exits non-zero, without
proceeding to the next step.

**`provision_tenant.py` invocation choice**: the script prints the **containerized** form —
`docker compose -f infra/docker-compose.yml exec gateway-api .venv/bin/python
scripts/provision_tenant.py --name "Your Tenant Name"` — matching `infra/README.md`'s own
full-stack-smoke-test section, not `gateway-api/README.md`'s host-venv form
(`.venv\Scripts\python.exe scripts\provision_tenant.py ...`). Rationale: this bootstrap script's
own step 4 just started `gateway-api` as a Compose container whose `DATABASE_URL` (per
`infra/docker-compose.yml`) points at the real Postgres `identity` schema via `naive_first_app`;
running `provision_tenant.py` from the host's own `.venv` instead would resolve
`app.dependencies.repositories`'s backend-selection logic against whatever `DATABASE_URL`/default
is set in the *host* shell (SQLite by default, a different, empty database from the one the
container the script just started is actually using) — so the containerized form is the only one
guaranteed to provision a tenant the just-started `gateway-api` container can actually see. Both
`bootstrap.sh`'s and `bootstrap.ps1`'s printed line use `.venv/bin/python` (POSIX path) because the
container image is Linux regardless of which host OS the bootstrap script itself runs on (confirmed
against `services/gateway-api/Dockerfile`, which sets
`ENV PATH="/repo/services/gateway-api/.venv/bin:${PATH}"`).
