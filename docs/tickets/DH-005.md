# DH-005 — Reject a configuration that produces zero splits

**Sprint**: 30. **Module**: `services/validation-service` (+ small `services/dashboard-web` extension).
**Status**: todo. **Priority**: Must. **Depends on**: none.
**File-overlap note**: touches `services/validation-service/src/app/routers/runs.py` (`create_run`)
and `services/dashboard-web/src/app/templates/run_new.html`'s split-estimate status block. DH-008
touches a *different* region of `run_new.html` (the Horizon-field hint) — land this ticket first per
the sprint plan's stated order so there is one committed baseline before DH-008 starts.

## Analysis

Backlog `docs/product/backlog-dataset-helpers.md` DH-005 (Must), finding #6: `create_run`'s RSS-004
guardrail only checks `split_count > MAX_SPLIT_COUNT`; there is no `== 0` check, so a configuration
that produces zero splits is silently accepted, persisted as `status="completed"` with zero
`split_results` rows, and is indistinguishable from a real (if uninteresting) null finding. This is a
request-shape guardrail, not a leakage or outcome-inspection concern (see backlog's own
"Leakage/honesty check" for this story) — no Harvey et al. correction or train/test boundary logic is
implicated.

## Design

**Pattern**: none of implementation-plan.md section 7's named patterns is newly invoked here — this
is a second boundary condition on RSS-004's existing guardrail code, not a new abstraction.

**Files touched** (both scoped to their own module, per implementation-plan.md section 3):
- `services/validation-service/src/app/routers/runs.py` — `create_run`, immediately alongside the
  existing `if split_count > MAX_SPLIT_COUNT:` block (lines ~266-276). Add `if split_count == 0:
  raise HTTPException(422, ...)` reusing the already-computed `split_count` variable — no second
  `generate_splits` call, no independently reimplemented formula.
- `services/dashboard-web/src/app/templates/run_new.html` — `computeEstimatedSplits()`'s existing
  branch that renders `"Approximately 0 split(s) estimated"` (currently reads as a valid-but-boring
  result). Add a distinct zero-split branch using the same `form-status-warn` CSS class already used
  for the over-cap case.

**DRY check note** (grepped `runs.py` before writing this ticket): `MAX_SPLIT_COUNT`'s existing
`if split_count > MAX_SPLIT_COUNT: raise HTTPException(422, ...)` block is the one thing to reuse the
*pattern* of (severity, status code, message shape) — not a shared helper function, since one 6-line
`if` block does not warrant extraction yet (DRY rule: extract on second duplication, and this is
literally the second occurrence of that same "compute once, branch twice" shape already established
by RSS-004 itself).

## Implementation acceptance criteria

- [ ] `create_run` raises `HTTPException(422, ...)` when `split_count == 0`, using the same
  already-computed `split_count` value RSS-004 (`> MAX_SPLIT_COUNT`) already computes — not a second
  independent computation.
- [ ] The `422` message states plainly that this configuration produces no splits and, where
  derivable, names the concrete cause by comparing `train_window + purge_gap_hours + test_window`
  against `len(series)` (the loaded series' actual row count) — e.g. "this dataset has 340 rows;
  train_window (360) + purge_gap (0) + test_window (40) = 400 exceeds that, so 0 splits would result.
  Reduce train_window/test_window or choose a dataset with more rows."
- [ ] Additive to RSS-004's existing guardrail — the existing `> MAX_SPLIT_COUNT` branch is untouched
  byte-for-byte except for the new sibling `if` block.
- [ ] No run row is created and `run_validation_protocol` is never invoked when this guardrail fires
  (same "reject before persisting anything" behavior RSS-004 already established for the over-cap
  case).
- [ ] `dashboard-web`'s `computeEstimatedSplits()` renders a distinct message when the live estimate is
  exactly `0` ("this configuration would produce no splits — widen the dataset's range, reduce
  train/test window, or reduce purge gap"), styled with the existing `form-status-warn` class, replacing
  the current "Approximately 0 split(s) estimated" wording for that specific case only — the non-zero
  estimate wording/styling is unchanged.
