# DH-002 — Detect and disclose exact full-row duplicate timestamps (local-file/inline/object-storage only)

**Sprint**: 30. **Module**: `services/validation-service` (+ `services/dashboard-web` rendering,
reusing DH-001's plumbing). **Status**: done. **Priority**: Should.
**Depends on**: DH-001 (reuses its `LoadedSeries`/`warnings` persistence plumbing directly — do not
re-derive it). **Blocks**: DH-003 (its conflict check runs on this ticket's deduped series).

## Analysis

Backlog DH-002 (Should), finding #3: exact full-row duplicate `(timestamp, value)` rows are silently
kept today, inflating `row_count` and distorting the splitter's window math. Per the backlog's own
"Leakage/honesty check," this is the one auto-fix in this backlog classified as mechanically safe by
construction — a byte-identical repeated row carries no additional information, so dropping it (first
occurrence kept) cannot change what the surviving data says. This distinguishes it from DH-090/091/092
(Won't-fix): those require a genuine judgment call, this does not.

## Design

**Pattern**: extends DH-001's `LoadedSeries`/warnings shape — no new pattern.

**Files touched** (scoped to `services/validation-service`, reusing DH-001's already-shipped
persistence path unchanged):
- `services/validation-service/src/app/dataset_source.py` — `_build_series` (or a small helper it
  calls), **after** DH-001's reordering check and **before** DH-003's conflict check (per the
  backlog's own required sequencing: dedup first, conflict-detection on the deduped result second):
  detect rows identical on both timestamp and value (index value + series value both equal), drop all
  but the first occurrence, append `f"dropped {n} exact-duplicate rows before validation"` to the
  warnings list when `n > 0`.
- No `services/validation-service` repository/contract change needed — `LoadedSeries.warnings` and its
  persistence already exist from DH-001; this ticket only adds a second string to the same list.
- `services/dashboard-web/src/app/templates/run_detail.html` — no template change needed if DH-001
  already renders `run.warnings` as a list (confirm this at implementation time; if DH-001 rendered a
  single warning string instead of iterating a list, this ticket fixes that to iterate, since multiple
  warnings can now coexist).

**DRY check note** (grepped `dataset_source.py` before writing this ticket): reuses DH-001's
`LoadedSeries` dataclass and the same warnings-list-append pattern — no second warnings mechanism, no
second field on the response/persistence layer.

## Implementation acceptance criteria

- [x] `_build_series` drops exact `(timestamp, value)` duplicates (first occurrence kept), reporting the
  count via the existing `LoadedSeries.warnings` list — `"dropped 3 exact-duplicate rows before
  validation"` (exact row count in the message), only appended when the count is `> 0`.
- [x] Scoped to `InlineOrLocalFileDatasetSource`/`ObjectStorageDatasetSource` only (both go through the
  same reused `_build_series`) — `IngestionServiceDatasetSource` is untouched (stored datasets already
  can't have this problem per the DB's `(tenant_id, source, event_time)` key, backlog finding #1); no
  redundant check added there.
- [x] The dedup runs **before** any split-count computation — `create_run`'s RSS-004/DH-005 guardrail
  (`split_count = len(generate_splits(series.index, ...))`) sees the post-dedup series, not the
  original, since it already operates on whatever `series` the load returned; confirm no second,
  pre-dedup row count leaks into that guardrail (it shouldn't, since `create_run` only ever sees the
  one `LoadedSeries.series` DH-001 already wired through).
- [x] Both DH-001's reordering warning and this ticket's dedup warning can coexist in the same
  `warnings` list for one load (e.g. an out-of-order file that also has exact duplicates) — verified by
  a test, not just asserted.

## Test acceptance criteria

- [x] Unit tests: dataset with one exact duplicate pair → warning present with correct count, series has
  the duplicate removed (length check); dataset with no duplicates → no dedup warning; dataset with both

- [x] A test proves a dataset that drops below `train_window + purge_gap + test_window` **after** dedup
  triggers DH-005's `422` using the post-dedup row count (construct a case where the pre-dedup count
  would have produced 1 split but the post-dedup count produces 0).
- [x] `uv run pytest -q` clean, zero regressions.
