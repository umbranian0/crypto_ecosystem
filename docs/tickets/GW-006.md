# GW-006 — API-key authentication

**Status: done**

## Analysis
Story: GW-006 (Must), depends on GW-005. Constraining docs: sprint-05.md's binding note (SHA-256, never bcrypt/argon2/scrypt — reasoning already recorded, not open for re-litigation), backlog AC (missing/malformed/unknown/revoked key -> 401 before any downstream call; valid key resolves to a `TenantContext`-equivalent value; comparison against stored hash only, never plaintext, never logged), backlog decision 3 (this is the literal mechanism LC-009's rationale names as the gap header-based trust downstream isn't the final design — this ticket is what makes that gap real, not LC-009 itself, which stays deferred). This is one of the two extra-sensitive tickets the Tech Lead personally verifies beyond the standard review pass.

## Design
Pattern: **Dependency Injection** (FastAPI `Depends()`), same mechanism as `naive_first_common.get_tenant_context`'s own precedent (`libs/common/src/naive_first_common/tenant_context.py`) but this is `gateway-api`'s own resolver, not a call into that module — GW-006 authenticates against `api_keys.key_hash`, which `naive_first_common` knows nothing about and must not be taught to know about (that would violate decision 3's boundary). File: `src/app/dependencies/auth.py` (new).

Header contract: reads `Authorization` (`Bearer <key>` scheme) or `X-Api-Key` (raw key) — implementer's choice per backlog wording ("`Authorization`/`X-Api-Key`-supplied key"); decision made: support both, `Authorization: Bearer <key>` checked first, `X-Api-Key` as fallback, since a caller reasonably might use either and the backlog doesn't force picking exactly one to the exclusion of the other. Missing both -> 401. Malformed (e.g. `Authorization` present but not `Bearer `-prefixed, or an empty key) -> 401. Hash the presented key with `hashlib.sha256(...).hexdigest()`, call `ApiKeyRepository.get_by_hash`. `None` result (unknown key) -> 401. Non-`None` but `revoked_at is not None` -> 401. Otherwise, resolve `tenant_id` from the record and return a value carrying it (decision: reuse `naive_first_common.TenantContext` itself as this ticket's "`TenantContext`-equivalent value," since `gateway-api` already depends on `naive_first_common` (GW-001) and the shape is identical — constructing a second, parallel value type here would be exactly the kind of duplicate shape DRY (implementation-plan.md section 9) warns against; GW-007 forwards this same object).

Never logs the presented key at any point (raw or partially) — only the resulting `tenant_id` (post-authentication) may appear in any log/error path. Comparison is exclusively hash-to-hash (`get_by_hash` does an exact SQL match, GW-004) — no `==` against a raw stored key anywhere, because no raw key is ever stored (GW-002/GW-004).

## Implementation acceptance criteria
- [x] `src/app/dependencies/auth.py`: a `get_authenticated_tenant` FastAPI dependency reading `Authorization`/`X-Api-Key`, hashing with SHA-256, resolving via `ApiKeyRepository.get_by_hash`.
- [x] Missing, malformed, unknown, or revoked (`revoked_at is not None`) key -> `HTTPException(401)` raised before any downstream/routing code runs.
- [x] Valid key resolves to a `naive_first_common.TenantContext` (or a documented equivalent, if a concrete reason to diverge surfaced during implementation — must be justified in this file, not silent) carrying the key's `tenant_id`. (No divergence needed; `TenantContext` reused directly, per the Design section.)
- [x] No line of code anywhere in `auth.py` (or anything it calls) logs, prints, or includes the presented raw key in an exception message.
