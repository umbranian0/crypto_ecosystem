# MR-012 — Widen the real-data window MR-008/MR-009 used, re-run at 1h/6h/24h

Status: done

Source story: `docs/product/backlog-model-research.md` MR-012. Sprint: `docs/sprints/sprint-52.md`.

## Analysis

- Story: "As a research candidate model already validated on the 209-day/5,026-row real window
  (MR-008/MR-009), I want the same `LightGBMBaseline`/`RegimeHMMBaseline` runs re-executed at 1h/6h/24h
  against a materially longer slice of the real `binance_price_btcusdt_1h` series, so that the MR-008/
  MR-009 finding is checked against a window that includes more market regimes, using the exact same
  pipeline and zero new model code."
- Acceptance criteria (backlog, verbatim):
  1. Date-range bound widened from MR-008's `2026-01-10`–`2026-08-07` window to a new, explicitly disclosed
     range/row count, staying within MR-008's CPU-only, sub-5-minute compute ceiling (not the full
     ~78,500-row history).
  2. Same `research/`-owned HTTP client (`load_real_hourly_returns`), no new connector, no
     `IngestionServiceDatasetSource` import.
  3. `pct_change().dropna()` applied before any Naive0 comparison.
  4. Same purge-gap values as MR-008 (`purge_gap=6` for 1h/6h) and MR-009 (`purge_gap=24` for 24h).
  5. `research/models/*.py` untouched.
  6. DM-vs-Naive0 verdict counts reported for all three horizons.
  7. Hard gate restated verbatim, honored.
- Depends on: MR-008 (done), MR-009 (done) — reuses their pipeline/data-source function unchanged.
- Constrains solution: implementation-plan.md section 7 Strategy pattern (baselines are swappable
  Strategy implementations, unmodified here); CLAUDE.md's service-boundary rule (research/ never imports
  `services/*`'s `app.*` code); this backlog's own compute-budget-discipline precedent (MR-004's 3,000-row
  cap, MR-008's 209-day cap) — widen deliberately, disclose the bound, don't default to "use everything."

## Design

- Design pattern: **Strategy** (implementation-plan.md section 7) — reuses the existing, unmodified
  `LightGBMBaseline`/`RegimeHMMBaseline` `Baseline` implementations via `config.extra_baselines`, exactly
  as MR-008/MR-009 already established. No new Strategy implementation.
- File touched (new): `research/tests/test_real_data_mr012.py` — three runs (horizon=1, 6, 24) against a
  wider real bounded window, reusing `research/real_data.py::load_real_hourly_returns` unmodified.
- **DRY check (dev agent must state this explicitly)**: grep `research/tests/` before writing anything —
  `test_real_data_mr008.py` and `test_real_data_mr009.py` both already define their own small
  fetch-and-transform helper inline (MR-009 explicitly chose not to extract a shared fixture, see its own
  Design section's "DRY choice" note). Follow that same precedent: reuse `load_real_hourly_returns`
  (`research/real_data.py`, unmodified) and `research/models/gradient_boosting.py::LightGBMBaseline`,
  `research/models/regime_hmm.py::RegimeHMMBaseline` (import directly, zero changes), and
  `naive_first_engine`'s `Baseline` Protocol/`ValidationConfig`/`run_validation_protocol`/`dm_test` (import
  and use directly). Do not touch or duplicate MR-008/MR-009's own test files.
- **Per this sprint's ML-adjacent-ticket routing rule**: this ticket re-runs a model/pipeline consumed via
  `naive_first_engine`'s `Baseline`/`extra_baselines` contract on a wider data source, so the dev agent
  follows `/ml-engineer`'s design→test→review sequencing and `/ml-feature-planning`'s train-only-fitting
  discipline. Tech Lead review personally checks: train-only splitting still holds on the wider real
  series (re-verified, not assumed carried over from MR-008/MR-009), no `.fit()` reaching outside the
  current split, no leakage into the DM-test error series, purge-gap values match exactly (6 for 1h/6h, 24
  for 24h — no narrowing to fit more splits into the compute budget).

## Compute-budget scoping decision for MR-012 (binding, Tech-Lead-verified against the live stack)

- **Tenant/source**: same as MR-008/MR-009 — `tenant_id="271d391dd7bf4213b3e5fb8ea6636563"`,
  `source="binance_price_btcusdt_1h"`, `field` omitted (defaults to `close`).
- **Widened date-range bound**: `start="2024-08-08T09:00:00"`, `end="2026-08-07T09:00:00"` — a 730-day
  (~2-year) window ending at the exact same end timestamp MR-008/MR-009 used, extended backward to
  materially include the 2024–2025 halving-cycle regime shift MR-008's 209-day window did not cover. The
  Tech Lead independently confirmed via a live `GET /datasets/binance_price_btcusdt_1h/series` call against
  the running `naive-first-ingestion-service` container that this window returns **17,497 raw rows**
  (17,496 returns after `.pct_change().dropna()`) — ~3.5x MR-008's 5,026-row window, not the full
  ~78,500-row/9-year history (still declined for compute-budget reasons, consistent with MR-008's own
  precedent).
- **Returns transform**: `raw_series.pct_change().dropna()`, applied by the caller (not inside
  `real_data.py`), consistent with MR-008/MR-009.
- **`ValidationConfig`**: `train_window=500, test_window=50, step=250` (identical to MR-008/MR-009);
  `purge_gap=6` for horizon=1 and horizon=6, `purge_gap=24` for horizon=24 — unchanged from MR-008/MR-009,
  no narrowing.
- **Expected split count**: with `train_window=500, test_window=50, step=250` over ~17,496 returns, this
  widened window is expected to produce roughly 3.5x MR-008/MR-009's 18 splits per horizon (~60-67 splits)
  — the dev agent must report the exact split count actually produced, not assume this estimate.
- **Expected runtime ceiling**: same discipline as MR-008/MR-009 — under 5 minutes for the full new test
  file (three horizons). Given MR-008/MR-009's per-split cost (~0.15-0.4s/split observed), ~60-67 splits x
  3 horizons is expected to comfortably clear this ceiling, but the dev agent must time its own full pytest
  run and report the actual wall-clock seconds. **If the measured runtime approaches or exceeds 5 minutes,
  the dev agent must stop, not silently narrow the window or the purge gap, and report the actual bound
  reached back to the Tech Lead** — per this ticket's own binding compute-budget-scoping requirement (no
  purge-gap narrowing permitted as a fallback).
- **Hyperparameters**: identical, fixed, no search — `LightGBMBaseline`/`RegimeHMMBaseline` used exactly as
  already implemented, zero parameter changes.
- **CPU-only. Horizons: 1, 6, and 24** (all three, unlike MR-008/MR-009 which split 1h/6h and 24h across
  two tickets — this ticket covers all three in one pass since it is a pure data-window re-run of an
  already-proven pipeline, not new protocol work).
