## Analysis

Story: log auth events (key issued, key revoked, failed auth attempts) with `tenant_id`/`timestamp`/
`outcome`, so there's a record to point to when a client or auditor asks "who could access this."
Acceptance criteria (verbatim):
- Key issuance, revocation, and failed-auth attempts are logged with `tenant_id`, `timestamp`, and
  `outcome` — no raw keys or secrets in the log line.
- Logging uses whatever structured-logging convention the rest of the platform already uses.

**Non-negotiable care condition**: build directly on `OPS-006`'s structured-logging convention rather
than inventing a second, parallel logging shape. No raw keys/secrets in any log line. No log
retention/shipping to any external system — stays "structured local log line," not "compliance-grade
retained audit trail."

**Three call sites, per the sprint's own dependency analysis** (state this plainly, do not
re-derive): key issuance — `scripts/provision_tenant.py` (GW-005, done); failed-auth — `dependencies/
auth.py`'s `get_authenticated_tenant` (GW-006, done); revocation — `scripts/revoke_api_key.py`
(GW-010, this sprint, Round 2 — **must already exist on disk** when this ticket starts, since this
ticket instruments a file GW-010 creates).

## Design

**Pattern**: none new from section 7 — this is instrumentation added to three already-existing call
sites, using `OPS-006`'s already-built logging convention (`naive_first_common.logging`'s
`configure_structured_logging`/structured `logging` calls). This ticket must not define its own
formatter, its own correlation-id mechanism, or its own log-shipping code — all of that is `OPS-006`'s
job, already done by the time this ticket starts.

**What "log" means here, concretely**: a `logging.getLogger(__name__).info(...)` (or `.warning(...)`
for failed-auth, matching typical severity conventions) call at each of the three sites, with a
structured `extra={...}` payload (not string-interpolated into the message) of exactly: `tenant_id`
(or `None`/omitted when not yet resolved — e.g. an unknown-key failed-auth attempt has no `tenant_id`
to log, only the fact that authentication failed), `timestamp` (ISO-8601, though `OPS-006`'s JSON
formatter may already inject this automatically — read its implementation first and don't duplicate a
timestamp field the formatter already adds), `event_type` (one of `"api_key_issued"`,
`"api_key_revoked"`, `"auth_failed"`), `outcome` (`"success"`/`"failure"`, redundant with
`event_type` for the first two but meaningful for a future richer `auth_failed` breakdown — keep it
simple, a fixed string per call site is fine).

**Files touched** (exactly the three call sites plus one new test file plus README — no new module):
- `services/gateway-api/scripts/provision_tenant.py` — one new log call in `provision()`, after
  `create_key` succeeds.
- `services/gateway-api/scripts/revoke_api_key.py` (GW-010's new file, must already exist) — one new
  log call in `revoke()`, after `revoke_key` succeeds.
- `services/gateway-api/src/app/dependencies/auth.py` — one new log call in
  `get_authenticated_tenant`, on each of the existing `401` conditions (missing/malformed header,
  unknown key, revoked key) — **before** raising `_UNAUTHORIZED`, not after (a raised exception must
  not skip the log call).
- `services/gateway-api/tests/test_audit_logging.py` (new).
- `services/gateway-api/README.md`.

**DRY check performed**: read `OPS-006`'s shipped `libs/common/src/naive_first_common/logging.py`
(must exist by the time this ticket starts) — reuse its `configure_structured_logging`/JSON-formatter
setup as-is; do not construct a second `Formatter`/`logging.config` call anywhere in this diff. Read
`auth.py`'s existing four `raise _UNAUTHORIZED` call sites (missing both headers; malformed
`Authorization`; empty `X-Api-Key`; unknown/revoked key) — this ticket adds a log call immediately
before each, not a refactor of the auth flow itself.

**No raw keys/secrets, structurally**: `auth.py`'s log calls must reference the resolved `record.tenant_id`
(when available) or a fixed literal like `"unknown"`/omit the field — **never** `raw_key`,
`key_hash`, or any variable derived from the presented credential. `provision_tenant.py`'s log call
references `tenant.id`/`tenant.name`, never `raw_key`. `revoke_api_key.py`'s log call references
`record.tenant_id`/`record.id`, never the raw key the operator passed in. This mirrors the existing,
already-enforced "raw key never logged/printed" rule in both scripts and `auth.py`'s own module
docstring — this ticket extends that rule to the new log calls, it does not relax it.

## Implementation acceptance criteria

- [x] `provision_tenant.py`'s `provision()`: after `api_key_repo.create_key(...)` succeeds, logs
  `event_type="api_key_issued"`, `outcome="success"`, `tenant_id=tenant.id` — no raw key in the log
  call's arguments or `extra` payload.
- [x] `revoke_api_key.py`'s `revoke()`: after `api_key_repo.revoke_key(...)` succeeds, logs
  `event_type="api_key_revoked"`, `outcome="success"`, `tenant_id=record.tenant_id` — no raw key.
- [x] `auth.py`'s `get_authenticated_tenant`: each of the four `401` paths logs
  `event_type="auth_failed"`, `outcome="failure"`, and `tenant_id=record.tenant_id` when a key record
  was actually resolved (the revoked-key case) or omitted/`None` for the three cases where no record
  was ever resolved (missing header, malformed header, unknown key) — never a raw key anywhere in any
  of the four log calls.
- [x] All new log calls use `logging.getLogger(__name__)` (module-level logger, matching
  `events.py`'s existing pattern) and rely on `OPS-006`'s already-configured JSON formatter/
  correlation-id injection — no new `Formatter`, no new `logging.basicConfig`/`logging.config` call
  anywhere in this diff.
- [x] No log-shipping/retention code (no file handler pointed outside stdout, no HTTP call to an
  external logging service, no new dependency) is added anywhere in this diff.

**One real, disclosed gap found and fixed by the Tech Lead, not present in the dev agent's own
diff**: the live end-to-end check above initially found `api_key_issued`/`api_key_revoked` produced
**no visible output at all** when `provision_tenant.py`/`revoke_api_key.py` were run for real as
standalone CLI processes (their actual real-world invocation, per GW-005/GW-010's own "standalone
script, not through FastAPI's request cycle" design) — `auth_failed` worked correctly because it
runs inside the already-running FastAPI process, which calls `configure_structured_logging()` at
`app.main` import time, but neither CLI script ever imports `app.main` or calls that function
itself. Python's `logging` module attaches no handler to the root logger by default, and its
"handler of last resort" only surfaces `WARNING`+, not the `INFO`-level calls these two scripts use
— so the audit events were silently dropped in real operator usage, even though
`test_audit_logging.py`'s `caplog`-based tests passed (`caplog` captures log records regardless of
handler configuration, masking exactly this gap). **Fixed**: both scripts now call
`configure_structured_logging()` at the top of their own `main()`, reusing OPS-006's exact
convention (no second logging shape). Re-verified live after the fix: all three event types now
appear correctly. Full suite re-confirmed clean after the fix: 98/98.
