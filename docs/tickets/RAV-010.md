**Majority rule (explicit, per this ticket's own Analysis-section instruction)**: a run counts as
having beaten Naive0 if strictly more of its splits fall in the "better" `dm_verdict` category than
in "worse" and "no significant difference" *combined*. Splits whose DM statistic is genuinely
undefined (both `dm_statistic`/`dm_pvalue` `None`, RAV-003's `UNDEFINED_VERDICT_CATEGORY`) are
excluded from both sides of the count — never defaulted into "worse" — and a run with no evaluable
split contributes to neither `beat_count` nor `total_count`. See `_run_beats_naive0`'s docstring in
`charting.py` for the same statement in code.

## Analysis

`SplitResultResponse.dm_verdict` (per split) is already fetched by RAV-009's own trend-view route
for every completed run in the selected group. This ticket computes, client-side (dashboard-web),
"beat Naive0 in N of M completed runs" where a run counts as "beat Naive0" if a majority of its own
splits have `dm_verdict == "better"` (dev's call on the exact majority rule — document it explicitly
in the ticket's implementation notes; e.g. strictly more "better" than "worse"+"no significant
difference" combined, or more "better" than any other single category — either is defensible, but
must be stated, not left implicit). No new significance test is computed outside
`naive_first_engine`'s existing Harvey-corrected DM test — this ticket only counts already-computed
verdicts.

## Design

**Pattern**: none from implementation-plan.md section 7 applies — read-only rendering addition.

**Files touched** (scoped to `services/dashboard-web` only):
- `services/dashboard-web/src/app/charting.py` — new pure function
  `compute_consistency_indicator(runs: list[tuple[RunSummaryResponse, list[SplitResultResponse]]])
  -> ConsistencyIndicator` (dataclass with `beat_count: int`, `total_count: int`, and a
  `has_data: bool`/similar flag distinguishing "zero runs matched" from "0 of 0"), reusing
  `_verdict_category`'s per-split None-DM handling (RAV-003) so a split whose DM statistic is
  undefined is never silently counted as "worse"/"no significant difference" when determining a
  run's own majority verdict.
- `services/dashboard-web/src/app/routers/runs.py` — RAV-009's trend-view route also calls
  `compute_consistency_indicator` on the same already-fetched per-run split data and passes the
  result to the template — no second fetch.
- `services/dashboard-web/src/app/templates/runs_list.html` (or RAV-009's new adjacent template) —
  renders the indicator ("beat Naive0 in N of M completed runs") next to RAV-009's chart; a
  zero-match selection (no group selected yet, or a selected group with zero completed runs) states
  plainly "no completed runs matched this selection" — never a fabricated "0 of 0" or "0% beat
  naive" framing.

**DRY check**: reuses RAV-003's `_verdict_category`/`UNDEFINED_VERDICT_CATEGORY` for per-split
categorization rather than a second None-DM rule; reuses RAV-009's already-fetched per-run split
data rather than a new `GET /runs/{id}/splits` call.

## Implementation acceptance criteria (carried over from the backlog story)

- Computed client-side from already-fetched `dm_verdict` values across the selected runs' splits —
  no new backend statistic, no new significance test computed outside `naive_first_engine`'s
  existing Harvey-corrected DM test.
- Explicitly framed as a descriptive count/ratio of past outcomes ("beat Naive0 in N of M completed
  runs"), never as a probability of future performance, a confidence score, or a recommendation.
- If zero runs match the selected grouping, states that plainly — never a fabricated 0/0 ratio
  rendered as "0% beat naive."

## Test acceptance criteria

- Unit test(s) for `compute_consistency_indicator` against a fixture set of runs with known verdict
  distributions (some runs majority-"better", some majority-"worse"/mixed, one run entirely
  `UNDEFINED_VERDICT_CATEGORY` splits) asserting the correct `beat_count`/`total_count`.
- A fixture with zero selected runs (or zero completed runs in the selected group) asserts the
  indicator's `has_data` flag is `False` and the route renders the "no completed runs matched" copy,
  not "0 of 0".
- Route-level test asserting the indicator's rendered text matches the fixture's known N/M values.
