# VS-021 — Fix `PostgresValidationRunRepository.create_run`'s post-commit `session.refresh()` losing RLS's per-transaction `app.tenant_id` scope

Status: **done** (dev-agent Implementation/Documentation phases complete; Test/Review criteria requiring the live RLS-enforced stack personally verified by the Tech Lead - see Outcome)
Backlog: not yet in `docs/product/backlog-validation-service.md` — a real, disclosed, production-breaking regression surfaced during Sprint 07's INF-014 work and reconfirmed live during Sprint 08 close-out (see `docs/tickets/INF-014.md`'s Outcome section, and `docs/tickets/README.md`'s Sprint 07 outcome). Treated with Must-equivalent urgency per INF-014's own escalation language, even though no backlog file carries it yet.
Sprint: docs/sprints/sprint-09.md (runs first, no dependency on anything else in this sprint)
Depends on: INF-014 (done — non-superuser `naive_first_app` Postgres role, RLS genuinely enforced)

## Analysis

Confirmed by reading the actual current state (not assumed):

- `services/validation-service/src/app/repositories/postgres_repository.py`'s `PostgresValidationRunRepository.create_run` (lines 77-101) calls `session.commit()` then `session.refresh(run)` before returning `_run_to_record(run)`.
- Every transaction opened by this module's `_tenant_scoped_session` helper issues `SELECT set_config('app.tenant_id', :tenant_id, true)` as its first statement (`set_config`'s third argument `true` = `SET LOCAL` semantics: scoped to that one transaction, reverts at `COMMIT`/`ROLLBACK` by design — see the module's own docstring, lines 25-36). `session.commit()` ends that transaction, so the `app.tenant_id` GUC reverts. `session.refresh(run)` then issues a brand-new `SELECT` in a **new** transaction that never re-runs `set_config`, so `migrations/versions/0002_add_row_level_security.py`'s `tenant_isolation` RLS policy correctly (if surprisingly, from the caller's point of view) hides the row that transaction just inserted. SQLAlchemy raises "could not refresh instance," which FastAPI's default exception handling surfaces as an HTTP `500`.
- This was invisible before INF-014 (Sprint 07) because both services connected to Postgres as `naive_first`, a Postgres superuser — Postgres unconditionally exempts superusers from RLS regardless of `FORCE ROW LEVEL SECURITY`, so this fail-closed behavior never triggered. INF-014 repurposed the runtime `DATABASE_URL` credential to `naive_first_app` (`NOSUPERUSER NOBYPASSRLS`), making RLS genuinely enforced against the app's real traffic — and exposed this bug live (confirmed: `POST /runs` through the real running `gateway-api` → `validation-service` chain, row correctly persisted and tenant-isolated per a direct superuser `psql` read, but the HTTP response was `500`).
- This is a **response-construction bug only** — not a data-loss or isolation bug. `get_run`/`update_run_status` on the same class are unaffected: `get_run` runs its `SELECT` inside the same tenant-scoped transaction that set `app.tenant_id` (no post-commit refresh involved), and `update_run_status` never calls `refresh()` at all.
- Constrained directly by CLAUDE.md's DRY rule (implementation-plan.md section 9: "DRY within a module's own boundary, always ... gets extracted ... as soon as it appears a second time") and by the cross-module precedent this ticket must mirror, not reinvent.

## Design

- **No new design pattern needed** — this is a bug fix inside the existing Repository pattern (implementation-plan.md section 7), applying a pattern already proven correct in this same codebase rather than introducing anything new.
- **File touched**: `services/validation-service/src/app/repositories/postgres_repository.py`, `PostgresValidationRunRepository.create_run` only. Scoped to this one service/file — no other module touched, per the Tech Lead's one-ticket-one-module rule.
- **DRY check (performed, not assumed)**: grepped `postgres_repository.py` for `session.refresh(` — the only occurrence is in `create_run`. `PostgresSplitResultRepository.add_splits`/`get_splits` never call `refresh()`. No existing helper in this module already avoids the post-commit-refresh pitfall; the fix pattern to mirror lives in a **different module** (`services/gateway-api`), so per implementation-plan.md section 9 the correct move is to copy the *pattern* (build the record from the already-fully-populated pre-commit object) into this module's own file, not to import code across the service boundary — services never import another service's code, only `libs/*` are shared, and this one-line pattern doesn't rise to the level of extracting a new `libs/common` helper for a single call site.
- **Fix**: build the returned `RunRecord` (via the existing `_run_to_record(run)` helper, already imported from `sqlite_repository`) from the already-fully-populated `run` ORM object **before** `session.commit()`, exactly mirroring `services/gateway-api/src/app/repositories/postgres_repository.py`'s `PostgresTenantRepository.create_tenant`/`PostgresUserRepository.create_user` (GW-012):
  ```python
  with _tenant_scoped_session(self._engine, tenant_id) as session:
      session.add(run)
      # Record built from the already-fully-populated object, not a
      # post-commit session.refresh(): every column here is set
      # client-side (no server-generated defaults - id/created_at are
      # both generated in Python above), and refreshing after commit()
      # would issue a new SELECT in a *new* transaction this class's own
      # _tenant_scoped_session has not (yet) re-scoped with
      # set_config('app.tenant_id', ...) - which RLS would then
      # correctly, if surprisingly, block. See gateway-api's
      # PostgresTenantRepository.create_tenant/PostgresUserRepository.create_user
      # (GW-012) for the identical precedent, and VS-021/INF-014 for the
      # root cause.
      record = _run_to_record(run)
      session.commit()
      return record
  ```
  This works because every column on `Run` (`id`, `tenant_id`, `dataset_id`, `horizon`, `purge_gap_hours`, `split_config`, `status`, `created_at`, `completed_at`, `failure_reason`) is already set client-side in Python before `session.add(run)` (confirmed by reading the constructor call in `create_run`, lines 85-96) — there is no server-generated default (no DB-side `DEFAULT`/sequence/trigger) that only becomes visible after `INSERT`, so nothing is lost by not refreshing.
- No change to `get_run`, `update_run_status`, or either method on `PostgresSplitResultRepository` — none of them exhibit this pattern.
