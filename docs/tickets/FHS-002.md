## Analysis

Per ADR-0007: a horizon selector (7/15/30 days) converts to `horizon` values 168/360/720 (hourly
sampling, `ASSUMED_SAMPLING_INTERVAL_HOURS = 1`, named/commented, not a magic number) and filters
the tenant's own completed runs by that value. No new backend call — `GET /runs` (gateway-api
`GW-016`) already returns every run's `horizon` via the shared `RunSummaryResponse`
(`libs/common/src/naive_first_common/contracts.py`), already parsed by `runs_list`
(`services/dashboard-web/src/app/routers/runs.py`). This ticket adds a **new page**,
`/runs/horizon-summary`, rather than overloading `/runs` itself — keeps `runs_list.html`
(FHS-002-untouched) and the new filtered view (which needs its own empty-state copy, distinct from
`runs_list.html`'s generic "no validation runs yet") as two clear, separately testable templates,
consistent with this backlog's own "don't over-specify UI placement, Tech Lead's call" note.

## Design

**Pattern**: none of Strategy/Repository/Adapter/Factory/Observer applies — plain server-side
templating and a client-side (this router's) filter over an already-fetched list, same DI seam
(`DownstreamHeadersDep`/`GatewayApiUrlDep`) every other route in this file already uses.

**Files touched** (scoped to `services/dashboard-web` only):
- `services/dashboard-web/src/app/routers/runs.py` — new `GET /runs/horizon-summary` route,
  registered near `runs_list` (readability, no path collision with `/runs/new` or `/runs/{run_id}`
  either way — `horizon-summary` is a distinct literal segment). Reuses `_call_downstream`/
  `_render_error_for_status` (no new near-identical try/except). Accepts an optional `days` query
  param (`7`, `15`, or `30`; default unset — first render shows the selector with no runs listed
  yet, matching `runs_list`'s own no-locally-invented-default convention). Converts `days` to
  `horizon` via a small module-level constant/function,
  `HOURS_PER_DAY = 24`, `ASSUMED_SAMPLING_INTERVAL_HOURS = 1` (named per ADR-0007, commented with a
  pointer to the ADR for the disclosed hourly-only assumption), then calls the existing `GET /runs`
  and filters the parsed `RunSummaryResponse` list client-side (this router) by `run.horizon ==
  converted_horizon`, most recent first (the list already comes back `created_at DESC` per
  DASH-005-01's existing convention — no client re-sort needed, only a filter).
- `services/dashboard-web/src/app/templates/horizon_summary.html` (new) — a horizon selector (three
  links/buttons for 7/15/30 days, `?days=N`), then either: the filtered runs table (same columns as
  `runs_list.html`'s table, reusing its row markup via a shared macro if straightforward, or a
  disclosed non-duplication if the two tables' semantics diverge enough not to share one — dev's
  call, documented either way) when `days` is set and matches are found; an explicit empty state
  ("No completed runs at this horizon yet." + a link to `/runs/new`) when `days` is set and zero
  runs match; nothing but the selector when `days` is unset.
- `services/dashboard-web/src/app/templates/base.html` — add a nav link to
  `/runs/horizon-summary`, next to the existing `/runs`/`/datasets` links (grep `base.html`'s nav
  block first to match its existing markup style, not invent a new nav pattern).

**DRY check**: grep `services/dashboard-web/src` for `horizon` — expect hits only in
`run_new.html`'s form field, `runs_list.html`'s/`run_detail.html`'s existing horizon display, and
`RunRequest`/`RunSummaryResponse`/`RunDetailResponse` field definitions in `libs/common` — no
existing horizon-filtering logic to reuse or duplicate. `_call_downstream`/`_render_error_for_status`
are reused, not reimplemented, same as every other route in `runs.py`.

## Implementation acceptance criteria (carried over from the backlog story)

- A horizon selector (7/15/30 days) is present on `/runs/horizon-summary`, each option converting to
  `horizon` per ADR-0007's documented conversion (168/360/720 for the one real hourly source today).
- Selecting a horizon lists only the tenant's completed runs whose `horizon` matches the converted
  value, most recent first (matches `runs_list.html`'s existing `created_at DESC` convention — no
  new sort).
- Zero matching runs renders an explicit empty state with a link to `/runs/new` — never a silent
  empty table, never a fallback to a different horizon's runs.
- No new backend/gateway-api/validation-service call beyond the existing `GET /runs` — confirmed by
  reading the diff (no new route added to `gateway-api`/`validation-service`).
- Copy uses only "validation runs"/"completed runs at this horizon" vocabulary — no "prediction,"
  "forecast," "signal," "target," or "recommendation" anywhere on the new page (grep-checked test).

## Test acceptance criteria

  file matching `tests/test_runs_detail.py`'s naming convention): a fixture `GET /runs` response with
