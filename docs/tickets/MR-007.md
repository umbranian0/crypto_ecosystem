# MR-007 — Read-only `GET /runs/{run_id}/features` export endpoint

Status: done

Source story: `docs/product/backlog-model-research.md` MR-007. Sprint: `docs/sprints/sprint-42.md`.

## Analysis

- Story: "As a `research/`-side candidate model, I want a single read-only `GET` route on
  `validation-service` that re-produces and returns the multi-column feature table
  `FeatureDatasetAssembler.assemble` built for a specific, already-executed `{tenant_id, run_id}`, so that
  MR-003's disclosed gap ... is closed with the smallest possible surface."
- Acceptance criteria (backlog, verbatim, condensed):
  1. `GET /runs/{run_id}/features` added to `routers/runs.py`, tenant-scoped via the same
     `X-Tenant-Id`/API-key dependency every other route in this router uses.
  2. Route re-invokes `FeatureDatasetAssembler.assemble` using the target run's persisted
     `feature_lineage`-derived parameters, returning `404` when `has_multimodal_features` is `False`.
  3. Plain JSON-serializable table response, no object-storage pointer.
  4. `create_run`'s existing internal call path unchanged — zero lines diff.
  5. Reproducibility test against the run's own lineage.
  6. `README.md`'s Routes list and "Multi-source feature assembly" section updated;
     `scripts/check_doc_sync.py` passes.
  7. No `libs/naive_first_engine` change, no re-implementation of `CompositeDatasetSource`/ADR-0008's
     alignment rule.
- Depends on: MR-003 (interface documented, done), MDF-003/VS-030 (shipped, Sprint 36).

## A real, disclosed schema gap this ticket must design around (read before implementing)

Grepped `services/validation-service/src/app/models.py`, `naive_first_common/contracts.py`, and
`routers/runs.py::create_run` before writing this ticket. The `runs` table does **not** persist enough to
literally replay the original `assemble()` call:

- `runs.feature_lineage` stores only `{"source", "field", "lag_hours"}` per reference — `lag_hours` is
  itself *derived* by `feature_dataset.py`'s `FEATURE_SOURCE_LAG_HOURS` table from `source`, so `source`
  + `field` alone is sufficient to reconstruct each `feature_references` entry (drop `lag_hours` when
  rebuilding — it is recomputed, not an input).
- `runs.missing_timestamp_policy` **does not exist as a column at all** — the policy a run originally used
  is not persisted anywhere. Adding a column and threading it through `_persist_new_run`'s call inside
  `create_run` would add a line to `create_run`'s body, which conflicts with AC4's literal "zero lines
  diff" requirement. This ticket therefore does **not** add such a column.
- The primary series (`target_index` that `assemble()` aligns onto) is only ever held in-memory during the
  original `POST /runs` request — `runs.dataset_id` is a plain string label, and the actual
  `dataset_reference` dict used to load it (`{"inline": ...}` / `{"path": ...}` / `{"object_key": ...}` /
  `{"source": ...}`) is not persisted either.

**Binding design decision for this ticket (document this plainly in the route's docstring and the README
update — do not silently paper over it)**:

- Reconstruct `feature_references` from `run.feature_lineage` as
  `[{"source": entry["source"], "field": entry["field"]} for entry in run.feature_lineage]`.
- Accept `missing_timestamp_policy` as an **optional query parameter** on the new route
  (`?missing_timestamp_policy=...`), defaulting to `"drop_row"` (the strictest, most conservative of the
  three policies) when omitted. This is not a new arbitrary-feature-reference input surface (AC7's
  concern) — it is the one genuinely unrecoverable parameter needed to replay an assemble() call, and
  accepting it as a query param (rather than silently guessing, or blocking the endpoint entirely) matches
  this module's own "fail closed / disclose, don't silently approximate" convention
  (`feature_dataset.py`'s `fetched_at`-gap handling is the precedent). If the caller passes a different
  policy than the run's original, the response may legitimately have a different row count than the
  original run's own target index — document this as a known limitation, not a bug.
- Reconstruct the primary series by calling `dataset_source.load({"source": run.dataset_id})` (the
  `IngestionServiceDatasetSource` shape) — this is the one dataset-loading shape whose reference can be
  reconstructed from a bare `dataset_id` string. Document explicitly that this only works for runs whose
  original `dataset_reference` was ingestion-service-backed with `source == dataset_id` (the common/primary
  path for real pilot data); a run originally loaded via `inline`/`path`/`object_key` cannot be re-loaded
  this way. If `dataset_source.load(...)` raises `DatasetSourceError`, the route returns `422` with a
  message naming this limitation explicitly — never a silent empty/wrong table.
- This is a first-cut, disclosed-limitation implementation, consistent with MR-007's own backlog framing
  ("an acceptable trade for a first cut... revisit as a follow-up story only if a real problem is
  observed"). A future ticket to persist `missing_timestamp_policy`/the original `dataset_reference`
  properly (accepting a `create_run` diff at that point) is the correct follow-up if this limitation
  proves to matter in practice — not solved ad hoc here.

## Design

- Design pattern: no new pattern introduced — this route is a thin HTTP adapter over the existing
  `FeatureDatasetAssembler` (already the module's Adapter-composition point) and `DatasetSource` Adapter,
  reused exactly as `create_run` already uses them. No Strategy/Factory/Observer applies here.
- Files touched: `services/validation-service/src/app/routers/runs.py` (new route only — `create_run`'s
  own body must show zero diff lines), `services/validation-service/tests/test_run_features_endpoint.py`
  (new file, matching `test_runs_endpoint.py`'s naming convention), `services/validation-service/README.md`
  (Routes list + "Multi-source feature assembly" section). Scoped to `services/validation-service` only —
  no `libs/naive_first_engine` file, no other service.
- **DRY check (dev agent must state this explicitly in its own report)**: grep `routers/runs.py` and
  `feature_dataset.py` before writing anything. Reuse, don't duplicate:
  - `FeatureDatasetAssemblerDep`/`DatasetSourceDep`/`ConnectorStatusCheckerDep` (already-existing FastAPI
    dependency seams in `app/dependencies/repositories.py`, already imported in `runs.py`) — the new route
    takes the same dependencies `create_run` already takes, no second wiring mechanism.
  - `run_repository.get_run(tenant.tenant_id, run_id)` + the existing `None` → `404` collapse pattern
    `get_run` (the existing `GET /runs/{run_id}` handler) already establishes for "doesn't exist or wrong
    tenant" — same single-404 pattern, not a new one.
  - `FeatureDatasetAssembler.assemble(...)` itself, called with the same keyword arguments `create_run`
    already uses (`target_index`, `feature_references`, `missing_timestamp_policy`, `dataset_source`,
    `connector_status_checker`) — no re-implementation of any alignment/lag logic.
  - JSON-response convention: grep the codebase for any existing DataFrame→JSON helper before inventing
    one; if none exists, use the `{"index": [...], "columns": [...], "data": [[...], ...]}` shape MR-007's
    backlog entry itself proposes (matches `pandas.DataFrame.to_dict(orient="split")`'s native shape —
    reuse `pandas`' own built-in rather than hand-rolling the same structure).

## Implementation acceptance criteria

- `GET /runs/{run_id}/features` added to `routers/runs.py`, decorated on the same `router`, taking
  `run_repository: ValidationRunRepositoryDep`, `dataset_source: DatasetSourceDep`,
  `feature_dataset_assembler: FeatureDatasetAssemblerDep`,
  `connector_status_checker: ConnectorStatusCheckerDep`, `tenant: TenantContext = Depends(get_tenant_context)`,
  and an optional `missing_timestamp_policy: str = Query(default="drop_row")` query parameter.
- Handler flow: `get_run` → `404` if `None` or `not run.feature_lineage` (mirrors `has_multimodal_features`'s
  existing derivation, `bool(run.feature_lineage)`) → reconstruct `feature_references` from
  `run.feature_lineage` → load the primary series via `dataset_source.load({"source": run.dataset_id})`,
  `422` with a descriptive message on `DatasetSourceError` → call `feature_dataset_assembler.assemble(...)`
  with the loaded series' index as `target_index` → `422` with a descriptive message on
  `FeatureDatasetError` → return the assembled `feature_dataframe` as
  `{"index": [...ISO8601 strings...], "columns": [...], "data": [[...], ...]}`.
- `create_run`'s existing body is byte-unchanged — confirmed via `git diff services/validation-service/src/app/routers/runs.py`
  showing zero changed/removed lines inside `create_run`'s own function body (only additions elsewhere in
  the file, plus any new imports at the top).
- No `libs/naive_first_engine/src` file touched, no `services/` directory other than
  `services/validation-service` touched.

## Test acceptance criteria

- A test proves `GET /runs/{run_id}/features` returns `404` for a run with `feature_lineage == []`
  (`has_multimodal_features == False`).
- A test proves a `200` response for a run that does have multimodal features, with a JSON body containing
  `index`/`columns`/`data`, and that `columns` matches the run's own `feature_lineage`-derived
  `{source}.{field}` naming convention (`feature_dataset.py`'s existing `column_name` construction).
- Reproducibility test (AC5): calling the endpoint twice for the same `run_id` returns byte-identical
  `columns` and the same `index` range both times — proving the re-export is deterministic given the same
  persisted lineage, not merely "returns 200."
- A test proves tenant isolation: a run belonging to tenant A returns `404` (not the data) when queried
  with tenant B's credentials — same single-404-for-both-cases pattern `get_run` already establishes.
- A test proves the `422` path when the primary series cannot be reloaded (e.g. `dataset_source.load`
  raises `DatasetSourceError` for a non-ingestion-service-backed `dataset_id`) — proving the documented
  limitation fails closed rather than silently returning wrong/empty data.
- Full `services/validation-service` suite re-run with zero regressions (this is checked personally by the
  Tech Lead in Review, not just claimed by the dev agent).
