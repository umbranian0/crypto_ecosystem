## Analysis

`SplitResultResponse` (`libs/common/src/naive_first_common/contracts.py`) already carries seven
model/naive0 metric pairs per split: `mae`, `rmse`, `smape`, `mase`, `da`, `f1`, `oos_r2`.
`RAV-002`'s `build_error_chart` only plots the `mae` pair, hardcoded. This ticket generalizes it to
take a `metric` parameter and switch which pair it plots, with a single selector control in
`run_detail.html` — no new backend field, no new endpoint, all seven pairs already fetched by the
existing `GET /runs/{id}/splits` call `run_detail` makes.

`da`/`f1` need explicit labeling as "directional accuracy"/"F1" (their real statistical meaning),
never reworded into hit-rate/win-rate trading language — the exact positioning line RAV-002/003
already established for MAE/DM-verdict must extend to these two in particular, since they are the
two metrics most likely to be misread as a trading signal if mislabeled.

## Design

**Pattern**: none from implementation-plan.md section 7 applies — read-only rendering addition,
same as RAV-002/003.

**Files touched** (scoped to `services/dashboard-web` only):
- `services/dashboard-web/src/app/charting.py` — change `build_error_chart(splits: list
  [SplitResultResponse], metric: str = "mae") -> ErrorChartData` to accept a `metric` key (one of
  `"mae", "rmse", "smape", "mase", "da", "f1", "oos_r2"`) and read `getattr(split, f"model_{metric}")`/
  `getattr(split, f"naive0_{metric}")` instead of the hardcoded `.model_mae`/`.naive0_mae`
  attribute access. Add a small metric registry (name -> (label, model attr, naive0 attr)) so the
  route/template don't hand-roll attribute-name string formatting themselves. Keep the default
  `metric="mae"` so any other caller/test that doesn't pass `metric` keeps RAV-002's exact
  behavior (backward compatible signature).
- `services/dashboard-web/src/app/routers/runs.py` — `run_detail` reads an optional `metric` query
  param (default `"mae"`, validated against the registry above; an unrecognized value falls back to
  `"mae"` rather than erroring, since this is a display preference, not a form submission with a
  422 path), and passes it to `build_error_chart`. This is a real change to `run_detail`'s existing
  wiring — flag it explicitly in the ticket's Design section rather than letting it appear as an
  undisclosed deviation later (the sprint plan's file-overlap note only names `charting.py`/
  `run_detail.html`/`style.css`; `runs.py` is a necessary fourth file for this ticket, same
  "necessary route-context wiring, not scope creep" precedent RAV-003/FHS-003 already used for their
  own `runs.py` additions).
- `services/dashboard-web/src/app/templates/run_detail.html` / `_error_chart.html` — add a single
  selector control (a plain `<select>` with `hx-get`/`hx-target` swapping `_error_chart.html`, or a
  plain link-based tab set re-rendering the whole page with `?metric=...` — dev's implementation
  choice, either satisfies "a single control," not a full page of separate charts) that switches the
  plotted metric among all seven pairs. Chart title/legend must read the metric's real name (e.g.
  "Model vs. Naive0 error by split (sMAPE)"), not a generic placeholder.
- `services/dashboard-web/src/app/static/style.css` — no new colors needed; reuses
  `--color-accent`/`--color-accent-2`, same as RAV-002, across all seven metrics.

**DRY check**: `build_error_chart`'s bar-geometry/scaling logic is untouched — only the value
lookup changes from a hardcoded pair to a registry lookup. No second chart-building function is
created; this is a single function's signature change, not a new one.
