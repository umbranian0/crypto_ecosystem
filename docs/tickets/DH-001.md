# DH-001 — Disclose the sort-on-load that already happens silently

**Sprint**: 30. **Module**: `services/validation-service` (+ `libs/common` contract field,
+ `services/dashboard-web` rendering). **Status**: todo. **Priority**: Must.
**Depends on**: DH-005 (shares `runs.py::create_run`; land after DH-005 to avoid merge collision, per
sprint plan). **Blocks**: DH-002, DH-003 (both extend the warnings-plumbing this ticket builds — do
not parallelize DH-001/002/003, same file chain in `dataset_source.py`).

## Analysis

Backlog DH-001 (Must), finding #2: `InlineOrLocalFileDatasetSource._build_series` already calls
`.sort_index()` unconditionally on every load — a non-monotonic input is silently reordered before any
validation math runs, with nothing in the response or dashboard disclosing it. Per CLAUDE.md's
no-silent-inference rule, disclosure is required even though the sort itself is not new behavior and
not a leakage risk (the splitter needs a sorted index and always assumed one — see backlog's own
"Leakage/honesty check"). This ticket is disclosure-only: no change to whether/how sorting happens.

## Design

**Pattern**: none of implementation-plan.md section 7's named patterns is newly invoked — this is an
additive return-shape change to the existing `DatasetSource` Adapter (section 7's existing
justification for that pattern — a future source can still swap in transparently) plus ordinary
Repository/contract field additions.

**Contract shape decision (binding on DH-002/003 too)**: `DatasetSource.load(reference) -> pd.Series`
becomes `DatasetSource.load(reference) -> LoadedSeries`, a new frozen dataclass in `dataset_source.py`:

```python
@dataclasses.dataclass(frozen=True)
class LoadedSeries:
    series: pd.Series
    warnings: list[str]
```

This is a uniform change applied to **all four** classes in the file (`InlineOrLocalFileDatasetSource`,
`ObjectStorageDatasetSource`, `IngestionServiceDatasetSource`, `CompositeDatasetSource`) — not a
two-tuple only some callers must learn to handle, and not a second parallel method. Grep confirms the
**only** external call sites are `services/validation-service/src/app/routers/runs.py`'s two
`dataset_source.load(...)` calls (the primary `dataset_reference` and VS-017's optional
`client_prediction_reference`) — both updated in this same ticket. `ObjectStorageSource`/
`IngestionServiceDatasetSource` always return `warnings=[]` today (their own paths cannot yet produce
a warning; DH-002/003 do not extend those two classes per the backlog's explicit scoping) but must
still return the new `LoadedSeries` shape uniformly, so `CompositeDatasetSource.load()`'s dispatch
stays a single return-type contract regardless of which branch serves a call.

`InlineOrLocalFileDatasetSource._build_series` (private helper, reused by `ObjectStorageDatasetSource`)
gains the reordering check: compare `pd.DatetimeIndex(...).is_monotonic_increasing` **before** calling
`.sort_index()`; if `False`, add
`"dataset rows were not in timestamp order and were sorted before validation"` to the warnings list.
No change to the sort call itself.

**Persistence shape**: warnings must survive from `POST /runs` (where the load happens) to a later
`GET /runs/{id}` (where `RunDetailResponse` is built from the persisted `RunRecord`), so this is not a
response-only field — it must be persisted:
- `services/validation-service/src/app/repositories/interfaces.py` — `RunRecord` gains
  `warnings: list[str]`; `ValidationRunRepository.create_run(...)` gains a `warnings: list[str]`
  keyword parameter.
- `services/validation-service/src/app/models.py` — `Run` SQLAlchemy model gains a `warnings` column
  (JSON type, matching `client_baseline_results`'s existing JSON-column precedent on `SplitResult`,
  not a new column type introduced for this ticket).
- A new Alembic migration under `services/validation-service/migrations/versions/` (next sequence
  number after `0007_retune_split_results_chunk_interval.py` — check `alembic history` for the actual
  head before writing the migration) adds the `warnings` column, `nullable=False, server_default='[]'`
  so existing rows backfill cleanly with no manual data migration.
- `services/validation-service/src/app/repositories/sqlite_repository.py` and `postgres_repository.py`
  — `create_run`/`get_run`/`list_runs` read/write the new column, converting to/from `list[str]` the
  same way `client_baseline_results` already converts to/from JSON in this codebase (grep that
  precedent before writing new conversion code — DRY).
- `libs/common/src/naive_first_common/contracts.py` — `RunDetailResponse` gains
  `warnings: list[str] = Field(default_factory=list)` — a default is required, not optional, because
  both `gateway-api`'s `runs.py::get_run` (`RunDetailResponse(**response.json())`) and
  `dashboard-web`'s `runs.py` do the same reconstruction-from-JSON; a required field with no default
  would break both the instant validation-service starts omitting it in any response gateway-api/
  dashboard-web haven't been redeployed to expect (defensive, matches this file's own existing
  precedent of nullable/defaulted fields for additive changes, e.g. `client_baseline` on
  `SplitResultResponse`).
- `services/validation-service/src/app/routers/runs.py::create_run` — the primary `series` load now
  unpacks `LoadedSeries(series, warnings)`; `warnings` is threaded through `_persist_new_run` (new
  parameter) into `ValidationRunRepository.create_run`. On the load-failure branch, no `LoadedSeries`
  exists (the exception fired before unpacking), so that branch's `_persist_new_run` call passes
  `warnings=[]`, unchanged from today.
- `services/dashboard-web/src/app/templates/run_detail.html` — renders `run.warnings` (if non-empty) in
  the same visual register already used for other non-fatal, disclosed conditions on that page (grep
  the page for the closest existing precedent — e.g. how it already renders `failure_reason` or any
  existing informational callout — reuse that CSS class, do not invent a new one for this ticket unless
  none exists).

**DRY check note** (grepped `dataset_source.py`, `repositories/*.py`, `models.py`, `contracts.py`
before writing this ticket): `client_baseline_results`'s existing JSON-column round-trip in
`sqlite_repository.py`/`postgres_repository.py` is the pattern to extend, not re-derive; `_json_safe_float`
in `runs.py` is unrelated (float-specific) and not reused here since `warnings` is a plain string list
with no NaN/Infinity concern.

## Implementation acceptance criteria

- [ ] `DatasetSource.load(reference) -> LoadedSeries` uniformly across all four classes in
  `dataset_source.py`; `CompositeDatasetSource.load()`'s dispatch is unchanged in structure (still
  routes on `reference`'s keys), only its return type changes.
- [ ] `_build_series` detects reordering via an `is_monotonic_increasing` check before `.sort_index()`
  runs, with no change to the sort itself.
- [ ] `RunDetailResponse.warnings` (default `[]`) is populated from the persisted `RunRecord.warnings`
  on `GET /runs/{run_id}` and `GET /runs`.
- [ ] The reordering warning, when present, is persisted via `create_run` and survives a `GET /runs/{id}`
  call (round-trip, not just present in the synchronous `POST /runs` response).
- [ ] `dashboard-web`'s run-detail page renders the warning when present, styled as non-fatal (not as an
  error), absent when the list is empty.
- [ ] No behavior change to the actual sort — a reordered-but-otherwise-valid dataset still validates
  successfully, just with the warning attached.
