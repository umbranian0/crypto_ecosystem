## Analysis
Story: NFE-017 (Should), depends on NFE-001 (done, Sprint 01 — package scaffolding). Serves the licensing/open-core revenue line (da-tese-ao-produto.md section 2.4) and solution-design.md section 3.4's promise that `naive_first_engine` can be extracted and published standalone "without a rewrite." This repo has no CI configured yet (confirmed: no `.github/workflows`, no other CI config found anywhere in the repo), so per the sprint's own instruction a documented, re-runnable local script is the right-sized deliverable — not a CI job that doesn't fit anywhere yet.

The risk this check guards against: `libs/naive_first_engine`'s `pyproject.toml` (already confirmed: `pandas`, `numpy`, `scipy` only, no web/DB deps) staying accurate as code changes, and no test/source file accidentally importing something from outside the package (e.g. reaching into `libs/common`, `services/*`, or repo-root tooling) that would only surface as a break at actual publish time.

## Design
No new pattern — this is a packaging/verification script, not library logic. New file only: `libs/naive_first_engine/scripts/check_standalone.sh` (or `.py` — dev agent's call, document which and why in the script's own header comment; a `.py` script is more portable across the Windows/PowerShell environment this repo runs in, so prefer `.py` unless there's a concrete reason not to). This ticket must not touch `src/` or existing `tests/`.

The script must, in one re-runnable pass:
1. Create a clean, throwaway virtual environment (not reuse the repo's existing `.venv`, which may have transitively picked up other repo packages or dev tooling).
2. Install `libs/naive_first_engine` into that clean venv using only its own `pyproject.toml` (`pip install .` from within `libs/naive_first_engine`, or equivalent) — no `-e` install from a workspace root that could implicitly resolve sibling packages, no `requirements.txt` reaching outside the package directory.
3. From that clean venv (not the repo's dev venv), run a smoke check: `import naive_first_engine` succeeds, and a minimal call to `run_validation_protocol` (small synthetic series, a couple of splits) completes without error and returns results.
4. Print a clear pass/fail result and exit non-zero on any failure, so it's usable as a future CI step without modification.
5. Clean up the throwaway venv afterward (or place it somewhere obviously temporary/gitignored) — must not leave build artifacts committed to the repo.

DRY check: nothing in `tests/` currently does an isolated-environment install (the whole test suite runs against the repo's dev `.venv`, per NFE-001's environment note), so there's no existing logic to reuse or duplicate here — confirm this by grepping `tests/` and `scripts/` (if it exists) before writing, and note the grep result in this ticket's status update if anything relevant turns up.
