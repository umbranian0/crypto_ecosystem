## Analysis

- Story: "As a research candidate model, I want a regime-switching or hybrid model (e.g. a hidden Markov
  model gating a simple linear model per regime) wrapped as a `Baseline` implementation, so that the
  thesis's top-listed future direction ... gets tested under the same honest protocol."

     MR-004.
  2. Regime detection/fit itself happens on the training fold only, per split — no regime labels computed

     against: regime state is often computed with hindsight).
  3. Result reported honestly regardless of outcome, same as MR-004.

  design→test→review sequencing and `/ml-feature-planning`'s train-only-fitting discipline, in addition

## Compute-budget ceiling — exact numeric caps (non-negotiable, per sprint-42.md)

- **Dataset**: the exact same seeded 3,000-row synthetic hourly-returns series MR-004 already uses (same
  `numpy.random.default_rng` seed/generator) — no new, larger, or real dataset. If MR-004's fixture cannot
  be imported/reused directly without a structural change to MR-004's own files (which this ticket may not
  touch), extract it into a small shared `research/tests/fixtures.py` module instead — that extraction is
  in scope for this ticket (it lives under `research/tests/`, not `research/models/`), and MR-004's own
  test file should then import from the same place rather than being duplicated. Document whichever path
  is taken in the Outcome section below.
- **Model**: exactly a 2-state Gaussian HMM (state count fixed, not searched — no `n_components` search
  loop of any kind) gating a simple linear regression, one fit per state on that state's own training-fold
  rows only. Use `hmmlearn.hmm.GaussianHMM(n_components=2, covariance_type="diag", n_iter=..., random_state=42)`
  (or an equivalent minimal, CPU-only, deterministic HMM implementation if `hmmlearn` cannot be installed
  cleanly — state the choice and why in the Outcome section) fit on the training fold's return values (and
  optionally a small lag/rolling feature set via `research/features.py`, correctly lagged) to obtain a
  per-row hidden state assignment; then fit one `sklearn.linear_model.LinearRegression` (or equivalent) per
  state, on that state's own training rows only.
- **Regime fit boundary (the one AC not to compress)**: the HMM's `.fit()` call must only ever see the
  `train` argument passed into `predict(train, test)` for that split — never a module-level or closed-over
  reference to the full series, never a regime label computed once outside the per-split loop and reused
  across splits. An explicit unit test must prove this structurally (see Test ACs below), mirroring
  MR-004's "re-instantiated per split" test precedent.
- **Hyperparameters**: fixed, no search loop — HMM `n_components=2` (fixed), `n_iter` capped at a small
  fixed value (e.g. 20-50, document the exact number chosen), `random_state=42`; per-state linear model
  uses `sklearn.linear_model.LinearRegression` defaults, no `GridSearchCV`/`RandomizedSearchCV`/Optuna
  anywhere in this ticket's code.
- **CPU-only**: no `device="gpu"`, no cloud training call.
- **Horizons**: exactly `1` and `6` — no `24` or other horizon in this ticket's run.
- **`ValidationConfig`**: reuse MR-004's exact `train_window=500, test_window=50, step=250, purge_gap=6`
  unless the dev agent finds this produces a materially slower run than MR-004's (HMM fitting is more
  expensive per split than a single LightGBM fit) — if so, narrow `step` further (fewer splits) or the
  dataset window, and document the change and why in the Outcome section, per sprint-42.md's explicit
  instruction to narrow further rather than silently exceed the runtime ceiling.
- **Expected runtime ceiling**: the dev agent must time its own full pytest run for the new test file and
  report the wall-clock seconds in its final message. Target: **under 5 minutes** for the full new test
  file alone, same ceiling MR-004 used. If actual measured time trends toward that mark, narrow further and
  re-measure — do not proceed and only flag it.
- **A 2-state HMM can legitimately fail to converge to two well-separated regimes on i.i.d.-Gaussian
  synthetic data** (there may be no real regime structure in MR-004's synthetic fixture at all — it was
  built for MR-004's boosting story, not to contain an actual planted regime shift). This is expected and
  acceptable: the story's job is to test the honest protocol on this model class, not to guarantee the HMM
  finds "real" regimes. If degenerate state assignment happens (e.g. one state captures almost all rows),
  document this plainly in the Outcome section rather than treating it as a bug to work around — do not
  add fallback/retry logic to force better-separated states, which would be exactly the kind of
  hyperparameter-search-in-disguise this ceiling forbids.

## Implementation acceptance criteria

- `research/models/regime_hmm.py` defines a `RegimeHMMBaseline` class (or similarly named) with
  `.predict(train: pd.Series, test: pd.Series) -> pd.Series` matching `Baseline`'s Protocol exactly, and a
  `.name` attribute (matching MR-004's documented `.name`-vs-`_baseline_key` reasoning — reuse that
  reasoning, don't re-derive it from scratch).
- Internally: fits a fresh 2-state Gaussian HMM on `train` only, derives per-row state assignments for
  `train`, fits one linear regression per state on that state's own rows, applies the fitted HMM's
  `.predict`/decoding to assign a state to each `test` row (using only information available at that row —

  its assigned state's linear model.
- `RegimeHMMBaseline.predict` never closes over or receives anything beyond its own `train`/`test`
  arguments — no module-level "full series" reference, same structural leakage-safety pattern as
  `LightGBMBaseline`.
- No `libs/naive_first_engine/src` file touched.
- `research/pyproject.toml` gains `hmmlearn` (and `scikit-learn`, if not already present via MR-004) as a
  dependency — only file outside `research/models/`/`research/tests/` this ticket may touch.
- The model is registered via `config.extra_baselines=[RegimeHMMBaseline()]` and run through the real,
  unmodified `run_validation_protocol` — not a hand-rolled fit/predict/metric loop.

### Correction — Tech Lead review found a same-row target-leakage bug (fixed)

Tech Lead review caught a real bug in the dev agent's original `RegimeHMMBaseline.predict` (in
`research/models/regime_hmm.py`): the test-fold regime routing step called `hmm.predict()` on
`test.to_numpy().reshape(-1, 1)` — i.e. `test`'s own current-row return values — to decide which state (and
therefore which per-state `LinearRegression`) governs row t's prediction. `return[t]` is the exact value
this baseline is asked to predict at row t, so using it to pick row t's regime/model is target leakage: no
real-time deployment would know `return[t]` before predicting it. This is the same category of bug MR-004's
review found in `gradient_boosting.py::_make_features` (using information only available at/after the
prediction target's own timestamp), just surfacing in the regime-routing step here rather than a regression
feature. Unlike MR-004's bug, this one did not produce a one-sided pre-fix verdict pattern here — the
pre-fix synthetic-fixture verdicts were already close to naive-like (`{'better': 0, 'worse': 0, 'no
significant difference': 10}` at 1h; `{'better': 1, 'worse': 0, 'no significant difference': 9}` at 6h) — so
the leakage was real and structural even though this specific seeded fixture didn't happen to surface it as
an obviously one-sided result.

**Fix**: `predict` now decodes test-fold states from the LAGGED return series (`test.shift(1)`), matching
this file's existing lag-feature convention (`lagged_returns`, `shift(lag>=1)`) rather than `test`'s own
current-row values. Row t's state is decoded from `return[t-1]`, which is genuinely available before
`return[t]` is observed. The first test row has no in-test lag, so it is backfilled from `train`'s own last
observed return (`train.iloc[-1]`) — still train-fold-only information, available before the test fold
starts. The per-state linear models themselves were already correct (only ever see lag features via
`_make_features`, never the row's own current return) and were not changed. `research/models/regime_hmm.py`
was the only file touched by the fix itself.
