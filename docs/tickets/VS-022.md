# VS-022 — Tenant-scoped `GET /runs` list endpoint

**Status: done**

## Analysis
Story: VS-022 (Must, `docs/product/backlog-validation-service.md`), depends on VS-003, VS-004, VS-013 (all done). Closes `DASH-005-GAP` (blocking `dashboard-web`'s `DASH-005` since Sprint 11) — this is the first of the sprint's two independent chains (`VS-022 -> GW-016`), and runs in parallel with `INF-018`.

Constraining acceptance criteria, read directly from the backlog entry, not summarized from memory:
- `limit` (default e.g. 20, hard server-side ceiling max 100, not merely a client-suggested default) / `offset` (default 0) query params; out-of-range `limit` (`<1` or `>100`) returns `422`, never silently clamped.
- Tenant-scoped via the existing `Depends(get_tenant_context)` seam VS-007/VS-008 already use — no bypass; `ValidationRunRepository.list_runs(tenant_id, limit, offset)` takes `tenant_id` as its first parameter, per `interfaces.py`'s module docstring AC2 (every method's first parameter after `self` is `tenant_id`, no exceptions).
- New `list_runs` method implemented by both `SQLiteValidationRunRepository` (VS-004) and `PostgresValidationRunRepository` (VS-013) — both already exist and are done; add the method to both without changing either's existing `create_run`/`get_run`/`update_run_status` call sites. The Postgres implementation relies on RLS (already enforced, `_tenant_scoped_session`/`set_config('app.tenant_id', ...)`, see `postgres_repository.py`) as the isolation mechanism, not an application-level `WHERE tenant_id = ...` alone — though the `WHERE` clause is still added, same "defense in depth, not the enforcement mechanism" stance the existing methods already use.
- Ordering is `created_at DESC` — the repository's job, not the caller's, mirroring `get_splits`'s "ordering is this method's responsibility" precedent.
- Response shape: a new `RunSummaryResponse` (strict subset of `RunDetailResponse` — `id, dataset_id, horizon, status, created_at, completed_at`, no `split_config`/`tenant_id`/`failure_reason`) added to `libs/common/src/naive_first_common/contracts.py` as the single canonical definition — same DRY convention ARCH-003 already established for `RunDetailResponse`/`SplitResultResponse`. This module is a shared `libs/*` package, imported by both `validation-service` and (in GW-016) `gateway-api` — do not redefine it in either service.
- Endpoint returns `{items: list[RunSummaryResponse], limit: int, offset: int, total: int}` (exact envelope documented in the README); `total` is a real count, not omitted.
- Empty tenant returns `200` with empty `items`, not `404`.
- Tests: 3-run tenant sees exactly its own 3 in `created_at DESC` order; a second tenant's runs never appear in the first tenant's results (non-tautological — asserts by id, not just count — extra review scrutiny per sprint-14.md's own flag); `limit`/`offset` paginate correctly across a seeded set larger than one page; `limit=0` or `limit>100` returns `422`.
- `services/validation-service/README.md`'s Routes section gains `GET /runs`; VS-016's doc-sync check (`scripts/check_doc_sync.py`) must still pass.

## Design
Pattern: none new — this is Repository (existing `ValidationRunRepository` interface, extended) and DI (existing `Depends(get_tenant_context)` seam), no new pattern introduced. Files touched (validation-service module + the one shared contract — this ticket does not touch `gateway-api` at all, per the sprint's module-boundary rule):
- `libs/common/src/naive_first_common/contracts.py` — add `RunSummaryResponse`. Also add it to whatever `__init__.py`/`__all__` re-export list `RunDetailResponse` etc. already appear in, so both `from naive_first_common.contracts import RunSummaryResponse` and any existing top-level re-export pattern stay consistent with the existing models.
- `services/validation-service/src/app/repositories/interfaces.py` — add `list_runs(self, tenant_id: str, limit: int, offset: int) -> list[RunRecord]` to `ValidationRunRepository`. Reuses the existing `RunRecord` dataclass — no new record type needed since `RunSummaryResponse` is a router-layer concern, not a repository-layer one; the repository still returns full `RunRecord`s, the router narrows the shape. Also add whatever total-count method/shape is needed for the response envelope's `total` field (e.g. `count_runs(tenant_id) -> int`, or a combined return) — implementer's choice, document whichever is chosen in the interface's docstring.
- `services/validation-service/src/app/repositories/sqlite_repository.py` — implement `list_runs` (and the total-count method, if separate) on `SQLiteValidationRunRepository`, following the exact `Session`/`select`/`.where(Model.tenant_id == tenant_id)` style already used by `get_run`, with `.order_by(Run.created_at.desc()).limit(limit).offset(offset)`.
- `services/validation-service/src/app/repositories/postgres_repository.py` — implement the same method(s) on `PostgresValidationRunRepository`, using `_tenant_scoped_session` (existing helper), same `.order_by`/`.limit`/`.offset` pattern.
- `services/validation-service/src/app/routers/runs.py` — new `GET /runs` handler (existing file already has `POST /runs`/`GET /runs/{id}` — VS-022 is additive to this file, no other ticket in this sprint touches it, so no collision risk). Validates `limit`/`offset` via FastAPI query-param constraints (`Query(default=20, ge=1, le=100)` for `limit` — this gets FastAPI's own `422` for free on out-of-range values, no hand-rolled validation needed).
- `services/validation-service/README.md` — Routes section gains `GET /runs`.

DRY check (performed before writing this ticket): grepped `services/validation-service/src/app/routers/runs.py` and `repositories/interfaces.py` — no existing list/pagination method exists to reuse; `get_splits`'s ordering-is-repository's-job precedent is the pattern to follow, not new logic to invent. `libs/common/src/naive_first_common/contracts.py` already has `RunDetailResponse` — `RunSummaryResponse` should be defined as an explicit subset (separate `BaseModel` with the six fields, cross-checked against `RunDetailResponse`'s existing field names/types exactly, not hand-copied incorrectly).
