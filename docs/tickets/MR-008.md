## A real, disclosed environment gap found and fixed before this ticket's own scope could even start

Before writing any research code, the Tech Lead verified the live local stack could actually serve
`binance_price_btcusdt_1h` end-to-end (this sprint's own escalation clause names exactly this as a
genuine-blocker candidate). Found and fixed, in order:

1. `naive-first-postgres` had exited; the other five containers were up but every DB-backed call failed
   (`failed to resolve host 'postgres'` — the container network was fine, Postgres itself was down).
   Fixed: `docker start naive-first-postgres`, then `docker restart` on `ingestion-service`/
   `validation-service`/`gateway-api` so their connection pools picked up a live Postgres.
2. The live Postgres is heavily polluted with **1,870 leftover tenants** from prior test-suite runs that
   evidently executed against the live Compose Postgres directly rather than an isolated test DB — a
   pre-existing environment hygiene issue, out of this ticket's scope to clean up, disclosed here for a
   future infra/ops ticket rather than silently worked around.
3. None of the tenants visible via `gateway-api`'s `GET /tenants` (including the named,
   non-test-fixture-looking ones from Sprint 35's UAT persona reviews) had real seeded platform history —
   `GET /datasets` returned `{"items": []}` or, for one tenant, 82 rows spanning three days (clearly a
   live-connector crawl artifact, not the Sprint 45 backfill). The Sprint 45 `INGEST-010` one-time backfill
   is not present in this Postgres volume's current state.
4. Created a fresh tenant via `POST /tenants` (operator-authenticated) to exercise `GW-030`'s
   provision-time auto-seed hook (`INGEST-030`'s `POST /internal/seed-platform-history`). It returned `503`
   (degraded, non-blocking, per that ticket's own design). Root cause, traced directly:
   `services/ingestion-service`'s Dockerfile/`infra/docker-compose.yml` never `COPY`/mount
   `services/ingestion-service/data/raw/_platform/` (the real seed CSVs, confirmed present on the host,
   `binance_btcusdt_1h/seed/*.csv` alone totals 64,730 rows) into the running container — `seed_platform_
   history.py`'s own `_SERVICE_ROOT`-relative path resolution had nothing to read inside the container.
   This is a real, pre-existing packaging gap (the CSVs are real and shipped in the repo; the container
   image/compose file just never includes them), not a data-existence problem and not something this
   ticket's own module scope (`research/`) is meant to fix permanently.
   **Live-only fix applied** (no `git`-tracked file changed, nothing persisted beyond the running
   container): `docker cp` the host `data/raw/_platform` directory straight into the running
   `naive-first-ingestion-service` container at the exact path `seed_platform_history.py` expects. This
   does not survive a container recreate — it is a live-environment repair scoped to making this sprint's
   real-data run possible today, not a permanent fix. **Flagged as a follow-up infra ticket**: add a
   `COPY`/bind-mount for `data/raw/_platform` in `services/ingestion-service`'s Dockerfile or
   `infra/docker-compose.yml` so this doesn't have to be repeated by hand.
5. Re-triggered `POST /internal/seed-platform-history` directly against a dedicated research tenant
   (`271d391dd7bf4213b3e5fb8ea6636563`, created via `POST /tenants` with the name "MR-008 real-data
   research run" — a genuine tenant, not a shared/production one, so this ticket's HTTP calls never touch
   another module's or another story's data). Result: `{"binance_price_btcusdt_1h": 78523,
   "blockchain_info_hash-rate": 1900, "blockchain_info_n-unique-addresses": 1884,
   "kaggle_bitcoin_sentiments_21_24": 11295}` — confirmed via `GET /datasets/binance_price_btcusdt_1h/
   series` returning real, correctly-ordered hourly close prices from 2017-08-17 through at least
   2026-08-07 for this tenant.

This is disclosed in full here (rather than only in the sprint's final report) because a future session
picking this ticket back up needs to know the real data path required a live repair, not just "already
worked."

## Design

- Design pattern: **Strategy** (implementation-plan.md section 7) — reuses the existing, unmodified
  `LightGBMBaseline`/`RegimeHMMBaseline` `Baseline` implementations and `config.extra_baselines`
  extension point, exactly as MR-004/MR-005 already established. This ticket adds no new Strategy
  implementation of its own; it swaps the *data source* feeding the same pipeline.
- File touched (new): `research/real_data.py` — a small, `research/`-owned HTTP client function that
  calls `ingestion-service`'s existing `GET /datasets/{source}/series` route directly by Compose hostname
  (`http://ingestion-service:8003` inside Compose; `http://127.0.0.1:8003` for a host-run test process
  talking to the already-running container, configurable via an env var/parameter, not hardcoded), sends
  `X-Tenant-Id`, and returns a sorted `pd.Series`.
- File touched (new): `research/tests/test_real_data_mr008.py` — the actual MR-008 run (1h, 6h) plus a
  unit test for `real_data.py` itself.
- **Binding "never import `app.*`" rule (per CLAUDE.md/this sprint's own restated constraint)**:
  `research/real_data.py` deliberately does **not** import
  `services/validation-service/src/app/dataset_source.py::IngestionServiceDatasetSource`, even though that
  class implements the identical HTTP contract and even though the sprint text names it — that class lives
  under `services/validation-service`'s own `app` package (a service module, not a `libs/*` shared
  package), and importing service code from `research/` would violate the same "call a service's HTTP API,
  never its app code" rule MR-003's own documented interface already established for exactly this kind of
  cross-module call. `research/real_data.py` re-implements only the minimal request/response handling
  needed (`GET .../series` → JSON → sorted `pd.Series`) — genuinely small and a JSON-shaped response, not a
  copy of `dataset_source.py`'s CSV-parsing logic (which handles a structurally different two/three-column
  CSV shape) — so this is not a DRY violation of implementation-plan.md section 9's cross-module-duplication
  rule, it is the same kind of "research calls the HTTP contract itself" pattern MR-003 already scoped for.
- **DRY check (dev agent must state this explicitly in its own report)**: grepped `research/` for any
  existing HTTP-client/dataset-loading code before writing anything — none exists (MR-002/004/005/006 all
  operate on an in-memory synthetic `pd.Series` built inside their own test files, never fetched over
  HTTP). Reuse, don't duplicate: `research/models/gradient_boosting.py::LightGBMBaseline`,
  `research/models/regime_hmm.py::RegimeHMMBaseline` (import directly, zero changes to either file —
  confirmed via `git status --porcelain research/models` empty at review time), `naive_first_engine`'s
  `Baseline` Protocol/`ValidationConfig`/`run_validation_protocol`/`dm_test` (import and use directly, no
  reimplementation).
- **Per this sprint's ML-adjacent-ticket routing rule**: this ticket re-runs a model/pipeline consumed via
  `naive_first_engine`'s `Baseline`/`extra_baselines` contract on a new data source, so the dev agent
  follows `/ml-engineer`'s design→test→review sequencing and `/ml-feature-planning`'s train-only-fitting
  discipline, in addition to this ticket's own ACs. Tech Lead review personally checks: train-only
  splitting actually enforced on the real series (same structural check as MR-004/005, re-verified against
  real data, not assumed to still hold because it held on synthetic data), no `.fit()` reaching outside the
  current split, no leakage into the DM-test error series, no re-introduction of either of MR-004's
  same-row-rolling-feature bug or MR-005's current-row-state-routing bug (both already fixed in the
  unmodified `research/models/*.py` files this ticket imports — a regression check, not a new risk, but
  checked anyway since this is genuinely new data).

## Compute-budget scoping decision for MR-008 (binding, disclosed explicitly per sprint-47.md)

- **Tenant/source**: `tenant_id="271d391dd7bf4213b3e5fb8ea6636563"`, `source="binance_price_btcusdt_1h"`,
  `field` omitted (defaults to `close`, the same default `ingestion-service`'s own route table uses).
- **Date range bound**: `start="2026-01-10T00:00:00"`, `end="2026-08-07T09:00:00"` — the most recent
  ~209-day / ~5,000-hour window of the real series (the full series runs 2017-08-17 through at least
  2026-08-07, ~78,500 rows; this ticket does **not** run against the full nine-year history, which would
  be far outside a CPU-only, minutes-not-hours budget). The dev agent must report the **exact** row count
  the API actually returned for this window (gaps are possible) rather than assuming exactly 5,000.
- **Returns transform**: `raw_series.pct_change().dropna()` — simple percentage returns on the `close`
  field, applied in `research/real_data.py` (or the calling test) before any baseline/Naive0 comparison,
  consistent with MR-001's "compare on returns, not levels" methodology. `research/` does not import
  `validation-service`'s `level_detection.py` (that module is `app.*` code, off-limits per the same rule
  above, and its job — hard-rejecting a submitted level series at `POST /runs` — has no equivalent need
  here since this ticket controls its own transform at the source); this ticket's own returns transform is
  applied unconditionally, not conditionally-detected.
- **`ValidationConfig`**: `train_window=500, test_window=50, step=250, purge_gap=6` — identical to
  MR-004/MR-005's synthetic-data config, reused rather than re-derived (`purge_gap=6` is still the larger
  of the two horizons in scope here, 1 and 6).
- **Hyperparameters**: identical, fixed, no search — `LightGBMBaseline`/`RegimeHMMBaseline` are used
  exactly as already implemented, zero parameter changes.
- **CPU-only. Horizons: exactly 1 and 6** — no `24` in this ticket (MR-009's own scope).
- **Expected runtime ceiling**: same as MR-004/MR-005, **under 5 minutes** for the full new test file. The
  dev agent must time its own full pytest run and report the wall-clock seconds.

## Implementation acceptance criteria

- `research/real_data.py` defines a function (e.g. `load_real_hourly_returns(tenant_id, source, start,
  end, base_url, field=None) -> pd.Series`) that: calls `GET {base_url}/datasets/{source}/series` with
  `params={"start": ..., "end": ..., "field": ...}` (omitting `field` when `None`) and header
  `{"X-Tenant-Id": tenant_id}`; raises a clear, typed error (not a bare `requests`/`httpx` exception) on a
  non-2xx response or malformed JSON; builds a `pd.Series` with a sorted `pd.DatetimeIndex` from the
  response's `timestamps`/`values`; does **not** itself compute returns (that step is the caller's, kept
  separate so the raw-level series is inspectable/testable on its own, mirroring `dataset_source.py`'s own
  separation of "load a series" from "what the caller does with it").
- `research/tests/test_real_data_mr008.py` calls `load_real_hourly_returns` against the live
  `ingestion-service` container (`http://127.0.0.1:8003`, the same host-reachable port every other
  live-deploy verification in this repo already uses), applies `.pct_change().dropna()`, and runs
  `run_validation_protocol` with `config.extra_baselines=[LightGBMBaseline(), RegimeHMMBaseline()]` at
  `horizon=1` and `horizon=6`, using the exact `ValidationConfig` caps above.
- No `libs/naive_first_engine/src`, `research/models/*.py`, or any `services/` file touched — confirmed via
  `git status --porcelain libs/naive_first_engine research/models services/` empty at review time.
- `research/pyproject.toml` gains `httpx` as a dependency only if not already present (confirm before
  adding — `services/validation-service` already depends on it, `research/` may not).

  transformed series, asserting the returned `SplitResult` list is non-empty and each split's
  `baseline_results` contains both the `LightGBMBaseline` and `RegimeHMMBaseline` entries with MAE/RMSE/
  DA/F1 and a `DMResult` (not `None`) vs. Naive0.

  agent's written note, verified by the Tech Lead) — no test asserts either model "beats" Naive0.
- No regression check against the thesis's published numbers applies (this is real BTC data but a

  neither expected nor asserted).
