# DASH-009-02 — Flow-3 update: navigate via `DASH-005`'s real list page

**Status: todo**

## Analysis

Extends `DASH-009` (Selenium E2E suite, done in Sprint 11, see `docs/tickets/DASH-009.md`'s Outcome)
per Sprint 15's own explicit sequencing decision and dissent flag (`docs/sprints/sprint-15.md`, "The
`DASH-009` scope decision" section) — this is a same-story-ID completion of `DASH-009`'s
already-approved acceptance criteria, not a new backlog item. **Runs strictly after `DASH-005-01` is
built, merged, and personally verified working by the Tech Lead** — this ticket needs the real
`GET /runs` list page to exist and render correctly before its own test can be rewritten against it.

Backlog constraint being closed (`docs/product/backlog-dashboard-web.md`'s `DASH-009` entry, "Depends
on" line): "`DASH-005` (or its `DASH-005-GAP` fallback)" — the fallback was explicitly named as a
stand-in "since `DASH-005` is deferred," not a permanent alternative. `DASH-009.md`'s own Outcome
section documents flow 3 exactly as it exists today: navigates directly to the run id returned by flow
2's own submit-and-redirect, with an explicit warning against inventing any list-page substitute
(correct at the time — no list page existed). That condition no longer holds after `DASH-005-01`.

**Scope, deliberately narrow — do not expand beyond this**:
- `services/dashboard-web/tests/e2e/test_core_loop.py`: flow 3's navigation step only. Today this is
  folded into `test_submit_run_valid_payload_redirects_and_shows_completed_results` (flow 2 + flow 3
  combined, per that test's own docstring/comment). Change **only** the "how did we get to this run's
  detail page" step: instead of relying on the post-submit redirect URL directly, navigate to
  `GET /runs` (the new list page) and click the link for the run just created, then proceed with the
  same status-polling and DOM assertions already in place. Do not change the assertions about what's
  rendered on the detail page itself (status, splits table, DM verdict) — those are `DASH-004`'s
  concern, unchanged.
- `services/dashboard-web/tests/e2e/conftest.py`: touch only if a new fixture/helper is genuinely
  needed for this navigation (unlikely — `driver`/`live_server`/`stub_gateway_api` should already be
  sufficient).
- `services/dashboard-web/tests/e2e/stub_gateway_api.py`: **this file will very likely need a new
  `GET /runs` handler added** — the stub fixture only implements `/health`, `POST /runs`,
  `GET /runs/{id}`, `GET /runs/{id}/splits` today (see its own module docstring, "Implements only the
  four gateway-api endpoints DASH-009's three flows actually exercise"). Since flow 3 will now
  navigate via the real list page, and the real list page calls `GET /runs` on gateway-api, the stub
  must grow a matching `GET /runs` handler returning the same envelope shape as the real
  `gateway-api`/`validation-service` (`{"items": [...], "limit": ..., "offset": ..., "total": ...}`,
  items shaped like `RunSummaryResponse`) — built from the created runs already tracked in the stub's
  own `_runs` dict, most-recent-first (the stub can sort by its own `created_at`, no new dependency).
  This is necessary plumbing for the narrow scope above, not new capability — it makes the *fixture*
  match the real contract it's already supposed to be emulating, it adds no new page/route/behavior to
  `dashboard-web` itself.
- No new page, route, or template in `dashboard-web` itself — `DASH-005-01` already built the only
  page this ticket needs.
- **If, once started, this surfaces a need for new `dashboard-web` capability beyond what
  `DASH-005-01`/`DASH-009` already specify (e.g. the real list page's DOM structure makes locating the
  right row meaningfully harder than a plain `find_element` by id/text) — that's still in scope (a
  harder selector is not new capability). If it surfaces something genuinely bigger (e.g. the list page
  needs search/filter to find a specific run reliably in a real browser), stop and flag it back to the
  Tech Lead/requester rather than silently expanding scope.**
