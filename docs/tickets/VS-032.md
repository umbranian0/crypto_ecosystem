# VS-032 — Retention/pruning policy for `split_points`, storage-growth estimate

**Module**: `services/validation-service` only.
**Story**: RAV-006, second half — retention (non-negotiable per this story's own acceptance criteria:
must ship in the same unit of work as persistence, not deferred — split into its own ticket here only
because it is independently testable, still landing in the same sprint immediately after VS-031, no
gap where unbounded `split_points` growth is live in any deployed state).
**Depends on**: VS-031 (needs the `split_points` table/repository to exist).
**Blocks**: VS-032 → VS-033 (RAV-007's read path must respect this cutoff).

## Analysis

RAV-006's acceptance criteria (`docs/product/backlog-run-analysis-visualization.md`) require a
concrete, implemented, tested retention bound — default **90 days OR 20 runs per tenant/dataset,
whichever is simpler to implement correctly** — enforced by either a scheduled deletion/archival
script (matching this platform's existing standalone-operator-run-script convention, e.g.
`services/gateway-api/scripts/provision_tenant.py`/`services/ingestion-service/scripts/seed_tenant.py`)
or a query-time cutoff in the repository/query layer.

**Chosen bound: 90 days by age**, not "20 runs per tenant/dataset." Rationale: `split_points` rows
carry `created_at` copied from the owning run's creation time (VS-031's design) — a plain `created_at
>= cutoff` predicate is a single indexed comparison, with no `GROUP BY tenant_id, dataset_id ORDER BY
created_at DESC LIMIT 20`-style windowing query, no need to reach into `runs.dataset_id` via a join,
and no per-tenant-per-dataset bookkeeping table. This is the "whichever is simpler to implement
correctly" the story explicitly permits choosing.

**Chosen mechanism: both**, not either/or, because the story's two options solve different failure
modes and RAV-007 needs one of them anyway:
1. **Scheduled, operator-run deletion script** — `scripts/prune_split_points.py --older-than-days 90`
   (default `90`), matching `provision_tenant.py`/`seed_tenant.py`'s existing "standalone script,
   operator/cron invoked" convention (no new orchestration framework introduced). This is what
   actually bounds the table's physical size regardless of whether anyone ever queries it — the
   real, primary mechanism.
2. **Query-time cutoff in `SplitPointRepository.get_points`** — a defense-in-depth read-path filter
   (`created_at >= now() - 90 days`) so that even in the window between two scheduled prune runs, a
   read never serves data past the retention bound. This is also what RAV-007 (VS-033) needs directly
   — "reads respect the retention cutoff" is that story's own acceptance criterion, satisfied here by
   construction rather than re-implemented in VS-033.

Both are real and tested, not "one documented, one stubbed" — the story's own words ("must be real and
testable... not merely a docstring claiming the policy exists") are treated as applying to whichever
mechanism(s) are chosen, plural in this case.

## Design

**Design pattern**: none from implementation-plan.md section 7 applies newly here — this is a
Repository-layer method extension (the same pattern VS-031 already introduced) plus a standalone
script, not a new pattern.

Files touched (scoped to `validation-service` only):
- `src/app/repositories/interfaces.py` — `SplitPointRepository.get_points` gains a docstring
  contract change (not a signature change): "returns only points with `created_at` within the
  retention window" — enforced inside the SQLite/Postgres implementations, not the caller.
- `src/app/repositories/sqlite_repository.py` / `postgres_repository.py` — `get_points` adds a
  `WHERE created_at >= :cutoff` predicate; `cutoff` computed from a module-level
  `SPLIT_POINT_RETENTION_DAYS = 90` constant (same "named constant, not a magic number" convention
  `MAX_SPLIT_COUNT`/`LAG1_AUTOCORR_THRESHOLD` already establish in this module) so a single place
  controls the bound both the script and the repository read.
- `scripts/prune_split_points.py` (new) — standalone script, same shape as
  `services/gateway-api/scripts/provision_tenant.py` (argparse, connects via `DATABASE_URL`/
  `VALIDATION_SERVICE_DB_PATH` env var same as the app itself, prints a summary of rows deleted).
  `--older-than-days` optional arg, default `SPLIT_POINT_RETENTION_DAYS` (imported from the repository
  module, not a second hardcoded `90`).
- **Storage-growth estimate** — written into this ticket file's Outcome section and into
  `services/validation-service/README.md` (not only here): rows = tenants × runs-per-tenant-per-90-days
  × splits-per-run × test-window-length × baselines-per-split. Using this platform's own disclosed
  real numbers as anchors (README's RSS-005 entry: up to 38,597 splits/run is possible but
  `MAX_SPLIT_COUNT=500` caps it; a typical `test_window` is on the order of hundreds of rows per the
  same RSS-005 example): a illustrative pilot-scale estimate — 10 tenants × 20 runs (90-day/20-run
  bound, whichever binds first) × 50 splits/run (well under the 500 cap) × 200-row test window × 2.3
  baselines/split avg (2 mandatory + ~30% of runs carrying a client baseline) ≈ **~46,000,000 rows**
  at steady state before the 90-day cutoff starts pruning. This is presented as an order-of-magnitude
  planning number, not a guarantee — real tenant/run/config volume is not yet known (no pilot client
  exists yet, per this service's own README disclosure). Flagged explicitly: this volume is why
  RAV-007 (VS-033) must paginate/scope-by-split rather than returning a whole run's points in one
  response.

**DRY check note**: grepped `services/*/scripts/` for an existing prune/deletion script — none exists;
`provision_tenant.py`/`revoke_api_key.py`/`seed_tenant.py` are the closest precedent for "standalone
script, env-var-driven DB connection, argparse CLI" shape, reused structurally (import pattern, env
var names) rather than copy-pasted verbatim (different domain logic).

## Implementation acceptance criteria

- [x] `SPLIT_POINT_RETENTION_DAYS = 90` is a single named constant, imported by both the repository
      implementations and `scripts/prune_split_points.py` — no second hardcoded `90`.
- [x] `SplitPointRepository.get_points` (both SQLite and Postgres implementations) excludes rows older
      than the retention cutoff.
- [x] `scripts/prune_split_points.py` connects to the same DB the running service uses (env-var driven,
      same convention as the app's own `DATABASE_URL`/`VALIDATION_SERVICE_DB_PATH`), deletes
      `split_points` rows with `created_at` older than `--older-than-days` (default 90), and prints a
      count of rows deleted — runnable standalone (`python scripts/prune_split_points.py`), no app
      process dependency.

## Test acceptance criteria

- [x] **Non-negotiable per RAV-006's own acceptance criteria**: a test proves old data is actually
      excluded/removed, not merely asserted as "the policy exists in code." Two tests required:
      1. Repository-level: insert `split_points` fixture rows with `created_at` both inside and outside
         the 90-day window (direct DB insert, bypassing the write path, to control `created_at`
         precisely); `get_points` returns only the in-window rows.
      2. Script-level: same fixture setup; run `prune_split_points.py`'s core deletion function (or
         invoke the script via subprocess against a test DB) and assert the out-of-window rows are
         physically gone from the table afterward (a direct `SELECT COUNT(*)` against the underlying
         table, not through the repository) while in-window rows remain untouched.
- [x] Test confirms the constant `SPLIT_POINT_RETENTION_DAYS` is the single source both mechanisms
      read (e.g. patching the constant changes both the query cutoff and the script's default in one
      place, proven by a test that patches it and observes both).

## Outcome

**Status: implemented, tests passing, Postgres-live-verification disclosed as not done this session.**

Files changed (all within `services/validation-service`):
- `src/app/repositories/interfaces.py` — `SplitPointRepository.get_points`'s docstring documents the
  retention-window contract (no signature change).
- `src/app/repositories/sqlite_repository.py` — new `SPLIT_POINT_RETENTION_DAYS = 90` module constant,
  new `_retention_cutoff()` helper (reads the module global at call time, not a default-argument capture,
  so `monkeypatch.setattr` on the constant is observed immediately), `SQLiteSplitPointRepository.get_points`
  gains a `SplitPoint.created_at >= _retention_cutoff()` predicate.
- `src/app/repositories/postgres_repository.py` — imports and reuses the same `_retention_cutoff` helper
  (no second copy of the cutoff arithmetic); `PostgresSplitPointRepository.get_points` gains the identical
  predicate.
- `scripts/prune_split_points.py` (new) — argparse CLI, `--older-than-days` default
  `SPLIT_POINT_RETENTION_DAYS` (imported, not re-hardcoded), resolves its DB connection via
  `app.dependencies.repositories`'s existing env-var/URL-resolution helpers, issues one
  `DELETE FROM split_points WHERE created_at < :cutoff`, prints the row count deleted. Core logic split
  into `prune_split_points(engine, older_than_days) -> int`, separate from the CLI wrapper, so tests can
  call it directly without subprocessing.
- `tests/test_split_point_retention.py` (new) — three tests: repository-level exclusion, script-level
  physical deletion (`SELECT COUNT`/`SELECT id` against the raw table, not through the repository), and a
  single-source-of-truth test that monkeypatches `SPLIT_POINT_RETENTION_DAYS` and observes both
  `get_points` and `prune_split_points` change behavior together.
- `services/validation-service/README.md` — new "Retention/pruning policy" paragraph appended to the
  `split_points` section, documenting the bound, both mechanisms, script invocation, and the
  storage-growth estimate.

**Mutation-style sanity check (self-performed, matching the Review AC's own instruction)**: both the
`get_points` cutoff predicate and the script's `DELETE ... WHERE created_at < cutoff` clause were each
temporarily neutered in turn and the new test file re-run — the relevant tests failed both times (query
cutoff removed: 2 of 3 tests fail; deletion predicate weakened to match nothing: 2 of 3 tests fail), then
both mutations were reverted. Confirms the tests are not vacuously passing.

**Storage-growth estimate** (formula: `rows = tenants × runs-per-tenant × splits-per-run ×
test-window-length × baselines-per-split`), same assumption set as this ticket's own Design section (10
tenants, 20 runs/tenant within the 90-day window, 50 splits/run, 200-row test window, 2.3 baselines/split
average): `10 × 20 × 50 × 200 × 2.3 = 4,600,000` rows. **This corrects the Design section's own
~46,000,000 figure**, which was a 10x arithmetic overstatement for the identical assumption set (re-derived
during this ticket's implementation, per the Documentation acceptance criterion's instruction to verify,
not just copy, the number) — 4,600,000 is the number now carried into README.md. Still an
order-of-magnitude planning figure, not a guarantee (no pilot client exists yet); the underlying
conclusion (RAV-007/VS-033 must paginate rather than return a whole run's points in one response) is
unaffected by the correction — 4.6 million rows is still large enough that an unpaginated
`GET /runs/{id}/points`-style response would be impractical.

directory — **217 passed** on the run counted for this ticket (includes the 3 new retention tests). One
