# RPT-002-02 -- reporting-service `consistency_trend` report kind

**Status: done.** Module: `services/reporting-service` only. Depends on RPT-002-01 (import `naive_first_common.consistency`). Story: RPT-002. Sprint: docs/sprints/sprint-65.md. Read services/reporting-service/README.md first.

## Analysis
Archivable point-in-time snapshot of "beat Naive0 in N of M completed runs" for a (dataset_id, horizon) group, same grouping as dashboard-web `GET /runs/trend` (see `runs_trend`, `_fetch_all_runs`, `_fetch_bounded_run_splits`, `MAX_RENDERED_SPLITS = 500` in services/dashboard-web/src/app/routers/runs.py). Interpretation (disclosed): "reads through the same contract" = reporting-service reads validation-service's `GET /runs` (paged, limit 100, `{items,limit,offset,total}`) and `GET /runs/{id}/splits/count` + `GET /runs/{id}/splits?limit&offset` with `X-Tenant-Id`, exactly the contract the gateway proxies; no new aggregation, rule from the shared lib. Honest framing: copy states "beat Naive0 in N of M completed runs", never prediction/signal/economic value; carries the platform's statistical-accuracy-is-not-economic-value disclaimer (reuse what `templates/validation_audit.html.jinja` and `naive_first_common.disclosures` already provide, do not reword); has_data False renders "no completed runs matched this selection", never "0 of 0"; may append `NOT_BEATING_NAIVE_IS_EXPECTED_SENTENCE` when has_data and beat_count == 0.

## Design
- Factory (`renderers/factory.py`): add `"consistency_trend"` branch; unknown kinds still raise `UnknownReportKindError`. The existing `ReportRenderer.render(run, splits)` interface does not fit a multi-run input: add a sibling ABC `TrendReportRenderer` in `renderers/base.py` with `render(dataset_id, horizon, runs_with_splits) -> str` (runs_with_splits = list of (RunSummaryResponse, list[SplitResultResponse])) and implement `ConsistencyTrendRenderer` in `renderers/consistency_trend.py` + `templates/consistency_trend.html.jinja`. Factory return type becomes the union; keep the Factory the only kind dispatch.
- Content: header with scope (dataset_id, horizon), the N-of-M headline from `compute_consistency_indicator`, one row per completed run (run id, created/completed time, per-run outcome: beat / did not beat / not evaluable via `run_beats_naive0`, and counts of better/worse/no-significant/undefined splits via `verdict_category`), methodology/disclaimer. Table only; no charts. Autoescape on.
- `generation.py`: new `generate_consistency_trend_report(tenant_id, dataset_id, horizon, client, repository, renderer_factory=get_report_renderer)`; reuse the existing `_call_downstream`/error classes (DRY; raise DownstreamResponseError on non-2xx). Filter runs to dataset_id+horizon+status "completed". Bound splits per run to the most recent 500 by the same count-then-offset rule as dashboard-web (define a constant in reporting with a comment that it must match dashboard-web's MAX_RENDERED_SPLITS so counts equal /runs/trend). Zero matching runs still produces a report with the no-data state. Persist via `repository.create_report(tenant_id, run_id=<scope key>, report_kind="consistency_trend", content, status="generated")`.
- Storage decision (Tech Lead, no migration): `reports.run_id` is NOT NULL and a trend has no run, so the scope is stored by documented convention in `run_id` as `consistency_trend:{dataset_id}:{horizon}`. Rationale: an additive migration plus RLS review is not justified for a Could story with no pilot ask; revisit if a second scoped kind appears. Document in models.py comment, README, and ticket outcome. No schema change.
- Router (`routers/report_generation.py`): `GenerateReportRequest` gains `kind: Literal["validation_audit","consistency_trend"] = "validation_audit"`, `run_id: str | None = None`, `dataset_id: str | None = None`, `horizon: int | None = None` with a model validator: validation_audit requires run_id (and rejects dataset_id/horizon), consistency_trend requires dataset_id and horizon (and rejects run_id) -> 422. A request with only `run_id` behaves byte-identically to today (same 201 body, same errors). Tenant only from `get_tenant_context`. Map existing exceptions as today.
- Pattern: Factory (existing, extended). DRY check: reuse `_call_downstream`, error classes, jinja Environment setup (extend `_env` rather than a second Environment if reasonable), disclosure constants.
