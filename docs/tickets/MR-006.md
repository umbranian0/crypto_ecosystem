  persisted per split alongside each split's metrics, so that the thesis's stated gap ('Explicabilidade
  consistente por split... Arquivo não guarda feature importance/SHAP por split,' section 1.6) is closed

- Acceptance criteria (backlog, verbatim):

  2. Artifacts are stored/reported through the existing report pipeline (same reporting-service path as
     metrics), not a parallel ad hoc file dump.
  3. Explicitly out of scope for MR-004/MR-005's initial "does it beat naive" question — additive
     instrumentation, not a precondition for those stories' own closure.
- Depends on: MR-004 (done), MR-005 (done) — this ticket covers both model shapes in one pass, per
  Sprint 42's explicit deferral reasoning.
- **Binding scope decision (sprint-43.md, not re-derived here)**: feature-importance-only, no SHAP, no new
  dependency. `LightGBMBaseline`: read `LGBMRegressor.feature_importances_` off the fitted object.
  `RegimeHMMBaseline`: per-state `LinearRegression.coef_`/`.intercept_` plus per-row active-state
  assignment for the test fold — SHAP does not map cleanly onto an HMM gate without inventing a
  background-distribution/sampling scheme, which this scope explicitly declines to do.
- **"Existing report pipeline" resolution (sprint-43.md, not re-derived here)**: `services/
  reporting-service` (trigger #7) is not built yet, so this reads as "the same in-process
  `SplitResult`-shaped output convention `research/`'s existing MR-004/MR-005 tests and README already
  use" — not a new persistence layer, not a raw pickle/CSV dump, and not a premature build-out of
  `reporting-service` itself.
- Routing note (this sprint's ML-adjacent-ticket rule): this ticket reads explainability artifacts off
  models consumed via `naive_first_engine`'s `Baseline`/`extra_baselines` contract, so it follows
  `/ml-engineer`'s design→test→review sequencing and `/ml-feature-planning`'s train-only-fitting
  discipline. Tech Lead review personally checks: no `.fit()` call anywhere in the explainability path
  beyond the one `predict()` already performs, Pydantic/contract-shape questions don't apply here (no API
  boundary — `research/` has no service surface), and no CLAUDE.md positioning-rule violation in new
  docstrings describing "explainability."

  `ExplainableRegimeHMM` in the new `research/explainability.py` are additional `Baseline`-protocol
  Strategy implementations, registered via `config.extra_baselines` exactly like MR-004/MR-005's own
  unwrapped classes. No change to the `Baseline` Protocol or `naive_first_engine`'s `SplitResult`/
  `run_validation_protocol` machinery — this ticket adds Strategy implementations, it does not modify the
  pattern's own machinery or the Template Method (`run_validation_protocol`) that drives it.
- Files touched, scoped to `research/` only:
  - `research/explainability.py` (new) — `ExplainabilityRecord` dataclass, `ExplainableLightGBM`,
    `ExplainableRegimeHMM`, `pair_with_split_results`.
  - `research/models/gradient_boosting.py` (changed) — `LightGBMBaseline.predict`'s body extracted into a

    `predict()` now calls it and discards the second return value. `predict()`'s own observable behavior

  - `research/models/regime_hmm.py` (changed) — same refactor pattern: `RegimeHMMBaseline.predict`'s body
    extracted into `_fit_predict_and_explain(train, test) -> tuple[pd.Series, dict]`; `predict()` now
    calls it and discards the second return value.
  - `research/tests/test_explainability.py` (new).
  - No `libs/naive_first_engine` or `services/` file touched (confirmed, see Review section).
- **DRY check**: grepped `research/` before writing anything — no existing explainability/SHAP/
  feature-importance code anywhere in the repo. Reused, not duplicated: `naive_first_engine`'s own
  `Baseline` Protocol/`ValidationConfig`/`run_validation_protocol` (imported, not reimplemented);
  `research/tests/fixtures.py::synthetic_hourly_returns` (the exact MR-004/MR-005 fixture, no new
  synthetic-data generator); MR-004/MR-005's own fit logic itself (extracted into a shared private
  function rather than re-implemented a second time for the explainability path — this is the specific
  DRY move this ticket makes: one fit implementation, two callers (`predict()` and the explainability
  wrapper), not two independent fit implementations that could silently drift apart).

## Why a wrapper and not a `naive_first_engine` change

The `Baseline` protocol's `predict(train, test) -> pd.Series` signature is deliberately narrow (see
`baselines.py`'s own docstring on the leakage-safety argument for that narrowness) and `SplitResult`
carries only metrics/DM-result per baseline key. Rather than growing `SplitResult` or `Baseline` to
carry an optional explainability payload (a high-scrutiny `naive_first_engine` change per this backlog's
own architecture-decision section), each `predict()` call already IS the one point where a given split's
model gets fit — `ExplainableLightGBM`/`ExplainableRegimeHMM` intercept that same call (by wrapping the
same underlying `_fit_predict_and_explain` function MR-004/MR-005's own unwrapped classes call), append
the artifact this call already produced to `self.records`, and return the identical prediction. After
`run_validation_protocol` returns its own unmodified `list[SplitResult]`, `pair_with_split_results` zips
it with the wrapper's `records` by `split_index` — both lists are produced in the same per-split order by
construction (the wrapper's `predict()` is called exactly once per split, in the same loop that builds
each `SplitResult`). This path worked cleanly; `libs/naive_first_engine` was never touched, so the
escalation path sprint-43.md described was not needed.

## Implementation acceptance criteria

- `research/explainability.py` defines `ExplainableLightGBM`/`ExplainableRegimeHMM`, each conforming to
  the `Baseline` Protocol (`.predict(train, test) -> pd.Series`, `.name` attribute) and each internally
  delegating to the same `_fit_predict_and_explain` function the corresponding unwrapped
  `LightGBMBaseline`/`RegimeHMMBaseline` class calls — one fit implementation, not two.
- `ExplainableLightGBM.records` accumulates one `ExplainabilityRecord` per `predict()` call, `artifact`
  being a `pd.Series` of `feature_importances_` indexed by feature name.
- `ExplainableRegimeHMM.records` accumulates one `ExplainabilityRecord` per `predict()` call, `artifact`
  being a `dict` with `"state_coefficients"` (per state: `coef`, `intercept`, `features`) and
  `"test_state_assignment"` (a `pd.Series`, indexed like that split's `test` fold, of HMM-decoded states).
- `pair_with_split_results(split_results, wrapper)` zips `run_validation_protocol`'s own `SplitResult`
  list with the wrapper's `records` by `split_index`, raising on any length/index mismatch.
- No `libs/naive_first_engine/src` file touched.
- No new dependency added to `research/pyproject.toml` — both artifacts use functionality already present
  (`lightgbm`, `scikit-learn`) via MR-004/MR-005's existing dependencies.
- `LightGBMBaseline.predict`/`RegimeHMMBaseline.predict` themselves are unchanged in observable behavior:
  same prediction output, same "no instance attribute ever set" invariant.

## Test acceptance criteria

- A test proving no second `.fit()` call anywhere in the explainability path: spies on
  `LGBMRegressor.fit`/`GaussianHMM.fit` during a full `run_validation_protocol` run using the wrapper as
  `extra_baselines`, and asserts the fit-call count equals exactly the number of splits (one fit per
  split, not two) — mirroring MR-004/MR-005's own re-instantiated-per-split leakage-discipline test
  precedent.
- A test proving `ExplainableLightGBM`'s predictions are bit-identical to plain `LightGBMBaseline`'s
  predictions on the same train/test split — confirms the wrapper's fit logic is genuinely the same code
  path, not a divergent implementation that happens to look similar.
- Tests asserting each artifact's shape for both model classes (non-empty `pd.Series` for LightGBM;
  `state_coefficients`/`test_state_assignment` keys present for the HMM model).
- A test proving `pair_with_split_results` correctly pairs each `SplitResult` with its
  `ExplainabilityRecord` by `split_index`, for both model shapes at both horizons (1h, 6h).
- No regression check against the thesis's published numbers applies (same reasoning as MR-004/MR-005 —
  this is instrumentation on a synthetic-data research baseline, not a reproduction of a published result
  row).
- No test asserts either model "beats" Naive0 — explainability is orthogonal to that question, per AC3.
