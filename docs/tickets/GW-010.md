## Analysis

Story: an operator-only path to revoke an API key, so a leaked or rotated key stops working
immediately without deleting/recreating the tenant. Acceptance criteria (verbatim):
- An endpoint or operator path sets `api_keys.revoked_at`, using GW-004's already-tested revocation
  semantics.
- A revoked key fails GW-006's auth check on the very next request (no caching window).

**Non-negotiable care condition**: keep this strictly an operator-facing path (CLI script or an
operator-gated endpoint, mirroring GW-005's "not a public sign-up flow" framing) — never a tenant
self-service revocation endpoint. No caching layer on the revocation check that could reintroduce a
window where a revoked key stays valid.

**What's already built, confirmed by reading the code directly** (not re-derived): `api_keys.revoked_at`
already exists on the model (GW-002); `ApiKeyRepository.revoke_key(tenant_id, key_id) -> None` is
already declared on the interface and already implemented on both `SQLiteApiKeyRepository` and
`PostgresApiKeyRepository` (`services/gateway-api/README.md`'s "Storage backend" section: "`revoke_key`
sets the `revoked_at` column rather than deleting the row on both backends"); `get_authenticated_tenant`
(GW-006, `dependencies/auth.py`) already rejects `record.revoked_at is not None` with a `401`. **This
ticket's actual scope is narrow**: there is currently no caller anywhere in `gateway-api` that invokes
`ApiKeyRepository.revoke_key` — this ticket adds the one missing call site.

## Design

**No new pattern from section 7** — this reuses the existing Repository interface
(`ApiKeyRepository.revoke_key`, already defined and implemented) and the existing DI seam
(`ApiKeyRepositoryDep`). This ticket is "the missing caller," not new architecture.

**Operator path choice**: a standalone CLI script, `services/gateway-api/scripts/revoke_api_key.py`,
mirroring `scripts/provision_tenant.py` (GW-005) exactly in shape and rationale — a script run by
whoever already has host/operator access, not an endpoint needing its own auth mechanism. This is the
lower-risk choice explicitly named as acceptable by the care condition ("CLI script or an
operator-gated endpoint") and avoids adding any new authenticated surface to `gateway-api` at all,
which is the more conservative choice for a Should-priority hardening item.

**Files touched** (new file only, plus one README section — zero edits to `dependencies/auth.py`,
confirmed as the sprint's own file-collision analysis expected):
- `services/gateway-api/scripts/revoke_api_key.py` (new).
- `services/gateway-api/tests/test_revocation.py` (new).
- `services/gateway-api/README.md` — new section, mirroring the existing "Provisioning (GW-005)"
  section's structure and tone.

**DRY check performed**: read `scripts/provision_tenant.py` in full — its `main()`/argparse/DI-provider
pattern (`get_api_key_repository()`, called directly, not through FastAPI's request cycle) is the
exact shape to copy for this script's own `main()`. Read `ApiKeyRepository`'s interface — `revoke_key`
takes `(tenant_id, key_id)`, both required; this script therefore needs a way to look up a key's id
given identifying information an operator plausibly has (a raw key, or a tenant id + listing). Since
`ApiKeyRepositoryDep`'s interface has no "list keys for tenant" method today, and adding one is outside
this ticket's minimal scope, the pragmatic operator workflow is: **revoke by presenting the raw API
key** (the operator has this on hand — it was printed once at provisioning time, GW-005) — the script
hashes it the same way `auth.py`'s `get_authenticated_tenant` does (`hashlib.sha256(...).hexdigest()`,
reused, not re-derived) and calls `ApiKeyRepository.get_by_hash(key_hash)` (already exists) to resolve
the `tenant_id`/`key_id`, then calls `revoke_key(tenant_id, key_id)`. This reuses two already-existing
repository methods (`get_by_hash`, `revoke_key`) with zero new repository/interface surface — the
minimal-scope option the Design section above commits to.

**No caching layer, explicitly**: confirm `get_authenticated_tenant` (GW-006) is not modified by this
ticket and that no new caching/memoization wraps `get_by_hash` anywhere in this diff — the care
condition's "no window where a revoked key stays valid" is satisfied by construction today (every
request calls `get_by_hash` fresh) and this ticket must not regress that.
