  120–132) is a pure, stateless four-way aggregation: `_own_health_status(engine)` (this service's own DB)
  plus one `_downstream_health_status(client)` call each for `validation-service`/`reporting-service`/
  `ingestion-service`. Each sub-check already returns exactly one of `"ok"`/`"unhealthy"` (own) or
  `"ok"`/`"degraded"`/`"unreachable"` (downstream). Nothing here stores state or runs on a schedule.
- `services/gateway-api/src/app/main.py` (read in full) has no `lifespan=`/`@app.on_event` hook of any

- No recurring in-process background-job precedent exists anywhere in this repo (confirmed by the sprint
  plan's repo-wide grep, independently spot-checked here) — this is the platform's first one. The nearest
  analogous shape is `services/reporting-service/src/app/subscriber.py`'s `run_subscriber` loop (a
  `while` loop with a `max_events` test seam so tests can drive a bounded number of iterations of the
  *same* running loop instead of looping forever) — this ticket's polling loop follows that same
  `max_iterations` test-seam shape, not a new invention.
- `libs/ai_assist/src/naive_first_ai_assist/client.py`'s `get_assist_client()` (lines 79–98) is the real,
  confirmed precedent for "optional env var, unset by default, returns `None`/does nothing rather than
  raising" — `os.environ.get(url_env)` with no default, `if not base_url: return None`. This ticket's
  `MONITORING_WEBHOOK_URL` follows the identical shape: read via `os.environ.get`, no default value, `None`
  means fully inert.
- `services/gateway-api/src/app/dependencies/repositories.py`'s `get_health_check_engine()` and
  `services/gateway-api/src/app/dependencies/http_client.py`'s `get_validation_service_client()`/
  `get_reporting_service_client()`/`get_ingestion_service_client()` are **already plain, undecorated
  functions** (FastAPI's `Depends()` wrapping is applied only at the route-handler parameter, via the
  `*Dep = Annotated[..., Depends(...)]` aliases) — they can be called directly from a background task with
  no FastAPI request/DI context needed at all. This is what makes reusing the health-aggregation logic
  outside a request straightforward: no fake `Request` object, no DI-context hack required.
- **Critical testability finding, confirmed by reading Starlette's `TestClient` source directly (not
  assumed)**: `services/gateway-api/tests/`'s existing 65 call sites all construct `TestClient(app)`
  directly, never `with TestClient(app) as client:`. `starlette.testclient.TestClient.__enter__` is the
  *only* place that starts a portal and runs `lifespan` startup/shutdown (`portal.start_task_soon(self.lifespan)`
  / `portal.call(self.wait_startup)`); a bare `TestClient(app).get(...)` call never enters that context
  manager, so it **never triggers `lifespan` at all**. This means: (a) adding a `lifespan=` hook to `main.py`
  is safe for all 65 existing tests — none of them will spawn the new background task, no behavior change,
  no slowdown, no accidental real network calls at collection/import time; (b) this ticket's own new tests
  that need to exercise the polling loop must either call `evaluate_and_notify`/`run_health_monitor`
  directly as plain async functions (preferred — no TestClient involvement needed at all, since neither
  function touches FastAPI routing) or explicitly use `with TestClient(app) as client:` if a test genuinely
  needs the ASGI lifespan wiring itself exercised (e.g. proving `main.py`'s `lifespan=` argument actually
  launches the task) — don't assume the existing bare-`TestClient(app)` idiom exercises it.

**Constraint from the docs**: `implementation-plan.md` section 2 — this stays entirely inside
`gateway-api`'s own module boundary; the webhook target is an external operator-configured URL, not
another service in this platform, so "no service imports another service's code" is not implicated.
CLAUDE.md positioning: this payload carries only `gateway-api`'s own aggregate infrastructure-health
status (`"healthy"`/`"non-healthy"`, derived from DB/HTTP reachability checks) — no price, prediction, or

## Design

**Pattern**: none of `implementation-plan.md` section 7's table is force-fit here. This is a plain polling
loop plus one best-effort outbound HTTP call — not Strategy (no swappable implementations), not Repository
(no persistence), not Observer/pub-sub in the section-7 sense (that entry names the Redis Streams
`run.completed` mechanism specifically; this is a direct outbound HTTP POST to an operator-configured URL,
not a new internal event published to Redis Streams — a genuinely different mechanism, not a second
instance of the same one). Dependency Injection is not used for the background task's own dependencies
either (per the testability finding above, it calls the plain provider functions directly, bypassing
`Depends()`, since there is no FastAPI request in flight for a background task to be injected into).

2. `services/gateway-api/src/app/health_monitor.py` (**new module**, top-level under `app/`, not under
   `routers/` — it owns no HTTP route, same precedent `provisioning.py` already establishes for a
   non-router top-level module):
   ```python
   """ADMIN-001: gateway-api's first recurring in-process background task.

   [module docstring: why this exists, why lifespan+asyncio.Task rather than
   an external cron endpoint (see docs/sprints/sprint-59.md's scope-decision
   section), single-instance in-memory previous_status only, no
   escalation/multi-channel/ack/paging scope -- point a future reader at the
   sprint file and this ticket rather than re-deriving the reasoning inline.]
   """

   from __future__ import annotations

   import asyncio
   import logging
   import os
   from datetime import datetime, timezone

   import httpx

   from app.dependencies.http_client import (
       get_ingestion_service_client,
       get_reporting_service_client,
       get_validation_service_client,
   )
   from app.dependencies.repositories import get_health_check_engine
   from app.routers.system import compute_system_health

   logger = logging.getLogger(__name__)

   _WEBHOOK_URL_ENV_VAR = "MONITORING_WEBHOOK_URL"
   _POLL_INTERVAL_ENV_VAR = "HEALTH_MONITOR_POLL_INTERVAL_SECONDS"
   _DEFAULT_POLL_INTERVAL_SECONDS = 60.0
   _WEBHOOK_TIMEOUT_SECONDS = 5.0

   _HEALTHY = "healthy"
   _NON_HEALTHY = "non-healthy"


   def _collapse_status(status: dict[str, str]) -> str:
       """All four sub-checks 'ok' -> healthy; any 'degraded'/'unhealthy'/
       'unreachable' -> non-healthy (AC's two-way collapse of the existing
       three-way per-sub-check vocabulary)."""
       return _HEALTHY if all(value == "ok" for value in status.values()) else _NON_HEALTHY


   def _send_webhook(webhook_url: str, previous_status: str, current_status: str) -> None:
       payload = {
           "event": "health_transition",
           "previous_status": previous_status,
           "current_status": current_status,
           "at": datetime.now(timezone.utc).isoformat(),
       }
       try:
           response = httpx.post(webhook_url, json=payload, timeout=_WEBHOOK_TIMEOUT_SECONDS)
           if response.status_code >= 400:
               logger.warning(
                   "health_monitor: webhook receiver returned %s for health_transition %s->%s",
                   response.status_code, previous_status, current_status,
               )
       except httpx.HTTPError as exc:
           # OPS-006 structured logging (plain logging.getLogger(__name__),
           # picked up by the already-configured JSON formatter) -- log and
           # drop, never re-raise: a bad webhook receiver must never affect
           # the health-evaluation path itself.
           logger.warning(
               "health_monitor: webhook delivery failed for health_transition %s->%s: %s",
               previous_status, current_status, exc,
           )


   def _compute_current_status() -> str:
       engine = get_health_check_engine()
       validation_client = get_validation_service_client()
       reporting_client = get_reporting_service_client()
       ingestion_client = get_ingestion_service_client()
       try:
           status = compute_system_health(engine, validation_client, reporting_client, ingestion_client)
       finally:
           validation_client.close()
           reporting_client.close()
           ingestion_client.close()
       return _collapse_status(status)


   async def evaluate_and_notify(
       previous_status: str | None,
       *,
       compute_status=_compute_current_status,
       webhook_url: str | None = ...,  # sentinel: read MONITORING_WEBHOOK_URL if not overridden
   ) -> str:
       """One evaluation cycle. Returns the new previous_status for the
       caller to remember (single-instance, in-memory only -- no external
       store, per the sprint's disclosed scope decision).

       previous_status=None means "no real baseline yet" (first-ever
       evaluation, or just-restarted process) -- never fires a webhook on
       this cycle regardless of the computed status, since there is nothing
       genuine to compare against yet (a restart resets the baseline rather
       than misfiring a spurious transition, per the sprint plan).
       """
       current = compute_status()

       if previous_status is not None and current != previous_status:
           url = os.environ.get(_WEBHOOK_URL_ENV_VAR) if webhook_url is ... else webhook_url
           if url:
               _send_webhook(url, previous_status, current)

       return current


   async def run_health_monitor(*, max_iterations: int | None = None) -> None:
       """Sleeps/wakes on HEALTH_MONITOR_POLL_INTERVAL_SECONDS (default 60s,
       disclosed in README). max_iterations is a test-only seam (same shape
       as subscriber.py's max_events) letting tests drive a bounded number of
       iterations of the same loop instead of looping forever.

       Never lets one bad evaluation cycle (e.g. a DB hiccup) kill the loop --
       caught, logged, previous_status left unchanged, retried next interval.
       """
       interval = float(os.environ.get(_POLL_INTERVAL_ENV_VAR, _DEFAULT_POLL_INTERVAL_SECONDS))
       previous_status: str | None = None
       iterations = 0
       while max_iterations is None or iterations < max_iterations:
           try:
               previous_status = await evaluate_and_notify(previous_status)
           except Exception:
               logger.exception("health_monitor: evaluation cycle failed, retrying next interval")
           iterations += 1
           if max_iterations is not None and iterations >= max_iterations:
               break
           await asyncio.sleep(interval)
   ```
   Exact function names/signatures above may be adjusted by the dev agent if a cleaner shape is found, but
   the following are **fixed contract, not negotiable**: (a) `compute_system_health` is called, not
   duplicated; (b) `MONITORING_WEBHOOK_URL` unset means zero `httpx.post` attempts, ever; (c)
   `previous_status=None` (first-ever cycle) never fires a webhook; (d) a webhook delivery failure
   (exception or non-2xx) is caught and logged, never raised out of `evaluate_and_notify`/
   `run_health_monitor`; (e) one bad evaluation cycle (exception anywhere in `compute_status()`) is caught
   at the `run_health_monitor` loop level and logged, never kills the loop.

3. `services/gateway-api/src/app/main.py` — add a `lifespan` async context manager, wired into the
   existing `FastAPI(...)` construction via `lifespan=lifespan` (new keyword argument; no other change to
   that call):
   ```python
   import asyncio
   import contextlib

   from app.health_monitor import run_health_monitor

   @contextlib.asynccontextmanager
   async def lifespan(app: FastAPI):
       # ADMIN-001: gateway-api's first recurring in-process background task
       # -- see health_monitor.py's module docstring / docs/sprints/
       # sprint-59.md for why lifespan+asyncio.Task, not an external cron
       # endpoint, and why single-instance in-memory state is the right
       # scope call for this phase.
       task = asyncio.create_task(run_health_monitor())
       try:
           yield
       finally:
           task.cancel()
           with contextlib.suppress(asyncio.CancelledError):
               await task

   app = FastAPI(
       title="gateway-api",
       description="The only internet-facing service (see README.md).",
       version="0.1.0",
       lifespan=lifespan,
   )
   ```
   No other line in `main.py` changes. Per the testability finding in Analysis, this is safe for all
   existing tests (none of them enter `TestClient`'s context-manager form, so none of them trigger this).

## Implementation acceptance criteria

- [x] `MONITORING_WEBHOOK_URL` env var, optional, unset by default, read the same way
  `NARRATIVE_API_URL`/`get_assist_client` reads its env var (`os.environ.get`, no default, absence means
  inert) — when unset, the polling task still runs (keeps `previous_status` warm) but never calls
  `httpx.post`.
- [x] `gateway-api` polls the same four-way aggregate health logic `GET /system/health` exposes
  (`compute_system_health`, reused via import, not duplicated) on a fixed interval
  (`HEALTH_MONITOR_POLL_INTERVAL_SECONDS`, default `60.0` seconds, disclosed in README).
- [x] Transition definition: all four sub-checks `"ok"` = `"healthy"`; any sub-check `"degraded"`,
  `"unhealthy"`, or `"unreachable"` = `"non-healthy"` (two-way collapse of the existing three-way
  vocabulary, exactly as the sprint plan specifies).
- [x] On a genuine `"healthy"` <-> `"non-healthy"` change from the previous evaluation, exactly one POST
  fires to `MONITORING_WEBHOOK_URL` with body `{"event": "health_transition", "previous_status": ...,
  "current_status": ..., "at": ...}` — no extra fields, no schema versioning.
- [x] No POST fires when the evaluated status is unchanged from the previous evaluation (including on the
  very first-ever evaluation, where there is no real previous status to compare against yet).
- [x] No retry/backoff/queueing — a single best-effort POST with a short timeout (`5.0` seconds). A failed
  delivery (timeout, connection error, non-2xx response) is logged via the existing OPS-006 structured
  logging convention (`logging.getLogger(__name__).warning(...)`, picked up by the already-configured JSON
  formatter) and dropped — never raised, never blocks/delays/crashes the evaluation path.
  This includes GET /system/health's own request path, which never awaits or depends on the background
  task in any way.
- [x] `GET /system/health`'s own response shape/behavior is completely unchanged by this ticket (the route
  now calls the extracted `compute_system_health` helper, but the route's own request/response contract is
  identical to before).
- [x] Explicitly out of scope, carried verbatim from the sprint plan / backlog AC: no escalation policy, no
  multiple channels/recipients, no acknowledgement/snooze mechanism, no paging-service integration
  (PagerDuty/Opsgenie/etc.). One URL, one event shape, fire and forget.
- [x] `app.main`'s new `lifespan` hook launches exactly one `asyncio` task at process start and cancels it
  cleanly at shutdown (no dangling task, no unhandled `CancelledError` propagating out of `lifespan`).
