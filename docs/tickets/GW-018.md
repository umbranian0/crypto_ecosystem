Real request/response shapes, confirmed by reading `reporting-service`'s actual router code directly (`services/reporting-service/src/app/routers/report_generation.py`, `report_retrieval.py`), not guessed:
- `POST /reports/generate` — request `GenerateReportRequest`: `{run_id: str}`. Response `GenerateReportResponse` (`201`): `{id: str, status: str}`. Error mapping already established inside `reporting-service` itself: a nonexistent/cross-tenant `run_id` → `404`; downstream (validation-service) unavailable/timeout/error → `502`/`504`/`502` respectively — these are `reporting-service`'s own responses, to be forwarded unmodified by this proxy, not reinterpreted.
- `GET /reports/{report_id}` — response `ReportDetailResponse` (`200`): `{id: str, run_id: str, report_kind: str, generated_at: datetime, status: str, content: str}` (note: no `tenant_id` field — `reporting-service`'s own `ReportDetailResponse` does not expose it). `404` if the report doesn't exist or belongs to a different tenant (`ReportRepository.get_report` already collapses both cases to `None`, same non-disclosure stance `validation-service`'s `GET /runs/{id}` uses).
- Both endpoints resolve tenant via `Depends(naive_first_common.get_tenant_context)` on the `reporting-service` side, reading `X-Tenant-Id` — exactly what `gateway-api`'s existing `build_downstream_headers` (GW-007) already produces; no change needed to that function.

## Design
Pattern: none new beyond DI — pure proxy, same shape as GW-008/GW-016. New file: `services/gateway-api/src/app/routers/reports.py` (deliberately a new module, not added to `runs.py` — `reports.py` proxies a different downstream service entirely, and keeping it separate avoids any file overlap with GW-016's `runs.py` edit, consistent with this service's own `runs.py`/(future `reports.py`) separation-by-downstream-service precedent implied by ARCH-007's tagging convention). New file: `services/gateway-api/src/app/dependencies/reporting_http_client.py` (or extend `http_client.py` with a second provider — implementer's choice, but must not collapse the two clients into one `httpx.Client` pointed at a single base URL that later needs runtime branching; two named providers, `ValidationServiceClientDep`/`ReportingServiceClientDep`, is the cleaner shape matching `VALIDATION_SERVICE_URL`'s own precedent) reading a new `REPORTING_SERVICE_URL` env var (default `http://localhost:8002` — matching `reporting-service`'s own `EXPOSE 8002`/Dockerfile port, for non-Compose local dev, same pattern `VALIDATION_SERVICE_URL` already established with its `http://localhost:8000` default).

Response models: `reports.py` defines its own `GenerateReportRequest`/`GenerateReportResponse`/`ReportDetailResponse` Pydantic models, field-for-field copies of `reporting-service`'s real ones (confirmed above) — these are NOT added to `naive_first_common.contracts` this sprint (out of scope; `RunSummaryResponse` was the only shared-contract addition this sprint, and it belongs to the `VS-022`/`GW-016` chain, not this one) — this mirrors GW-008's original pre-ARCH-003 approach (field-for-field copy in the router file) since `reporting-service` has no existing shared-contract dependency on `naive_first_common.contracts` for its report models to hang off of. Document this version-sync caveat explicitly in the README, same as GW-008's original note did before ARCH-003 centralized the run/split models.

Handler flow (fixed, mirrors GW-008/GW-016 exactly): resolve `tenant: TenantContext = Depends(get_authenticated_tenant)` (GW-006) → `headers = build_downstream_headers(tenant)` (GW-007, unchanged, reused as-is) → forward request body/path param via `httpx` to `REPORTING_SERVICE_URL` + the matching path, using `_call_downstream` for transport-failure translation (reuse the existing helper from `runs.py` — either import it if it's exported, or, if it's module-private, factor it into a shared location `dependencies/routing.py` or similar so it's not duplicated; check `runs.py`'s current structure before deciding — DRY within the module, per implementation-plan.md section 9) → `_raise_for_error`-equivalent pass-through of non-2xx → return the response unmodified in shape.

DRY check (performed before writing this ticket): grepped `services/gateway-api/src/app/routers/` and `dependencies/` — `_call_downstream`/`_raise_for_error` currently live as module-private functions in `runs.py`; this ticket's implementer must either import them (if feasible without circular imports) or extract them into a shared module (e.g. `dependencies/routing.py`, which already exists and holds `build_downstream_headers`) so `reports.py` does not duplicate the transport-failure-translation logic — this is exactly the "DRY within a module's own boundary, extract on second duplication" rule from implementation-plan.md section 9, and this is the second use of that logic within `gateway-api`.
