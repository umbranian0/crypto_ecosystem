## Analysis

Story: DBOPT-001 (`docs/product/backlog-db-optimization.md`). `PostgresApiKeyRepository.get_by_hash`
(`services/gateway-api/src/app/repositories/postgres_repository.py`) runs
`SELECT ... FROM api_keys WHERE key_hash = :key_hash`, called from
`app.dependencies.auth.get_authenticated_tenant` on **every single authenticated request** to this
service — the hottest query path in the platform. `get_by_hash` is one of GW-003's documented
tenant-agnostic exceptions (runs before a tenant is known), so it can never be scoped to a per-tenant
slice — it always scans the full table.

Live-verified by the DBA (`docs/product/backlog-db-optimization.md` DBOPT-001): `EXPLAIN (ANALYZE,
BUFFERS)` on the real 197-row table shows `Seq Scan on api_keys ... Filter: (key_hash = ...) Rows
Removed by Filter: 196`. Cheap today only because the table is small platform-wide, not per-tenant —
this is the constraint (implementation-plan.md section 5: schema-per-service, no shortcuts on the auth
hot path) that makes this a Must, not a Should.

## Implementation acceptance criteria

- New Alembic migration adds `CREATE UNIQUE INDEX ix_api_keys_key_hash ON identity.api_keys (key_hash);`
  — unique, per the DBA's own migration shape (matches `get_by_hash`'s `scalar_one_or_none()` assumption
  that at most one row exists per hash; also gives Postgres a cheaper index-only-scan path than a plain
  btree).
- Migration is Postgres-only-guarded (same idiom as `0002_add_identity_rls.py`/GW-012's other
  migrations) so `alembic upgrade head` against a `sqlite:///` `DATABASE_URL` (this service's own
  `tests/test_models.py::test_alembic_upgrade_head_creates_matching_schema`) still no-ops cleanly, not
  errors.
- `downgrade()` drops the index (`DROP INDEX IF EXISTS ix_api_keys_key_hash`), Postgres-guarded the same
  way.
- Zero changes to `src/app/repositories/postgres_repository.py`, `src/app/dependencies/auth.py`, or any
  route/business-logic file — this is schema-only. `get_by_hash`'s query text is unchanged; the index
  makes the existing query plan cheaper, it does not require a new query shape.


usable; whether the live planner picks it today is a function of current table size, not of this
