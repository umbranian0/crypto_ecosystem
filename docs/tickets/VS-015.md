# VS-015 — Object-storage-backed `DatasetSource` implementation

**Module**: `services/validation-service`. **Priority**: Should. **Depends on**: VS-005 (done).
**Round**: 2 (parallel with GW-010) — practically wants `INF-008` (Round 1) landed first for
realistic testing against a real MinIO instance, not a formal blocker.
**Source**: `docs/product/backlog-validation-service.md` VS-015, `docs/product/backlog-hardening-wave-review.md`
Category 1, `docs/sprints/sprint-17.md`.

## Analysis

Story: a `DatasetSource` implementation reading from the `processed/{tenant_id}/...` object-storage
zone (solution-design.md section 3.2), so runs can eventually be triggered against datasets
`ingestion-service` has landed, instead of only inline payloads or local files. Acceptance criteria
(verbatim):
- Implements the same `DatasetSource` interface as VS-005 against the processed object-storage zone
  path scheme.
- Swapping VS-005's interim implementation for this one requires no change to `POST /runs`'s handler
  code.
- Still does not write to or own any part of the object-storage prefix — read-only.

**Non-negotiable care condition**: pulling this forward makes the read-side *adapter* real; it must
**not** be presented or documented as meaning a real, tenant-scoped `processed/{tenant_id}/...` zone
is actually populated with real pilot data — that still depends on `ingestion-service` actually
writing there, a separate, not-yet-confirmed fact. State this distinction explicitly in
`services/validation-service/README.md`'s own update for this story.

## Design

**Pattern**: Adapter (implementation-plan.md section 7) — `DatasetSource` is already the interface
(`load(reference) -> pd.Series`, `libs`... no, `services/validation-service/src/app/dataset_source.py`),
with `InlineOrLocalFileDatasetSource` as VS-005's interim implementation. This ticket adds a second
implementation behind the same interface, the same "second implementation, swap via DI, no call-site
change" pattern already used for VS-004 → VS-013 (Postgres repositories).

**New client dependency**: neither service currently depends on any S3-compatible client (`boto3`
grep-confirmed absent from both `pyproject.toml`s). Add `boto3` to
`services/validation-service/pyproject.toml`'s `dependencies` (MinIO is S3-API-compatible; `boto3`
is the standard, well-supported choice, avoids adding a second, less-common SDK — do not add both
`boto3` and `minio`-the-package).

**New class**: `ObjectStorageDatasetSource` in `app/dataset_source.py` (same file as the existing
interface + `InlineOrLocalFileDatasetSource`, per this file's existing single-file-per-concern
convention — do not split into a new file, since this file's whole job is "the DatasetSource
interface and its implementations"). Constructed with an S3 client + bucket name (env-var driven,
mirroring `REDIS_URL`/`DATABASE_URL`'s existing convention). `load(reference)` accepts a reference
dict with an `"object_key"` key (e.g. `{"object_key": "processed/{tenant_id}/{dataset_id}.csv"}`),
fetches the object, parses it with the exact same two-column-CSV parsing logic
`InlineOrLocalFileDatasetSource._read_csv`/`_build_series` already implement — **reuse those static
methods directly** (they're already `@staticmethod` on the interim class; call
`InlineOrLocalFileDatasetSource._build_series`/read the object into an in-memory buffer and reuse the
existing CSV-parsing code path, e.g. via `csv.reader` over a `io.StringIO`/`io.TextIOWrapper` of the
downloaded bytes) rather than re-deriving CSV parsing a second time — this is the DRY check's
concrete finding: `_read_csv`'s per-row parsing loop and `_build_series`'s
timestamp/float-coercion/sort/empty-check logic must not be duplicated.

**DI wiring, mirroring VS-013's env-var-driven swap pattern exactly**: `get_dataset_source()` in
`dependencies/repositories.py` currently unconditionally returns `InlineOrLocalFileDatasetSource()`.
Change it to a small composite: if `reference` carried an `"object_key"` key it should route to
`ObjectStorageDatasetSource`, but `get_dataset_source()` is called with no arguments (it doesn't see
the request body) — so the correct DI-level design is a single **composite `DatasetSource`**
(`CompositeDatasetSource`, new class in the same file) wrapping both implementations and dispatching
on `reference`'s keys at `load()` time (`"inline"`/`"path"` → delegate to
`InlineOrLocalFileDatasetSource`; `"object_key"` → delegate to `ObjectStorageDatasetSource`; anything
else → the existing `DatasetSourceError`). `get_dataset_source()` returns
`CompositeDatasetSource(InlineOrLocalFileDatasetSource(), ObjectStorageDatasetSource(...))` always —
this satisfies AC2 exactly ("swapping requires no change to `POST /runs`'s handler code": the handler
still just calls `dataset_source.load(request.dataset_reference)`, unaware which underlying
implementation actually served it) while keeping both source kinds available simultaneously, matching
how a real deployment will actually need both (inline for tests/local dev, object-storage for real
tenant data) rather than one replacing the other.

**Env vars** (new, `OBJECT_STORAGE_` prefix to match this platform's `DATABASE_URL`/`REDIS_URL`
single-var-per-concern convention, but object storage needs endpoint+credentials+bucket, not one
URL): `OBJECT_STORAGE_ENDPOINT_URL` (e.g. `http://minio:9000` inside Compose), `OBJECT_STORAGE_ACCESS_KEY`,
`OBJECT_STORAGE_SECRET_KEY`, `OBJECT_STORAGE_BUCKET` (default matching solution-design.md section 5's
bucket name if one is specified there; otherwise a sensible default like `naive-first`). Read from
`os.environ` the same way `_database_url()`/`REDIS_URL` are read in `dependencies/repositories.py` —
unset means `ObjectStorageDatasetSource` is constructed but any `load()` call against it fails loudly
with a clear `DatasetSourceError`, not a silent no-op (mirrors "fail loudly" conventions already used
elsewhere in this repo, e.g. `infra/migrate.sh`).

**Read-only, explicitly**: `ObjectStorageDatasetSource` must have no method that writes/deletes/puts
an object — grep-checkable (`put_object`/`upload_file`/`delete_object` must not appear anywhere in
this ticket's diff).

**DRY check performed**: read `app/dataset_source.py` in full — `_read_csv`/`_build_series` are the
reusable pieces; `_parse_inline` is not relevant here (object storage only serves CSV-shaped data per
this ticket's scope, matching the interim implementation's own two supported shapes). Read
`dependencies/repositories.py`'s `get_dataset_source` — the only call site to change.

## Implementation acceptance criteria

- [ ] `services/validation-service/pyproject.toml` gains `boto3` in `dependencies`.
- [ ] `app/dataset_source.py` gains `ObjectStorageDatasetSource` (constructed with an S3 client +
  bucket, `load({"object_key": ...})` fetches + parses via the reused CSV-parsing static methods, no
  write/delete method anywhere on the class) and `CompositeDatasetSource` (dispatches on reference
  shape to the interim or object-storage implementation; raises the existing `DatasetSourceError` for
  an unrecognized reference shape, unchanged from today's behavior for `"inline"`/`"path"` requests).
- [ ] `dependencies/repositories.py`'s `get_dataset_source()` returns a `CompositeDatasetSource`
  wrapping both implementations; the S3 client/bucket config is read from the new `OBJECT_STORAGE_*`
  env vars, memoized consistently with this module's existing `functools.lru_cache`-by-URL pattern if
  a client needs to be reused across requests (avoid constructing a new `boto3` client per request).
- [ ] `POST /runs`'s handler code (`runs.py`) is **not modified** by this ticket — confirm via `git
  diff --stat` that `src/app/routers/` has zero changes (this is the literal proof of AC2).
- [ ] No `put_object`/`upload_file`/`delete_object`/any write-capable S3 call exists anywhere in the
  diff (read-only, per AC3).

## Test acceptance criteria

- [ ] `services/validation-service/tests/test_dataset_source.py` (extended, not duplicated): unit
  tests for `ObjectStorageDatasetSource` against a mocked S3 client (e.g. `moto`, or a hand-rolled
  fake implementing the subset of the `boto3` client interface used) covering: successful load of a
  well-formed CSV object, a missing-object error mapped to `DatasetSourceError` (not a raw `boto3`
  exception leaking through), a malformed-CSV object mapped to `DatasetSourceError` (reusing the
  existing `_read_csv`/`_build_series` error paths, proving the reuse is real, not just structurally
  similar code).
- [ ] `CompositeDatasetSource` unit tests: an `"inline"` reference still routes to (and behaves
  identically to) `InlineOrLocalFileDatasetSource`; a `"path"` reference likewise; an `"object_key"`
  reference routes to `ObjectStorageDatasetSource`; an unrecognized reference shape still raises
  `DatasetSourceError` with the same message shape as today.
- [ ] **Real-MinIO integration test** (gated the same way `test_postgres_repository.py`'s real-Postgres
  tests are gated — skipped when no real object storage is reachable, not silently mocked away): if
  `INF-008`'s MinIO container is up (check via the same `OBJECT_STORAGE_ENDPOINT_URL` env var being
  set and reachable), a test uploads a small real CSV object via a direct `boto3` call in the test
  fixture itself (test-only write, not through `ObjectStorageDatasetSource`, which stays read-only)
  and confirms `ObjectStorageDatasetSource.load` reads it back correctly end-to-end against the real
  container — this is the sprint's own "test against a real MinIO instance if practical, not just a
  mocked client" requirement.
- [ ] Existing `test_dataset_source.py` tests for `InlineOrLocalFileDatasetSource` are unmodified and
  still pass (byte-identical behavior, confirmed not just assumed).
