## Analysis

Confirmed by reading the actual current state: `infra/README.md`'s "Migrations verified against
Compose Postgres" section documents the one-off command used during INF-005:

```
DATABASE_URL=postgresql://naive_first:naive_first_dev_password@localhost:5432/naive_first python -m alembic upgrade head
```

run by hand from each service's own `.venv`, from the service's own directory, against the
host-published Postgres port. This has already been independently re-derived at least three times
in this project's history (INF-005, VS-013, GW-012), per the backlog's own accounting. Post-INF-014,
this invocation must also change: migrations run as `naive_first` (the migration-time role,
INF-014), never the new `naive_first_app` runtime-only role — `naive_first_app` has no `CREATE`/
ownership privileges by design and would fail at the first `CREATE TABLE`.

No existing script in `infra/` does this today — `infra/postgres-init/` only contains
container-startup SQL/shell (runs once, on fresh volume boot, as the Postgres entrypoint), not a
developer-invoked command.

## Design

- Two scripts, `infra/migrate.sh` (bash) and `infra/migrate.ps1` (PowerShell) — matching the
  repo's existing convention of plain shell/PowerShell for `infra/` tooling (no new Python
  entrypoint, consistent with INF-015's own stated reasoning for the same choice).
- Interface: `infra/migrate.sh <service>` / `infra/migrate.ps1 -Service <service>`, where
  `<service>` is `validation-service`, `gateway-api`, or `both` (default `both` if omitted, since
  "apply whatever changed" is the common case and running the no-op side is harmless — Alembic
  already no-ops at head).
- Each invocation: `cd services/<service>`, set `DATABASE_URL` to the migration-time connection
  string (`postgresql://naive_first:<POSTGRES_PASSWORD>@localhost:<POSTGRES_PORT>/naive_first`,
  reading `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_PORT`/`POSTGRES_DB` from the environment
  with the same defaults `.env.example` documents — never `naive_first_app`), run
  `python -m alembic upgrade head` from that service's own `.venv` interpreter (not a bare
  `python`/`alembic` that might resolve to the wrong environment).
- Fails loudly: non-zero exit and a clear message if a service's `.venv` doesn't exist (tell the
  caller to create it first, not a raw Python traceback), and propagates Alembic's own non-zero
  exit code / stderr on migration failure.
- Idempotent by construction (delegates to `alembic upgrade head`, which Alembic itself already
  no-ops at head) — the script does not need to detect "nothing to do" itself, just needs to not
  break on repeat invocation, which a plain `alembic upgrade head` call already guarantees.
- **Design decision, stated explicitly**: no migration-generation helper
  (`alembic revision --autogenerate`) and no CI/deploy-time auto-migration hook — matches the
  backlog's explicit out-of-scope note. This script performs the same manual-but-easy action a
  developer already decided to take; it does not decide *when* to run.
- **Pattern/DRY check**: this is the one place `alembic upgrade head`'s exact invocation
  (interpreter path, `DATABASE_URL` construction, working directory) lives. INF-015's bootstrap
  script must call this script for its own migration step rather than re-deriving the same
  invocation — flagged here explicitly since INF-015 is sequenced immediately after this ticket and
  its own ticket text commits to this.

**Files modified:**

  "Migrations verified against Compose Postgres (INF-005)" section's content intact, as required).

**Deviation from the ticket's literal Design text, found during testing, not assumed:** the
Design section's connection string (and INF-005's own historical one-off command) use the bare
`postgresql://` scheme. Running that literally against the live `.venv`s fails with
`ModuleNotFoundError: No module named 'psycopg2'` — both services' `pyproject.toml` declare
`psycopg[binary]>=3.1` (psycopg v3) as their Postgres driver, not `psycopg2`, and SQLAlchemy's
default dialect for a bare `postgresql://` scheme resolves to `psycopg2`. Each service's own app
code (`dependencies/repositories.py`) already rewrites an incoming `postgresql://` `DATABASE_URL`
to `postgresql+psycopg://` before use; `alembic`'s `env.py` does not perform that rewrite (it only
checks the scheme string for schema-targeting purposes, both `postgresql://` and
`postgresql+psycopg://` are accepted there). Both scripts here therefore build the `DATABASE_URL`
with the explicit `postgresql+psycopg://` scheme, not the bare one the ticket text shows. Confirmed
`psycopg` v3.3.4 is actually installed in both `.venv`s (`python -c "import psycopg;
print(psycopg.__version__)"`), so this is not a missing-dependency problem, only a driver-scheme
mismatch between the ticket's example DSN and what's actually installed.
