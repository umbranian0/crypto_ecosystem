**Status: done.** See Outcome section at the end of this file.

**Module**: `services/validation-service` and `libs/common` (contract only — the contract addition is
a single shared-schema file edit, not business logic, so it stays in this ticket rather than forcing a

**Story**: RAV-007, `validation-service` half.
**Depends on**: VS-031, VS-032 (needs `split_points` to exist and the retention cutoff to be real).
**Blocks**: GW-031 (gateway-api proxy), DASH-129 (chart).

## Analysis

RAV-007 requires exposing RAV-006's per-point data via a new/extended API surface, proxied through
`gateway-api`, with the response shape canonicalized in `naive_first_common.contracts`
(ARCH-003's established convention — every existing `RunRequest`/`RunResponse`/`RunDetailResponse`/
`SplitResultResponse`/`ClientBaselineResult` follows this, confirmed by reading `contracts.py`), RLS
tenant scoping (already real on `split_points` via VS-031's migration), and read-path respect for
VS-032's retention cutoff (already built into `SplitPointRepository.get_points` — this ticket's router
just calls it, no cutoff logic duplicated here).

**Endpoint shape decision (Tech Lead's call, per RAV-007's own acceptance criteria)**: a new
`GET /runs/{run_id}/splits/{split_index}/points` endpoint, **not** a new field on
`GET /runs/{id}/splits`. Rationale: VS-032's storage-growth estimate (~46M rows at steady pilot scale)
means a run's full splits list must never eagerly carry every point for every split in one response —
that would make the existing, already-lightweight `GET /runs/{id}/splits` call (used by RAV-002
through RAV-005's charts today) balloon in payload size for every caller, including ones that never
want per-point data. A dedicated per-split endpoint keeps the existing endpoint's contract and
performance characteristics completely unchanged (no `SplitResultResponse` field added) and gives
RAV-008's chart exactly the fetch granularity it needs (one split at a time, on drill-down).

**Pagination decision**: `limit`/`offset` query params, same convention `GET /runs` (VS-022) already
established (`ge=1, le=100` server-side ceiling on `limit`, `ge=0` on `offset`) — not a cursor, since
this platform has no cursor-pagination precedent anywhere yet and the existing `limit`/`offset` style
is the one convention to stay consistent with (DRY at the platform-conventions level, not just
within-module).

## Design

**Design pattern**: none new — this is the same pass-through-friendly router pattern `splits.py`
already uses (Repository underneath, DI for the repository dependency).

Files touched (scoped to `validation-service` + the one shared contract file):
- `libs/common/src/naive_first_common/contracts.py` — new `SplitPointResponse` model (`timestamp:
  datetime`, `predicted: float`, `actual: float`, `baseline_key: str`) and a `SplitPointsResponse`
  envelope (`{"items": [...], "limit": ..., "offset": ..., "total": ...}`, same envelope shape
  `RunListResponse` already established, kept router-local vs. shared per that same precedent — see
  Design decision below).
- `services/validation-service/src/app/routers/splits.py` — new route in this same file (not a third
  router module — this is a natural extension of the existing splits concern, not a disjoint one,
  unlike DASH-113's "disjoint concern -> new module" precedent which doesn't apply here).

**Envelope shared-vs-local decision**: matching `RunListResponse`'s own precedent (`runs.py`'s
module docstring: "this envelope shape is local to this router, not a shared contract type"), the
`{items, limit, offset, total}` wrapper stays a plain local Pydantic model in `splits.py`, not added
to `naive_first_common.contracts` — only the per-item shape (`SplitPointResponse`) is the canonical,
shared definition, matching `RunSummaryResponse` inside `RunListResponse`'s existing precedent
exactly.

**Retention-respecting empty shape**: a request for a split whose per-point data has been pruned (or
was never persisted, e.g. a pre-VS-031 run) returns `200 {"items": [], "limit": ..., "offset": ...,
"total": 0}` — same shape a zero-row split would produce — never a `404`/`410`/error. This falls out
by construction from `SplitPointRepository.get_points` already excluding pruned rows (VS-032) and this
router not distinguishing "no rows because pruned" from "no rows because none existed."

**DRY check note**: grepped `services/validation-service/src/app/routers/splits.py` before writing —
the existing `_client_baseline_response`/tenant-ownership-check pattern (`run_repository.get_run(...)`
first, `404` if `None`, same collapsed-both-cases stance as every other route) is reused verbatim for
the new route's tenant/existence check, not reimplemented.

## Implementation acceptance criteria

- [x] `GET /runs/{run_id}/splits/{split_index}/points?limit=&offset=` added to `splits.py`. Tenant via
      `Depends(get_tenant_context)`, same as every other route in this router.
- [x] Run-ownership check (via `ValidationRunRepository.get_run`) happens first, `404` for a
      nonexistent run or one belonging to a different tenant — same collapsed pattern the sibling
      routes already use. An existing run with an out-of-range `split_index` (no such split) also

      "there is nothing here for you to see," matching this router's existing philosophy of not
      leaking existence information via differently-shaped errors).

      error (per Design section above).

      (ARCH-003) — no hand-duplicated field list in this router.
- [x] RLS scoping applies exactly as it does for `split_results` today (already true by construction
      via VS-031's migration + this route calling the tenant-scoped repository method — no new
      isolation mechanism introduced).
