# NFE-019: `generate_splits` accepts a negative `purge_gap`, producing train/test row overlap

**Status**: done
**Module**: `libs/naive_first_engine`
**Priority**: urgent (live blocking-severity leakage bug, not a scheduled sprint item)
**Depends on**: none (fixes a defect in NFE-002/NFE-003, both done)

## Problem

QA's leakage sweep found that `generate_splits` silently accepts a negative
`purge_gap` and, for the position-based branch, produces a `Split` whose
`test_start` is at or before `train_end` -- meaning the same underlying index
rows are counted in both the train and test windows of that split. This is a
real train/test leakage failure mode, not a cosmetic one: it is exactly the
class of bug CLAUDE.md's engineering rules exist to prevent ("Preprocessing
... must be fit on the training fold only ... never globally. This is the
exact leakage failure mode the whole business case is built on avoiding.").

## Root cause (diagnosed against the actual code)

`libs/naive_first_engine/src/naive_first_engine/splitting.py`,
`_generate_splits_by_position`, line 71:

```python
test_start_pos = train_end_pos + purge_gap
```

With `purge_gap=-3` and a 10-row train window, `test_start_pos` lands at
position 7 while `train_end_pos` is 10 -- i.e. inside the train window, so
rows 7-9 are double-counted as both train and test data for that split.
Neither `splitting.py`, `protocol.py`, nor `ValidationConfig` had any guard
rejecting `purge_gap < 0` before this fix. The time-based branch
(`_generate_splits_by_time`) was already safe: its `index > actual_train_end`
mask structurally prevents the same failure even with a negative
`pd.Timedelta`, so it required no change.

QA's regression test
(`libs/naive_first_engine/tests/test_splitting.py::
test_negative_purge_gap_must_not_produce_overlapping_train_test_rows`)
reproduced the position-based case directly.

## Fix

A single guard added at the shared `generate_splits` entry point (not
duplicated per branch), rejecting any `purge_gap < 0` (both `int` and
`pd.Timedelta` kinds) with a `ValueError`, matching this module's existing
convention for invalid input (`dm_test.py`'s horizon check, `metrics.py`'s
index-mismatch checks both raise `ValueError` rather than silently producing
a wrong result):

```python
zero = pd.Timedelta(0) if isinstance(purge_gap, pd.Timedelta) else 0
if purge_gap < zero:
    raise ValueError(
        f"purge_gap must be >= 0 (negative purge gap causes train/test row "
        f"overlap); got {purge_gap!r}"
    )
```

A negative purge gap has no valid interpretation for either splitting kind
(it cannot be satisfied without overlap), so rejecting it outright -- rather
than clamping or reinterpreting it -- is the only fix that both (a)
guarantees non-overlap and (b) works uniformly for `int` and `pd.Timedelta`
without branch-specific special-casing.

QA's originally-drafted regression test asserted on the *returned splits*
directly (no exception expected), which conflicts with the raise-based fix.
Since raising is the correct, convention-matching behavior (confirmed by
grepping this module's existing error-handling style before choosing an
approach, per this ticket's own DRY/consistency instruction), the test was
updated to assert `pytest.raises(ValueError, match="purge_gap")` for both the
`int` and `pd.Timedelta` negative cases, preserving its actual intent (a
negative purge gap must never produce overlap) rather than weakening it.

## Out of scope

- No configurability, "strict mode" flag, or generalization beyond rejecting
  `purge_gap < 0` -- explicitly excluded by this ticket's own instruction.
- No change to `_generate_splits_by_time`, which was not affected.
- No change to `ValidationConfig`'s own field-level validation (the guard
  lives in `generate_splits`, the single call site both branches share).
