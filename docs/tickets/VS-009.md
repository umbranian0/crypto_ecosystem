# VS-009 — `run.completed` event publishing interface + interim implementation

**Status: done**

## Analysis
Story: VS-009 (Must), depends on VS-006. Constraining docs: this service's README "owns" section ("emitting the run.completed event"), implementation-plan.md section 7 (Observer/pub-sub pattern, named explicitly for `run.completed` → `reporting-service`), implementation-plan.md section 4 (Redis Streams is the eventual transport, not yet available — trigger #7), backlog decision 3(a). This ticket has a direct dependency on VS-012 (failure handling) proving the negative case, but VS-012 depends on this ticket existing first — VS-009 only needs to prove "publishes on success," VS-012 later proves "does not publish on failure."

## Design
Pattern: **Observer/pub-sub** (implementation-plan.md section 7, named for exactly this event). Files: `src/app/events.py` (new — `EventPublisher` interface, `InProcessLogEventPublisher` interim implementation), `src/app/routers/runs.py` (edit — VS-006's `POST /runs` success path, after `update_run_status(..., status="completed", ...)`, calls `event_publisher.publish("run.completed", {...})`; this is a same-file edit on top of VS-007's changes, so this ticket must run after VS-007 lands, and should avoid touching the same lines VS-008 touches — VS-008 is a separate file, so no conflict there), `src/app/dependencies/repositories.py` or a new `src/app/dependencies/events.py` (DI provider for `EventPublisher`). DRY check: grep `src/app/` for any existing event/logging abstraction before writing.

**Payload shape** (documented now so VS-014's future Redis-backed implementation has a stable contract to match): `{"event": "run.completed", "run_id": ..., "tenant_id": ..., "status": "completed", "completed_at": <iso8601>}`.

**Interim implementation**: logs a structured line (e.g. `logging.getLogger(__name__).info(...)` with the payload as structured fields/extra) and appends to an in-memory list on the instance, retrievable in tests (`publisher.published` or similar) — sufficient to prove the call happens at the right point without a live broker, per AC3.

## Implementation acceptance criteria
- [x] `EventPublisher` interface exists (`publish(event_name: str, payload: dict) -> None`, Protocol or ABC, consistent style with `DatasetSource`/`Baseline`).
- [x] `POST /runs`' success path calls `event_publisher.publish("run.completed", {...})` with run ID, tenant ID, status, exactly once per successfully completed run — placed after the run's status is persisted as `"completed"`, never before.
- [x] `InProcessLogEventPublisher` logs the event and stores it in an in-memory list.

## Test acceptance criteria
- [x] `tests/test_events.py` and/or an extension of `tests/test_runs_endpoint.py`: a successful `POST /runs` call results in exactly one `run.completed` entry in the injected `InProcessLogEventPublisher`'s recorded list, with the correct `run_id`/`tenant_id`/`status`.
- [x] A test confirms the event is published **exactly once** (not zero, not twice) per completed run — matters because a naive placement (e.g. inside a loop over splits) could double- or N-publish.
- [x] Run via `.venv\Scripts\python.exe -m pytest -q`, confirm pass, paste output. (The "not published on failure" half of AC4 is VS-012's test, not this ticket's — this ticket proves the positive case only; note that split explicitly so nothing here fakes the negative case.)
