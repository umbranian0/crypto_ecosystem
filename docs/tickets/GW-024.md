# GW-024 — Proxy passthrough confirmed for `INGEST-015`'s new crawl-trigger contract

## Analysis

`INGEST-015` changes `ingestion-service`'s `POST /connectors/{source}/run` from "blocks until the
crawl finishes, `202` with the final outcome" to "returns `202` immediately, `status: "queued"`,
work continues in the background," and adds a `409` ("crawl already in progress") outcome that did
not exist before. `services/gateway-api/src/app/routers/ingestion.py`'s `run_connector` (`GW-019`)
is a generic pass-through: `_call_downstream` → `_raise_for_error` → `return response.json()`, with
no local Pydantic model for the response body and no special-casing of any particular status code
(everything `>= 400` already raises `HTTPException(response.status_code, detail)` unchanged, via
`_raise_for_error`, imported from `runs.py`). Read directly: this generic shape already forwards a
`409` correctly with zero code change — there is no hardcoded status-code allowlist anywhere in this
path to update.

This ticket therefore has **no behavioral code change** to make — it exists to (a) prove the above
claim with a real test rather than asserting it from a design read, since "the proxy is generic
enough to already handle this" is exactly the kind of claim that should be tested, not assumed, and
(b) update `gateway-api`'s own documentation, which currently describes the old synchronous
contract and would otherwise silently drift.

The 240s `GATEWAY_API_DOWNSTREAM_TIMEOUT_SECONDS` override in `infra/docker-compose.yml` (added as
the original band-aid, already committed by the QA sweep) is **not** touched by this ticket — once
`INGEST-015` lands, the long timeout is simply no longer load-bearing for this route (the downstream
response now returns in milliseconds, not ~70s), but reverting it is a separate, low-risk config
decision left to the requester, flagged here rather than bundled into this ticket's file scope.

## Design

**File touched**: `services/gateway-api/src/app/routers/ingestion.py` (docstring only — see below),
`services/gateway-api/tests/` (one new test file or an addition to the existing ingestion-router test
file — whichever already exists), `services/gateway-api/README.md`. No change to
`_call_downstream`/`_raise_for_error` (`runs.py`, reused unmodified, per this file's own existing
"reuse, don't duplicate" precedent) and no change to `run_connector`'s actual code.

**DRY check**: grepped `services/gateway-api/src/app/routers/ingestion.py` and `runs.py` for any
existing status-code-specific branching in the proxy path — none exists beyond the generic `>= 400`
check in `_raise_for_error`; nothing to consolidate or duplicate.

## Implementation acceptance criteria

- [ ] `ingestion.py`'s `run_connector` docstring/module docstring updated to describe the new
      response body shape (`{source, status: "queued", since, queued_at}` on `202`) and the new
      `409` outcome — no functional code change expected; if the dev agent finds a real gap while
      writing the Test acceptance criteria below (e.g. `status_code=202` hardcoded on the route
      decorator masking a non-202 success somehow), it must be reported to the Tech Lead before being
      fixed, since that would mean this ticket's Analysis section's central claim was wrong.

## Test acceptance criteria

- [ ] A new test (against a stub/fake downstream `ingestion-service`, matching this router's existing
      test convention) asserts a downstream `409` (`{"detail": "crawl already in progress for
      connector ..."}`) is forwarded through `POST /ingestion/connectors/{source}/run` as a `409`
      with the same detail string, unmodified — proving the generic passthrough claim rather than
      assuming it.
- [ ] A test asserts a downstream `202` with the new `{source, status: "queued", since, queued_at}`
      body is forwarded as `202` with that exact body (`response.json()` equality) — confirming no
      stale expectation of `row_count`/`fetched_at` lingers in any existing test for this route.
- [ ] Full `services/gateway-api` suite re-run, zero regressions.

- [ ] Re-run the two new tests personally, confirm they'd fail against a reverted `_raise_for_error`

## Documentation acceptance criteria
