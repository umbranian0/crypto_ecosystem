**Real evidence to record (confirmed live by the Tech Lead against `validation.runs`/`validation.split_results`
before this ticket was written)**: tenant `e80a603ffd5e4e9e98bbfe2cba39b6e1`'s `binance_price_btcusdt_1h`
source (79,180 real ingested rows), `train_window=360, test_window=1540, step=2, purge_gap_hours=24` →
38,597 splits (`SELECT COUNT(*) FROM validation.split_results WHERE run_id = ...`), two independent runs
completed in 502.7s and 488.4s (`completed_at - created_at`, both `status=completed`, zero errors) — ≈78
splits/second on this hardware. At that rate the shipped cap (500 splits) would complete in ≈6.4 seconds:
an extremely conservative, effectively-instant margin relative to both this measured throughput and
`gateway-api`'s 240s downstream timeout (which these two incident runs' own real durations already
exceeded — see the separate documentation note below). This is one real data point on one
dataset/config, not a calibrated performance benchmark — state plainly that 500 is conservative-by-design,
not performance-tuned, and that a future, deliberate throughput benchmark (varying dataset shape/model
complexity) would be needed before ever tightening the number, not this one incident's data point alone.

**Separate, required documentation note (not a new story, a documentation-only flag)**: the same incident
that grounds this ticket's cap also revealed that `GATEWAY_API_DOWNSTREAM_TIMEOUT_SECONDS` (240s, set in
Sprint 18) is shorter than a request that legitimately completed in ~495s when called directly against
`validation-service` — meaning a caller going through `gateway-api`'s proxy would have received a `504`
while the run kept computing and completed anyway ("zombie success": client believes the request failed;
the tenant's run actually exists and succeeded). RSS-004's guardrail (500-split cap, ≈6.4s at measured
throughput) makes this scenario unreachable for any request that passes the new guardrail — but this is
worth recording here as a documented, disclosed gap in `gateway-api`'s timeout-vs-actual-duration
relationship for any future work that revisits synchronous execution or timeout tuning, not silently
left for someone to rediscover.
