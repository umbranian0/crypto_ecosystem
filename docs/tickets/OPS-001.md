# OPS-001 — Wire an automated CI pipeline running every module's test suite

Status: **done**
Backlog: docs/product/backlog-operability.md, OPS-001 [Must]
Sprint: docs/sprints/sprint-08.md, runs first (parallel with OPS-005)
Depends on: none

## Analysis

Story: OPS-001 (Must). Acceptance criteria (backlog): (1) a CI workflow runs on every push/PR and
executes each of the five modules' own documented test commands; (2) a failing test in one module
fails CI for that module specifically, not one opaque monorepo-wide result; (3) the workflow is
documented from a single authoritative pointer; (4) `naive_first_engine`'s NFE-015 regression suite
specifically is confirmed to run, not skipped.

Constraining docs: `implementation-plan.md` section 8 states, as a binding convention: "for libs, the
public function signatures in the README stay in sync with the code — CI should fail if they drift
(add a doc-check step once the first lib ships)." That trigger fired in Sprint 01/02 when
`naive_first_engine` shipped NFE-018 (`scripts/check_doc_sync.py`, also runnable as
`tests/test_doc_sync.py`); this ticket is the first time anything actually runs it automatically.
`libs/naive_first_engine/pyproject.toml`'s `[tool.pytest.ini_options] testpaths = ["tests"]` means a
plain `pytest`/`uv run pytest` invocation already picks up `test_regression_1h.py` (NFE-015),
`test_regression_6h.py`/`test_regression_24h.py` (NFE-016), and `test_doc_sync.py` (NFE-018) with no
skip markers anywhere in `tests/` (confirmed by grep) — so "wire the module's own test command into
CI" is sufficient to satisfy AC4, no special-casing needed.

Session constraint (do not violate): `services/ingestion-service` has no `pyproject.toml` — it uses a
plain `requirements.txt` + a hand-built `.venv`, per its own README's documented setup
(`python -m venv .venv`, `pip install -r requirements.txt pytest`, `pytest tests/ -q`). The workflow
must accommodate this module's non-`uv` setup as its own job, not force it into the other four
modules' `uv`-based pattern.

Session constraint (do not violate): this ticket touches only a new `.github/workflows/` file plus
each module's own README (a one-line CI pointer) and the root `README.md`. It must not touch
`infra/postgres-init/`, `infra/migrate.*`, `infra/bootstrap.*`, or any other Sprint-07-owned file —
confirmed no overlap by reading `infra/` directly before writing this ticket.

## Design

No `implementation-plan.md` section 7 design pattern applies — this is CI/tooling configuration, not
application code inside a module boundary.

Files touched (all new or root/doc-only, no single service/lib's source code changed):
- `.github/workflows/ci.yml` (new)
- `libs/naive_first_engine/README.md`, `libs/common/README.md`,
  `services/validation-service/README.md`, `services/gateway-api/README.md`,
  `services/ingestion-service/README.md` — each gains a one-line "CI" pointer (per AC3, "how do I
  know this passed" needs one authoritative answer)
- Root `README.md` — the single authoritative pointer AC3 asks for; the repo's other doc-sync
  precedent (e.g. `docs/tickets/README.md` as the ticket-index pointer) is a root-level file, so this
  follows the same convention rather than inventing a second one

DRY check: grepped the repo for `.github` and any other CI config (`.gitlab-ci.yml`, `azure-pipelines.yml`,
etc.) — zero matches anywhere. Nothing to reuse or extend; this is greenfield.

Workflow design: five separate jobs (not a single job running five shell commands in sequence), so
each module gets its own pass/fail status in the GitHub Actions UI — this is what satisfies AC2
("not one opaque monorepo-wide result") mechanically, not by convention.

- `naive-first-engine`, `libs-common`, `validation-service`, `gateway-api`: each job `working-directory: <module>`,
  installs `uv` (e.g. `astral-sh/setup-uv@v3`), runs `uv sync` then `uv run pytest -q`. This is the
  exact command each of those four modules' own `pyproject.toml`/README already documents — the
  workflow does not invent a different invocation.
- `ingestion-service`: its own job, `working-directory: services/ingestion-service`, sets up a plain
  Python venv (`actions/setup-python`, no `uv`), runs
  `pip install -r requirements.txt pytest` then `pytest tests/ -q` — matching its README's own
  documented setup verbatim, not approximated.
- Trigger: `on: push` and `on: pull_request` (both, so a failing PR is caught before merge and a
  direct push to `main` is still caught after).
- No job depends on another (`needs:`) — all five run in parallel, since they are independent modules
  with no shared build artifact.
