# GW-030 — `provision()` calls `INGEST-030`'s seed endpoint, degraded-not-blocking

**Sprint**: 45. **Module**: `services/gateway-api`. **Status**: done. **Priority**: Must.
**Depends on**: `INGEST-030` (needs the real endpoint to call), `SETUP-002`/`SETUP-011` (both done — the
two existing tenant-creation front doors this hook attaches to). Third/last in this sprint's sequential
chain.

## Analysis

Story: backlog `INGEST-029`'s gateway-api half — every code path that creates a tenant
(`scripts/provision_tenant.py` and `POST /setup/initialize`/`POST /tenants`, all of which already funnel
through the single shared `provision()` function in `src/app/provisioning.py`, per that file's own
docstring: "One function, two callers -- never two implementations") must also seed platform historical
data for the new tenant, **without** ever blocking or failing tenant creation itself if the seed call
fails. Split from `INGEST-030` per this repo's two-modules-two-tickets rule.

## Design

**File**: `services/gateway-api/src/app/provisioning.py` only (the one shared function every
tenant-creation front door already calls through — confirmed by reading the file: `scripts/
provision_tenant.py` and `app.routers.setup`'s `POST /setup/initialize` both call `provision()`, and
`SETUP-011`'s `POST /tenants` — confirm at implementation time whether that route also calls `provision()`
or its own tenant-creation path; if it does not, extend it to call the same `provision()` function rather
than adding a second seed-call site, since duplicating the seed-trigger logic at two call sites would be
exactly the DRY violation this backlog's own text warns against).

**DRY check**: reuses `app.dependencies.http_client.get_ingestion_service_client`/
`IngestionServiceClientDep` (already exists, `INGESTION_SERVICE_URL` env var, already wired for
`GW-019`/`GW-020`/`GW-021`'s proxy routes) — no second httpx client provider. `provision()` itself is a
plain function, not a route handler, so it cannot use FastAPI's `Depends()` injection directly; call
`get_ingestion_service_client()` the same way any other plain-function caller of that provider would (a
new optional `ingestion_client: httpx.Client | None = None` parameter on `provision()`, defaulting to a
freshly built client via that same provider function when not supplied by the caller/test — mirrors the
existing pattern of `provision()` accepting `tenant_repo`/`api_key_repo` as injectable parameters rather
than reaching for a global).

**Call site**: synchronous (Tech Lead's call, per the sprint's own explicit call-out that this is
undecided by the sprint plan) — call the seed endpoint immediately after `api_key_repo.create_key`
succeeds and before `provision()` returns, wrapped in a `try`/`except` that catches any `httpx` transport
exception *and* a non-2xx response, logs a structured warning (`event_type="tenant_seed_degraded"`,
`outcome="degraded"`, `tenant_id=tenant.id`, matching this file's own existing `logger.info(...,
extra={"event_type": ...})` convention for `api_key_issued`), and does **not** re-raise — `provision()`
still returns `(tenant, raw_key)` normally. Chosen over fire-and-forget/background-task because
`gateway-api`'s request/response cycle for `POST /tenants`/`POST /setup/initialize` is already
synchronous end-to-end (no existing background-task infrastructure in this service to reuse, and adding
one would be a second, heavier mechanism just for this), and the seed call's own upstream endpoint
(`INGEST-030`) is disclosed as synchronous-execution-for-the-MVP itself — chaining two synchronous calls
is consistent with the platform's existing "disclosed synchronous, not scaled yet" posture
(`validation-service`'s own `POST /runs` carries the same disclosed tradeoff).

## Implementation acceptance criteria

- [x] `provision()` calls `INGEST-030`'s `POST /internal/seed-platform-history` (with the `tenant.id` just
  created, and the `X-Internal-Token` header sourced from a new `INGESTION_INTERNAL_TOKEN` env var read
  the same way `INGESTION_SERVICE_URL` is read today) exactly once, after the tenant + API key are both
  created.
- [x] A downstream failure (timeout, connection refused, non-2xx response) is caught, logged as a
  structured degraded-outcome warning, and does **not** raise — `provision()`'s return value and the
  calling route's response to the client are unaffected; tenant creation succeeds either way.
- [x] Both `scripts/provision_tenant.py` and `POST /tenants` (`SETUP-011`) end up calling this same
  `provision()` code path — no second, divergent seed-trigger call site. Confirmed at implementation
  time: `POST /tenants` already called `provision()` directly (no refactor needed); `POST /setup/initialize`
  also already called it.
- [x] Idempotent by construction: reuses `INGEST-030`'s already-idempotent endpoint — no additional
  idempotency logic needed in `gateway-api` itself, and a retried/duplicate seed call for the same tenant
  is safe.

## Test acceptance criteria

- [x] A new tenant created via `scripts/provision_tenant.py` (or its underlying `provision()` call in a
  test) and via `POST /tenants` both result in exactly one seed call to `ingestion-service`, verified
  against a fake `httpx` transport (mirroring `GW-019`'s own fake-transport test convention) — proving
  cross-front-door parity, this sprint's own explicit Definition of Done item. Also covered for
  `POST /setup/initialize`.
- [x] A downstream `ingestion-service` failure (fake transport raising `httpx.ConnectError`, and
  separately a fake `500` response) during provisioning does not raise out of `provision()` and does not
  fail the tenant-creation route's own response — the route still returns its normal `201`/success body.
- [x] The structured degraded-outcome log line is asserted (not just "no exception raised") — same
  non-tautological discipline `VS-022`'s tests established for tenant isolation, applied here to
  "the failure was actually recorded, not silently swallowed."
- [x] A successful seed call is asserted to pass the newly created tenant's real `id`, not a placeholder.
