## Analysis

`runs_list` (`services/dashboard-web/src/app/routers/runs.py`, lines 726–769) today calls only
`GET /runs` — it has no access to any run's per-split verdict/error data. `RAV-013`'s verdict indicator
and `RAV-014`'s sparkline both need that data, per run, for every run on the currently rendered page,
without turning one page load into an uncapped number of downstream calls (the runs list is very likely
this platform's highest-traffic page).

**Mechanism is already decided by the sprint plan — not open for re-litigation in this ticket.**
Sprint-60.md's "Sequencing call" section picks mechanism (a): a new batched endpoint on
`validation-service` (+ `gateway-api` pass-through) accepting a page of run IDs and returning each run's
per-split data in one round trip, reusing `SplitResultResponse`'s existing shape — not (b) a hard-capped
N+1, not (c) a precomputed field. Rationale (full text in sprint-60.md): the runs list pays this cost on
every visit forever, proportional to whatever N+1 cap was chosen; `GET /system/runs-summary`
(`SETUP-022`) is this platform's own live precedent for "hide N downstream calls behind one endpoint";
the new endpoint is a small, disciplined addition following an already-established pass-through pattern,
not new architectural surface.

**Route-path collision, must be avoided (found during ticket planning, not obvious from the AC text)**:
`GET /runs/{run_id}` already exists in both `validation-service`'s `runs.py` and `gateway-api`'s
`runs.py`. A 2-path-segment route like `GET /runs/splits-summary` would collide with `/runs/{run_id}`'s
pattern (FastAPI/Starlette match by registration order for same-segment-count paths — a request to
`/runs/splits-summary` would bind `run_id="splits-summary"` against `GET /runs/{run_id}` if that route is
registered first, which it is in both services' current `main.py`/router file). **Use a 3-path-segment
route instead: `GET /runs/splits/summary`.** This cannot collide with `/runs/{run_id}` (different segment
count) or with `/runs/{run_id}/splits` (also 3 segments, but segment 3 is the literal `"summary"` vs.
that route's literal `"splits"` — mismatches for any real run id, which is always a uuid hex, never the
literal string `"splits"`), regardless of registration order. Do not invent a different path without
re-checking this collision reasoning.

## Design

**Design pattern**: none new — this is the same pass-through Repository/DI pattern every other
`splits`-adjacent route in this codebase already uses (`GET /runs/{id}/splits`, VS-008/GW-008;
`GET /runs/{id}/splits/{index}/points`, VS-033/GW-031).

### 1. `libs/common/src/naive_first_common/contracts.py`

Add, after `SplitPointResponse`:

```python
class RunSplitSummary(BaseModel):
    """RAV-012: one run's entry within the batched `GET /runs/splits/summary`
    response. Reuses `SplitResultResponse` verbatim for the per-split shape
    — never a fourth hand-duplicated field list (ARCH-003)."""

    run_id: str
    splits: list[SplitResultResponse]
```

This is the **single canonical shared shape** this ticket adds. The outer `{"items": [...]}` envelope
stays a router-local Pydantic model in each service (matching `RunListResponse`/`SplitPointsResponse`'s
existing "shared item shape, local envelope" precedent — do not add the envelope itself to
`contracts.py`).

### 2. `services/validation-service`

- `src/app/repositories/interfaces.py` — add one method to the existing `SplitResultRepository`
  `Protocol` (do not create a new protocol):
  ```python
  def get_splits_for_runs(self, tenant_id: str, run_ids: list[str]) -> dict[str, list[SplitResultRecord]]:
      """Batched form of get_splits (RAV-012). A run_id with no splits, or
      not belonging to this tenant, is simply absent from the result dict
      -- never an error, never a KeyError for the caller to guard against.
      Each present run's list is ordered by split_index ascending, same as
      get_splits."""
      ...
  ```
- `src/app/repositories/sqlite_repository.py` and `postgres_repository.py` — implement it on
  `SQLiteSplitResultRepository`/`PostgresSplitResultRepository` as **one query**, not a loop calling
  `get_splits` per run id: `select(SplitResult).where(SplitResult.run_id.in_(run_ids),
  SplitResult.tenant_id == tenant_id).order_by(SplitResult.run_id, SplitResult.split_index)`, then group
  rows into `dict[str, list[SplitResultRecord]]` in Python. Reuse the existing `_split_result_to_record`
  conversion helper both files already import/define — do not write a second row→record mapping.
- `src/app/routers/splits.py` — new route `GET /runs/splits/summary`, added to this same file (natural
  home: this file already owns every `split_results`-adjacent batch/detail read). **DRY, mandatory**:
  `get_splits` (line 121–160 today) currently inlines a 20-field `SplitResultResponse(...)` construction
  from a `SplitResultRecord`. Extract that into a private helper, e.g.
  `_split_result_to_response(split: SplitResultRecord) -> SplitResultResponse`, used by **both**
  `get_splits` and this new route — do not write a second copy of that field mapping (this is the exact
  "extract on second duplication" case implementation-plan.md section 9 describes).
  Handler shape (no run-ownership 404 here — unlike single-run routes, an unknown/cross-tenant run id in
  a batch request is simply absent from the response, not a request-level error, since the caller
  supplied a *page* of ids it already believes are its own):
  ```python
  @router.get("/runs/splits/summary", response_model=RunSplitsSummaryResponse)
  def get_splits_summary(
      split_repository: SplitResultRepositoryDep,
      tenant: TenantContext = Depends(get_tenant_context),
      run_id: list[str] = Query(default=[]),
  ) -> RunSplitsSummaryResponse:
      if not run_id:
          return RunSplitsSummaryResponse(items=[])
      splits_by_run = split_repository.get_splits_for_runs(tenant.tenant_id, run_id)
      return RunSplitsSummaryResponse(
          items=[
              RunSplitSummary(
                  run_id=rid,
                  splits=[_split_result_to_response(s) for s in splits],
              )
              for rid, splits in splits_by_run.items()
          ]
      )
  ```
  `RunSplitsSummaryResponse` (`items: list[RunSplitSummary]`) is a local Pydantic model in this file,
  importing `RunSplitSummary` from `naive_first_common.contracts` — same "local envelope, shared item"
  precedent as `SplitPointsResponse` in this same file.
- **No change to `GET /runs/{run_id}/splits`'s existing contract or behavior** — this is additive only
  (binding AC).
- RLS/tenant scoping: automatic via `_tenant_scoped_session`'s existing `set_config('app.tenant_id', ...)`
  mechanism — no new isolation mechanism introduced, same as every other method in this repository.

### 3. `services/gateway-api`

- `src/app/routers/runs.py` — new pass-through route, same file, mirroring `get_splits`/
  `get_split_points`'s exact shape immediately above/below them:
  ```python
  class RunSplitsSummaryResponse(BaseModel):
      items: list[RunSplitSummary]

  @router.get("/runs/splits/summary", response_model=RunSplitsSummaryResponse)
  def get_splits_summary(
      client: ValidationServiceClientDep,
      tenant: TenantContext = Depends(get_authenticated_tenant),
      run_id: list[str] = Query(default=[]),
  ) -> RunSplitsSummaryResponse:
      headers = build_downstream_headers(tenant)
      response = _call_downstream(
          client.get, "/runs/splits/summary", params={"run_id": run_id}, headers=headers
      )
      _raise_for_error(response)
      return RunSplitsSummaryResponse(**response.json())
  ```
  `RunSplitSummary` imported from `naive_first_common.contracts`, never redefined. No business logic
  reimplemented — pure forward, same as every other route in this file.

### 4. `services/dashboard-web`

- `src/app/routers/runs.py`'s `runs_list` (lines 726–769): after fetching `runs` (the existing `GET
  /runs` call), if `runs` is non-empty, make **exactly one** additional call:
  `client.get("/runs/splits/summary", params=[("run_id", r.id) for r in runs], headers=headers)`
  (httpx accepts a list of `(key, value)` tuples for repeated query params — this is how one call
  carries N run ids, not N calls). Parse into `dict[str, list[SplitResultResponse]]` keyed by
  `run_id` (default to `{}` for any run id absent from the response — a run with zero splits, or a
  transport/non-200 failure on this one call).
- **Failure handling, explicit design decision**: a transport failure or non-200 on this new call must
  **not** block the runs list itself from rendering (the primary `GET /runs` call already succeeded) —
  degrade to an empty `{}` summary dict, same "degrade, don't block" precedent
  `_fetch_ingestion_datasets` already established for `run_new_form`/`datasets_list`. `RAV-013`'s
  verdict column then shows "no results yet" and `RAV-014`'s sparkline shows its placeholder for every
  run in that case — not a broken page.
- Do not add this to `_call_downstream`/`_render_error_for_status`'s blocking-failure path — this call's
  failure mode is "degrade the two new columns," not "fail the whole page," a deliberately different
  contract from every other call in this file (state this explicitly in code comments so a future editor
  doesn't merge it into the blocking pattern by habit).
- Pass the resulting `dict[str, list[SplitResultResponse]]` into the template context (e.g.
  `run_splits_summary`) — `RAV-013`/`RAV-014` consume it from there; this ticket does not itself render
  anything new in `runs_list.html`.

**DRY check note**: grepped `services/dashboard-web/src/app/routers/runs.py` before writing this design
— no existing helper batches a list of run ids into one call; this is genuinely new, not a duplicate of
`runs_trend`'s per-run-in-a-loop `GET /runs/{id}/splits` calls (which this ticket does not touch or
replace — `runs_trend` is out of scope here).
