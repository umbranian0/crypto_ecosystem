# GW-029 — UAT-005: fix `openapi.json`'s collapsed/incorrect security schemes

**Module**: `services/gateway-api` only.
**Depends on**: none. Independent of Track A, runs in parallel.

## Analysis

Covers `docs/product/backlog-uat-findings.md` UAT-005. **Live-verified root cause** (not hypothetical):
booted the real app (`app.main.app`) and called `app.openapi()` directly. Found:
- `components.securitySchemes` contains exactly **one** entry, `"APIKeyHeader"` — `auth.py`'s
  `_authorization_scheme` (`Authorization`), `_x_api_key_scheme` (`X-Api-Key`), and `operator_auth.py`'s
  `_operator_token_scheme` (`X-Operator-Token`) all collapse into it.
- `/runs`, `/tenants`, `/diagnostics/recent-errors` (a mix of tenant-gated and operator-gated routes) all show
  `security: [{"APIKeyHeader": []}]` — identical and indistinguishable in the published schema, even though
  they are gated by two structurally separate dependencies (`get_authenticated_tenant` vs.
  `get_authenticated_operator`).

**Real cause**: `fastapi.security.APIKeyHeader(name=..., auto_error=False)`'s `name=` parameter sets the
**header name** only. FastAPI's OpenAPI generator names each `securityScheme` component after
`SecurityBase.scheme_name`, which defaults to the **class name** (`"APIKeyHeader"`) when not explicitly
passed. All three instances share the same class and none passes `scheme_name=`, so all three collapse into
one shared, wrongly-labeled component — this is the actual bug, not a missing `Security()` wiring (the
`Security()`+sub-dependency wiring itself is already correct: `get_authenticated_tenant`'s and
`get_authenticated_operator`'s own `Security(...)` parameters do propagate to each route that depends on
them via `Depends(get_authenticated_tenant)`/`Depends(get_authenticated_operator)` — confirmed live, every
route's `security` list is populated, just with the wrong/collapsed scheme).

## Design

**Pattern**: none new — this is ARCH-008's existing `Security()` + `APIKeyHeader` convention, fixed to name
its three scheme instances distinctly instead of introducing a new pattern.

**DRY check**: grepped `services/gateway-api/src/app/dependencies/`. Exactly two files define
`APIKeyHeader` instances: `auth.py` (`_authorization_scheme`, `_x_api_key_scheme`) and `operator_auth.py`
(`_operator_token_scheme`). No third definition exists. Fix both in place — no shared helper needed for a
three-line, three-instance change.

**Files touched**:
- `services/gateway-api/src/app/dependencies/auth.py`: give `_authorization_scheme` and `_x_api_key_scheme`
  distinct `scheme_name=` values, e.g. `APIKeyHeader(name="Authorization", scheme_name="AuthorizationBearer", auto_error=False)` and `APIKeyHeader(name="X-Api-Key", scheme_name="XApiKey", auto_error=False)`.
- `services/gateway-api/src/app/dependencies/operator_auth.py`: give `_operator_token_scheme` its own
  `scheme_name="XOperatorToken"`.
- No route files change — the `Security()` wiring into each route via `Depends(get_authenticated_tenant)`/
  `Depends(get_authenticated_operator)` is already correct; only the scheme *naming* was broken.
