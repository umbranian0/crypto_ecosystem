## Design

**Pattern**: Repository (implementation-plan.md section 7) — same shape as the three existing
`identity`-schema repositories, so a future move to a separate physical DB stays a DI-only swap, not a
call-site rewrite. Dependency Injection (FastAPI `Depends()`) for the new repository provider, same as
every other provider in `dependencies/repositories.py`. No Strategy/Adapter/Factory applies — this is a
plain append-only log table with one write path and one paginated read path.

**Files touched** (scoped to `services/gateway-api` only):

1. `services/gateway-api/src/app/models.py` — add:
   ```python
   class OperatorAuditLog(Base):
       __tablename__ = "operator_audit_log"

       id: Mapped[str] = mapped_column(String, primary_key=True)
       action: Mapped[str] = mapped_column(String, nullable=False)
       # Nullable: not every future action type necessarily targets one tenant
       # (AC's own "nullable" wording) -- both of today's two actions do set it.
       target_tenant_id: Mapped[str | None] = mapped_column(
           String, ForeignKey("tenants.id"), nullable=True
       )
       correlation_id: Mapped[str] = mapped_column(String, nullable=False)
       at: Mapped[datetime] = mapped_column(DateTime, nullable=False)
   ```
   No `key_hash`/raw-token column of any kind anywhere on this model (AC's non-negotiable constraint).

2. `services/gateway-api/migrations/versions/0006_create_operator_audit_log.py` — new migration,
   `revision = '0006'`, `down_revision = '0005'`. Plain `op.create_table(...)`, unguarded (runs against
   both sqlite and postgres), mirroring `0001_create_identity_schema.py`'s own unguarded `create_table`
   calls (env.py already sets `search_path=identity` for Postgres runs, so no explicit `schema=` kwarg is
   needed, matching `0001`'s precedent exactly). **Deliberately no RLS on this table** — document this
   decision in the migration's own docstring: `operator_audit_log` is an operator-only, cross-tenant
   resource, never queried under a tenant-scoped session (unlike `tenants`/`users`/`api_keys`, which are
   both operator- and tenant-facing in different code paths) — every repository method on this table
   (see below) is deliberately tenant-agnostic (never calls `_set_tenant_scope`), the same category as
   `list_tenants()`/`tenant_exists()`, so enabling RLS here would add a policy that is never actually
   exercised from a tenant angle. This is a considered, disclosed Tech Lead design call, not an oversight
   — flag it for Review to confirm.

3. `services/gateway-api/src/app/repositories/interfaces.py` — add:
   ```python
   @dataclass(frozen=True)
   class OperatorAuditLogRecord:
       id: str
       action: str
       target_tenant_id: str | None
       correlation_id: str
       at: datetime

   @typing.runtime_checkable
   class OperatorAuditLogRepository(typing.Protocol):
       """Tenant-agnostic by nature (every method here is a sixth-and-seventh
       documented exception to the tenant_id-first convention, alongside the
       five already listed above) -- this whole interface is an operator-only,
       cross-tenant resource; there is no tenant scoping concept for it to
       apply."""

       def record(
           self, action: str, target_tenant_id: str | None, correlation_id: str
       ) -> OperatorAuditLogRecord: ...

       def list_entries(self, limit: int, offset: int) -> tuple[list[OperatorAuditLogRecord], int]:
           """Returns `(page, total)` -- `total` is the full unpaginated row
           count, backing `GET /operator-audit-log`'s `{items, limit, offset,
           total}` envelope (same shape as `GET /runs`'s existing
           `RunListResponse`)."""
           ...
   ```
   Extend the module docstring's existing exception list to note these two new tenant-agnostic methods,
   same convention as the existing four-exceptions note.

4. `services/gateway-api/src/app/repositories/sqlite_repository.py` — add `SQLiteOperatorAuditLogRepository`
   (`__init__(self, db_path: str, engine: Engine | None = None)`, matching the other three classes
   exactly). `record()`: builds an `OperatorAuditLog` row with `id=uuid4().hex`, `at=datetime.utcnow()`,
   inserts, commits, `session.refresh`, returns the mapped record (same shape as
   `SQLiteTenantRepository.create_tenant`). `list_entries()`: one `SELECT ... ORDER BY at DESC LIMIT
   :limit OFFSET :offset` plus one `SELECT count(*)`, both unfiltered (no tenant scoping — this backend
   has no RLS concept at all, so this is naturally already tenant-agnostic).

5. `services/gateway-api/src/app/repositories/postgres_repository.py` — add
   `PostgresOperatorAuditLogRepository` (`__init__(self, engine: Engine)`, matching the other three
   Postgres classes). `record()`/`list_entries()` mirror the SQLite versions but deliberately do **not**
   call `_set_tenant_scope` (per this table's no-RLS design decision above) — document this inline the
   same way `list_tenants()`/`tenant_exists()` document their own tenant-agnostic exception.

6. `services/gateway-api/src/app/dependencies/repositories.py` — add `get_operator_audit_log_repository()`
   following the existing `_select_backend(postgres_cls, sqlite_cls)` helper exactly (no new branching
   logic invented — DRY reuse of the helper the module docstring already calls out as shared), plus
   `OperatorAuditLogRepositoryDep = Annotated[OperatorAuditLogRepository, Depends(get_operator_audit_log_repository)]`.

7. `services/gateway-api/src/app/routers/tenants.py` — two write-on-success call sites, both **after**
   the underlying mutation already succeeded, right before each handler's existing `return`:
   - `create_tenant`: `audit_log_repository.record("tenant.create", tenant.id, correlation_id_var.get())`.
   - `revoke_api_key`: `audit_log_repository.record("api_key.revoke", tenant_id, correlation_id_var.get())`
     — written unconditionally on every 200 response, **including the already-revoked no-op branch**
     (design decision, stated explicitly since the AC's "write-on-success" wording is ambiguous between
     "state actually changed" and "the request succeeded"): from an audit-trail perspective, an operator
     successfully invoking revoke happened either way, and a 403/404 (the only other outcomes) never
     reaches this line at all — so "on success" is read here as "on 200 response," matching the AC's
     plain English. Both handlers gain `audit_log_repository: OperatorAuditLogRepositoryDep` as a new
     parameter (DI, no other call site needs it).
   - Import `from naive_first_common.logging import correlation_id_var` (reuse, not a new mechanism — see
     Analysis).
   - `list_tenants` (`GET /tenants`, a read) is unchanged — writes only, per the AC's own scope line.

## Implementation acceptance criteria

- [x] `identity.operator_audit_log` table exists with `id`, `action`, `target_tenant_id` (nullable),
  `correlation_id`, `at` — no `key_hash`/raw-token/hashed-token column anywhere on the model.
- [x] `POST /tenants` writes exactly one row (`action="tenant.create"`, `target_tenant_id=<new tenant's
  id>`, `correlation_id=<this request's correlation id>`) on every `201` response, zero rows on any
  non-`201` response (there is no failure branch in `create_tenant` today — `provision()` either succeeds
  or raises unhandled, so a 500 case legitimately writes no row either, which is correct: nothing
  succeeded).
- [x] `POST /tenants/{tenant_id}/api-keys/{key_id}/revoke` writes exactly one row
  (`action="api_key.revoke"`, `target_tenant_id=<tenant_id>`, `correlation_id=<this request's correlation
  id>`) on every `200` response (both the real-revoke and already-revoked-no-op branches), zero rows on
  the `404` branch.
- [x] `GET /operator-audit-log` is gated by `get_authenticated_operator` (401 with no/invalid operator
  token, before any repository call), paginates via `limit`/`offset` query params (defaults `20`/`0`,
  matching `GET /runs`'s own defaults), and returns `{items, limit, offset, total}`.
- [x] No response body, log line, or DB row produced by this ticket's code ever contains the raw or
  hashed `OPERATOR_TOKEN` value, or a tenant's raw/hashed API key.
