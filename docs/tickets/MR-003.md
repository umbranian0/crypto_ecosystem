# MR-003 — Documented interface for `research/` to eventually consume `validation-service`'s multi-source feature assembly

Status: **done** (built directly by the Tech Lead, no dev agent — interface-design-and-documentation
scope only, per docs/sprints/sprint-41.md).

Source story: `docs/product/backlog-model-research.md` MR-003. Sprint: `docs/sprints/sprint-41.md`.

## Analysis

- Story: "As a research candidate model, I want the aligned multi-source feature table produced by
  MDF-003 to be consumable by a `research/`-side candidate model without duplicating the
  alignment/purge-gap logic ADR-0008/0009 already specified."
- Acceptance criteria (backlog, verbatim):
  1. A documented interface is written before any research code touches multimodal data.
  2. Explicitly blocked, with the blocking condition stated: cannot start implementation until MDF-003
     ships. **Sprint-41 pre-read finding revises this**: MDF-003/VS-030 shipped in Sprint 36
     (`services/validation-service/src/app/feature_dataset.py`, `FeatureDatasetAssembler`) — but there
     is still no `GET` route that returns its assembled `DataFrame` to an external caller. The blocking
     condition this ticket documents is therefore the *export endpoint*, not MDF-003 itself.
  3. No `naive_first_engine` change — confirmed: this ticket touches no file under
     `libs/naive_first_engine`.
- Constraining docs read: `services/validation-service/README.md`'s "Multi-source feature assembly
  (VS-030/MDF-003)" section (confirms `FeatureDatasetAssembler.assemble`'s output is consumed only
  internally by `routers/runs.py::create_run`, immediately reduced to `series.loc[assembled.index]`
  before `run_validation_protocol` runs — never returned by any route); `docs/adr/0010-multimodal-
  candidate-model-interface.md` (the `CandidateModel` Strategy interface already exists in
  `libs/naive_first_engine`, additive, not wired into `protocol.py`, no service-side call site written
  yet); `docs/implementation-plan.md` section 4 (inter-service communication: HTTP only, never a
  service's DB schema) and section 2 (module boundaries — `research/` is not a service, has no HTTP
  surface itself, and must call `validation-service` the same way `reporting-service` does: by hostname,
  never by importing `app.*`).

## Design

- No design pattern from implementation-plan.md section 7 is being introduced by this ticket — it
  documents a future HTTP client call shape, it does not implement a client. Forcing a pattern (e.g.
  Adapter) onto a documentation-only deliverable would be exactly the "don't force one where the table
  doesn't call for it" case this platform's process explicitly warns against.
- File touched: `research/README.md` only (new "Multimodal feature interface (MR-003)" section). Scoped
  to one module (`research/`), per the "a ticket spanning two modules should be two tickets" rule — this
  ticket does not touch `services/validation-service`.
- **DRY check**: grepped `research/` for any existing HTTP-client code, `httpx`/`requests` import, or
  multimodal-related name before writing anything — none exists (`research/features.py` and
  `research/tests/test_features.py` are the only non-scaffolding files in the directory, both pure
  functions over a single `pd.Series`, no I/O). Nothing to reuse/extend; this is a net-new documentation
  section, not a duplication risk.

## Implementation acceptance criteria

- `research/README.md` gains a section stating, in prose, the interface `research/` code *would* call
  once an export endpoint exists: an HTTP `GET` request to `validation-service` (by Compose hostname,
  never through `app.*` imports — `research/` is not a service and has no privileged DB access) returning
  the assembled multi-column feature table (or a reference/pointer to it) for a given
  `{tenant_id, run_id}` or `{tenant_id, feature_references, missing_timestamp_policy}` pair, structurally
  mirroring `IngestionServiceDatasetSource`'s "by hostname, never by schema" precedent.
- Explicitly states the interface's expected shape (a JSON-serializable multi-column time-indexed table.
  or a `{"object_key": ...}` pointer into object storage the caller then fetches, mirroring
  `ObjectStorageDatasetSource`'s existing convention) and expected auth (tenant-scoped, same
  `X-Tenant-Id`/API-key convention every other `validation-service` route already uses — no new auth
  mechanism invented here).
- Explicitly, unambiguously states the gap: **no such endpoint exists today**. `FeatureDatasetAssembler.
  assemble`'s output is consumed only internally by `routers/runs.py::create_run`, immediately reduced
  to a re-indexed target `pd.Series` before `run_validation_protocol` runs — it is never returned by any
  `GET` route. `FeatureFoldScaler` (the per-fold-fit preprocessing surface) is likewise "not yet wired
  into any candidate-model inference call" per that same README section.
- States plainly that MR-004 (this sprint's other story) does **not** use this interface — MR-004 trains
  on the returns series ± MR-002's engineered features, not multimodal data, because no export endpoint
  exists yet to pull real multimodal data through.
- Does not write, and explicitly disclaims writing, any code that fetches or trains on real multimodal
  data this sprint.
