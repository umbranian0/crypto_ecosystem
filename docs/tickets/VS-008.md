# VS-008 — `GET /runs/{id}/splits` endpoint

**Status: done**

## Analysis
Story: VS-008 (Must), depends on VS-006 (only — sequenced alongside VS-007 in the backlog, but does not depend on VS-007). Constraining docs: solution-design.md section 4 ("is the model still beating naive this month," the reason `split_results` is wide/per-split), same tenant-isolation stance as VS-007.

## Design
Pattern: none new. Files: **`src/app/routers/splits.py` (new, separate file from `runs.py`)** — deliberately kept as its own router module (mounted at the same `/runs` prefix) rather than added to `runs.py`, specifically so this ticket has no file overlap with VS-007 (also editing `runs.py`) and VS-009 (also editing `runs.py`'s `POST` handler) — this lets VS-008 run in parallel with VS-009 once VS-007 has landed. `src/app/main.py` (edit — mount the new router). DRY check: reuse VS-006/007's repository `Depends()` providers from `dependencies/repositories.py`, don't redeclare.

**Tenant isolation**: same interim explicit `tenant_id` query param pattern as VS-007; same `404`-not-`403`-not-leaked-data stance. Must check the *run's* tenant ownership (via `ValidationRunRepository.get_run`) before returning splits — a `SplitResultRepository.get_splits(tenant_id, run_id)` call alone, if `run_id` isn't itself tenant-checked first, could theoretically be tricked by a `run_id` that belongs to another tenant if `get_splits` were ever implemented without its own tenant filter (it isn't, per VS-004 — but this handler should still 404 via the run lookup first, both as defense in depth and because a run that doesn't exist for this tenant has no meaningful "splits" response either way).

- [x] Splits returned in `split_index` order.
