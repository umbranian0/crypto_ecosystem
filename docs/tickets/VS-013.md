# VS-013 — Postgres-backed repository implementation (validation-service)

Status: **done**
Backlog: docs/product/backlog-validation-service.md, VS-013 [Should]
Sprint: docs/sprints/sprint-06.md, Phase 4
Depends on: ARCH-001, ARCH-002, ARCH-004 (Phase 1 Track A), INF-001, INF-005 (Phase 2)

## Analysis

`validation-service` currently only has `SQLiteValidationRunRepository`/
`SQLiteSplitResultRepository` (VS-004) behind the `ValidationRunRepository`/
`SplitResultRepository` Protocol interfaces (VS-003). This ticket adds a Postgres-backed sibling
implementation behind the same interfaces, swapped in via DI with no route-handler changes —
proving the Repository pattern did its job.

## Design

- **Binding decision (grooming, #3)**: Postgres driver is `psycopg` (v3), synchronous
  (`postgresql+psycopg://` URLs) — no async rewrite. Keeps existing `Session`-based repository
  method signatures unchanged.
- **Binding decision (grooming, #1/#2 dependency)**: build the engine via
  `naive_first_common.db.build_engine(url, Base)` (ARCH-001) and obtain it through the
  memoized-by-URL provider (ARCH-002) — do not reintroduce a per-request `create_engine` call.
- New `PostgresValidationRunRepository`/`PostgresSplitResultRepository` classes in a new module
  (e.g. `services/validation-service/src/app/repositories/postgres_repository.py`), implementing
  the exact same Protocol methods as VS-004's SQLite classes. Row-conversion logic
  (`_run_to_record`/`_split_result_to_record`) is reused/duplicated only as much as VS-004's
  already is — do not invent a generic mapper (ARCH-006 precedent: rejected for this exact
  reason).
- **Binding decision (grooming, #4), UPGRADED FROM SHOULD TO HARD REQUIREMENT by an INF-005
  finding**: Alembic `migrations/env.py` gains a `search_path`/`version_table_schema` addition so
  `alembic upgrade head` targets the `validation` schema specifically (not `public`) inside the
  one shared Postgres database/two-schema design INF-001 provisions. INF-005 empirically proved
  this is not optional polish: running both services' current (public-schema,
  `version_table_schema`-less) migrations back-to-back against the same Postgres database causes
  the second one to find `public.alembic_version` already stamped `'0001'` and silently *skip its
  own `upgrade()` with no error* — a real, reproduced, order-independent collision, not a
  hypothetical. `version_table_schema="validation"` (SQLAlchemy/Alembic's
  `context.configure(..., version_table_schema=...)`) is required, not a nice-to-have, and must be
  combined with pointing `target_metadata`/connection `search_path` at the `validation` schema so
  `runs`/`split_results` are created there, not in `public`.
- **Binding decision (grooming, #7)**: real Postgres RLS policies (`CREATE POLICY`), matching
  GW-012's mechanism — treat VS-013's "row-level tenant scoping... not just application-level
  filtering" AC wording as the same requirement as GW-012's explicit "RLS policies", not a
  deliberately weaker bar. Concretely: `ALTER TABLE runs ENABLE ROW LEVEL SECURITY;` +
  `CREATE POLICY tenant_isolation ON runs USING (tenant_id = current_setting('app.tenant_id'));`
  (and same for `split_results`), added via a new Alembic migration. The repository's session
  must `SET LOCAL app.tenant_id = :tenant_id` per-transaction — same `SET LOCAL` mechanism as
  GW-012 (binding decision #8), implemented at the same seam ARCH-002 introduced.
- DI wiring: `dependencies/repositories.py`'s `get_validation_run_repository`/
  `get_split_result_repository` swap to the Postgres classes when `DATABASE_URL` env var is set
  (Postgres URL scheme), falling back to SQLite via `VALIDATION_SERVICE_DB_PATH` otherwise — no
  route handler or business logic changes (AC2).
- The interim SQLite implementation (VS-004) is retained, not deleted.

## Implementation acceptance criteria

- [x] `PostgresValidationRunRepository`/`PostgresSplitResultRepository` implement the same
      interfaces as VS-004 against Postgres, using `psycopg` v3, synchronous.
- [x] Uses `naive_first_common.db.build_engine` + the ARCH-002 memoized-by-URL provider — no local
      `create_engine` call.
- [x] `migrations/env.py` targets the `validation` schema via BOTH `search_path` (for table
      creation) AND `version_table_schema="validation"` (for `alembic_version` tracking) — not
      `public`. This is a hard requirement per INF-005's empirically reproduced collision (see
      Design), not optional. Verified live against Postgres: `runs`, `split_results`, and
      `alembic_version` all land under `information_schema.tables.table_schema='validation'` after
      a fresh `alembic upgrade head`. (Both settings are conditional on
      `connection.dialect.name == "postgresql"` — required after discovering
      `tests/test_models.py::test_alembic_upgrade_head_creates_matching_schema` runs the same
      `env.py` against a real `sqlite:///` `DATABASE_URL`, which has no `SET search_path`/schema
      concept; this conditional keeps that pre-existing SQLite test green.)
- [x] RLS policies (`CREATE POLICY`) added via a new Alembic migration
      (`migrations/versions/0002_add_row_level_security.py`) for `runs` and `split_results`,
      scoping every query to `current_setting('app.tenant_id')`. Also added `FORCE ROW LEVEL
      SECURITY` (beyond the ticket's literal SQL): this sprint's infra provisions the app's own
      Postgres role (`naive_first`) as a **superuser with BYPASSRLS**, which Postgres always
      exempts from RLS regardless of `ENABLE`/`FORCE` — `FORCE` doesn't change that for a
      superuser specifically, but is still the correct setting for a real non-superuser app role.
      Both DDL statements are conditional on `op.get_bind().dialect.name == "postgresql"` for the
      same SQLite-migration-test reason as the `env.py` bullet above.
- [x] Repository session sets `app.tenant_id` per-transaction before any query, as the first
      statement — implemented as `SELECT set_config('app.tenant_id', :tenant_id, true)` rather
      than the ticket's literal `SET LOCAL app.tenant_id = :tenant_id` text, because plain `SET
      LOCAL ... = :param` is not valid Postgres syntax (`SET` does not accept a bind parameter,
      only a literal). `set_config('app.tenant_id', value, true)` is `SET LOCAL`'s
      parameter-bindable equivalent — same "for this transaction only" semantics (third arg
      `true`), without string-formatting a caller-influenced `tenant_id` directly into SQL.
- [x] Swapping VS-004 → VS-013 in DI wiring is the only change required for route handlers — this
      ticket's own diff touches zero files under `routers/`. (`git diff --
      src/app/routers/` is non-empty in the working tree, but every line is attributable to a
      concurrent sibling change, ARCH-003's contract-sharing work, already in progress before this
      ticket started — confirmed by reading that diff directly: it swaps two `pydantic.BaseModel`
      definitions for `naive_first_common.contracts` imports, nothing repository/DI-related.)
- [x] VS-004's SQLite implementation retained, unmodified in behavior —
      `src/app/repositories/sqlite_repository.py` has zero diff from this ticket.

## Outcome

Implemented as scoped. Two deviations from the ticket's literal text, both required for the code to
actually work / actually prove what the AC asks — documented inline above and in the touched files:

1. `SET LOCAL app.tenant_id = :tenant_id` (literal, parameterized) is not valid Postgres syntax —
   used `SELECT set_config('app.tenant_id', :tenant_id, true)` instead (same "current transaction
   only" semantics, still parameter-bound).
2. The RLS migration also sets `FORCE ROW LEVEL SECURITY` (the ticket's SQL only specified
   `ENABLE`), and the tenant-isolation proof test runs as a dedicated non-superuser role rather
   than the app's own `naive_first` role, because that role is provisioned as a Postgres superuser
   with `BYPASSRLS` and would make any RLS assertion pass vacuously otherwise. This was caught
   during self-review (the first version of the test passed against the superuser role even before
   `FORCE` was added), not by the Tech Lead — flagging it explicitly since it's exactly the kind of
   gap the Review ACs above ask the Tech Lead to independently verify.

The Review-acceptance-criteria checkboxes are left unchecked above per this role's process — they
are explicitly the Tech Lead's own personal-verification step, not something the implementer
self-certifies.
