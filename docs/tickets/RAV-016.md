## Analysis

`run_detail` (`services/dashboard-web/src/app/routers/runs.py`, lines ~1329-1344 as of this
sprint's start — will have shifted slightly once `DBOPT-011` lands earlier in the same handler)
issues one `GET /runs/{run_id}/splits/{split_index}/points` call per rendered split (bounded by
`MAX_RENDERED_SPLITS = 500`, but still up to 500 sequential two-hop round trips through gateway-api
to validation-service). Sprint 60 QA measured a real 550-split run's `run_detail` page at ~20
seconds server-side because of this. **Stated latency budget, non-negotiable per the backlog's own
AC**: under 2 seconds server-side for a realistic 550-split run — not met by any implementation
still issuing more than one downstream points call per page load, regardless of individual call
latency.

**Mechanism is founder-decided, not open for renegotiation**: follow the exact batched-endpoint
precedent `RAV-012` already established (`GET /runs/splits/summary`,
`PostgresSplitResultRepository.get_splits_for_runs`, one `WHERE ... IN (...)` query, gateway-api
pass-through, dashboard-web calling it once per page load), applied to `split_points` instead of
`split_results`. Exact route naming/shape is decided by the sprint plan (not open for this ticket
to re-litigate): `GET /runs/{run_id}/splits/points`, repeated `split_index` query param, new
`SplitPoints{split_index, points}` + `RunSplitPointsResponse{items}` contract types mirroring
`RunSplitSummary`/`RunSplitsSummaryResponse` one level down, new repository method
`get_points_for_splits(tenant_id, run_id, split_indices)` mirroring `get_splits_for_runs`.

**Behavioral parity required, explicit**: this endpoint's per-split point count defaults to the
same 20-point limit `GET /runs/{run_id}/splits/{split_index}/points` already defaults to (VS-033) —
this ticket does not change how many points are plotted per split, only how many round trips it
costs to fetch them (the existing `get_points`/`SplitPointRepository.get_points` has no
`limit`/`offset` of its own; `get_points_for_splits` mirrors that same unbounded-per-split shape, no
new pagination invented here). Retention (VS-032) applies identically via the shared
`_retention_cutoff()` helper — no second cutoff implementation. **The existing single-split `GET
/runs/{run_id}/splits/{split_index}/points` endpoint (VS-033) is completely unchanged** — same
contract, same behavior, stays live for the standalone `points-chart` route.

**Per-index degrade rule, different from `RAV-012`'s own batch endpoint — read carefully**: unlike
`get_splits_summary` (which silently *omits* an unknown/absent run id from its `items` list), this
endpoint must return **exactly one `SplitPoints` entry per requested `split_index`**, in the
response, even when that split has no points (pruned, never persisted, or — should never happen on
a real user path — not a real split of this run). The `split_index` values passed in are always
drawn from `run_detail`'s own already-fetched, already-validated `rendered_splits` list, so this
endpoint does **not** perform `VS-033`'s per-split "collapse into 404 if the split doesn't belong to
this run" validation — doing so would fail the *entire* batch over one bad index. Degrade that
index's own entry to `points: []` instead (same empty-points shape a pruned/never-persisted split
already gets from the single-split endpoint), consistent with `run_detail`'s existing per-split
degrade-on-transport-failure contract, now applied to a per-index data-availability question instead
of a transport failure.

## Design

**Design pattern**: none new — same pass-through Repository/DI pattern `RAV-012` already used for
`split_results`, applied here to `split_points`.

**DRY check note**: grepped `services/validation-service/src/app/routers/splits.py` and
`repositories/{sqlite,postgres}_repository.py` before writing this design. `get_split_points`
(VS-033, `splits.py:212-262`) currently inlines its per-point `SplitPointResponse(...)` construction
in a list comprehension (lines 250-256) — this must be extracted into a shared
`_split_point_to_response(point: SplitPointRecord) -> SplitPointResponse` helper and reused by
**both** `get_split_points` and this new route, mirroring exactly how `RAV-012` extracted
`_split_result_to_response` from `get_splits` for the analogous reason (implementation-plan.md
section 9's "extract on second duplication"). `PostgresSplitPointRepository.get_points`/
`SQLiteSplitPointRepository.get_points` (VS-031/VS-032) is the direct query-shape precedent for the
new `get_points_for_splits` — same `_retention_cutoff()` import, same table, one more `.in_(...)`
predicate instead of a single `==`.

### 1. `libs/common/src/naive_first_common/contracts.py`

Add, after `RunSplitSummary`:

```python
class SplitPoints(BaseModel):
    """RAV-016: one split's entry within the batched
    `GET /runs/{run_id}/splits/points` response. Reuses `SplitPointResponse`
    verbatim for the per-point shape -- never a fourth hand-duplicated field
    list (ARCH-003). Mirrors `RunSplitSummary`'s own `{run_id, splits}` shape
    one level down (per-split instead of per-run)."""

    split_index: int
    points: list[SplitPointResponse]
```

This is the single canonical shared shape this ticket adds. The outer `{"items": [...]}` envelope
stays a router-local Pydantic model in each service (`RunSplitPointsResponse`), same "shared item
shape, local envelope" precedent as `RunSplitSummary`/`RunSplitsSummaryResponse`.

### 2. `services/validation-service`

- `src/app/repositories/interfaces.py` — add one method to the existing `SplitPointRepository`
  `Protocol` (do not create a new protocol):
  ```python
  def get_points_for_splits(
      self, tenant_id: str, run_id: str, split_indices: list[int]
  ) -> dict[int, list[SplitPointRecord]]:
      """Batched form of get_points (RAV-016). A split_index with no points
      (pruned, never persisted, or absent from this call's request) is
      simply absent from the result dict -- never an error, never a
      KeyError for the caller to guard against. Each present split's list
      is ordered by timestamp ascending, same as get_points. Retention
      (VS-032) applies identically -- only points within
      SPLIT_POINT_RETENTION_DAYS are returned."""
      ...
  ```
- `src/app/repositories/{sqlite,postgres}_repository.py` — implement as **one query**, not a loop
  calling `get_points` per split index:
  ```python
  def get_points_for_splits(
      self, tenant_id: str, run_id: str, split_indices: list[int]
  ) -> dict[int, list[SplitPointRecord]]:
      with Session(self._engine) as session:  # or _tenant_scoped_session for Postgres
          rows = (
              session.execute(
                  select(SplitPoint)
                  .where(
                      SplitPoint.run_id == run_id,
                      SplitPoint.tenant_id == tenant_id,
                      SplitPoint.split_index.in_(split_indices),
                      SplitPoint.created_at >= _retention_cutoff(),
                  )
                  .order_by(SplitPoint.split_index, SplitPoint.timestamp)
              )
              .scalars()
              .all()
          )
          result: dict[int, list[SplitPointRecord]] = {}
          for row in rows:
              result.setdefault(row.split_index, []).append(_split_point_to_record(row))
          return result
  ```
  Reuses the existing `_retention_cutoff`/`_split_point_to_record` helpers — no second copy.
- `src/app/routers/splits.py` — **DRY, mandatory**: extract `get_split_points`'s inlined per-point
  mapping (lines 250-256 today) into:
  ```python
  def _split_point_to_response(point: SplitPointRecord) -> SplitPointResponse:
      """Extracted from get_split_points (RAV-016) so the 4-field mapping
      has exactly one copy -- reused by both get_split_points and
      get_splits_points below."""
      return SplitPointResponse(
          timestamp=point.timestamp,
          predicted=point.predicted,
          actual=point.actual,
          baseline_key=point.baseline_key,
      )
  ```
  Update `get_split_points` to use this helper (no behavior change, pure extraction). New route,
  same file:
  ```python
  class RunSplitPointsResponse(BaseModel):
      """RAV-016 response envelope for GET /runs/{run_id}/splits/points:
      `items` is `SplitPoints` (imported from naive_first_common.contracts,
      never redefined here) -- same "local envelope, shared item shape"
      precedent RunSplitsSummaryResponse above already established."""
      items: list[SplitPoints]

  @router.get("/runs/{run_id}/splits/points", response_model=RunSplitPointsResponse)
  def get_splits_points(
      run_id: str,
      run_repository: ValidationRunRepositoryDep,
      split_point_repository: SplitPointRepositoryDep,
      tenant: TenantContext = Depends(get_tenant_context),
      split_index: list[int] = Query(default=[]),
  ) -> RunSplitPointsResponse:
      """RAV-016: batched form of get_split_points above, for every
      rendered split of one run in a single round trip. Run-ownership
      check first (same collapsed-404 stance as get_splits/
      get_split_points) since a request is always scoped to exactly one
      run -- but, unlike get_split_points, does NOT additionally validate
      each requested split_index against split_results: the indices
      always come from run_detail's own already-validated
      rendered_splits, so a per-index 404 would only ever fire on an
      internal bug and would fail the whole batch over one bad index.
      Every requested split_index gets exactly one entry in `items`, in
      request order, with `points: []` for any index absent from the
      repository's result dict (pruned, never persisted -- degrades the
      same way the single-split endpoint's empty-items response already
      does, never an error).

      4-path-segment route (runs/{run_id}/splits/points), distinct in
      segment count from /runs/{run_id}/splits (3 segments) and
      /runs/{run_id}/splits/{split_index}/points (5 segments); shares a
      segment count with DBOPT-011's /runs/{run_id}/splits/count but
      differs in its literal 4th segment ("points" vs "count"), so
      neither collides regardless of registration order.
      """
      run = run_repository.get_run(tenant.tenant_id, run_id)
      if run is None:
          raise HTTPException(status_code=404, detail="run not found")
      if not split_index:
          return RunSplitPointsResponse(items=[])
      points_by_split = split_point_repository.get_points_for_splits(
          tenant.tenant_id, run_id, split_index
      )
      return RunSplitPointsResponse(
          items=[
              SplitPoints(
                  split_index=idx,
                  points=[_split_point_to_response(p) for p in points_by_split.get(idx, [])],
              )
              for idx in split_index
          ]
      )
  ```
- **No change to `GET /runs/{run_id}/splits/{split_index}/points`'s existing contract or behavior**
  — binding AC.
- RLS/tenant scoping: automatic via the existing `set_config('app.tenant_id', ...)` mechanism — no
  new isolation mechanism introduced.

### 3. `services/gateway-api`

- `src/app/routers/runs.py` — new pass-through route, mirroring `get_splits_summary`'s exact shape:
  ```python
  class RunSplitPointsResponse(BaseModel):
      items: list[SplitPoints]

  @router.get("/runs/{run_id}/splits/points", response_model=RunSplitPointsResponse)
  def get_splits_points(
      run_id: str,
      client: ValidationServiceClientDep,
      tenant: TenantContext = Depends(get_authenticated_tenant),
      split_index: list[int] = Query(default=[]),
  ) -> RunSplitPointsResponse:
      headers = build_downstream_headers(tenant)
      response = _call_downstream(
          client.get,
          f"/runs/{run_id}/splits/points",
          params={"split_index": split_index},
          headers=headers,
      )
      _raise_for_error(response)
      return RunSplitPointsResponse(**response.json())
  ```
  `SplitPoints` imported from `naive_first_common.contracts`, never redefined. No business logic
  reimplemented — pure forward.

### 4. `services/dashboard-web`

- `src/app/routers/runs.py`'s `run_detail`: replace the per-split points-fetch loop with one
  batched call:
  ```python
  split_points_charts: dict[int, PredictedVsActualChartData] = {}
  if rendered_splits:
      points_response, points_transport_status = _call_downstream(
          client.get,
          f"/runs/{run_id}/splits/points",
          headers=headers,
          params=[("split_index", split.split_index) for split in rendered_splits],
      )
      if points_transport_status is not None or points_response.status_code in (502, 504):
          # RAV-016: the single batched call's own failure mode -- there is
          # no per-split fallback left once this one call has failed, so
          # every rendered split's chart degrades to the existing
          # has_data=False placeholder. The rest of the page (run detail,
          # table, verdict/error charts) still renders -- this must never
          # propagate to _render_error_for_status for the whole page.
          for split in rendered_splits:
              split_points_charts[split.split_index] = build_predicted_vs_actual_chart([])
      else:
          points_by_split = (
              {item["split_index"]: item["points"] for item in points_response.json()["items"]}
              if points_response.status_code == 200
              else {}
          )
          for split in rendered_splits:
              raw_points = points_by_split.get(split.split_index, [])
              points = [SplitPointResponse(**p) for p in raw_points]
              split_points_charts[split.split_index] = build_predicted_vs_actual_chart(points)
  ```
  Exactly **one** downstream call for points, covering every rendered split, replacing the previous
  one-call-per-split loop. **No change** to the per-run splits fetch (`DBOPT-011`'s own call site,
  landed earlier in this same handler) or to the existing verdict/error chart logic — this ticket
  touches only the points-fetch path.

not reused/extended here since it serves a structurally different response shape — this is a new,
small, single-purpose block inline in `run_detail`, not a duplicate of anything existing.
