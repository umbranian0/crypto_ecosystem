# GW-009 — Downstream failure handling (timeouts, connection errors)

**Status: done**

## Analysis
Story: GW-009 (Must), depends on GW-008. Constraining docs: backlog AC (connection failure -> 502 generic body, no leaked internals; timeout -> 504, configurable; validation-service's own `201`-with-`status:"failed"` passed through unmodified, not reinterpreted as a gateway failure). Precedent for "distinguish a downstream *business* failure from a *transport* failure": validation-service's own VS-012 (`runs.py`'s `try`/`except Exception` around the protocol call, returning `201`+`status:"failed"` rather than `500`) — GW-009 must not collapse that same distinction back together at the gateway hop.

## Design
Pattern: none new — this wraps GW-008's existing `httpx` calls with explicit exception handling, same file (`src/app/routers/runs.py`) plus a small shared helper if the same try/except shape is needed at all three call sites (DRY within module: extract on second duplication, per implementation-plan.md section 9 — with three call sites here, extract from the start rather than waiting for a literal second occurrence, since the shape is already known to repeat three times before this ticket is even written).

File: `src/app/dependencies/http_client.py` (edit, GW-008's file) — add a `GATEWAY_API_DOWNSTREAM_TIMEOUT_SECONDS` env var (sane default, e.g. `30.0`) configuring the `httpx.Client`'s timeout. `src/app/routers/runs.py` (edit) — wrap each of the three proxy calls: `httpx.ConnectError`/`httpx.ConnectTimeout` (or the broader `httpx.ConnectError` family reached on a refused connection) -> `HTTPException(502, detail="downstream service unavailable")` (generic body — no hostname, no `str(exc)`, no stack trace in the response); `httpx.TimeoutException` (broader than just connect-timeout, covers a slow response too) -> `HTTPException(504, detail="downstream service timed out")`.

Explicit non-goal (binding, backlog AC3): validation-service's `POST /runs` returning `201` with body `{"id": ..., "status": "failed"}` is a *successful* HTTP response from `httpx`'s perspective (status 201, no exception raised) — this ticket's exception handlers never fire for it, and the router forwards that response body/status unmodified, exactly as GW-008 already does for a `200`/`201` "completed" response. No new branch inspects `status` and reinterprets it as a gateway-level error.

## Implementation acceptance criteria
- [x] A connection failure to `validation-service` (refused/unreachable) returns `502` from `gateway-api` with a generic body — response body/detail contains no hostname, port, or stack trace.
- [x] A request exceeding `GATEWAY_API_DOWNSTREAM_TIMEOUT_SECONDS` (env var, sane default) returns `504`.
- [x] `validation-service`'s `201`+`status:"failed"` response is returned by `gateway-api` byte-for-shape unmodified (still `201`, still `status:"failed"` in the body) — no code path reinterprets it as a `502`/`504`/`500`.
- [x] Applied uniformly to all three proxied endpoints (`POST /runs`, `GET /runs/{id}`, `GET /runs/{id}/splits`), via a shared helper rather than three independent copies of the same try/except (DRY).
