## Analysis

- Story: "As a Tech Lead scoping the rest of this backlog, I want a documented spike comparing at least
  two open-source/open-weights serving options... so that every downstream story has a concrete answer to
  'what actually runs this model and how fast' instead of assuming a specific stack."
- Acceptance criteria (backlog, verbatim, all four must be satisfied by the ADR):
  1. Compares at least (a) a small quantized open-weights model served locally via Ollama/llama.cpp as a
     new Compose service, and (b) a hosted open-weights inference API — approximate p50/p95 latency for a
     ~500-token summarization prompt, approximate memory/CPU footprint if local, fit against "local-first,
     cloud-portable, no GPU required."
  2. Recommendation justified against AI-003's need (async-friendly, `run.completed` subscriber) vs.
     AI-004's need (synchronous chat-turn, tighter budget). Note: sprint-48.md's own prose (lines 43-45)
     and the backlog's prioritization section both use "AI-003" for the synchronous chat feature and
     "AI-002" for narrative generation in places, but the backlog's own story headers are authoritative:
     AI-002 = report narrative (async, `run.completed`-triggered), AI-003 = Q&A chat (synchronous,
     dashboard-web). This ticket and the ADR use the story-header definitions (AI-002 = async narrative,
     AI-003 = sync chat), and flags the sprint doc's inverted shorthand explicitly rather than silently
     picking one without comment.
  3. Explicit answer to the `libs/ai_assist` question — binding for AI-002/003/004's future ticket
     scoping.
  4. Explicit list of safe vs. unsafe synchronous extension points, confirming `GET /runs/{id}` is unsafe.
- Constraining docs read: `docs/implementation-plan.md` section 9 (DRY "extract on second duplication"
  rule; no service imports another service's code); `docs/solution-design.md` section 1 (local-first,
  cloud-portable, multi-tenant, server-rendered frontend — no GPU dependency implied anywhere in the
  deployment story) and its architecture diagram (no model-serving component exists yet); `CLAUDE.md`
  (naive-first-by-default, no profitability claims — out of scope for *this* ticket's content but binding
  on AI-002/003/004 that follow); `services/reporting-service/README.md` (confirms the `run.completed`
  Redis Streams subscriber already exists and is the async extension point AI-002 would use — RS-006,
  done); `docs/adr/0009-multimodal-timestamp-alignment-design.md` and `docs/tickets/MR-003.md` as the
  precedent for a Tech-Lead-authored, no-dev-agent, decision-only ADR/ticket pair.
- This ticket does not touch `research/`, `libs/naive_first_engine`, or
  `docs/product/backlog-model-research.md` — confirmed out of scope per sprint-48.md and the requester's
  explicit constraint; verified no file under those paths is touched by this ticket.

## Design

- No design pattern from implementation-plan.md section 7 is introduced by this ticket — it is a serving-
  pattern comparison and recommendation document, not a code change. Forcing a pattern onto a spike would
  be exactly the "don't force one where the table doesn't call for it" case this platform's process
  warns against. The ADR does, however, note which pattern a *future* implementation ticket should use
  (Adapter, for the model-calling client — so `reporting-service` and, later, `dashboard-web` can swap
  local-Ollama vs. hosted-API backends without changing call sites) as a forward-looking design note, not
  something this ticket builds.
- File touched: `docs/adr/0011-ai-assist-model-serving.md` (new). No other file's content changes as part
  of the ADR itself; `docs/tickets/README.md` and `docs/sprints/sprint-48.md` are updated separately as
  this ticket's own Documentation acceptance criteria (below), same as every other ticket in this repo.
- **DRY check**: grepped `docs/adr/` for any existing AI/LLM/model-serving ADR before writing — none
  exists (0001-0010 cover economic-service scaffolding, trading-product decline, credential encryption,
  dataset semantics, dashboard charting, forecast-horizon units, and multimodal fusion/alignment/interface
  — no overlap with LLM serving). Nothing to extend; this is a net-new ADR, not a duplication risk. Also
  grepped `services/reporting-service/` and `services/dashboard-web/` for any existing `ollama`/`llm`/
  `openai`-shaped import or client — none exists, confirming no prior AI-serving code this ADR needs to
  reconcile with.
