# RSS-004 — Server-side split-count guardrail on `POST /runs`

**Status: done**

## Analysis
Story: RSS-004 (Must, `docs/product/backlog-run-submission-safety.md`), sprint sequencing per
`docs/sprints/sprint-25.md`: first, no dependency, ships regardless of what else lands this sprint.
Real incident that motivates this ticket (live-verified by the Tech Lead against `validation.runs`
before this ticket was written, not merely reported): tenant `e80a603ffd5e4e9e98bbfe2cba39b6e1`'s
`binance_price_btcusdt_1h` source has exactly 79,180 real ingested rows; two `POST /runs` calls against
it with `train_window=360, test_window=1540, step=2, purge_gap_hours=24` each generated 38,597 splits
(confirmed via `SELECT COUNT(*) FROM validation.split_results WHERE run_id = ...`) and ran
synchronously for 502.7s / 488.4s respectively before completing successfully. Both durations exceed
`gateway-api`'s `GATEWAY_API_DOWNSTREAM_TIMEOUT_SECONDS` (240s, set in Sprint 18) — had this request
gone through `gateway-api` instead of hitting `validation-service` directly, the caller would have
received a `504` while the run kept computing and completed anyway server-side (a "zombie success").
This ticket does not fix that timeout mismatch (out of scope, flagged in RSS-005's documentation
instead as a candidate follow-up) — it only stops the request from ever running that long.

Constraining acceptance criteria, read directly from the backlog entry, not summarized from memory:
- The computed split count used for the check must be **provably identical** to what
  `run_validation_protocol` would actually produce for the same input — call `generate_splits` itself
  (`naive_first_engine.splitting.generate_splits`), never an independently reimplemented formula.
- The check runs **after** `DatasetSource.load` succeeds (so the real row count/index is known) but
  **before** `run_repository.create_run` persists any row and before `run_validation_protocol` is
  invoked at all — no run record, no partial computation, no CPU spent on baselines/metrics/DM-test for
  a rejected request, regardless of `dataset_reference` mode (local path / inline / stored source).
- On rejection: `422` with the actual computed split count in the message, plus a concrete suggestion
  ("increase `step`", "narrow the date range", and/or "reduce `train_window`/`test_window`").
- The cap is a **named constant**, currently **500**, with a comment citing this backlog's OQ-1/OQ-2 and
  stating it is a conservative-by-design safety margin (not a performance-tuned ceiling) — see the real
  throughput evidence below.
- Sole enforcement point: no reliance on `dashboard-web`'s client-side estimate or a second `gateway-api`
  check; `gateway-api` already forwards `POST /runs`'s body/response (including `422`s) verbatim — no
  `gateway-api` change is in scope for this ticket.
- Test coverage: the literal incident input asserting `422`; a boundary case at exactly the cap
  (accepted) and cap+1 (rejected); a structural proof the check runs before `run_validation_protocol`
  for at least one input shape per `dataset_reference` mode.

**Real throughput evidence backing the 500 cap (from the incident above)**: 38,597 splits in
~495s average ≈ **78 splits/second** on this hardware. At that rate, 500 splits would take ≈6.4
seconds — an extremely conservative, effectively-instant cap relative to both this measured throughput
and `gateway-api`'s 240s downstream timeout. This is a single real data point on one dataset/config, not
a performance benchmark suite — the cap is deliberately far below what this one measurement would
justify as a tighter number, precisely to avoid false confidence from a single measurement. RSS-005
documents this evidence in `services/validation-service/README.md`; this ticket only needs to cite it in
the code comment, not restate it in full (DRY, implementation-plan.md section 9).

## Design
Pattern: none new — this is a validation/precondition check added to an existing FastAPI handler
(`create_run`), not a new pattern from implementation-plan.md section 7. File touched (single service,
per the "one ticket, one module" rule): `services/validation-service/src/app/routers/runs.py` only (no
`libs/naive_first_engine`, no `gateway-api`, no `dashboard-web` change in this ticket).

**DRY check (performed before writing this ticket)**: grepped `services/validation-service/src` for any
existing split-count computation or cap — none exists; `generate_splits` is already imported by
`libs/naive_first_engine.protocol.run_validation_protocol` only, not by `runs.py` — this ticket adds a
new, direct import of `generate_splits` into `runs.py` (the library's public function, not internal
detail) rather than duplicating its formula. `create_run`'s existing "create run row before try, so a
`run.id` always exists to attach a failure to" structure (VS-012) is a real constraint this ticket must
work around, not silently break: dataset-load failures must still surface as a `"failed"` run row +
`201` exactly as they do today (VS-012's Review-acceptance-tested contract) — that behavior is
unchanged by this ticket, only reordered relative to when the run row itself is created.

**Required control-flow restructuring in `create_run`** (this is the ticket's core design decision, not
left to the dev agent's own judgement, since it changes an existing, tested handler's control flow):

1. Load `series = dataset_source.load(request.dataset_reference)` **outside and before** any run row is
   created. If this raises, create the run row now (so VS-012's "a run that fails is a completed request,
   not a 500" contract is preserved) and immediately mark it `"failed"` with `failure_reason=str(exc)`,
   returning `201 {"id": ..., "status": "failed"}` — byte-identical outward behavior to today for this
   failure case, just with the run row created one step later than before.
2. **RSS-004 guardrail**: once `series` is loaded successfully, call
   `generate_splits(series.index, config.train_window, config.test_window, config.step, purge_gap=config.purge_gap)`
   directly and take `len(...)`. If this exceeds `MAX_SPLIT_COUNT` (module-level constant, `= 500`, with
   the OQ-1/OQ-2 rationale comment), raise `HTTPException(422, detail=...)` **before** any run row is
   created — no `run_repository.create_run` call happens on this path at all.
3. Otherwise, proceed exactly as today: `run_repository.create_run(...)`, then the existing `try` block
   (client-prediction load if present, `run_validation_protocol(series, run_config)` — reusing the
   already-loaded `series`, not loading it a second time — split persistence, `run.completed` event).
4. Extract the `run_repository.create_run(tenant_id=..., dataset_id=..., horizon=..., purge_gap_hours=...,
   split_config=...)` call (identical arguments in both the load-failure branch and the main flow) into
   one small local helper (e.g. `_persist_new_run(run_repository, tenant, request)`) so the same call
   isn't written twice in the diff — DRY within this module, per implementation-plan.md section 9's
   "extract on second duplication" rule, applied proactively here since the duplication is introduced by
   this same ticket.

Note: `run_validation_protocol` will call `generate_splits` again internally (its own Template Method,
unchanged) — this means `generate_splits` runs twice for an accepted request (once for the guardrail
check, once inside the protocol). This is deliberate and accepted: `generate_splits` itself is a cheap,
non-fitting, non-CPU-bound splitter (no baseline/metric/DM computation), so the duplicate call's cost is
negligible relative to the protocol it gates, and it is the only way to guarantee the check and the real
math can never disagree (per the backlog's own explicit preference for calling the real function).

## Implementation acceptance criteria
- [x] `MAX_SPLIT_COUNT = 500` defined as a module-level constant in `runs.py`, with a comment citing
      `docs/product/backlog-run-submission-safety.md`'s OQ-1/OQ-2 and stating the value is a
      conservative-by-design safety margin, not a performance-tuned ceiling.
- [x] `create_run` loads the dataset, then computes `len(generate_splits(series.index, config.train_window, config.test_window, config.step, purge_gap=config.purge_gap))` and compares against `MAX_SPLIT_COUNT` **before** any `run_repository.create_run` call and before `run_validation_protocol` is invoked.
- [x] On exceeding the cap: `422` with a message stating the actual computed split count and at least one concrete suggestion (increase `step` / narrow the date range / reduce `train_window`/`test_window`).
- [x] No run row is persisted for a rejected request (verified by a test asserting `run_repository`'s state, not just the HTTP response).
- [x] Dataset-load failures (pre-existing VS-012 behavior) are unchanged: still produce a `"failed"` run row and a `201` response, not a `500` and not a `422`.
- [x] `gateway-api`/`dashboard-web` are not touched by this ticket — `gateway-api`'s existing verbatim-forwarding of `POST /runs`'s response already carries this `422` through unmodified (confirmed by re-reading `gateway-api`'s `runs.py`/README, not assumed).
