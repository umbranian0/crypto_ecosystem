**Documented deviation from the ticket's literal shorthand signature**: the Design section writes `check_economic_eligibility(result: UpstreamValidationResult) -> EligibilityDecision`, but also requires (a) `compute_economic_simulation` is only ever called from *inside* the guard's own success branch, and (b) the router never imports/calls the computation function directly, and the guard structural check (option (a)) requires the computation function's name to never appear in `routers/simulations.py` at all. Since `compute_economic_simulation` needs `SimulationRequest.run_id` to build `EligibleSimulationResult`, and the router is the only caller that has the `SimulationRequest`, those three constraints can only all hold if the guard itself receives the request and computes the result internally. Implemented signature: `check_economic_eligibility(result: UpstreamValidationResult, request: SimulationRequest) -> EligibilityDecision`, with `EligibilityDecision.simulation: EligibleSimulationResult | None` populated only on the eligible branch. The router calls `check_economic_eligibility` and nothing else; on success it returns `decision.simulation` (never a second call to any computation function). This keeps the router's only import from `app.eligibility` to `check_economic_eligibility` (plus `EligibilityReason` for the refusal-message lookup table) — `compute_economic_simulation` is never imported by the router, verified by the guard structural check below.

**The guard's exact two-condition logic, as implemented** (`src/app/eligibility.py::check_economic_eligibility`):
1. `if result.source != "live": return EligibilityDecision(reason=EligibilityReason.NO_REAL_UPSTREAM_RESULT)`
2. `if not result.dm_verdict.startswith("significant_outperformance"): return EligibilityDecision(reason=EligibilityReason.UPSTREAM_RESULT_DID_NOT_BEAT_NAIVE)`
3. Otherwise: `simulation = compute_economic_simulation(result, request); return EligibilityDecision(reason=EligibilityReason.ELIGIBLE, simulation=simulation)`

Each fact is checked in its own `if`, independently, in that order, so the returned `reason` tells the caller which fact failed.

## Post-verification correction (repo-validation session)

A subsequent full-repo validation session cross-referenced this gate's `dm_verdict.startswith("significant_outperformance")` check against `naive_first_engine`'s actual `Verdict` type (`libs/naive_first_engine/src/naive_first_engine/dm_test.py`) and found the check was built on an invented vocabulary: the real type is `Literal["better", "worse", "no significant difference"]`, with Harvey's correction applied unconditionally inside the computation itself (never encoded as a string suffix). As originally written, the gate would have refused even a real, live, significant outperformance result once `VS-017` ships, since `"better"` doesn't start with `"significant_outperformance"` — fail-safe in effect, but built on a false assumption about the upstream contract, and the loose `startswith()` match (not an exact/enum comparison) would also have accepted a near-miss string that merely shared the invented prefix. Corrected: `UpstreamValidationResult.dm_verdict` is now typed `DmVerdict` (`contracts.py`, a `Literal` mirroring the real upstream type exactly), and the guard now checks `dm_verdict == "better"` (exact match, not prefix). `MockValidationResultClient`'s fixture verdict was updated from the invented `"no_real_upstream_verdict_exists"` to the real `"no significant difference"` value. All 50 tests re-verified passing after the fix. Full detail in `contracts.py`/`eligibility.py`/`upstream_client.py`'s own updated docstrings.
