## Analysis

Story: convert `split_results` (and no other table) to a TimescaleDB hypertable, so direct
time-series queries over metrics history perform well once that access pattern exists. Acceptance
criteria (verbatim): a migration/setup script converts the table with the partitioning column chosen
and documented; existing repository/query behavior is unaffected (hypertables remain queryable via
plain SQL).

**Non-negotiable care condition**: scope narrowly to the conversion itself, proven not to break
existing query behavior — do not build any new time-series query surface. No real caller for a
direct time-series query exists yet (`dashboard-web`'s `DASH-004` routes all reads through
`validation-service`'s existing `GET /runs/{id}/splits` API, not a direct SQL query) — this ticket
does not add one.

## Design

No Strategy/Repository/Adapter/Factory pattern from section 7 is being introduced or modified here —
this is a schema-level performance change underneath the existing `SplitResultRepository`
implementation. The Repository pattern already in place (`postgres_repository.py`) is exactly what
makes this safe: the hypertable conversion happens entirely inside Postgres/the migration, with zero
change to `PostgresSplitResultRepository`'s query code, `SplitResultRepository`'s interface, or any
router.

**File touched**: a new Alembic migration under `services/validation-service/migrations/versions/`
only (the `validation` schema is this service's own — `infra` owns no schema-touching code per
implementation-plan.md section 5). `infra/README.md` gets a documentation-only addition. This does
not touch `infra/docker-compose.yml` (no new service, no config change to the `postgres` container
itself — `timescaledb` extension is already loaded, per the `timescale/timescaledb:latest-pg16`
image already in use).

**DRY check**: read `services/validation-service/migrations/versions/` and `migrations/env.py` first.
The existing `0001_create_validation_schema.py`/`0002_add_row_level_security.py` migrations are the
pattern to extend (schema-qualified, guarded to `connection.dialect.name == "postgresql"` only, same
as the RLS migration's own guard, since `test_models.py::test_alembic_upgrade_head_creates_matching_schema`
runs `alembic upgrade head` against SQLite and must be unaffected). Do not write a second, parallel
"is this Postgres" check — reuse the exact guard idiom already in `0002_add_row_level_security.py`.

**Partitioning column choice**: `split_results.test_start` (a `DateTime`/timestamp column already
present per VS-002's schema, representing the split's own time-series position) is the correct
partitioning column — not `created_at` (doesn't exist on this table) and not `split_index` (an
integer ordinal, not a time value; TimescaleDB hypertables partition on a time or integer range
column, and `test_start` is the column that gives this table its actual time-series meaning, per
solution-design.md section 4's schema). Document this choice in the migration's own docstring per
the acceptance criteria's "documented" requirement.
