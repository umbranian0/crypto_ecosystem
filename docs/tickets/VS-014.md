# VS-014 — Redis Streams-backed run.completed publisher (validation-service)

## Analysis

`validation-service`'s current `EventPublisher` implementation (VS-009) is an in-process log
stand-in. This ticket replaces it with a Redis Streams-backed implementation behind the same
interface — independent of the ARCH/Postgres work entirely (backlog-infra.md decision 3).

## Design

- **Binding decision (grooming, #9)**: Redis Streams wire format — `event_name` is the literal
  stream key (`XADD run.completed ...`), payload flattened into individual string fields
  (`run_id`, `tenant_id`, `status`, `completed_at` as ISO-8601) — NOT a nested JSON blob.
- **Binding decision (grooming, #10)**: connection via single `REDIS_URL` env var, mirroring
  `DATABASE_URL`'s convention (already wired by INF-002).
- New `RedisStreamsEventPublisher` class implementing the same `EventPublisher` Protocol as
  VS-009's `InProcessLogEventPublisher` — same `publish(event_name: str, payload: dict)` (or
  equivalent) signature, internals call `redis.xadd(event_name, flattened_payload)`.
- `dependencies/repositories.py`'s `get_event_publisher` provider swaps to the Redis
  implementation when `REDIS_URL` is set, falling back to the in-process log publisher otherwise
  — no change to `POST /runs`'s call site.
- VS-009's interim implementation retained, not deleted.

## Outcome

Implemented as designed. Changes:

- `services/validation-service/src/app/events.py`: added `RedisStreamsEventPublisher`
  (constructor takes an injected redis client; `publish` calls
  `redis_client.xadd(event_name, fields)` with all payload values coerced to `str`,
  `None` → `""`). `InProcessLogEventPublisher` untouched.
- `services/validation-service/src/app/dependencies/repositories.py`: additive-only edit,
  confined to the event-publisher lines (`redis` import, `RedisStreamsEventPublisher` import,
  a `REDIS_URL`-keyed `functools.lru_cache`d `_get_redis_publisher`, and `get_event_publisher`
  now branching on `os.environ.get("REDIS_URL")`) — no other provider in this file touched, to
  stay out of VS-013's way in the same file.
- `services/validation-service/pyproject.toml`: added `redis>=5.0` runtime dependency;
  installed into the service `.venv`.
- `services/validation-service/tests/test_redis_events.py` (new): integration test against real
  Redis (`redis://localhost:6379/0`) exercising `publish` → `XRANGE`, plus two DI-seam tests for
  the `REDIS_URL` env-var swap/fallback.
- `services/validation-service/README.md`: documented the Redis Streams payload shape under a
  reorganized "Event publishing" section.

One pre-existing failure unrelated to this ticket surfaced during the full-suite run:
`tests/test_models.py::test_alembic_upgrade_head_creates_matching_schema` fails because VS-013's
concurrent edit to `migrations/env.py` now unconditionally runs `SET search_path TO validation`
(Postgres-only syntax) even when the target is sqlite, which is what that test uses. That file
and behavior are entirely VS-013's, outside this ticket's stated files/module — flagged for the
Tech Lead / VS-013's author rather than fixed here.
