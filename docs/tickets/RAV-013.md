# RAV-013 — Per-run verdict indicator on the runs list

**Status: todo.**

**Module**: `services/dashboard-web` only.
**Story**: `RAV-013`, `docs/product/backlog-run-analysis-visualization.md` Epic D.
**Depends on**: `RAV-012` (needs its per-run split data — must land first).
**Sprint**: 60 (`docs/sprints/sprint-60.md`). Sequenced **third**, immediately after RAV-012.

## Analysis

Each row on `runs_list.html` should show a compact indicator of that run's benchmark-comparison outcome
against Naive0 (better/worse/no significant difference/undefined), so a tenant scanning many runs sees
the pattern without opening each run. `RAV-012` makes `runs_list`'s handler receive, for every rendered
run, that run's `list[SplitResultResponse]` (`run_splits_summary[run.id]`, defaulting to `[]`).

**Binding constraint (CLAUDE.md positioning rule, restated here since this is the story most likely to
be misread as a trading signal if worded carelessly)**: the indicator reads only as a benchmark-
comparison outcome for *this run*, never "good/bad to trade," never a buy/sell/signal word. Four
status-neutral categories/colors only, never green/red.

## Design

**Design pattern**: none new — pure aggregation over already-fetched data, same as every other
`charting.py` function.

**Files touched** (scoped to `dashboard-web`):
- `services/dashboard-web/src/app/charting.py` — one new function + one new dataclass.
- `services/dashboard-web/src/app/routers/runs.py` — `runs_list` computes the indicator per run.
- `services/dashboard-web/src/app/templates/runs_list.html` — new column.
- `services/dashboard-web/src/app/static/style.css` — badge styling, reusing existing color variables
  only.

**DRY check note (mandatory, grepped `charting.py` before writing this design)**: `_verdict_category`
(line 438) maps one split's `dm_verdict`/`None`-handling to one of the four fixed categories —
**reuse this verbatim, do not reimplement it.** `_CATEGORY_CSS_SLUGS` (line 393) maps a category to its
CSS slug — **reuse this verbatim.** `UNDEFINED_VERDICT_CATEGORY` (line 381) — **reuse this constant.**
No existing function aggregates a run's *many* splits into *one* category (`build_headline_verdict_
summary` produces a sentence with a raw `better_count`, not a single category; `_run_beats_naive0`
produces a bool for "majority better," not one of four categories) — this ticket adds exactly that one
new aggregation function, specified below, and nothing else.

**Aggregation algorithm (specified here so the dev does not need to invent a tie-breaking rule)** —
add to `charting.py`:

```python
@dataclass(frozen=True)
class RunVerdictIndicator:
    """`has_data=False` for a zero-split run -- the caller must render a
    plain "no results yet" state, never a fabricated category (this
    ticket's binding AC)."""

    has_data: bool
    category: str | None = None
    css_slug: str | None = None
    label: str | None = None


def compute_run_verdict_indicator(splits: list[SplitResultResponse]) -> RunVerdictIndicator:
    """RAV-013: one aggregate category for an entire run's splits, reusing
    `_verdict_category` per split (no recomputation of the underlying DM
    verdict) and `_CATEGORY_CSS_SLUGS` for the color slug. Generalizes
    `_run_beats_naive0`'s existing "better > combined other" majority rule
    to also detect a majority-worse run, instead of only a boolean
    beat/not-beat:

    - zero splits -> has_data=False (caller renders "no results yet").
    - every split UNDEFINED_VERDICT_CATEGORY (no evaluable split) ->
      category=UNDEFINED_VERDICT_CATEGORY.
    - better_count > (worse_count + no_sig_count) -> category="better".
    - worse_count > (better_count + no_sig_count) -> category="worse".
    - otherwise (no strict majority either way) ->
      category="no significant difference".

    `label` is a compact benchmark-comparison sentence only -- "Beat Naive0
    on N/M splits" -- never a buy/sell/signal word (CLAUDE.md, binding on
    this story specifically).
    """
    if not splits:
        return RunVerdictIndicator(has_data=False)

    better = sum(1 for s in splits if _verdict_category(s) == "better")
    worse = sum(1 for s in splits if _verdict_category(s) == "worse")
    no_sig = sum(1 for s in splits if _verdict_category(s) == "no significant difference")
    total = len(splits)

    if better + worse + no_sig == 0:
        category = UNDEFINED_VERDICT_CATEGORY
    elif better > worse + no_sig:
        category = "better"
    elif worse > better + no_sig:
        category = "worse"
    else:
        category = "no significant difference"

    return RunVerdictIndicator(
        has_data=True,
        category=category,
        css_slug=_CATEGORY_CSS_SLUGS[category],
        label=f"Beat Naive0 on {better}/{total} splits",
    )
```

**Route wiring** (`runs_list`, `routers/runs.py`): build a per-run view model, e.g.
```python
run_verdict_indicators = {
    run.id: compute_run_verdict_indicator(run_splits_summary.get(run.id, []))
    for run in runs
}
```
and pass `run_verdict_indicators` into the template context alongside the existing `runs` list — do not
restructure `runs` itself (`RAV-014` adds a second, parallel per-run dict the same way; keep both
independent, simple lookups rather than merging into one combined structure, so each story's diff stays
additive and reviewable on its own).

**Rendering choice (Tech Lead's call per the AC, decided here)**: plain styled text/badge, **not** SVG —
a compact `<span class="verdict-badge verdict-badge-{{ css_slug }}">{{ label }}</span>` is simpler than
an SVG for a short text label and still satisfies ADR-0006 (no client-side JS, no new dependency; a
`<span>` is not a "chart" the ADR's server-rendered-SVG decision governs). `style.css` gains
`.verdict-badge-better { color: var(--color-status-completed-text); }`,
`.verdict-badge-worse { color: var(--color-status-failed-text); }`,
`.verdict-badge-no-sig-diff { color: var(--color-status-running-text); }`,
`.verdict-badge-undefined { color: var(--color-text-muted); }` — reusing the exact four CSS variables
`_dm_verdict_chart.html`'s own verdict-bar classes already use (never a new hex value, never green/red).
