## Analysis

**Correction to the sprint plan's own citation — read carefully before implementing.**
`docs/sprints/sprint-58.md` names `connectors/base.py:175` (inside `run_incremental`'s `except Exception:`
block) as "the failure write site." That citation is accurate as far as it goes, but incomplete: reading
`services/ingestion-service/src/app/routers/connectors.py` in full (this ticket's own independent
verification, per the Tech Lead's standing instruction not to take the sprint plan's citations on trust)
shows `run_incremental` (`connectors/base.py`) is **only reachable from each connector's own `__main__`
CLI block** — the standalone/offline script path (see `connectors/base.py`'s own docstring, "CSV (default,
unchanged)... this is the standalone/no-tenant fallback for local/offline dev"). The actual **live,
API-triggered crawl path** — the one `POST /connectors/{source}/run` (tenant-authenticated,
`routers/connectors.py`'s `run_connector`) and `dashboard-web`'s "Restart crawl" button actually invoke —
runs through a **second, structurally parallel** implementation: `_execute_crawl`
(`routers/connectors.py:344-404`), whose own `except Exception:` block at **lines 401-402** writes
`repository.record_crawl_run(tenant_id, connector.name, since, utcnow(), 0, "failed")` — the exact same
bare-`"failed"`-literal gap, at a second call site the sprint plan's citation did not name.
`routers/connectors.py`'s own module docstring confirms these are two independent implementations of the
same DB-write sequence, not one calling the other ("the only reason this isn't a plain call to
`run_incremental` is that `since` is already resolved by the caller").

**This matters concretely for this sprint's own Definition of Done**: the DoD requires QA to verify "a
real triggered connector failure (not just a unit-level mocked exception) produces a readable, non-secret
`failure_detail` end to end through `GET /connectors/{source}/status` and into the rendered crawl-status
panel." A real triggered failure — anything QA or a tenant does through the actual running service — only
ever goes through `_execute_crawl`, never `run_incremental`. **Fixing only `connectors/base.py:175` would
leave every real, API-triggered crawl failure showing `failure_detail: null` forever** — the CLI-only path
would be fixed, the only path any user or QA can actually exercise would not be. Both call sites are in
scope for this ticket; this is a correction discovered during this ticket's own Analysis, not a scope
expansion invented independently of the sprint's actual goal (which is exactly "surface why a crawl
failed" for crawls a tenant/operator can actually see) — flag this deviation to the Tech Lead's own report,
already noted here for Review to confirm.

Verified directly (do not re-derive):
- `services/ingestion-service/src/app/models.py:113-134` — `CrawlRun.status` is a bare `String`, no
  `failure_detail` column anywhere.
- `services/ingestion-service/migrations/versions/` holds `0001` through `0008`; **`0009` is the next
  unused number**. `0008_add_crawl_runs_progress_columns.py` is the exact additive-nullable-column
  precedent to mirror (unguarded-vs-Postgres-only pattern, plain `op.add_column`).
- `record_crawl_run`'s signature (`repositories/interfaces.py:121-138`, implemented in
  `postgres_repository.py:267-289`) takes six positional params, no `failure_detail` param today. Only two
  of its production call sites ever pass `status="failed"`: `connectors/base.py:175` and
  `routers/connectors.py:402`. Every other call site (`"queued"`/`"running"`/`"completed"`/`"cancelled"`/
  `"cancelling"`) is unaffected by adding a new, defaulted `failure_detail: str | None = None` parameter —
  confirmed by grep, no other call site needs to change.
- `services/ingestion-service/tests/fake_repository.py`'s `FakeConnectorRecordRepository.crawl_runs` is a
  list of 8-element tuples (`tenant_id, source, since_watermark, fetched_at, row_count, status,
  rows_fetched_so_far, updated_at`), consumed positionally by index in `tests/test_connectors_router.py`
  (`repository.crawl_runs[-1][5]` for `status`) and by full-tuple unpack in `tests/test_base.py` (three
  call sites: lines 289, 320, 351, e.g. `tenant_id, source, since_watermark, fetched_at, row_count, status,
  _rows_so_far, _updated_at = repository.crawl_runs[0]`). Appending `failure_detail` as a **ninth element,
  at the end**, keeps every existing index-based access (`[5]`, `[-1][5]`) valid; the three full-tuple
  unpacks in `test_base.py` **must be updated** in this ticket (add one more name to each unpack) or they
  will raise `ValueError: too many values to unpack` — this is expected, in-scope collateral, not a
  regression to avoid.
- `services/ingestion-service/src/app/routers/datasets.py:136-152`'s `connector_status` (not
  `connectors.py` — the sprint plan's own correction, independently re-confirmed here) builds
  `ConnectorStatusResponse` from `repository.latest_crawl_run(...)`'s `CrawlRunSummary`
  (`repositories/interfaces.py:208-220`) — both the Pydantic response model and the dataclass need a new
  `failure_detail: str | None = None` field.
- Connectors import `requests` (`binance_price.py`, `blockchain_onchain.py`) and `praw` (local-imported
  inside `reddit_sentiment.py`, an optional dependency) for their own network calls — `connectors/base.py`
  itself imports neither today.

**Constraint from the docs**: the AC's own explicit constraint — "no raw credential, connection string, or
stack trace is ever placed in `failure_detail`" — is the binding design driver below, not a nice-to-have.

## Design

**Pattern**: none of Strategy/Repository/Adapter/Factory/Observer applies to this specific change — the
Adapter pattern (implementation-plan.md section 7) already governs `IngestionSource`/connector shape and
is unchanged here; this ticket only widens one existing repository method's signature and adds one shared
helper function.

**Files touched** (scoped to `services/ingestion-service` only):

1. `services/ingestion-service/src/app/models.py` — add
   `failure_detail: Mapped[str | None] = mapped_column(String, nullable=True)` to `CrawlRun`, after
   `updated_at` (line 134).

2. `services/ingestion-service/migrations/versions/0009_add_crawl_runs_failure_detail.py` — new
   migration, `revision = '0009'`, `down_revision = '0008'`, Postgres-only-guarded `op.add_column`
   (identical shape to `0008`'s own `upgrade()`/`downgrade()`), one nullable `String` column.

3. `services/ingestion-service/connectors/base.py` — add one shared, safe-by-construction helper
   (module-level function, defined once, used by both write sites — this is the DRY point both this
   module and `routers/connectors.py` share since the latter already imports from this module):
   ```python
   def describe_crawl_failure(source: str, exc: Exception) -> str:
       """Redacted, readable `crawl_runs.failure_detail` value (ADMIN-003) derived
       from a caught fetch/write exception. Never includes `str(exc)` or any
       part of the exception's own message text -- some exception types (a DB
       driver's OperationalError, in particular) can embed a connection
       string/credential in their message, and this must never reach a
       tenant/operator-visible field (AC's own non-negotiable constraint,
       "no raw credential, connection string, or stack trace"). Safe by
       construction rather than by best-effort redaction: only the source
       name (already non-secret, already visible everywhere this value is
       shown) and the exception's class name are used -- never its args/message.
       """
       return f"{source}: {type(exc).__name__} while fetching or writing -- see service logs for detail"
   ```
   This is deliberately not per-connector-categorized (no `isinstance(exc, requests.exceptions.*)`/
   `prawcore`-specific branching) — simplicity over completeness (YAGNI, per this sprint's own
   keep-it-simple instruction): the exception class name alone (`ConnectionError`, `Timeout`,
   `HTTPError`, `RuntimeError`, etc.) is already a real, useful signal, and adding per-library exception
   taxonomy is unnecessary complexity for a "why did it fail" troubleshooting field, not a correctness
   requirement.

4. `services/ingestion-service/connectors/base.py`'s `run_incremental` — in the `except Exception as exc:`
   block currently at line 174-176 (change `except Exception:` to `except Exception as exc:` to bind the
   caught exception), call
   `repository.record_crawl_run(tenant_id, connector.name, since, result.fetched_at, 0, "failed",
   failure_detail=describe_crawl_failure(connector.name, exc))` immediately before the existing `raise`
   (unchanged — this ticket must not alter the existing re-raise behavior, per the AC's own "existing
   raise behavior is unaffected" requirement).

5. `services/ingestion-service/src/app/routers/connectors.py`'s `_execute_crawl` — in the
   `except Exception:` block at lines 401-402 (change to `except Exception as exc:`), call
   `repository.record_crawl_run(tenant_id, connector.name, since, utcnow(), 0, "failed",
   failure_detail=describe_crawl_failure(connector.name, exc))`. Import `describe_crawl_failure` from
   `connectors.base` (this file already imports `latest_watermark_from_db, utcnow` from the same module —
   add to that existing import line, not a new import statement).

6. `services/ingestion-service/src/app/repositories/interfaces.py` — `record_crawl_run`'s signature gains
   `failure_detail: str | None = None` as a new, defaulted, trailing parameter (every other existing call
   site is unaffected by the default). `CrawlRunSummary` gains `failure_detail: str | None = None`,
   trailing, same reasoning.

7. `services/ingestion-service/src/app/repositories/postgres_repository.py` — `record_crawl_run` accepts
   and persists `failure_detail` onto the new `CrawlRun.failure_detail` column; `latest_crawl_run` includes
   `failure_detail=row.failure_detail` when building `CrawlRunSummary`.

8. `services/ingestion-service/src/app/routers/datasets.py` — `ConnectorStatusResponse` gains
   `failure_detail: str | None = None`; `connector_status` passes `failure_detail=summary.failure_detail`
   through. **Never a placeholder string for a non-`"failed"` status** — this falls out by construction
   (only the two write sites above ever pass a non-`None` value, and only when `status="failed"`), but
   state it explicitly since it's an AC line item.

9. `services/ingestion-service/tests/fake_repository.py` — `FakeConnectorRecordRepository.crawl_runs`
   tuples grow one trailing element (`failure_detail`, appended last, default `None` for every existing
   call site that doesn't pass it); `record_crawl_run` gains the matching `failure_detail: str | None =
   None` parameter; `latest_crawl_run` includes it in the returned `CrawlRunSummary`.

**DRY check note** (grepped before writing this ticket): `describe_crawl_failure` is the one new function
this ticket introduces, defined once in `connectors/base.py` (already imported by `routers/connectors.py`
for two other names) and called from both of this ticket's two write sites — not duplicated into
`routers/connectors.py` as a second copy. No existing "safe exception message" helper exists anywhere in
this service to reuse instead.
