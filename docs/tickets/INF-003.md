# INF-003 — validation-service wired into Docker Compose

Status: **done**
Backlog: docs/product/backlog-infra.md, INF-003 [Must]
Sprint: docs/sprints/sprint-06.md, Phase 2
Depends on: INF-001, INF-002

## Analysis

Neither service has a `Dockerfile` yet. This ticket is packaging/wiring only — no change to
`services/validation-service/src/`, per the backlog's explicit boundary (decision 1 note: no
story here touches service application code).

## Design

- `services/validation-service/Dockerfile`: builds the service per its existing `uv`-managed
  `pyproject.toml`, starts the FastAPI app (`uvicorn app.main:app ...`).
- `infra/docker-compose.yml` gains a `validation-service` entry: `build: ../services/validation-service`,
  env vars for `DATABASE_URL` (internal Compose hostname `postgres:5432`, targeting the
  `validation` schema — see VS-013 for the schema-targeting Alembic change; this ticket just
  passes the URL through) and `REDIS_URL` (`redis:6379`) sourced from the same `.env`/`.env.example`
  INF-001/INF-002 introduced.
- Must still run standalone against SQLite/no-Redis for unit tests — this ticket does not remove
  that capability, only adds the Compose path as an additional way to run it.
- No change to any file under `services/validation-service/src/`.

## Outcome

Implemented as designed. `services/validation-service/Dockerfile` builds the image; since
`pyproject.toml`'s `naive_first_engine`/`naive_first_common` path dependencies live outside the
service directory (`../../libs/...`), the compose entry uses a named `additional_contexts: {libs:
../libs}` build context (Compose long-form `build:`, still `context: ../services/validation-service`
as the primary context) so the Dockerfile can `COPY --from=libs ...` them in, mirroring the
monorepo layout under `/repo` inside the image.

`infra/docker-compose.yml` gained a `validation-service` entry: `depends_on: postgres: condition:
service_healthy` (no `redis` dependency — VS-014 hasn't landed), `DATABASE_URL`/`REDIS_URL` env
vars sourced from new `VALIDATION_SERVICE_DATABASE_URL`/`VALIDATION_SERVICE_REDIS_URL` vars (added
additively to `infra/.env.example`, defaulting to the internal Compose hostnames `postgres:5432`/
`redis:6379`, not `localhost`). Host port `8001` by default (`VALIDATION_SERVICE_PORT`), mapped to
the container's `8000`.

**Manually verified** (implementer's own run — not a substitute for the Tech Lead's personal
verification above):
- `docker compose -f infra/docker-compose.yml up -d --build validation-service` — built and started
  successfully; `docker compose ps` showed `naive-first-validation-service` `Up`, alongside
  `naive-first-postgres` (healthy) and `naive-first-redis` (healthy).
- `curl http://localhost:8001/health` → `200 {"status":"ok"}`.
- `curl http://localhost:8001/openapi.json` and `/docs` → both `200`.
- `POST /runs` (with `X-Tenant-Id: smoke-tenant` header and a minimal 30-point inline dataset) →
  `201 {"id":"c6036407ecb34e4cb3ebb3916d799c89","status":"completed"}`.
- `GET /runs/c6036407ecb34e4cb3ebb3916d799c89` (same tenant header) → `200`, full run row,
  `"status":"completed"`.
- `GET /runs/c6036407ecb34e4cb3ebb3916d799c89/splits` → `200`, 4 split rows with metrics/DM-test
  fields populated — confirms the pre-VS-013 SQLite-backed behavior works unchanged inside the
  container.

Zero files under `services/validation-service/src/` were edited by this ticket (confirmed via
`git diff --stat -- services/validation-service/src/` before/after — the only diffs there are
pre-existing, unrelated in-flight changes from other work in this shared working tree, not
anything touched by this implementation).

Containers left running after this work: `naive-first-postgres`, `naive-first-redis`,
`naive-first-validation-service`.
