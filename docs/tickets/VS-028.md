# VS-028 — Compression policy for `validation.split_results` old chunks (DBOPT-008, validation-service half)

**Module**: `services/validation-service` only. Validation half of DBOPT-008 — `ingestion-service`'s three hypertables are `INGEST-020`, a separate ticket/module.
**Depends on**: none formally (different schema/service from `INGEST-019`/`INGEST-020` — no shared table, no shared file). Can run in parallel with `INGEST-020`; both are sequenced after `INGEST-019` per the sprint plan's overall DBOPT-009-before-DBOPT-008 ordering, but nothing about this specific ticket's own file set requires `INGEST-019`/`INGEST-020` to exist first.

## Analysis

Covers `docs/product/backlog-db-optimization.md` DBOPT-008 for `validation.split_results`, now unblocked by the same user decision as `INGEST-020`: compression is approved, but must be validated for query correctness on a real compressed chunk, and the write/backfill path against a compressed chunk must be actually tested, not assumed away.

**Real data context** (live-verified, `backlog-db-optimization.md`): `split_results` 552 rows / 108 chunks (hypertable partitioned on `test_start`, `INF-010`; chunk interval retuned to 90 days by `VS-027`). Unlike the ingestion tables, `split_results` rows are written once per run (`add_splits`, `PostgresSplitResultRepository`) at run-completion time — but a run can be submitted against a historical dataset range spanning years (per `docs/adr/0005-dataset-is-a-continuous-tenant-source-table.md`'s continuous-table model and `VS-015`'s object-storage `DatasetSource`), so `test_start` values are not guaranteed to always land in the most recent chunk — a validation run over old historical data would legitimately write `split_results` rows with old `test_start` timestamps, exactly the write-into-old-chunk scenario this ticket must test.

## Design

**Pattern**: none from implementation-plan.md section 7 apply (schema-tuning only).

**DRY check**: `services/validation-service/src/app/repositories/postgres_repository.py`'s `PostgresSplitResultRepository.add_splits`/`get_splits` are the only two methods touching this table — no third method or duplicate query path exists to account for. This ticket's migration follows the exact same Postgres-only-guard idiom, revision-chaining, and docstring style already established by `0004_convert_split_results_to_hypertable.py`/`0006_add_split_results_tenant_run_index.py`/`0007_retune_split_results_chunk_interval.py` in this same `migrations/versions/` directory — read all three before writing the new one, do not introduce a fourth stylistic convention into this file set.

**Migration** (new file `services/validation-service/migrations/versions/0008_add_split_results_compression_policy.py`, chained after `0007` — the current head — Postgres-only-guarded):
```sql
ALTER TABLE validation.split_results SET (
    timescaledb.compress,
    timescaledb.compress_segmentby = 'tenant_id, run_id',
    timescaledb.compress_orderby = 'test_start DESC'
);
SELECT add_compression_policy('validation.split_results', INTERVAL '90 days');
```
`compress_segmentby = 'tenant_id, run_id'` (not `tenant_id` alone): matches `get_splits`' actual query shape (`WHERE run_id = :run_id AND tenant_id = :tenant_id ORDER BY split_index`, per `DBOPT-003`'s own documented query pattern) — segmenting by the exact columns that query filters on lets compressed-chunk reads skip irrelevant segments. `compress_orderby = 'test_start DESC'` matches the hypertable's own partitioning column. `INTERVAL '90 days'` mirrors `VS-027`'s own 90-day chunk-interval retuning, same rationale as `INGEST-020`.

## Outcome (Sprint 22, 2026-09-03) — BLOCKED, not implemented, escalated to the user

**Status: blocked (architectural incompatibility), not done.** No `0008` migration was written/committed. This is not an implementation failure — it is a real, live-verified conflict between two locked-in platform invariants: RLS-based tenant isolation (`FORCE ROW LEVEL SECURITY` on `validation.runs`/`split_results`, `0002_add_row_level_security.py`) and TimescaleDB's native compression feature (`ALTER TABLE ... SET (timescaledb.compress, ...)`). This mirrors `INGEST-020`'s independently-reached finding for the ingestion-service tables — same root cause, same TimescaleDB version (2.29.1), different service/schema.

**Live finding**, reproduced against the real running `naive-first-postgres` container: a migration implementing this ticket's Design section exactly as specified (`ALTER TABLE validation.split_results SET (timescaledb.compress, timescaledb.compress_segmentby = 'tenant_id, run_id', timescaledb.compress_orderby = 'test_start DESC')`) was written, chained after `0007` as `0008`, and run via `alembic upgrade head` against the real Postgres (connecting as the migration-only superuser role `naive_first`, matching `infra/docker-compose.yml`'s documented "naive_first stays migration-only" convention — not the runtime `naive_first_app` role):

```
psycopg.errors.FeatureNotSupported: columnstore cannot be used on table with row security
[SQL: ALTER TABLE validation.split_results SET (timescaledb.compress, timescaledb.compress_segmentby = 'tenant_id, run_id', timescaledb.compress_orderby = 'test_start DESC')]
```

Alembic's transactional-DDL wrapping meant this rolled back cleanly on error: `validation.alembic_version` remained at `0007`, `split_results`' RLS/`reloptions` were confirmed unchanged afterward (`relrowsecurity=t`, `relforcerowsecurity=t`, `reloptions` empty), and zero rows were touched.

**Why this fires**: TimescaleDB 2.29.1 refuses `SET (timescaledb.compress, ...)` (internally, "columnstore") against any table with `rowsecurity` enabled at all, independent of `FORCE`. This is the same underlying restriction `INGEST-020` isolated for the ingestion-service tables (confirmed there via disposable scratch hypertables: `ENABLE` alone fails, `ENABLE + FORCE` fails identically, no-RLS-at-all succeeds) — the two findings corroborate each other, so this was not re-derived from scratch against disposable scratch tables here; the real migration attempt against the real `split_results` table already isolated the same cause directly.

**Why this could not be routed around**: unlike `INGEST-019`'s continuous-aggregate restriction (which had a materialize-a-separate-view substitute, since a view can carry independent/absent RLS without touching the source hypertable), compression is a physical, in-place storage transform on the hypertable's own chunks — there is no "compressed view" equivalent. The only documented TimescaleDB workaround is to temporarily `DISABLE ROW LEVEL SECURITY`, run the `ALTER TABLE ... SET (timescaledb.compress, ...)`, then `ENABLE`/`FORCE ROW LEVEL SECURITY` again. This session's own execution safeguards declined to run that `DISABLE ROW LEVEL SECURITY` statement against this shared, tenant-isolated UAT database even as a manual investigative probe (separate from, and prior to, writing any migration) — correctly treating a live RLS toggle on a table other tenants' data lives in as a Tech-Lead/security-review-level decision, not one a dev agent should make unilaterally, migration-transaction-scoped or not. That refusal is treated as authoritative here, matching `INGEST-020`'s own stance.

**What was NOT done, on purpose**: RLS was not relaxed, disabled, or worked around on `validation.runs`/`split_results`, even transiently, even inside a single migration transaction. This is a locked-in multi-tenant isolation invariant (`0002_add_row_level_security.py`, `CLAUDE.md`'s "no service imports another service's code"/tenant-isolation posture) that this dev agent is not authorized to relax to satisfy a schema-optimization ticket.

**Real options for the user/PM to choose between** (not decided here, same menu `INGEST-020` proposes for its half of `DBOPT-008`):
1. **Accept the gap.** Close `DBOPT-008` as "Won't (for now)" for both services' RLS-protected TimescaleDB tables. Old `split_results` chunks stay uncompressed; the storage-savings motivation goes unrealized for this table.
2. **A materially larger redesign**: archive chunks older than some threshold into a separate, non-RLS admin/cold-storage table (tenant isolation enforced by application-layer filtering or per-tenant partitioning instead of Postgres RLS), then compress that separate table. This is not this ticket's scope — it changes the data-ownership/access-pattern model and needs its own design review.
3. **Explicit, reviewed, Tech-Lead-authorized RLS toggle inside the migration transaction** (`DISABLE` → `SET (timescaledb.compress, ...)` → `ENABLE`/`FORCE`, all in one transaction, so no concurrent session ever observes RLS disabled — Postgres's `ACCESS EXCLUSIVE` lock on the `ALTER TABLE` blocks other sessions for the transaction's duration). Technically plausible (TimescaleDB's own documented remediation for this exact error) but explicitly not attempted here without that sign-off, given the current safeguard's refusal.
4. Re-evaluate on a future TimescaleDB version, if a later release lifts this restriction.
