The only internet-facing service. See [../../docs/solution-design.md](../../docs/solution-design.md) section 3.6 and [../../docs/implementation-plan.md](../../docs/implementation-plan.md) sections 2, 4.

**Owns**: the `identity` Postgres schema (tenants, users, api_keys), JWT/API-key auth, tenant-context resolution, request routing to internal services over HTTP.

**Does not own**: any business logic — this service orchestrates calls to `ingestion-service`, `validation-service`, `reporting-service`; it does not duplicate their logic (DRY across service boundaries means routing here, not reimplementation).

**Design notes**:
- Tenant context is resolved once per request and injected via FastAPI `Depends()` into every downstream call — this is the Dependency Injection point referenced in implementation-plan.md section 7.
- No direct DB access to other services' schemas, ever — only their HTTP APIs.
- **Downstream header forwarding (GW-007)**: `src/app/dependencies/routing.py` provides `build_downstream_headers(tenant: TenantContext) -> dict[str, str]`, returning `{"X-Tenant-Id": tenant.tenant_id}` sourced *only* from GW-006's already-authenticated `TenantContext` — it never reads the inbound request or any of the inbound request's own headers, so a client-supplied `X-Tenant-Id` on the inbound request can never reach a downstream service. This is an **interim forwarding mechanism that relies on network topology** (internal services such as `validation-service` are unreachable except through `gateway-api`), not a cryptographically verified internal channel — a service on the internal network could still forge an `X-Tenant-Id` header directly. Hardening that boundary (e.g. signed/verified internal headers) is out of scope here and belongs to `libs/common`'s deferred **LC-009** and/or a future **GW-015**, not this ticket. GW-008 calls `build_downstream_headers` when it makes its actual HTTP call to `validation-service`; this ticket only defines the seam.
- **Repository interfaces (GW-003)**: `src/app/repositories/interfaces.py` declares `TenantRepository`, `UserRepository`, `ApiKeyRepository` as `typing.Protocol` (no ABC — none needs a shared default method), and each returns/accepts plain `@dataclass(frozen=True)` record types (`TenantRecord`, `UserRecord`, `ApiKeyRecord`, field-for-field mirrors of `app.models.Tenant`/`User`/`ApiKey`) rather than the SQLAlchemy models directly — that keeps `interfaces.py` free of any `sqlalchemy` import, mechanically checked by `tests/test_repository_interfaces.py`. Method sets:
  - `TenantRepository`: `create_tenant(name) -> TenantRecord`, `get_tenant(tenant_id) -> TenantRecord | None`, `tenant_exists() -> bool` (SETUP-001).
  - `UserRepository`: `create_user(tenant_id, email, role) -> UserRecord`, `get_user_by_email(email) -> UserRecord | None`.
  - `ApiKeyRepository`: `create_key(tenant_id, key_hash) -> ApiKeyRecord`, `get_by_hash(key_hash) -> ApiKeyRecord | None`, `revoke_key(tenant_id, key_id) -> None`.
  - Every method takes `tenant_id` first after `self` except four documented exceptions: `create_tenant` (a tenant has no id yet at creation), `get_by_hash` (GW-006's auth check must resolve a raw key to its tenant, not already know it), `get_user_by_email` (login-time lookup doesn't yet know the tenant either), `tenant_exists` (SETUP-001, takes no arguments at all -- a fresh-install check is inherently not about any one tenant).
  - DI seam: `src/app/dependencies/repositories.py` declares `get_tenant_repository`/`get_user_repository`/`get_api_key_repository` providers typed against these interfaces, plus `TenantRepositoryDep`/`UserRepositoryDep`/`ApiKeyRepositoryDep` `Annotated[..., Depends(...)]` aliases for route handlers. Concrete wiring to GW-004's SQLite implementation (see "Storage backend" below) is live as of GW-004.

**Storage backend (GW-004, Postgres by GW-012)**: `src/app/dependencies/repositories.py`'s three providers pick the implementation by inspecting `DATABASE_URL`: a `postgresql://`/`postgresql+psycopg://` value routes to `app.repositories.postgres_repository`'s classes (below); anything else (unset, or any other scheme) keeps the original `src/app/repositories/sqlite_repository.py` classes (`SQLiteTenantRepository`/`SQLiteUserRepository`/`SQLiteApiKeyRepository`, path from `GATEWAY_API_DB_PATH`, defaulting to `./gateway.db`), which remain the default for local dev and this service's own unit tests (`tests/test_sqlite_repository.py`, unmodified by GW-012). No router/business-logic code imports either module directly -- both stay behind the `TenantRepository`/`UserRepository`/`ApiKeyRepository` interfaces (GW-003), a DI-only swap per backlog decision 2. `revoke_key` sets the `revoked_at` column rather than deleting the row on both backends -- `get_by_hash` continues to resolve a revoked key's record (GW-006/GW-010 decide what to *do* with it).

**Postgres backend + row-level security (GW-012)**: `src/app/repositories/postgres_repository.py` provides `PostgresTenantRepository`/`PostgresUserRepository`/`PostgresApiKeyRepository`, targeting the `identity` Postgres schema, built via `naive_first_common.db.build_engine` + ARCH-002's memoized-by-URL `_get_engine`, using the `psycopg` v3 driver (`postgresql+psycopg://` -- `_postgres_engine_url` in `dependencies/repositories.py` rewrites a bare `postgresql://` `DATABASE_URL` to force this driver, and pins the connection's `search_path` to `identity` via a `-c search_path=identity` libpq option).
- **Migrations** (`migrations/env.py`, `migrations/versions/0001_create_identity_schema.py` + `0002_add_identity_rls.py`): against a `postgresql` URL, both online and offline modes set `search_path` to `identity` (so `tenants`/`users`/`api_keys` land there, not `public`) *and* pass `version_table_schema="identity"` to `context.configure(...)`, so Alembic's own `alembic_version` bookkeeping table also lives in `identity` rather than the shared `public` schema. The latter is a **hard requirement**, not polish: INF-005 empirically reproduced a silent migration collision when both `gateway-api` and `validation-service` wrote to the same default `public.alembic_version` table against the same real Postgres database -- whichever ran second found it already stamped and silently no-opped its own `upgrade()`. Both are guarded to the `postgresql` dialect only, since this service's own `tests/test_models.py::test_alembic_upgrade_head_creates_matching_schema` runs `alembic upgrade head` against a real sqlite file, which has no schema/search_path concept.
- **Row-level security** (`0002_add_identity_rls.py`): `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` (the latter needed because the app connects as the same role that owns these tables -- Postgres exempts an owner from its own RLS policies by default) plus a `tenant_isolation` policy on all three tables, scoping to `current_setting('app.tenant_id')`. `get_by_hash`/`get_user_by_email` (GW-003's documented tenant-agnostic exceptions) get a permissive additional USING clause on `users`/`api_keys` that also allows the read when no `app.tenant_id` is set for the current transaction, normalized via `NULLIF(current_setting('app.tenant_id', true), '')` (a plain `current_setting(..., true) IS NULL` check is insufficient -- Postgres reverts a custom GUC to `''`, not `NULL`, once referenced at all on a pooled connection, found empirically while writing this ticket's own tests). `tenants` carries no such fallback -- `create_tenant` scopes to its own newly-generated id before inserting, satisfying the policy without one.
- **The `SET LOCAL` mechanism** (binding decision #8, "the subtlest cross-story interaction" of its sprint): `postgres_repository.py`'s `_set_tenant_scope` runs `SELECT set_config('app.tenant_id', :tenant_id, true)` (the parameterizable equivalent of `SET LOCAL app.tenant_id = ...` -- Postgres's `SET`/`SET LOCAL` grammar doesn't accept bind parameters) as the **first statement of every method's own `Session(engine)` block**, before any real query, for every method that knows its tenant. This is per-transaction, not per-connection or once-at-startup: a SQLAlchemy `Session` doesn't check out a pooled connection until its first `execute()`, so the scoping statement and the connection checkout happen together, and the transaction's end is also when the connection is released back to the pool -- `SET LOCAL`/`set_config(..., true)` reverts automatically at that point, so a connection recycled into a different tenant's request never carries the previous tenant's scope forward. Per-tenant Postgres roles were explicitly rejected in grooming in favor of this single-role-plus-session-variable approach. See `tests/test_postgres_repository.py::test_set_local_scope_does_not_leak_across_pooled_connection_reuse` for the non-tautological proof (forces physical-connection reuse via a single-connection pool, and checks for leakage on a transaction that deliberately never sets the scope itself).
- **Resolved infra caveat (was open at GW-012's original writing, fixed by INF-014)**: this service's `DATABASE_URL` originally pointed at `naive_first`, a Postgres **superuser** provisioned by the official image's `POSTGRES_USER` mechanism -- and Postgres superusers bypass RLS unconditionally, `FORCE ROW LEVEL SECURITY` included, so RLS was proven-in-test but not actually enforced against the real running app. INF-014 (`infra/postgres-init/02-create-app-role.sh`) provisions a non-superuser, non-`BYPASSRLS`, no-`CREATEDB`/`CREATEROLE` role (`naive_first_app`) scoped to `SELECT`/`INSERT`/`UPDATE`/`DELETE` on `identity.*`/`validation.*` only, and `infra/docker-compose.yml`'s `DATABASE_URL` for this service now points at that role, not `naive_first` (which is repurposed migration-only). RLS enforcement is therefore live end-to-end against the current infra credentials, not just proven in `tests/test_postgres_repository.py`'s ephemeral test-only role.
- **`identity.api_keys.key_hash` unique index (GW-025/DBOPT-001)**: `migrations/versions/0003_add_api_keys_key_hash_index.py` adds `CREATE UNIQUE INDEX ix_api_keys_key_hash ON identity.api_keys (key_hash)`, Postgres-only-guarded the same way as `0002_add_identity_rls.py`. This serves `PostgresApiKeyRepository.get_by_hash` (`src/app/repositories/postgres_repository.py`), the query `app.dependencies.auth.get_authenticated_tenant` runs on every single authenticated request -- the auth hot path -- which the DBA's live `EXPLAIN (ANALYZE, BUFFERS)` (`docs/product/backlog-db-optimization.md` DBOPT-001) found doing a full `Seq Scan` with no supporting index. `UNIQUE` (not a plain btree) matches `get_by_hash`'s existing `scalar_one_or_none()` assumption of at most one row per hash. Zero application-code change -- `get_by_hash`'s query text is unchanged, only its plan is now cheaper as the table grows. Note: on the current ~200-row table the planner still chooses `Seq Scan` over the new index by cost estimate (small-table behavior, not a defect) -- proven usable via `SET enable_seqscan = off`; see `docs/tickets/GW-025.md`'s Outcome section for the full before/after `EXPLAIN` capture.
- **`identity.users.email` unique index (GW-026/DBOPT-005)**: `migrations/versions/0004_add_users_email_index.py` adds `CREATE UNIQUE INDEX ix_users_email ON identity.users (email)`, Postgres-only-guarded the same way as `0003_add_api_keys_key_hash_index.py`. This serves `PostgresUserRepository.get_user_by_email` (`src/app/repositories/postgres_repository.py`), the login-time resolution path -- another of GW-003's documented tenant-agnostic exceptions, alongside `get_by_hash` -- which the DBA's live `EXPLAIN (ANALYZE, BUFFERS)` (`docs/product/backlog-db-optimization.md` DBOPT-005) found doing a full `Seq Scan` with no supporting index. `UNIQUE` (not a plain btree) reflects a binding user decision that `email` is meant to be globally unique across tenants, not merely per-tenant, matching `get_user_by_email`'s existing `scalar_one_or_none()` assumption of at most one row per email. Zero application-code change -- `get_user_by_email`'s query text is unchanged, only its plan is now cheaper and the uniqueness guarantee is now enforced at the DB level, not merely assumed by the query shape. Live-verified: a second `INSERT` with an already-present email is rejected by the database itself (`psycopg.errors.UniqueViolation`/`sqlalchemy.exc.IntegrityError`), not merely by the schema's presence; see `docs/tickets/GW-026.md`'s Outcome section for the full before/after proof.

**Provisioning (GW-005)**: `scripts/provision_tenant.py` is an **operator/test-fixture tool, not a public sign-up flow** -- there is no real pilot client yet (backlog decision 1), so this script exists to create the tenant + API-key fixture data that GW-006's auth mechanism (once it lands) will check requests against. It is a standalone CLI script, deliberately not an operator endpoint: an endpoint would need its own auth mechanism before GW-006 exists, a chicken-and-egg problem a local script avoids (whoever can run a script on the host already has operator-level access).

Run it from `services/gateway-api`:
```
.venv\Scripts\python.exe scripts\provision_tenant.py --name "Acme Corp"
```
It creates one `tenants` row (`TenantRepository.create_tenant`) and one `api_keys` row (`ApiKeyRepository.create_key`) for it, using the same DI-wired repositories (`app.dependencies.repositories`) as the rest of the service (GW-004's SQLite backend, `GATEWAY_API_DB_PATH`). The raw API key is generated with `secrets.token_urlsafe(32)` and hashed with `hashlib.sha256(...).hexdigest()` before it is persisted (sprint-05's binding, non-negotiable hashing choice -- never bcrypt/argon2/scrypt) -- only the hash is ever stored, in `api_keys.key_hash`. **The raw key is printed to stdout exactly once, at creation, and is never recoverable afterward** -- it is not logged, not written to any file, and does not appear anywhere else in the script's output, including error paths.

**Revocation (GW-010)**: `scripts/revoke_api_key.py` is an **operator/test-fixture tool, not a tenant-self-service mechanism** -- there is no HTTP path to reach this functionality at all (no new FastAPI router/endpoint/route is added anywhere by this ticket), the same "operator-only" framing `scripts/provision_tenant.py` (GW-005) established. It exists so a leaked or rotated key can be revoked immediately, without deleting/recreating the tenant.

**Structured logging / correlation id (OPS-006)**: `src/app/main.py` calls
`naive_first_common.configure_structured_logging()` at import time and
registers `naive_first_common.CorrelationIdMiddleware` -- every log line this
service emits is a JSON object (`timestamp`/`level`/`logger`/`message`/
`correlation_id`); the middleware reads an inbound `X-Correlation-Id` header
if present, otherwise generates `uuid4().hex`, attaches it to every log line
emitted during that request (via a context var, not passed explicitly
through every function call), and sets it on the response too.
`app.dependencies.routing.build_downstream_headers` forwards the same id to
`validation-service` as a header, so one logical request's logs can be
joined across both services by that one id. This does not stand up a
log-aggregation backend (still declined, see `docs/product/backlog-operability.md`
OPS-007) -- it ends at "logs are structured and correlatable."

Run it from `services/gateway-api`:
```
.venv\Scripts\python.exe scripts\revoke_api_key.py --key "<the raw API key>"
```
The operator presents the raw key they already have on hand (printed once at provisioning time, GW-005). The script hashes it with `hashlib.sha256(...).hexdigest()` (the same, non-negotiable hashing call `auth.py`'s `get_authenticated_tenant` and `provision_tenant.py` use -- never bcrypt/argon2/scrypt), calls `ApiKeyRepository.get_by_hash(key_hash)` (already existed, GW-004) to resolve the key's `tenant_id`/`id`, then calls `ApiKeyRepository.revoke_key(tenant_id, key_id)` (already existed on both storage backends, GW-004/GW-012) -- this ticket adds the one missing call site, no new repository/interface surface. An unresolvable raw key produces a clear "no matching key" message and a non-zero exit, never a raw stack trace; a key that's already revoked is a graceful no-op that preserves its original `revoked_at` rather than erroring or re-stamping a new timestamp. **The raw key is never printed, logged, or included in any exception message anywhere in this script**, matching `provision_tenant.py`'s own discipline -- only the confirmation line (`Revoked key id=... for tenant_id=... at <revoked_at>`) is printed on success.

**No caching window**: `get_authenticated_tenant` (GW-006) calls `ApiKeyRepository.get_by_hash` fresh on every single request -- there is no cache/memoization anywhere between this script's `revoke_key` call and the next request's auth check, and this ticket adds none. A revoked key therefore fails auth on the very next request after revocation, with no propagation delay.

**Auth event audit logging (GW-014)**: builds directly on **OPS-006**'s structured-logging convention (`naive_first_common.configure_structured_logging`, already wired in `main.py` above) rather than a second, parallel logging shape -- every event below is a plain `logging.getLogger(__name__).info(...)`/`.warning(...)` call with a structured `extra={...}` payload, picked up by OPS-006's already-configured JSON formatter/correlation-id filter with no new `Formatter`/`basicConfig` call anywhere in this diff. Three event types, at three real call sites:
- `api_key_issued` (`scripts/provision_tenant.py`'s `provision()`, **GW-005**) -- logged after `create_key` succeeds. `extra`: `event_type="api_key_issued"`, `outcome="success"`, `tenant_id=tenant.id`.
- `api_key_revoked` (`scripts/revoke_api_key.py`'s `revoke()`, **GW-010**, the revocation path this ticket instruments) -- logged after `revoke_key` succeeds. `extra`: `event_type="api_key_revoked"`, `outcome="success"`, `tenant_id=record.tenant_id`. The already-revoked no-op path logs nothing new -- there is no new revocation outcome to record.
- `auth_failed` (`src/app/dependencies/auth.py`'s `get_authenticated_tenant`, **GW-006**) -- logged immediately before each of the four existing `401` raises (missing both headers; malformed `Authorization`; empty `X-Api-Key`; unknown-or-revoked key), never after (a raised exception never skips the log call). `extra`: `event_type="auth_failed"`, `outcome="failure"`, `tenant_id=record.tenant_id` for the one case where a real `ApiKeyRecord` was actually resolved (a revoked key) or `tenant_id=None` for the other three cases (no record was ever resolved -- there is nothing non-secret to attribute the attempt to yet).
- **No raw keys/secrets, ever**: every log call above references only already-resolved, non-secret fields (`tenant.id`/`record.tenant_id`/a fixed literal string) -- never `raw_key`, `key_hash`, or any variable derived from the presented credential, mirroring the same "raw key never logged/printed" rule `provision_tenant.py`/`revoke_api_key.py`/`auth.py` already enforced before this ticket. Proven non-tautologically in `tests/test_audit_logging.py` -- a real `caplog` capture across all three call sites, asserting the actual raw key string used in each test case is absent from the actual captured log record's rendered output.
- **Scope, stated explicitly**: this stays a "structured local log line" -- no log retention/shipping/aggregation to any external system is added by this ticket (that remains declined, `docs/product/backlog-operability.md` OPS-007), and this is not a compliance-grade retained audit trail until a real auditor/compliance conversation defines retention requirements.
- **Real-usage caveat, found and fixed during Sprint 17 live verification, not left implicit**:
  `provision_tenant.py`/`revoke_api_key.py` each call `naive_first_common.configure_structured_logging()`
  themselves, at the top of their own `main()` -- both run as standalone CLI processes that never
  import `app.main` (where the FastAPI process itself calls this), so without their own call the
  `api_key_issued`/`api_key_revoked` log lines would be silently dropped in real operator usage
  (Python attaches no handler to the root logger by default, and its own "handler of last resort"
  only surfaces `WARNING`+, not these `INFO`-level calls) -- a gap the `caplog`-based unit tests do
  not catch, since `caplog` captures regardless of handler configuration. Live-verified after the fix:
  running both scripts against the real Compose stack now produces real, visible JSON log lines for
  both event types.

**Authentication (GW-006)**: `src/app/dependencies/auth.py` provides `get_authenticated_tenant`, a FastAPI `Depends()` dependency that authenticates a request's presented API key and resolves it to a `naive_first_common.TenantContext` (reused directly — GW-001 already depends on `naive_first_common` and the shape is identical, so a second parallel value type here would duplicate it; see implementation-plan.md section 9). It is `gateway-api`'s own resolver, not a call into `naive_first_common` — that library knows nothing about `api_keys.key_hash` and must not be taught to.
- **Header contract**: `Authorization: Bearer <key>` is checked first; `X-Api-Key: <key>` (raw key) is the fallback if `Authorization` is absent.
- **Hashing**: the presented key is hashed with `hashlib.sha256(...).hexdigest()` before any lookup — sprint-05.md's binding, non-negotiable choice (never bcrypt/argon2/scrypt; see docs/sprints/sprint-05.md). Comparison is exclusively hash-to-hash via `ApiKeyRepository.get_by_hash`'s SQL-level exact match (GW-004) — no raw key is ever compared against a stored value, because no raw key is ever stored (GW-002/GW-004). The raw key is never logged, printed, or included in any exception message.
- **401 conditions** (all raised before any downstream/routing code runs): both `Authorization` and `X-Api-Key` missing; `Authorization` present but not `Bearer `-prefixed (or the key portion is empty); `X-Api-Key` present but empty; the hashed key matches no `api_keys` row (unknown key); the matched row has `revoked_at is not None` (revoked key). Each of these four paths also logs an `auth_failed` audit event immediately before its `raise` -- see **Auth event audit logging (GW-014)** above.
- **Required pattern for any future header-based auth dependency (ARCH-008)**: any future header-based auth dependency added to this service must source its header value(s) via `Security()` + a `fastapi.security` class (e.g. `APIKeyHeader`), never bare `Header()` — this is what makes FastAPI register the header as an OpenAPI `securityScheme` and keeps it inside the single global Swagger "Authorize" dialog GW-006 already established, instead of reintroducing per-endpoint header re-entry. `auth.py`'s `_authorization_scheme`/`_x_api_key_scheme` (both `fastapi.security.APIKeyHeader` instances, consumed via `Security(_authorization_scheme)`/`Security(_x_api_key_scheme)`) are the reference implementation to copy this shape from. `Security()`/`APIKeyHeader` is responsible only for *sourcing* the raw header string for OpenAPI registration — it performs no parsing or validation of its own. `_extract_raw_key` remains the single place any format-checking of that raw string happens, regardless of which FastAPI mechanism supplied it; a future auth dependency must not duplicate format-checking logic alongside a new `Security()`/`APIKeyHeader` instance — it reuses (or extends, if genuinely a new header shape) `_extract_raw_key`'s pattern rather than re-implementing validation next to the sourcing mechanism.
- **`GW-029` (UAT-005 fix) — distinct `scheme_name=` per `APIKeyHeader` instance, required**: every `APIKeyHeader(...)` instance in this service must pass an explicit `scheme_name=` distinct from every other instance's. `fastapi.security.APIKeyHeader`'s `name=` parameter only sets the *header name*; the published OpenAPI `securityScheme` component is named after `SecurityBase.scheme_name`, which defaults to the class name (`"APIKeyHeader"`) when omitted — so any two instances that both omit it collapse into one shared, wrongly-labeled `securityScheme` in `GET /openapi.json`, making structurally distinct gates (tenant vs. operator) look identical in the published contract. `auth.py`'s `_authorization_scheme`/`_x_api_key_scheme` now pass `scheme_name="AuthorizationBearer"`/`scheme_name="XApiKey"`; `operator_auth.py`'s `_operator_token_scheme` passes `scheme_name="XOperatorToken"`. `components.securitySchemes` in the published schema therefore now has three distinctly-named entries, `/runs` (and other `get_authenticated_tenant`-gated routes) list only `AuthorizationBearer`/`XApiKey` in their `security` array, and operator-gated routes (`/tenants`, `/diagnostics/recent-errors`, `/system/runs-summary`) list only `XOperatorToken` — previously all three collapsed into one shared `"APIKeyHeader"` scheme and every gated route's `security` array was indistinguishable regardless of which dependency actually gated it. This was a schema-metadata-only fix — no runtime auth-decision code changed. See `tests/test_openapi_security_schemes.py`.

**Operator authentication (GW-021, narrow slice of `SETUP-010`; `SETUP-010` closed the remaining 401/403 gap)**: `src/app/dependencies/operator_auth.py` provides `get_authenticated_operator`, a *second*, structurally separate `Depends()` dependency from `get_authenticated_tenant` above -- no shared function, no shared header, no shared *grant* path, and no code path by which a tenant's own API key can satisfy this dependency or vice versa (proven in `tests/test_operator_auth.py`).
- **This is a deliberate stopgap, not `SETUP-010`'s full scope**: a single shared `OPERATOR_TOKEN` environment-variable secret gates the entire operator surface -- there is no multi-admin user table, no per-operator identity, no audit trail distinguishing one human operator from another. `SETUP-010`'s own full scope (and `SETUP-011`'s full `/tenants` list/create/revoke surface) remains that sibling backlog's own scope, not duplicated here -- this sprint pulled only the minimal slice needed to unblock `DASH-112`/`DASH-113`.
- **Header contract**: `X-Operator-Token: <token>`, sourced via `Security()` + `fastapi.security.APIKeyHeader` (`ARCH-008`'s convention, same shape `auth.py`'s `_authorization_scheme`/`_x_api_key_scheme` already established), so it registers as its own OpenAPI `securityScheme`.
- **Hashing**: the presented token is hashed with `hashlib.sha256(...).hexdigest()` and compared to a hash of the `OPERATOR_TOKEN` environment variable -- the same non-negotiable hash-to-hash discipline `get_authenticated_tenant`/`sprint-05.md` established, reused rather than reinvented. `OPERATOR_TOKEN` is read from the environment fresh on every call (not memoized at import), so rotating it in the running environment takes effect on the very next request.
- **401 conditions**: missing header, unset/empty `OPERATOR_TOKEN` environment value, or a hash mismatch that resolves to no tenant key at all (or a revoked one).
- **403 condition (`SETUP-010`, closing GW-021's disclosed status-code gap)**: when the presented value's hash fails the `OPERATOR_TOKEN` comparison *and* it resolves to a real, non-revoked tenant `ApiKeyRecord` via `ApiKeyRepository.get_by_hash` -- the credential is real, just the wrong kind for this gate, so the dependency now distinguishes "who are you" (`401`) from "I know who you are, and you may not do this" (`403`). The repository lookup is reachable **only** on this already-failed branch, after the primary `OPERATOR_TOKEN` hash comparison; `OPERATOR_TOKEN`'s hash match remains the sole path to `200` (see `operator_auth.py`'s module docstring and `tests/test_operator_auth.py`'s `test_tenant_api_key_presented_as_operator_token_is_rejected`/`test_revoked_tenant_api_key_presented_as_operator_token_returns_401`/`test_unknown_value_presented_as_operator_token_returns_401`).

  - **`INGEST-012` (live-UAT fix)**: this route originally proxied a downstream path `ingestion-service` never built (`INGEST-009`'s `GET /connectors/{source}/status` is crawl-run status, a different resource from credential presence) -- that gap surfaced in live UAT, not in this ticket's own mocked test suite, the exact lesson `docs/sprints/sprint-18.md`'s UAT addendum names.   - **`tenant_id` (required query parameter)**: the caller here is an operator, who has no `TenantContext` of their own to source `X-Tenant-Id` from (unlike every tenant-authenticated proxy route above) -- the operator explicitly names which tenant's credential status to check. Headers are built by hand here (`{"X-Tenant-Id": tenant_id}`), not via `build_downstream_headers` (GW-007) -- that helper's signature takes a `TenantContext`, which an operator caller does not have; this route is also deliberately narrower than `build_downstream_headers` (no `X-Correlation-Id`) since extending it to carry correlation IDs is a separate, undiscussed change.

Proven in `tests/test_operator_routing.py` (mocked transport, tenant_id forwarding, missing-`tenant_id` `422`) and `tests/test_operator_auth.py` (unchanged, re-confirming a tenant's own API key never satisfies `get_authenticated_operator`).

**Health check (OPS-005-02)**: `GET /health` performs a real, cheap connectivity check against the
active repository backend (whichever `DATABASE_URL`/SQLite path GW-004/GW-012's `_select_backend`
would otherwise resolve, via the same `dependencies/repositories.py` DI seam's new
`get_health_check_engine`/`HealthCheckEngineDep`) instead of unconditionally returning `ok`: it opens
a connection and runs `SELECT 1`. Healthy case is unchanged and additive -- still `200`
`{"status": "ok"}`, byte-identical to before this ticket. On any connection/execution failure it
returns `503` `{"status": "unhealthy", "detail": "database unreachable"}`, a fixed generic string with
no raw exception text, connection string, or credential -- the same body shape `validation-service`'s
own `/health` (OPS-005-01) uses, kept consistent across both services even though each implementation
is independent, per-service code. `gateway-api` has no Redis dependency, so this check is DB-only.

**Data model** (GW-002): `tenants`, `users`, `api_keys` are defined once in `src/app/models.py` (SQLAlchemy 2.0 declarative, backend-agnostic) and shared by the repository layer (GW-004) and the Alembic migration (`alembic.ini` + `migrations/`) — no duplicate schema definitions.
- `tenants(id, name, created_at)` — no `tenant_id` column on this table itself (a tenant doesn't have an id to scope by yet, GW-003).
- `users(id, tenant_id, email, role, created_at)` — `tenant_id` not-null, denormalized directly onto the row so repositories can filter by tenant without a join.
- `api_keys(id, tenant_id, key_hash, created_at, revoked_at)` — `tenant_id` not-null, same denormalization rationale. **Stores only `key_hash`** (a SHA-256 hex digest); the raw key is returned once at creation (GW-005) and never persisted — there is no `key_plaintext`/`raw_key` column anywhere in this model. `revoked_at` is nullable: revocation is a flag on the row (GW-004/GW-010), not a delete.

**Service identification convention (ARCH-007)**: every downstream-service identifier attached to an
API surface in this service follows one naming rule, kept consistent across protocols even though
only one of the three below is actually built today.
- **REST (built, in use today)**: every router mounted in `src/app/main.py` is tagged with its
  backing downstream service's name via `app.include_router(<router>, tags=["<service-name>"])`.
  The first real instance is `app.include_router(runs.router, tags=["validation-service"])` --
  `runs.router` proxies to `validation-service` (GW-008), so its OpenAPI tag names that service, not
  this one. GW-018 follows the same rule for its own router: `app.include_router(reports.router,
  tags=["reporting-service"])` -- `reports.router` proxies to `reporting-service`, so its tag names
  that service, not this one either. This is not a one-off exception; it is the pattern every future
  router follows.
- **gRPC (future, not built -- see implementation-plan.md section 4, "explicitly not using
  Kafka/RabbitMQ/gRPC yet")**: if/when a `.proto` surface is added for a downstream service, its
  `package`/`service` name must carry the same downstream-service identifier as the REST tag, e.g. a
  service currently tagged `tags=["validation-service"]` over REST would be exposed as a
  `validation_service.v1` package (or a service method namespaced consistently with that string) --
  so a reader can map a gRPC service name to the same backing service a REST tag names, without a
  separate lookup table. This is a naming rule for when gRPC is introduced, not a proposal to
  introduce it now.
- **GraphQL (future, not built)**: if/when this service's REST proxy surface is fronted or
  supplemented by a stitched GraphQL schema, each downstream service's types are namespaced with a
  type-prefix matching its REST tag (e.g. `ValidationServiceRun`, `ValidationServiceSplitResult` for
  types backed by the service tagged `validation-service`), so multiple downstream services' types
  never collide in one unified schema. Same caveat as gRPC: this documents the naming rule for later,
  it does not add GraphQL now.
- **Note for the Tech Lead**: any future router added to `gateway-api` (e.g. proxying
  `ingestion-service` once that service exists) must carry `tags=["<service-name>"]` following this
  exact convention as part of that router's own ticket's acceptance criteria -- this is process
  guidance for ticket-writing, not something enforced in code.
