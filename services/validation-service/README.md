# validation-service

**Status: implemented (Sprint 03 done — all 11 in-scope Must stories, VS-001 through VS-009/VS-011/VS-012, complete. VS-010 (tenant context resolution, unblocked by `libs/common`'s LC-001–004) is now complete too; VS-013–VS-017 deferred. See docs/sprints/sprint-03.md, docs/sprints/sprint-04.md, and docs/tickets/README.md for live ticket status). Trigger #3 (implementation-plan.md section 6) has fired.**

Wraps [`libs/naive_first_engine`](../../libs/naive_first_engine/README.md) as a REST service. See [../../docs/solution-design.md](../../docs/solution-design.md) section 3.4 and [../../docs/implementation-plan.md](../../docs/implementation-plan.md).

**Owns**: the `validation` Postgres schema (`runs`, `split_results` — see solution-design.md section 4), triggering/executing validation runs, emitting the `run.completed` event (Redis Streams) on finish.

**Does not own**: the validation algorithm itself (that's `naive_first_engine`), dataset storage (`ingestion-service`), or report rendering (`reporting-service`).

**Design notes**:
- Data access goes through a Repository layer (`ValidationRunRepository`, `SplitResultRepository`) — see implementation-plan.md section 7 — so schema-per-service can later become DB-per-service without touching call sites.
- **Repository interfaces (VS-003)**: `src/app/repositories/interfaces.py` declares both as `typing.Protocol` (no ABC — neither needs a shared default method), every method's first parameter after `self` is `tenant_id`, and both return/accept plain `@dataclass(frozen=True)` record types (`RunRecord`, `SplitResultRecord`, field-for-field mirrors of `app.models.Run`/`SplitResult`) rather than the SQLAlchemy models directly — that keeps `interfaces.py` free of any `sqlalchemy` import, mechanically checked by `tests/test_repository_interfaces.py`. Method sets:
  - `ValidationRunRepository`: `create_run(tenant_id, dataset_id, horizon, purge_gap_hours, split_config) -> RunRecord`, `get_run(tenant_id, run_id) -> RunRecord | None`, `update_run_status(tenant_id, run_id, status, *, completed_at=None, failure_reason=None) -> None`.
  - `SplitResultRepository`: `add_splits(tenant_id, run_id, splits: list[SplitResultRecord]) -> None`, `get_splits(tenant_id, run_id) -> list[SplitResultRecord]` — returned already ordered by `split_index` (the repository's job, not the caller's).
  - DI seam: `src/app/dependencies/repositories.py` declares `get_validation_run_repository`/`get_split_result_repository` provider stubs typed against these interfaces, plus `ValidationRunRepositoryDep`/`SplitResultRepositoryDep` `Annotated[..., Depends(...)]` aliases for route handlers. Concrete wiring to VS-004's implementation lands in VS-004/VS-006.
- Any client-model wrapper beyond the naive baselines (e.g. running a client-supplied prediction column through the same protocol) is a Strategy implementation of the same interface used by `naive_first_engine.baselines`, not a special case.
- Run execution follows the Template Method already encoded in `naive_first_engine`: split → baseline → metrics → DM test, fixed order, no shortcuts.

**Contract**: FastAPI service. Exact request/response *shapes* (field names, types, required-ness) are **not** hand-duplicated here -- the running service's `/openapi.json` (machine-readable) and `/docs` (interactive Swagger UI) are the source of truth (implementation-plan.md section 8: "for services, FastAPI's generated OpenAPI schema is the source of truth -- don't hand-maintain a duplicate"). The narrative below stays because it documents *behavior/design* OpenAPI can't express on its own -- tenant isolation semantics, failure handling, the synchronous-execution caveat -- not the wire shape.

## Routes

The route list below (path + method) is machine-checked against the live FastAPI app by [`scripts/check_doc_sync.py`](scripts/check_doc_sync.py) (also runnable as `tests/test_doc_sync.py`; VS-016) -- **re-run it (`.venv\Scripts\python.exe scripts/check_doc_sync.py` from this directory) after adding, removing, or renaming any route.** This list only tracks route *existence* (path + method), not request/response shape -- see `/openapi.json`/`/docs` above for that.

- `GET /health`
- `POST /runs`
- `GET /runs/{run_id}`
- `GET /runs/{run_id}/splits`

**`GET /health` (OPS-005-01)**: performs a real, cheap connectivity check against the active repository backend (opens a connection via a memoized `Engine` -- `dependencies/repositories.py`'s `get_health_check_engine`, reusing the same URL-resolution helpers as the repository providers -- and runs `SELECT 1`), instead of returning a hardcoded status. On success: `200 {"status": "ok"}`, unchanged from before this ticket (additive, not breaking). On any connection/execution exception: `503 {"status": "unhealthy", "detail": "database unreachable"}` -- the detail is a fixed generic string, never the raw exception text, connection string, or credential. Redis connectivity is out of scope here (tracked separately, VS-014's producer-side concern).
**Tenant resolution (VS-010)**: all three endpoints below resolve the caller's tenant via `Depends(naive_first_common.get_tenant_context)`, not a request field/query parameter. The interim explicit `tenant_id` body field (`POST /runs`) and `tenant_id` query parameters (both `GET` endpoints) present through Sprint 03 are retired and removed entirely. Callers now authenticate via the `X-Tenant-Id` request header. `validation-service` contains no tenant-resolution logic of its own -- `get_tenant_context`/`TenantContext` are imported as-is from `naive_first_common`; see [../../libs/common/README.md](../../libs/common/README.md) for the resolver's own documented behavior (401 on a missing/empty/whitespace-only header, interim header-based extraction pending LC-009).

- **`POST /runs` (VS-006, implemented; failure handling VS-012)**: `src/app/routers/runs.py`. Tenant: `X-Tenant-Id` request header (VS-010; see above). Request body: `dataset_id` (str, interim explicit field -- no `datasets` registry table exists in this sprint's schema, so there is nothing yet to derive it from), `dataset_reference` (dict, passed through as-is to `DatasetSource.load` -- VS-005's `InlineOrLocalFileDatasetSource` shape), `horizon` (int, >=1), `purge_gap_hours` (int, >=0), `train_window`/`test_window`/`step` (int, all >0). A missing/empty/whitespace-only `X-Tenant-Id` header returns `401` before any of these fields, `DatasetSource`, any repository, or `run_validation_protocol` is touched. Invalid values on any of the last five fields return `422` before `DatasetSource`, any repository, or `run_validation_protocol` is touched. On success (`201`): loads the dataset, builds a `naive_first_engine.protocol.ValidationConfig`, persists a `runs` row, calls `run_validation_protocol` exactly as the library exposes it, persists one `split_results` row per split, marks the run `"completed"`, and returns `{"id": ..., "status": "completed"}`. **Execution is synchronous** -- the whole protocol runs inside the request/response cycle; there is no Prefect/worker orchestration yet, so a large dataset/config will hold the HTTP connection open for the full run duration. **Failure handling (VS-012)**: `DatasetSource.load`, `run_validation_protocol`, and the split persistence that depends on their output are wrapped in a single `try`/`except Exception`. On any exception, the `runs` row is marked `status="failed"` with `failure_reason` set to `str(exc)`, and the handler still returns `201` with `{"id": ..., "status": "failed"}` -- not a `500` -- because the HTTP request itself was handled correctly; only the run failed. `run.completed` is **never** published for a failed run: the `except` branch returns immediately, and the `publish` call sits after the whole `try`/`except` statement with no `finally`/fallthrough connecting the two, so it is structurally unreachable once an exception has been caught (see `tests/test_failure_handling.py`, which asserts this against the injected `EventPublisher`'s recorded-events list, not just the HTTP response).
- **`GET /runs/{id}` (VS-007, implemented)**: same `src/app/routers/runs.py`. Tenant: `X-Tenant-Id` request header (VS-010; see above): `GET /runs/{id}`. On success (`200`): returns the full `runs` row -- `id`, `tenant_id`, `dataset_id`, `horizon`, `purge_gap_hours`, `split_config`, `status`, `created_at`, `completed_at`, `failure_reason` (VS-012; `null` unless `status="failed"`). **Tenant isolation**: a run that doesn't exist, and a run that exists but belongs to a different tenant than the header, both return `404` with the same response shape (`ValidationRunRepository.get_run` already returns `None` for both cases -- the handler never distinguishes them, since a `403` or a differently-shaped error for "exists but wrong tenant" would itself leak that the run exists).
- **`GET /runs/{id}/splits` (VS-008, implemented)**: `src/app/routers/splits.py` -- deliberately its own router module (mounted at the same `/runs` prefix, wired in `src/app/main.py`), not added to `runs.py`, so it has no file overlap with VS-007/VS-009 (both editing `runs.py`). Tenant: `X-Tenant-Id` request header (VS-010; see above): `GET /runs/{id}/splits`. On success (`200`): a list of one entry per split, ordered by `split_index` ascending (`SplitResultRepository.get_splits`'s own responsibility per VS-003's binding decision -- the handler does not re-sort), each with the full `split_results` field set per VS-002's schema/mapping decision (see "Data model" below): `split_index`; boundaries `train_start`/`train_end`/`purge_start`/`purge_end`/`test_start`/`test_end`; `model_mae`/`rmse`/`smape`/`mase`/`da`/`f1`/`oos_r2` (the `"naive_last"` baseline); `naive0_mae`/`rmse`/`smape`/`mase`/`da`/`f1`/`oos_r2` (the `"naive0"` baseline); `dm_statistic`/`dm_pvalue`/`dm_verdict` (`"naive_last"`'s DM-test result). **Tenant isolation**: the run's ownership is checked first via `ValidationRunRepository.get_run` (defense in depth -- `SplitResultRepository.get_splits` is itself tenant-scoped, but a run absent for this tenant has no meaningful splits response either way); a nonexistent run and a run belonging to a different tenant both collapse into the same `404`, same stance as `GET /runs/{id}`.

**Data model** (VS-002): `runs` and `split_results` are defined once in `src/app/models.py` (SQLAlchemy 2.0 declarative, backend-agnostic) and shared by the repository layer and the Alembic migration (`alembic.ini` + `migrations/`) — no duplicate schema definitions. `naive_first_engine.protocol.run_validation_protocol` returns per-baseline results keyed by name (`"naive0"`, `"naive_last"`); this sprint only ever produces those two. `split_results.model_*` and `dm_*` map to the `"naive_last"` baseline (the persistence-floor benchmark and its DM-test result), and `split_results.naive0_*` maps to the `"naive0"` baseline's metrics directly — see `models.py`'s module docstring for the full rationale. When VS-017 adds a client-supplied prediction baseline, `model_*`/`dm_*` will stop meaning "naive_last" and start meaning "the client model"; update this note and `models.py`'s docstring together at that point.

**Storage backend (VS-004, VS-013)**: `src/app/repositories/sqlite_repository.py` provides `SQLiteValidationRunRepository`/`SQLiteSplitResultRepository`, the original interim implementations of VS-003's interfaces, backed by a file-based SQLite database (path from `VALIDATION_SERVICE_DB_PATH`, defaulting to `./validation.db`) so run/split state survives a process restart -- still the default for local dev and the unit-test suite (`tests/test_sqlite_repository.py`, ARCH-004's `db_path` fixture), unmodified by VS-013.

Postgres is now available: `src/app/repositories/postgres_repository.py` provides `PostgresValidationRunRepository`/`PostgresSplitResultRepository`, class-for-class siblings behind the same interfaces, using `psycopg` v3 (`postgresql+psycopg://`, synchronous) via `naive_first_common.db.build_engine` (ARCH-001) and the memoized-by-URL `_get_engine` seam (ARCH-002). `src/app/dependencies/repositories.py`'s `get_validation_run_repository`/`get_split_result_repository` switch to the Postgres classes when the `DATABASE_URL` env var is set to a `postgresql://`/`postgresql+psycopg://` URL (INF-003 already wires this through Compose; see `infra/.env.example`'s `VALIDATION_SERVICE_DATABASE_URL`), falling back to the SQLite behavior above when it isn't set -- this is purely a DI swap, no route-handler or business-logic code changed (backlog decision 2). **Resolved bug (VS-021)**: `PostgresValidationRunRepository.create_run` previously called `session.refresh(run)` after `session.commit()`, which under real (non-superuser) RLS enforcement (INF-014) lost the per-transaction `app.tenant_id` scope at commit and made the post-commit refresh's own `SELECT` invisible to RLS, surfacing as an HTTP 500 despite the row being correctly persisted -- fixed by building the returned `RunRecord` from the already-fully-populated pre-commit `run` object instead, mirroring `gateway-api`'s `PostgresTenantRepository.create_tenant`/`PostgresUserRepository.create_user` (GW-012).

Tenant isolation on Postgres is enforced by real Postgres row-level security, not an application-side filter: `migrations/versions/0002_add_row_level_security.py` enables and *forces* RLS on `runs`/`split_results` with a `tenant_isolation` policy keyed on `current_setting('app.tenant_id')`, and every transaction the Postgres repository classes open sets that GUC (`SELECT set_config('app.tenant_id', :tenant_id, true)`, `SET LOCAL`'s parameter-bindable equivalent) as its first statement, before any query -- see `postgres_repository.py`'s module docstring for the full mechanism.

`migrations/env.py` targets the `validation` schema specifically for Postgres, both for table creation (`SET search_path TO validation` on the migration connection) and for `alembic_version` tracking (`version_table_schema="validation"`) -- required (not optional) per an INF-005 finding: running two services' schema-less, `public`-targeting migrations back-to-back against the same shared Postgres database caused the second one to find `public.alembic_version` already stamped and silently skip its own `upgrade()`. Both settings are conditional on the connection actually being Postgres (`connection.dialect.name == "postgresql"`) so `alembic upgrade head` against a `sqlite:///` `DATABASE_URL` (as `tests/test_models.py::test_alembic_upgrade_head_creates_matching_schema` does) is unaffected.

`src/app/dependencies/repositories.py` remains the only module that imports `sqlite_repository`/`postgres_repository` directly; route/business-logic code depends on the `ValidationRunRepository`/`SplitResultRepository` interfaces only.

**Dataset access (VS-005)**: `src/app/dataset_source.py` defines the `DatasetSource` Adapter interface (`load(reference) -> pd.Series`) and an interim implementation, `InlineOrLocalFileDatasetSource`, that accepts either an inline payload (timestamp/value pairs) or a local CSV file path. This is deliberately interim: a durable, remotely-backed implementation (VS-015) is blocked on trigger #6 (implementation-plan.md section 6) and will be a separate class behind the same interface. It does not, and will not, read `ingestion-service`'s object-storage prefixes in this sprint — dataset storage stays out of `validation-service`'s bounded context (see "Does not own" above).

**Event publishing (VS-009, durable transport VS-014)**: `src/app/events.py` defines the `EventPublisher` Observer interface (`publish(event_name: str, payload: dict) -> None`), the interim `InProcessLogEventPublisher` (VS-009), and the durable `RedisStreamsEventPublisher` (VS-014). `POST /runs`' success path (`src/app/routers/runs.py`) calls `publish("run.completed", payload)` exactly once, after the run's status is persisted as `"completed"`, with `payload = {"run_id": ..., "tenant_id": ..., "status": "completed", "completed_at": <iso8601>}` — unchanged by which implementation is wired in.

- **`InProcessLogEventPublisher`** (VS-009, interim): logs a structured line and appends to an in-memory list (`.published`); does not deliver anywhere outside this process. Used whenever `REDIS_URL` is unset.
- **`RedisStreamsEventPublisher`** (VS-014, durable): calls `redis_client.xadd(event_name, fields)`. **Wire format (binding decision, grooming #9)**: the stream key *is* the event name (`XADD run.completed ...`), and the payload is flattened into individual string fields on the stream entry — **not** a nested JSON blob in a single field:
  ```
  XADD run.completed * run_id <uuid> tenant_id <tenant> status completed completed_at <ISO-8601 timestamp>
  ```
  All four fields (`run_id`, `tenant_id`, `status`, `completed_at`) are always present as strings; `completed_at` is ISO-8601 (`datetime.isoformat()`). This is the stable, documented contract `reporting-service`'s eventual consumer (`XRANGE`/`XREAD` against the `run.completed` stream) should be built against.
- **Wiring**: `src/app/dependencies/repositories.py`'s `get_event_publisher` provider reads a single `REDIS_URL` env var (mirroring `DATABASE_URL`'s convention) — when set, it returns a memoized-by-URL `RedisStreamsEventPublisher`; when unset, it falls back to the VS-009 in-process singleton. `POST /runs`'s call site is unchanged either way. `reporting-service`'s eventual subscription to `run.completed` is still not wired end-to-end; this section only documents the producer-side contract.

See that file's own disclosure block for exactly what's reproduced vs. independently derived — it's a wiring/integration check, not a re-derivation of the algorithm's correctness (that remains `naive_first_engine`'s own regression suite's job).
