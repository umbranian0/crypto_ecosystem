**Status: implemented (Sprint 03 done — all 11 in-scope Must stories, VS-001 through VS-009/VS-011/VS-012, complete. VS-022 (`GET /runs` tenant-scoped list endpoint, closing `DASH-005-GAP`) is also done.**

Wraps [`libs/naive_first_engine`](../../libs/naive_first_engine/README.md) as a REST service. See [../../docs/solution-design.md](../../docs/solution-design.md) section 3.4 and [../../docs/implementation-plan.md](../../docs/implementation-plan.md).

**Owns**: the `validation` Postgres schema (`runs`, `split_results` — see solution-design.md section 4), triggering/executing validation runs, emitting the `run.completed` event (Redis Streams) on finish.

**Does not own**: the validation algorithm itself (that's `naive_first_engine`), dataset storage (`ingestion-service`), or report rendering (`reporting-service`).

**Design notes**:
- Data access goes through a Repository layer (`ValidationRunRepository`, `SplitResultRepository`) — see implementation-plan.md section 7 — so schema-per-service can later become DB-per-service without touching call sites.
- **Repository interfaces (VS-003, extended VS-022)**: `src/app/repositories/interfaces.py` declares both as `typing.Protocol` (no ABC — neither needs a shared default method), every method's first parameter after `self` is `tenant_id`, and both return/accept plain `@dataclass(frozen=True)` record types (`RunRecord`, `SplitResultRecord`, field-for-field mirrors of `app.models.Run`/`SplitResult`) rather than the SQLAlchemy models directly — that keeps `interfaces.py` free of any `sqlalchemy` import, mechanically checked by `tests/test_repository_interfaces.py`. Method sets:
  - `ValidationRunRepository`: `create_run(tenant_id, dataset_id, horizon, purge_gap_hours, split_config) -> RunRecord`, `get_run(tenant_id, run_id) -> RunRecord | None`, `update_run_status(tenant_id, run_id, status, *, completed_at=None, failure_reason=None) -> None`, `list_runs(tenant_id, limit, offset) -> list[RunRecord]` (VS-022; returned already ordered by `created_at` descending — the repository's job, not the caller's, mirroring `get_splits`'s precedent), `count_runs(tenant_id) -> int` (VS-022; unpaginated total, backs `GET /runs`'s response envelope `total` field).
  - `SplitResultRepository`: `add_splits(tenant_id, run_id, splits: list[SplitResultRecord]) -> None`, `get_splits(tenant_id, run_id) -> list[SplitResultRecord]` — returned already ordered by `split_index` (the repository's job, not the caller's).
  - DI seam: `src/app/dependencies/repositories.py` declares `get_validation_run_repository`/`get_split_result_repository` provider stubs typed against these interfaces, plus `ValidationRunRepositoryDep`/`SplitResultRepositoryDep` `Annotated[..., Depends(...)]` aliases for route handlers. Concrete wiring to VS-004's implementation lands in VS-004/VS-006.
- Any client-model wrapper beyond the naive baselines (e.g. running a client-supplied prediction column through the same protocol) is a Strategy implementation of the same interface used by `naive_first_engine.baselines`, not a special case.
- Run execution follows the Template Method already encoded in `naive_first_engine`: split → baseline → metrics → DM test, fixed order, no shortcuts.

**Contract**: FastAPI service. Exact request/response *shapes* (field names, types, required-ness) are **not** hand-duplicated here -- the running service's `/openapi.json` (machine-readable) and `/docs` (interactive Swagger UI) are the source of truth (implementation-plan.md section 8: "for services, FastAPI's generated OpenAPI schema is the source of truth -- don't hand-maintain a duplicate"). The narrative below stays because it documents *behavior/design* OpenAPI can't express on its own -- tenant isolation semantics, failure handling, the synchronous-execution caveat -- not the wire shape.

## Routes

The route list below (path + method) is machine-checked against the live FastAPI app by [`scripts/check_doc_sync.py`](scripts/check_doc_sync.py) (also runnable as `tests/test_doc_sync.py`; VS-016) -- **re-run it (`.venv\Scripts\python.exe scripts/check_doc_sync.py` from this directory) after adding, removing, or renaming any route.** This list only tracks route *existence* (path + method), not request/response shape -- see `/openapi.json`/`/docs` above for that.

- `GET /health`
- `POST /runs`
- `GET /runs`
- `GET /runs/{run_id}`
- `GET /runs/{run_id}/splits`

**`GET /health` (OPS-005-01)**: performs a real, cheap connectivity check against the active repository backend (opens a connection via a memoized `Engine` -- `dependencies/repositories.py`'s `get_health_check_engine`, reusing the same URL-resolution helpers as the repository providers -- and runs `SELECT 1`), instead of returning a hardcoded status. On success: `200 {"status": "ok"}`, unchanged from before this ticket (additive, not breaking). On any connection/execution exception: `503 {"status": "unhealthy", "detail": "database unreachable"}` -- the detail is a fixed generic string, never the raw exception text, connection string, or credential. Redis connectivity is out of scope here (tracked separately, VS-014's producer-side concern).
**Tenant resolution (VS-010)**: all four endpoints below resolve the caller's tenant via `Depends(naive_first_common.get_tenant_context)`, not a request field/query parameter. The interim explicit `tenant_id` body field (`POST /runs`) and `tenant_id` query parameters (both `GET` endpoints) present through Sprint 03 are retired and removed entirely. Callers now authenticate via the `X-Tenant-Id` request header. `validation-service` contains no tenant-resolution logic of its own -- `get_tenant_context`/`TenantContext` are imported as-is from `naive_first_common`; see [../../libs/common/README.md](../../libs/common/README.md) for the resolver's own documented behavior (401 on a missing/empty/whitespace-only header, interim header-based extraction pending LC-009).

- **`POST /runs` (VS-006, implemented; failure handling VS-012)**: `src/app/routers/runs.py`. Tenant: `X-Tenant-Id` request header (VS-010; see above). Request body: `dataset_id` (str, interim explicit field -- no `datasets` registry table exists in this sprint's schema, so there is nothing yet to derive it from), `dataset_reference` (dict, passed through as-is to `DatasetSource.load` -- VS-005's `InlineOrLocalFileDatasetSource` shape), `horizon` (int, >=1), `purge_gap_hours` (int, >=0), `train_window`/`test_window`/`step` (int, all >0). A missing/empty/whitespace-only `X-Tenant-Id` header returns `401` before any of these fields, `DatasetSource`, any repository, or `run_validation_protocol` is touched. Invalid values on any of the last five fields return `422` before `DatasetSource`, any repository, or `run_validation_protocol` is touched. On success (`201`): loads the dataset, builds a `naive_first_engine.protocol.ValidationConfig`, persists a `runs` row, calls `run_validation_protocol` exactly as the library exposes it, persists one `split_results` row per split, marks the run `"completed"`, and returns `{"id": ..., "status": "completed"}`. **Execution is synchronous** -- the whole protocol runs inside the request/response cycle; there is no Prefect/worker orchestration yet, so a large dataset/config will hold the HTTP connection open for the full run duration. **Failure handling (VS-012)**: `DatasetSource.load`, `run_validation_protocol`, and the split persistence that depends on their output are wrapped in a single `try`/`except Exception`. On any exception, the `runs` row is marked `status="failed"` with `failure_reason` set to `str(exc)`, and the handler still returns `201` with `{"id": ..., "status": "failed"}` -- not a `500` -- because the HTTP request itself was handled correctly; only the run failed. `run.completed` is **never** published for a failed run: the `except` branch returns immediately, and the `publish` call sits after the whole `try`/`except` statement with no `finally`/fallthrough connecting the two, so it is structurally unreachable once an exception has been caught (see `tests/test_failure_handling.py`, which asserts this against the injected `EventPublisher`'s recorded-events list, not just the HTTP response). **Client-supplied prediction baseline (VS-017)**: when `client_prediction_reference` is present, the handler loads it via the same `DatasetSourceDep` seam as `dataset_reference` (no second dataset-loading mechanism), wraps the resulting series in `app.client_baseline.ClientPredictionBaseline` (a Strategy implementation of `naive_first_engine.baselines.Baseline`), and passes it as `ValidationConfig.extra_baselines=[...]` -- a third, strictly additive entry. The two mandatory naive baselines (Naive0/NaiveLast) are never conditional on this. When `client_prediction_reference` is absent (the default), behavior is byte-identical to before this ticket.
- **`GET /runs` (VS-022, implemented)**: same `src/app/routers/runs.py`. Tenant: `X-Tenant-Id` request header (VS-010; see above). Query params: `limit` (int, default 20, `ge=1, le=100` -- a hard server-side ceiling, not a client-suggested default; FastAPI's own `Query(...)` constraints reject out-of-range values with `422` before `ValidationRunRepository` is touched, never silently clamped) and `offset` (int, default 0, `ge=0`). On success (`200`): `{"items": [...], "limit": ..., "offset": ..., "total": ...}` -- `items` is a page of `RunSummaryResponse` (imported from `naive_first_common.contracts`, ARCH-003; a strict subset of `RunDetailResponse`'s fields -- `id`, `dataset_id`, `horizon`, `status`, `created_at`, `completed_at`, deliberately omitting `split_config`/`tenant_id`/`failure_reason`), ordered `created_at` descending (`ValidationRunRepository.list_runs`'s own responsibility, not the handler's, mirroring `get_splits`'s "ordering is this method's job" precedent); `total` is a real, unpaginated count of this tenant's runs (`ValidationRunRepository.count_runs`), never omitted or estimated. **Tenant isolation**: `list_runs`/`count_runs` are `tenant_id`-scoped the same way every other repository method in this file is (SQL `WHERE`/RLS depending on backend) -- a caller only ever sees its own tenant's runs, never another tenant's, regardless of `limit`/`offset`. **Empty tenant**: a tenant with no runs gets `200` with `"items": []` and `"total": 0`, never a `404` -- an empty list is a valid, successful answer to "what are this tenant's runs".
- **`GET /runs/{id}` (VS-007, implemented)**: same `src/app/routers/runs.py`. Tenant: `X-Tenant-Id` request header (VS-010; see above): `GET /runs/{id}`. On success (`200`): returns the full `runs` row -- `id`, `tenant_id`, `dataset_id`, `horizon`, `purge_gap_hours`, `split_config`, `status`, `created_at`, `completed_at`, `failure_reason` (VS-012; `null` unless `status="failed"`). **Tenant isolation**: a run that doesn't exist, and a run that exists but belongs to a different tenant than the header, both return `404` with the same response shape (`ValidationRunRepository.get_run` already returns `None` for both cases -- the handler never distinguishes them, since a `403` or a differently-shaped error for "exists but wrong tenant" would itself leak that the run exists).
- **`GET /runs/{id}/splits` (VS-008, implemented)**: `src/app/routers/splits.py` -- deliberately its own router module (mounted at the same `/runs` prefix, wired in `src/app/main.py`), not added to `runs.py`, so it has no file overlap with VS-007/VS-009 (both editing `runs.py`). Tenant: `X-Tenant-Id` request header (VS-010; see above): `GET /runs/{id}/splits`. On success (`200`): a list of one entry per split, ordered by `split_index` ascending (`SplitResultRepository.get_splits`'s own responsibility per VS-003's binding decision -- the handler does not re-sort), each with the full `split_results` field set per VS-002's schema/mapping decision (see "Data model" below): `split_index`; boundaries `train_start`/`train_end`/`purge_start`/`purge_end`/`test_start`/`test_end`; `model_mae`/`rmse`/`smape`/`mase`/`da`/`f1`/`oos_r2` (the `"naive_last"` baseline); `naive0_mae`/`rmse`/`smape`/`mase`/`da`/`f1`/`oos_r2` (the `"naive0"` baseline); `dm_statistic`/`dm_pvalue`/`dm_verdict` (`"naive_last"`'s DM-test result). **Tenant isolation**: the run's ownership is checked first via `ValidationRunRepository.get_run` (defense in depth -- `SplitResultRepository.get_splits` is itself tenant-scoped, but a run absent for this tenant has no meaningful splits response either way); a nonexistent run and a run belonging to a different tenant both collapse into the same `404`, same stance as `GET /runs/{id}`. **`client_baseline` (VS-017)**: `ClientBaselineResult | null`, nested rather than flattened into a fifth near-duplicate 10-field group -- `null` whenever the run's `POST /runs` call had no `client_prediction_reference`; otherwise a nested object with the same 7 `MetricSet` fields plus `key`/`dm_statistic`/`dm_pvalue`/`dm_verdict`/**`disclaimer`**. `disclaimer` is the mandatory positioning text (`app.client_baseline.CLIENT_PREDICTION_AUDIT_DISCLAIMER`), present verbatim in every split entry that has a non-null `client_baseline` -- it states that this platform audits the *comparison* between the client-supplied series and the naive baselines under the leakage-aware protocol, and explicitly does **not** certify the *provenance* of the client's own predictions.

**Data model** (VS-002, extended VS-017): `runs` and `split_results` are defined once in `src/app/models.py` (SQLAlchemy 2.0 declarative, backend-agnostic) and shared by the repository layer and the Alembic migration (`alembic.ini` + `migrations/`) — no duplicate schema definitions. `naive_first_engine.protocol.run_validation_protocol` returns per-baseline results keyed by name (`"naive0"`, `"naive_last"`, plus one optional client-supplied entry keyed by its class name). `split_results.model_*` and `dm_*` map to the `"naive_last"` baseline (the persistence-floor benchmark and its DM-test result), and `split_results.naive0_*` maps to the `"naive0"` baseline's metrics directly — see `models.py`'s module docstring for the full rationale. **These two mandatory baselines are always computed by `run_validation_protocol` itself, unconditionally, regardless of whether a client prediction is supplied** — VS-017 never made `model_*`/`naive0_*`/`dm_*` conditional (`tests/test_naive_baselines_mandatory.py` proves this structurally, mirroring VS-012's own "structurally unreachable" test style). **VS-017's `split_results.client_baseline_results`** (nullable JSON column) is a *separate* column, not a repurposing of `model_*`/`dm_*` — it stores the optional third (client-supplied) baseline's full result (`{"key", "metrics": {...7 MetricSet fields...}, "dm_statistic", "dm_pvalue", "dm_verdict"}`) per split, `NULL` whenever no `client_prediction_reference` was supplied for that run (`migrations/versions/0003_add_client_baseline_results.py`).

**Storage backend (VS-004, VS-013)**: `src/app/repositories/sqlite_repository.py` provides `SQLiteValidationRunRepository`/`SQLiteSplitResultRepository`, the original interim implementations of VS-003's interfaces, backed by a file-based SQLite database (path from `VALIDATION_SERVICE_DB_PATH`, defaulting to `./validation.db`) so run/split state survives a process restart -- still the default for local dev and the unit-test suite (`tests/test_sqlite_repository.py`, ARCH-004's `db_path` fixture), unmodified by VS-013.

Postgres is now available: `src/app/repositories/postgres_repository.py` provides `PostgresValidationRunRepository`/`PostgresSplitResultRepository`, class-for-class siblings behind the same interfaces, using `psycopg` v3 (`postgresql+psycopg://`, synchronous) via `naive_first_common.db.build_engine` (ARCH-001) and the memoized-by-URL `_get_engine` seam (ARCH-002). `src/app/dependencies/repositories.py`'s `get_validation_run_repository`/`get_split_result_repository` switch to the Postgres classes when the `DATABASE_URL` env var is set to a `postgresql://`/`postgresql+psycopg://` URL (INF-003 already wires this through Compose; see `infra/.env.example`'s `VALIDATION_SERVICE_DATABASE_URL`), falling back to the SQLite behavior above when it isn't set -- this is purely a DI swap, no route-handler or business-logic code changed (backlog decision 2). **Resolved bug (VS-021)**: `PostgresValidationRunRepository.create_run` previously called `session.refresh(run)` after `session.commit()`, which under real (non-superuser) RLS enforcement (INF-014) lost the per-transaction `app.tenant_id` scope at commit and made the post-commit refresh's own `SELECT` invisible to RLS, surfacing as an HTTP 500 despite the row being correctly persisted -- fixed by building the returned `RunRecord` from the already-fully-populated pre-commit `run` object instead, mirroring `gateway-api`'s `PostgresTenantRepository.create_tenant`/`PostgresUserRepository.create_user` (GW-012).

Tenant isolation on Postgres is enforced by real Postgres row-level security, not an application-side filter: `migrations/versions/0002_add_row_level_security.py` enables and *forces* RLS on `runs`/`split_results` with a `tenant_isolation` policy keyed on `current_setting('app.tenant_id')`, and every transaction the Postgres repository classes open sets that GUC (`SELECT set_config('app.tenant_id', :tenant_id, true)`, `SET LOCAL`'s parameter-bindable equivalent) as its first statement, before any query -- see `postgres_repository.py`'s module docstring for the full mechanism. VS-022's `list_runs`/`count_runs` reuse this same `_tenant_scoped_session` helper -- no new isolation mechanism introduced.

**Index (VS-025/DBOPT-002)**: `validation.runs` has a composite index, `ix_runs_tenant_id_created_at` on `(tenant_id, created_at DESC)` (`migrations/versions/0005_add_runs_tenant_created_at_index.py`), serving the `tenant_id` equality filter shared by `list_runs`, `count_runs`, and the RLS policy above, plus `list_runs`'s `ORDER BY created_at DESC` directly from the index (no separate `Sort` node). Live-verified against the real Compose Postgres container: both queries went from a full `Seq Scan` (1,928+ rows) to an `Index Scan`/`Index Only Scan` on this index.

`split_results` is also a TimescaleDB hypertable (INF-010, migration `0004_convert_split_results_to_hypertable.py`), partitioned on `test_start` -- a performance-only change with no effect on the repository methods above (a hypertable is queried via plain SQL exactly like an ordinary table) and no new query surface; see `infra/README.md`'s own INF-010 section for the full detail. **Index (VS-026/DBOPT-003)**: `validation.split_results` also has a composite index, `ix_split_results_tenant_run` on `(tenant_id, run_id)` (`migrations/versions/0006_add_split_results_tenant_run_index.py`), serving `SplitResultRepository.get_splits`'s `WHERE run_id = :run_id AND tenant_id = :tenant_id` predicate -- issued once against the hypertable root and confirmed (live, against the real Compose Postgres container, TimescaleDB 2.29.1) to propagate to all 108 pre-existing chunks, not only chunks created after the migration ran. **Chunk interval retuning (VS-027/DBOPT-004)**: alidation.split_results's chunk_time_interval was retuned from TimescaleDB's 7-day default to 90 days (migrations/versions/0007_retune_split_results_chunk_interval.py), live-verified against the real Compose Postgres container. This only affects chunks created after the change -- the existing 108 undersized chunks (averaging ~5 rows/chunk under the old 7-day default) are not retroactively resized or merged; their count and boundaries are confirmed unchanged immediately after this migration runs.

`migrations/env.py` targets the `validation` schema specifically for Postgres, both for table creation (`SET search_path TO validation` on the migration connection) and for `alembic_version` tracking (`version_table_schema="validation"`) -- required (not optional) per an INF-005 finding: running two services' schema-less, `public`-targeting migrations back-to-back against the same shared Postgres database caused the second one to find `public.alembic_version` already stamped and silently skip its own `upgrade()`. Both settings are conditional on the connection actually being Postgres (`connection.dialect.name == "postgresql"`) so `alembic upgrade head` against a `sqlite:///` `DATABASE_URL` (as `tests/test_models.py::test_alembic_upgrade_head_creates_matching_schema` does) is unaffected.

`src/app/dependencies/repositories.py` remains the only module that imports `sqlite_repository`/`postgres_repository` directly; route/business-logic code depends on the `ValidationRunRepository`/`SplitResultRepository` interfaces only.

**Dataset access (VS-005, extended VS-015)**: `src/app/dataset_source.py` defines the `DatasetSource` Adapter interface (`load(reference) -> pd.Series`) and an interim implementation, `InlineOrLocalFileDatasetSource`, that accepts either an inline payload (timestamp/value pairs) or a local CSV file path. It does not, and will not, own the bucket/prefix scheme itself -- dataset storage layout stays `ingestion-service`'s scope (see "Does not own" above).

`ObjectStorageDatasetSource` (VS-015) is the durable, remotely-backed implementation behind the same interface: `reference` is a dict with an `"object_key"` key (e.g. `{"object_key": "processed/{tenant_id}/{dataset_id}.csv"}`) naming a two-column CSV object in the `processed/{tenant_id}/...` object-storage zone (solution-design.md section 3.2), fetched via a `boto3` S3-compatible client against `INF-008`'s MinIO container and parsed by reusing `InlineOrLocalFileDatasetSource._read_csv`/`_build_series` directly (no second CSV-parsing implementation). It is read-only by construction -- no `put_object`/`upload_file`/`delete_object` method exists anywhere on the class. `CompositeDatasetSource` wraps both implementations behind the single `DatasetSource` interface and dispatches on `reference`'s keys at `load()` time (`"inline"`/`"path"` -> `InlineOrLocalFileDatasetSource`, `"object_key"` -> `ObjectStorageDatasetSource`, anything else -> the same `DatasetSourceError` as before); `src/app/dependencies/repositories.py`'s `get_dataset_source()` always returns a `CompositeDatasetSource` wrapping both, so `POST /runs`'s handler code is unaware of, and unchanged by, which underlying implementation actually serves a given call. New env vars (S3 client memoized by connection params, mirroring `_get_engine`'s memoized-by-URL pattern): `OBJECT_STORAGE_ENDPOINT_URL` (e.g. `http://minio:9000` inside Compose, `http://localhost:9000` for a local host run), `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY`, `OBJECT_STORAGE_BUCKET` (defaults to `naive-first` if unset).

**Non-negotiable care condition -- read this before assuming anything about real data**: this ticket makes the read-side *adapter* real (a genuine, tested `boto3` reader against the live `INF-008` MinIO container -- see `tests/test_dataset_source.py`'s real-MinIO integration test) but it does **not** mean a real, tenant-scoped `processed/{tenant_id}/...` zone is actually populated with real pilot data. That still depends on `ingestion-service` actually writing there, which is a separate, not-yet-confirmed fact this story does not assume into existence -- today, calling `CompositeDatasetSource.load` with an `"object_key"` reference against a real deployment will only succeed once something else has actually put an object at that key.

**Dataset access, fourth mode (VS-023, revised per ADR-0005)**: `IngestionServiceDatasetSource` reads a `{tenant_id, source}` continuous-table time-range slice by calling `ingestion-service`'s own `GET /datasets/{source}/series?start=&end=&field=` endpoint (`INGEST-009`) directly by Compose hostname (`http://ingestion-service:8003`) -- never through `gateway-api` (that hop is reserved for `dashboard-web`'s external calls) and never by importing `ingestion.*` tables/schema directly, matching this module's hard "no service reads another service's schema" rule (implementation-plan.md section 2) and the same direct-by-hostname precedent `reporting-service` already uses for its own call into `validation-service`. `reference` shape: `{"source": str, "start": "<iso8601, optional>", "end": "<iso8601, optional>", "field": "<optional>"}` -- a fourth, distinct dispatch key (`"source"`) alongside `"inline"`/`"path"`/`"object_key"`, reflecting the locked-in continuous-table dataset semantics (a dataset is `{tenant, source}` itself, not a discrete snapshot -- see `docs/adr/0005-dataset-is-a-continuous-tenant-source-table.md`). Reuses `InlineOrLocalFileDatasetSource._build_series` for the fetched JSON's timestamp/value parsing (no second parsing implementation); a downstream timeout/404/malformed-response/connection failure all raise the same `DatasetSourceError` every other `DatasetSource` implementation already raises. `CompositeDatasetSource` takes an optional fourth constructor argument (`ingestion_service_source`, default `None`) so existing call sites/tests built with only the first two/three sources keep working unmodified; a `"source"`-shaped reference against a composite built without one raises `DatasetSourceError` rather than an `AttributeError`. Grep-checkable rule proven at ticket time: `grep -R "ingestion\." services/validation-service/src` returns nothing beyond comments/docstrings. **Live-UAT finding, methodological (see docs/sprints/sprint-18.md's UAT addendum)**: `ingestion-service`'s `field` values (`close`, `value`, `reddit_sid_com`) are all raw levels, not returns -- validating a model against a raw price level is not a meaningful naive-first audit (Naive0 is nonsensically wrong by construction on levels, producing an artifact "better than naive" verdict, not a real finding). Neither this module nor `ingestion-service` currently computes a returns series -- that transform is the caller's responsibility today until a product decision is made about whether it belongs in this pipeline at all.

**Tenant-identity forwarding is real (`VS-024`)**: `IngestionServiceDatasetSource` now requires a `tenant_id` at construction time (not a `load()` argument -- `load(reference)` is the fixed `DatasetSource` Protocol signature every implementation shares) and sends it as an `X-Tenant-Id` header on every outbound `GET /datasets/{source}/series` call, so a same-named `source` table scoped to a different tenant can never come back for the calling tenant. `src/app/dependencies/repositories.py`'s `get_dataset_source()` provider resolves the current request's own `TenantContext` (via `Depends(get_tenant_context)`) and threads it straight into a freshly-constructed `IngestionServiceDatasetSource` for that request -- `POST /runs`'s handler code is unchanged (it still only ever calls `dataset_source.load(reference)`); the tenant scoping happens entirely inside this provider. New env vars, same convention as `gateway-api`'s own `dependencies/http_client.py`: `INGESTION_SERVICE_URL` (default `http://localhost:8003`), `VALIDATION_SERVICE_DOWNSTREAM_TIMEOUT_SECONDS` (default `30.0`). **Not yet done**: `infra/docker-compose.yml`'s `validation-service` entry does not set `INGESTION_SERVICE_URL` (that env var block is out of this ticket's stated file scope, `dependencies/repositories.py` only) -- a real Compose deployment needs that entry added (mirroring `gateway-api`'s own `INGESTION_SERVICE_URL` wiring) before this path works against the live network, same category of gap Sprint 18's UAT found for `gateway-api`. `tests/test_ingestion_dataset_source_tenant_forwarding.py` is the non-tautological cross-tenant proof: two tenants with a same-named source but different actual values, verified by asserting on the actual persisted split metrics, not just "a series came back".

**Event publishing (VS-009, durable transport VS-014)**: `src/app/events.py` defines the `EventPublisher` Observer interface (`publish(event_name: str, payload: dict) -> None`), the interim `InProcessLogEventPublisher` (VS-009), and the durable `RedisStreamsEventPublisher` (VS-014). `POST /runs`' success path (`src/app/routers/runs.py`) calls `publish("run.completed", payload)` exactly once, after the run's status is persisted as `"completed"`, with `payload = {"run_id": ..., "tenant_id": ..., "status": "completed", "completed_at": <iso8601>}` — unchanged by which implementation is wired in.

- **`InProcessLogEventPublisher`** (VS-009, interim): logs a structured line and appends to an in-memory list (`.published`); does not deliver anywhere outside this process. Used whenever `REDIS_URL` is unset.
- **`RedisStreamsEventPublisher`** (VS-014, durable): calls `redis_client.xadd(event_name, fields)`. **Wire format (binding decision, grooming #9)**: the stream key *is* the event name (`XADD run.completed ...`), and the payload is flattened into individual string fields on the stream entry — **not** a nested JSON blob in a single field:
  ```
  XADD run.completed * run_id <uuid> tenant_id <tenant> status completed completed_at <ISO-8601 timestamp>
  ```
  All four fields (`run_id`, `tenant_id`, `status`, `completed_at`) are always present as strings; `completed_at` is ISO-8601 (`datetime.isoformat()`). This is the stable, documented contract `reporting-service`'s eventual consumer (`XRANGE`/`XREAD` against the `run.completed` stream) should be built against.
- **Wiring**: `src/app/dependencies/repositories.py`'s `get_event_publisher` provider reads a single `REDIS_URL` env var (mirroring `DATABASE_URL`'s convention) — when set, it returns a memoized-by-URL `RedisStreamsEventPublisher`; when unset, it falls back to the VS-009 in-process singleton. `POST /runs`'s call site is unchanged either way. `reporting-service`'s eventual subscription to `run.completed` is still not wired end-to-end; this section only documents the producer-side contract.
