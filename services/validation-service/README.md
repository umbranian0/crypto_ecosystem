Wraps [`libs/naive_first_engine`](../../libs/naive_first_engine/README.md) as a REST service. See [../../docs/solution-design.md](../../docs/solution-design.md) section 3.4 and [../../docs/implementation-plan.md](../../docs/implementation-plan.md).

**Owns**: the `validation` Postgres schema (`runs`, `split_results` — see solution-design.md section 4), triggering/executing validation runs, emitting the `run.completed` event (Redis Streams) on finish.

**Does not own**: the validation algorithm itself (that's `naive_first_engine`), dataset storage (`ingestion-service`), or report rendering (`reporting-service`).

**Design notes**:
- Data access goes through a Repository layer (`ValidationRunRepository`, `SplitResultRepository`) — see implementation-plan.md section 7 — so schema-per-service can later become DB-per-service without touching call sites.
- **Repository interfaces (VS-003, extended VS-022)**: `src/app/repositories/interfaces.py` declares both as `typing.Protocol` (no ABC — neither needs a shared default method), every method's first parameter after `self` is `tenant_id`, and both return/accept plain `@dataclass(frozen=True)` record types (`RunRecord`, `SplitResultRecord`, field-for-field mirrors of `app.models.Run`/`SplitResult`) rather than the SQLAlchemy models directly — that keeps `interfaces.py` free of any `sqlalchemy` import, mechanically checked by `tests/test_repository_interfaces.py`. Method sets:
  - `ValidationRunRepository`: `create_run(tenant_id, dataset_id, horizon, purge_gap_hours, split_config) -> RunRecord`, `get_run(tenant_id, run_id) -> RunRecord | None`, `update_run_status(tenant_id, run_id, status, *, completed_at=None, failure_reason=None) -> None`, `list_runs(tenant_id, limit, offset) -> list[RunRecord]` (VS-022; returned already ordered by `created_at` descending — the repository's job, not the caller's, mirroring `get_splits`'s precedent), `count_runs(tenant_id) -> int` (VS-022; unpaginated total, backs `GET /runs`'s response envelope `total` field).
  - `SplitResultRepository`: `add_splits(tenant_id, run_id, splits: list[SplitResultRecord]) -> None`, `get_splits(tenant_id, run_id) -> list[SplitResultRecord]` — returned already ordered by `split_index` (the repository's job, not the caller's).
  - DI seam: `src/app/dependencies/repositories.py` declares `get_validation_run_repository`/`get_split_result_repository` provider stubs typed against these interfaces, plus `ValidationRunRepositoryDep`/`SplitResultRepositoryDep` `Annotated[..., Depends(...)]` aliases for route handlers. Concrete wiring to VS-004's implementation lands in VS-004/VS-006.
- Any client-model wrapper beyond the naive baselines (e.g. running a client-supplied prediction column through the same protocol) is a Strategy implementation of the same interface used by `naive_first_engine.baselines`, not a special case.
- Run execution follows the Template Method already encoded in `naive_first_engine`: split → baseline → metrics → DM test, fixed order, no shortcuts.

**Contract**: FastAPI service. Exact request/response *shapes* (field names, types, required-ness) are **not** hand-duplicated here -- the running service's `/openapi.json` (machine-readable) and `/docs` (interactive Swagger UI) are the source of truth (implementation-plan.md section 8: "for services, FastAPI's generated OpenAPI schema is the source of truth -- don't hand-maintain a duplicate"). The narrative below stays because it documents *behavior/design* OpenAPI can't express on its own -- tenant isolation semantics, failure handling, the synchronous-execution caveat -- not the wire shape.

**`GET /health` (OPS-005-01)**: performs a real, cheap connectivity check against the active repository backend (opens a connection via a memoized `Engine` -- `dependencies/repositories.py`'s `get_health_check_engine`, reusing the same URL-resolution helpers as the repository providers -- and runs `SELECT 1`), instead of returning a hardcoded status. On success: `200 {"status": "ok"}`, unchanged from before this ticket (additive, not breaking). On any connection/execution exception: `503 {"status": "unhealthy", "detail": "database unreachable"}` -- the detail is a fixed generic string, never the raw exception text, connection string, or credential. Redis connectivity is out of scope here (tracked separately, VS-014's producer-side concern).
**Tenant resolution (VS-010)**: all four endpoints below resolve the caller's tenant via `Depends(naive_first_common.get_tenant_context)`, not a request field/query parameter. The interim explicit `tenant_id` body field (`POST /runs`) and `tenant_id` query parameters (both `GET` endpoints) present through Sprint 03 are retired and removed entirely. Callers now authenticate via the `X-Tenant-Id` request header. `validation-service` contains no tenant-resolution logic of its own -- `get_tenant_context`/`TenantContext` are imported as-is from `naive_first_common`; see [../../libs/common/README.md](../../libs/common/README.md) for the resolver's own documented behavior (401 on a missing/empty/whitespace-only header, interim header-based extraction pending LC-009).

- **`POST /runs` (VS-006, implemented; failure handling VS-012)**: `src/app/routers/runs.py`. Tenant: `X-Tenant-Id` request header (VS-010; see above). Request body: `dataset_id` (str, interim explicit field -- no `datasets` registry table exists in this sprint's schema, so there is nothing yet to derive it from), `dataset_reference` (dict, passed through as-is to `DatasetSource.load` -- VS-005's `InlineOrLocalFileDatasetSource` shape), `horizon` (int, >=1), `purge_gap_hours` (int, >=0), `train_window`/`test_window`/`step` (int, all >0). A missing/empty/whitespace-only `X-Tenant-Id` header returns `401` before any of these fields, `DatasetSource`, any repository, or `run_validation_protocol` is touched. Invalid values on any of the last five fields return `422` before `DatasetSource`, any repository, or `run_validation_protocol` is touched. On success (`201`): loads the dataset, builds a `naive_first_engine.protocol.ValidationConfig`, persists a `runs` row, calls `run_validation_protocol` exactly as the library exposes it, persists one `split_results` row per split, marks the run `"completed"`, and returns `{"id": ..., "status": "completed"}`. **Split-count guardrail (RSS-004)**: once the dataset loads successfully, before any `runs` row is created or `run_validation_protocol` is invoked, the handler calls `naive_first_engine.splitting.generate_splits` directly (the same function/arguments the protocol uses internally) and rejects with `422` (actual computed split count + a suggestion to increase `step`/narrow the date range/reduce `train_window`/`test_window`) if the result exceeds `MAX_SPLIT_COUNT = 500` -- a conservative-by-design safety margin, not a performance-tuned ceiling; see `docs/product/backlog-run-submission-safety.md` (OQ-1/OQ-2/OQ-3) for the full rationale. **Zero-split guardrail (DH-005)**: the same guardrail also rejects with `422` when the already-computed split count is exactly `0` (a config whose `train_window + purge_gap_hours + test_window` exceeds the loaded series' row count), naming the concrete cause (row count vs. the three window values and their sum) in the message -- previously this was silently accepted as a `"completed"` run with zero `split_results` rows, indistinguishable from a real null finding. **Throughput evidence (RSS-005)**: on tenant `e80a603ffd5e4e9e98bbfe2cba39b6e1`'s `binance_price_btcusdt_1h` source (79,180 real ingested rows), a `train_window=360, test_window=1540, step=2, purge_gap_hours=24` config produced 38,597 splits (`SELECT COUNT(*) FROM validation.split_results WHERE run_id = ...`); two independent runs completed in 502.7s and 488.4s (`completed_at - created_at`, both `status=completed`, zero errors) -- ≈78 splits/second on this hardware, at which rate the shipped `MAX_SPLIT_COUNT = 500` cap would complete in ≈6.4s. This is one real data point on one dataset/config, not a calibrated benchmark suite -- 500 is conservative-by-design, not performance-tuned, and a future, deliberate throughput benchmark (varying dataset shape/model complexity) would be needed before ever tightening the number further. **Disclosed gap, not fixed this sprint**: `gateway-api`'s `GATEWAY_API_DOWNSTREAM_TIMEOUT_SECONDS` (240s, the Compose default set in Sprint 18 per live E2E QA findings -- see `infra/docker-compose.yml` and `services/gateway-api/src/app/dependencies/http_client.py`) is shorter than these two incident runs' own ~495s average real duration; a request that had gone through `gateway-api`'s proxy instead of calling `validation-service` directly would have received a `504` while the run kept computing and completed anyway server-side -- a "zombie success" where the client believes the request failed but the tenant's run actually exists and succeeded in `validation.runs`. RSS-004's guardrail (500-split cap, ≈6.4s at measured throughput) makes this scenario unreachable for any request that passes the guardrail; it is recorded here as a disclosed gap in `gateway-api`'s timeout-vs-actual-duration relationship for any future work that revisits synchronous execution or timeout tuning, not silently omitted. **Execution is synchronous** -- the whole protocol runs inside the request/response cycle; there is no Prefect/worker orchestration yet, so a large dataset/config will hold the HTTP connection open for the full run duration. **Failure handling (VS-012)**: `DatasetSource.load`, `run_validation_protocol`, and the split persistence that depends on their output are wrapped in a single `try`/`except Exception`. On any exception, the `runs` row is marked `status="failed"` with `failure_reason` set to `str(exc)`, and the handler still returns `201` with `{"id": ..., "status": "failed"}` -- not a `500` -- because the HTTP request itself was handled correctly; only the run failed. `run.completed` is **never** published for a failed run: the `except` branch returns immediately, and the `publish` call sits after the whole `try`/`except` statement with no `finally`/fallthrough connecting the two, so it is structurally unreachable once an exception has been caught (see `tests/test_failure_handling.py`, which asserts this against the injected `EventPublisher`'s recorded-events list, not just the HTTP response). **Client-supplied prediction baseline (VS-017)**: when `client_prediction_reference` is present, the handler loads it via the same `DatasetSourceDep` seam as `dataset_reference` (no second dataset-loading mechanism), wraps the resulting series in `app.client_baseline.ClientPredictionBaseline` (a Strategy implementation of `naive_first_engine.baselines.Baseline`), and passes it as `ValidationConfig.extra_baselines=[...]` -- a third, strictly additive entry. The two mandatory naive baselines (Naive0/NaiveLast) are never conditional on this. When `client_prediction_reference` is absent (the default), behavior is byte-identical to before this ticket. **Price-level guardrail (MR-001)**: immediately after the DH-005 zero-split check and before any `runs` row is created, the handler calls `app.level_detection.detect_price_level_series` on the same already-loaded `series` (no second dataset load) and rejects with `422` if the series looks like a raw price/metric level rather than a returns series. Detection is a dependency-free heuristic (no `statsmodels`/ADF test), ANDing two signals: lag-1 autocorrelation of the raw series `> 0.90` (a price level moves in small increments relative to itself, so consecutive values are highly correlated; a returns series is close to i.i.d. noise) and `abs(mean)/std > 1.0` (a returns series is centered near 0 by construction; a price level is not). Both thresholds are conservative-by-design and disclosed in `app/level_detection.py`'s module docstring, same convention as `MAX_SPLIT_COUNT`. The `422` body names the concrete computed `lag1_autocorr`/`mean_over_std` values and instructs the caller to resubmit a returns-based series (a different `field`, or a pre-differenced dataset) -- no auto-transform is performed, matching DH-003's hard-block-not-auto-resolve precedent. **Fixture-conflict found and fixed at Tech Lead review**: this heuristic initially surfaced 19 unrelated pre-existing test failures across `test_client_baseline_endpoint.py`, `test_events.py`, `test_ingestion_dataset_source_tenant_forwarding.py`, `test_runs_endpoint.py`, `test_split_count_guardrail.py`, `test_splits_endpoint.py`, plus one of `test_regression_api.py`'s two scenarios -- all of them monotonic/near-monotonic filler series (e.g. `pd.Series(range(n))`) built for unrelated concerns (tenant isolation, split persistence, event publishing, DM-verdict wiring) that incidentally matched the price-level heuristic. Fixed by replacing the filler with deterministic, zero-centered, low-autocorrelation synthetic values in all 6 affected files -- no threshold in `level_detection.py` was retuned. Full suite passes 169/169; see `docs/tickets/MR-001.md`'s Outcome section for the full root-cause writeup.
- **`GET /runs` (VS-022, implemented)**: same `src/app/routers/runs.py`. Tenant: `X-Tenant-Id` request header (VS-010; see above). Query params: `limit` (int, default 20, `ge=1, le=100` -- a hard server-side ceiling, not a client-suggested default; FastAPI's own `Query(...)` constraints reject out-of-range values with `422` before `ValidationRunRepository` is touched, never silently clamped) and `offset` (int, default 0, `ge=0`). On success (`200`): `{"items": [...], "limit": ..., "offset": ..., "total": ...}` -- `items` is a page of `RunSummaryResponse` (imported from `naive_first_common.contracts`, ARCH-003; a strict subset of `RunDetailResponse`'s fields -- `id`, `dataset_id`, `horizon`, `status`, `created_at`, `completed_at`, deliberately omitting `split_config`/`tenant_id`/`failure_reason`), ordered `created_at` descending (`ValidationRunRepository.list_runs`'s own responsibility, not the handler's, mirroring `get_splits`'s "ordering is this method's job" precedent); `total` is a real, unpaginated count of this tenant's runs (`ValidationRunRepository.count_runs`), never omitted or estimated. **Tenant isolation**: `list_runs`/`count_runs` are `tenant_id`-scoped the same way every other repository method in this file is (SQL `WHERE`/RLS depending on backend) -- a caller only ever sees its own tenant's runs, never another tenant's, regardless of `limit`/`offset`. **Empty tenant**: a tenant with no runs gets `200` with `"items": []` and `"total": 0`, never a `404` -- an empty list is a valid, successful answer to "what are this tenant's runs".
- **`GET /runs/{id}` (VS-007, implemented)**: same `src/app/routers/runs.py`. Tenant: `X-Tenant-Id` request header (VS-010; see above): `GET /runs/{id}`. On success (`200`): returns the full `runs` row -- `id`, `tenant_id`, `dataset_id`, `horizon`, `purge_gap_hours`, `split_config`, `status`, `created_at`, `completed_at`, `failure_reason` (VS-012; `null` unless `status="failed"`). **Tenant isolation**: a run that doesn't exist, and a run that exists but belongs to a different tenant than the header, both return `404` with the same response shape (`ValidationRunRepository.get_run` already returns `None` for both cases -- the handler never distinguishes them, since a `403` or a differently-shaped error for "exists but wrong tenant" would itself leak that the run exists).
- **`GET /runs/{id}/splits` (VS-008, implemented)**: `src/app/routers/splits.py` -- deliberately its own router module (mounted at the same `/runs` prefix, wired in `src/app/main.py`), not added to `runs.py`, so it has no file overlap with VS-007/VS-009 (both editing `runs.py`). Tenant: `X-Tenant-Id` request header (VS-010; see above): `GET /runs/{id}/splits`. On success (`200`): a list of one entry per split, ordered by `split_index` ascending (`SplitResultRepository.get_splits`'s own responsibility per VS-003's binding decision -- the handler does not re-sort), each with the full `split_results` field set per VS-002's schema/mapping decision (see "Data model" below): `split_index`; boundaries `train_start`/`train_end`/`purge_start`/`purge_end`/`test_start`/`test_end`; `model_mae`/`rmse`/`smape`/`mase`/`da`/`f1`/`oos_r2` (the `"naive_last"` baseline); `naive0_mae`/`rmse`/`smape`/`mase`/`da`/`f1`/`oos_r2` (the `"naive0"` baseline); `dm_statistic`/`dm_pvalue`/`dm_verdict` (`"naive_last"`'s DM-test result). **Tenant isolation**: the run's ownership is checked first via `ValidationRunRepository.get_run` (defense in depth -- `SplitResultRepository.get_splits` is itself tenant-scoped, but a run absent for this tenant has no meaningful splits response either way); a nonexistent run and a run belonging to a different tenant both collapse into the same `404`, same stance as `GET /runs/{id}`. **`client_baseline` (VS-017)**: `ClientBaselineResult | null`, nested rather than flattened into a fifth near-duplicate 10-field group -- `null` whenever the run's `POST /runs` call had no `client_prediction_reference`; otherwise a nested object with the same 7 `MetricSet` fields plus `key`/`dm_statistic`/`dm_pvalue`/`dm_verdict`/**`disclaimer`**. `disclaimer` is the mandatory positioning text (`app.client_baseline.CLIENT_PREDICTION_AUDIT_DISCLAIMER`), present verbatim in every split entry that has a non-null `client_baseline` -- it states that this platform audits the *comparison* between the client-supplied series and the naive baselines under the leakage-aware protocol, and explicitly does **not** certify the *provenance* of the client's own predictions. **`has_client_model` (VS-029)**: both `RunDetailResponse` and `SplitResultResponse` also carry a plain `has_client_model: bool` -- a derived fact, not a second independent signal: on `SplitResultResponse` it is exactly `client_baseline_results is not None` for that split (`splits.py::get_splits`); on `RunDetailResponse` it is `any(...)` of that same condition across the run's own splits (`runs.py::get_run`, which now also depends on `SplitResultRepositoryDep` to compute it), `False` for a run with zero splits (still `pending`/`failed`). Exists so a caller (e.g. `dashboard-web`'s run-detail page, `DASH-125`) doesn't have to infer "was a real client model submitted" by checking every split's `client_baseline` itself.

**Data model** (VS-002, extended VS-017): `runs` and `split_results` are defined once in `src/app/models.py` (SQLAlchemy 2.0 declarative, backend-agnostic) and shared by the repository layer and the Alembic migration (`alembic.ini` + `migrations/`) — no duplicate schema definitions. `naive_first_engine.protocol.run_validation_protocol` returns per-baseline results keyed by name (`"naive0"`, `"naive_last"`, plus one optional client-supplied entry keyed by its class name). `split_results.model_*` and `dm_*` map to the `"naive_last"` baseline (the persistence-floor benchmark and its DM-test result), and `split_results.naive0_*` maps to the `"naive0"` baseline's metrics directly — see `models.py`'s module docstring for the full rationale. **These two mandatory baselines are always computed by `run_validation_protocol` itself, unconditionally, regardless of whether a client prediction is supplied** — VS-017 never made `model_*`/`naive0_*`/`dm_*` conditional (`tests/test_naive_baselines_mandatory.py` proves this structurally, mirroring VS-012's own "structurally unreachable" test style). **VS-017's `split_results.client_baseline_results`** (nullable JSON column) is a *separate* column, not a repurposing of `model_*`/`dm_*` — it stores the optional third (client-supplied) baseline's full result (`{"key", "metrics": {...7 MetricSet fields...}, "dm_statistic", "dm_pvalue", "dm_verdict"}`) per split, `NULL` whenever no `client_prediction_reference` was supplied for that run (`migrations/versions/0003_add_client_baseline_results.py`).

**Raw per-point predicted/actual persistence (`VS-031`)**: a new table, `split_points` (`src/app/models.py`'s
`SplitPoint`, migration `migrations/versions/0011_add_split_points_table.py`), stores one row per
`(split, baseline, test-window timestamp)` triple -- `id`, `run_id` (FK to `runs.id`), `tenant_id`
(denormalized, same rationale as `SplitResult.tenant_id`), `split_index`, `baseline_key` (one of
`"naive_last"`, `"naive0"`, or the client baseline's key -- `naive_first_engine.protocol`'s own
`NAIVE0_KEY`/`NAIVE_LAST_KEY`/class-name convention, never a repurposed enum, per VS-017's precedent
applied to this new axis), `timestamp`, `predicted`, `actual`, and `created_at` (copied from the owning
run's own `created_at` at write time -- **not** `datetime.utcnow()` recomputed per row -- so VS-032's
future age-based retention cutoff needs no join back to `runs` to filter). A separate table, not a
JSON/array column on `split_results`: the retention mechanism (VS-032) needs to delete/filter
individual rows by age, and a future paginated per-split read (RAV-007) needs `LIMIT`/`OFFSET`, neither
of which a JSON blob column supports without loading the whole blob first. RLS is enabled and forced on
`split_points` exactly matching `runs`/`split_results`'s `tenant_isolation` policy shape
(`migrations/versions/0002_add_row_level_security.py`).

`SplitPointRepository` (`src/app/repositories/interfaces.py`) is a `typing.Protocol` sibling to
`SplitResultRepository` (a different row shape, volume profile, and retention lifecycle from
`split_results` -- not a method bolted onto the existing repository): `add_points(tenant_id, run_id,
points: list[SplitPointRecord]) -> None`, `get_points(tenant_id, run_id, split_index) -> list[SplitPointRecord]`.
`SQLiteSplitPointRepository`/`PostgresSplitPointRepository` (`sqlite_repository.py`/`postgres_repository.py`)
reuse the exact same `Session`/`_tenant_scoped_session` patterns their `SplitResultRepository` siblings
already use -- no new session-management code. DI seam: `get_split_point_repository`/`SplitPointRepositoryDep`
in `src/app/dependencies/repositories.py`, same shape as `get_split_result_repository`/`SplitResultRepositoryDep`.

`POST /runs`'s existing handler (`create_run`, `src/app/routers/runs.py`) gains an additive second
persistence step per split: for each of `naive_last` (model), `naive0`, and the client baseline (when
`client_prediction_reference` was supplied), it builds `SplitPointRecord`s from the already-computed
prediction `pd.Series` and the corresponding slice of the input `series` (the same series
`run_validation_protocol` was already called with -- no second dataset load, no second `.predict()`
call), and calls `split_point_repository.add_points(...)` alongside the existing
`split_repository.add_splits(...)` call. `split_results`'s own persistence is byte-unchanged.

**Retention/pruning policy (`VS-032`)**: `split_points` is unbounded-growth-by-construction (see the
storage-growth estimate below), so a 90-day age-based retention bound ships in the same sprint as
persistence, not deferred. Bound chosen: **90 days by `created_at`**, not "20 runs per tenant/dataset"
(RAV-006's other permitted option) -- `created_at` is already denormalized onto every `split_points` row
(copied from the owning run at write time, see above), so a plain `created_at >= cutoff` predicate is a
single indexed comparison, with no per-tenant-per-dataset windowing query needed. Two enforcement
mechanisms, both real and tested, not one documented/one stubbed:
1. **`scripts/prune_split_points.py`** (new, standalone, operator/cron-run -- same shape as
   `services/gateway-api/scripts/provision_tenant.py`/`services/ingestion-service/scripts/seed_tenant.py`):
   `python scripts/prune_split_points.py [--older-than-days 90]`. Resolves the DB connection the same way
   the running service does (`DATABASE_URL` if set and Postgres-shaped, else `VALIDATION_SERVICE_DB_PATH`,
   both via `app.dependencies.repositories`'s existing URL-resolution helpers -- no second copy of that
   logic), issues one `DELETE FROM split_points WHERE created_at < :cutoff`, and prints the number of rows
   deleted. This is the primary mechanism -- it physically bounds the table's size regardless of whether
   anyone ever queries it. Runnable standalone, no running app process required.
2. **Query-time cutoff in `SplitPointRepository.get_points`** (`sqlite_repository.py`/
   `postgres_repository.py`): a defense-in-depth read-path filter (`SplitPoint.created_at >=
   now() - SPLIT_POINT_RETENTION_DAYS days`) so a read between two scheduled prune runs never serves data
   past the retention bound -- this is also exactly what RAV-007 (VS-033, "reads respect the retention
   cutoff") needs, satisfied here by construction.

Both mechanisms read a single named constant, `SPLIT_POINT_RETENTION_DAYS = 90`
(`src/app/repositories/sqlite_repository.py`, imported by `postgres_repository.py` and
`scripts/prune_split_points.py` -- same "named constant, not a magic number" convention `MAX_SPLIT_COUNT`/
`LAG1_AUTOCORR_THRESHOLD` already establish in this module); there is no second hardcoded `90` anywhere in
this policy's code.

**Storage-growth estimate** (formula: `rows = tenants × runs-per-tenant × splits-per-run ×
test-window-length × baselines-per-split`), anchored to this service's own disclosed real numbers (RSS-005
above: up to 38,597 splits/run is possible but `MAX_SPLIT_COUNT = 500` caps it; a `test_window` on the
order of hundreds of rows per that same example) -- illustrative pilot-scale assumptions, not a
guarantee (no pilot client exists yet):

- 10 tenants
- 20 runs/tenant within the 90-day retention window (the "20 runs" bound RAV-006 also permits, used here
  only as a volume assumption, not as the enforcement mechanism -- see "Bound chosen" above)
- 50 splits/run (well under the 500 cap)
- 200-row test window
- 2.3 baselines/split average (2 mandatory -- `naive_last`, `naive0` -- plus a client baseline on
  ~30% of runs)

`10 × 20 × 50 × 200 × 2.3 = 4,600,000` rows at steady state before the 90-day cutoff starts pruning. This

**`LoadedSeries` contract and the reordering-disclosure warning (DH-001)**: `DatasetSource.load(reference)` returns `LoadedSeries` (a frozen dataclass, `{series: pd.Series, warnings: list[str]}`), not a bare `pd.Series` -- applied uniformly across all four classes in `dataset_source.py` (`InlineOrLocalFileDatasetSource`, `ObjectStorageDatasetSource`, `IngestionServiceDatasetSource`, `CompositeDatasetSource`), so `CompositeDatasetSource.load()`'s dispatch stays a single return-type contract regardless of which branch serves a call. `InlineOrLocalFileDatasetSource._build_series` (reused by `ObjectStorageDatasetSource`/`IngestionServiceDatasetSource`) already called `.sort_index()` unconditionally before this ticket -- non-new, non-leakage-risk behavior (the splitter needs a sorted index and always assumed one) that was previously silently applied with no disclosure. It now also checks `is_monotonic_increasing` *before* that pre-existing, byte-unchanged sort call, and if the input was out of order, appends `"dataset rows were not in timestamp order and were sorted before validation"` (`InlineOrLocalFileDatasetSource.REORDERED_ON_LOAD_WARNING`) to the returned `warnings` list -- disclosure-only, per CLAUDE.md's no-silent-inference rule; the sorted output is unchanged. `ObjectStorageDatasetSource`/`IngestionServiceDatasetSource` reuse the same `_build_series` helper (see DH-002 below for the second, dedup, warning check it now also runs), so both can technically surface either warning -- though in practice `IngestionServiceDatasetSource`'s rows come from `ingestion-service`'s `(tenant_id, source, event_time)`-unique-keyed table, so its dedup warning should never actually fire (see DH-002's own paragraph). `POST /runs`'s primary `dataset_reference` load unpacks `LoadedSeries` and threads `warnings` through `_persist_new_run`/`ValidationRunRepository.create_run(..., warnings=[...])` into the persisted `runs.warnings` column (JSON, `nullable=False, server_default='[]'`, `migrations/versions/0008_add_runs_warnings_column.py`, same column-type precedent as `split_results.client_baseline_results`) -- so the warning survives a `GET /runs/{id}` call, not just the synchronous `POST /runs` response, via `RunDetailResponse.warnings` (`naive_first_common.contracts`, default `[]` -- required so gateway-api's/dashboard-web's own `RunDetailResponse(**response.json())` reconstruction sites stay safe against a validation-service response that temporarily omits the field during a rolling deploy). The optional VS-017 `client_prediction_reference` load also returns `LoadedSeries` (uniform contract), but its own `warnings` are not currently persisted anywhere -- out of this ticket's binding scope, which is the primary `dataset_reference` load only. This `LoadedSeries` shape is binding on DH-002/DH-003, which extend it further (same same-file chain in `dataset_source.py`).

**Exact-duplicate-row dedup (DH-002)**: `InlineOrLocalFileDatasetSource._build_series` now runs a second check immediately after DH-001's reordering check (and, per the backlog's required sequencing, before DH-003's future conflict check) and before constructing the returned `LoadedSeries` -- it drops rows that match an earlier row on *both* timestamp and value (first occurrence kept; a same-timestamp-different-value row is left alone, since resolving that is DH-003's job, not this one), and if any rows were dropped, appends `f"dropped {n} exact-duplicate rows before validation"` to the same `warnings` list DH-001 already built (both warnings can coexist on one load). This is a pure, deterministic, information-preserving transformation applied once, before any split boundary is computed -- a byte-identical duplicate row carries no new information, so first-occurrence-kept dedup cannot change what the surviving data says, and it carries no per-split leakage risk since it never looks at where a row would later fall relative to a split boundary. Because `ObjectStorageDatasetSource` and `IngestionServiceDatasetSource` both reuse this same `_build_series` helper, the dedup applies to `ObjectStorageDatasetSource` too (per this ticket's scope); `IngestionServiceDatasetSource`'s rows come from `ingestion-service`'s `(tenant_id, source, event_time)`-unique-keyed table, so its dedup warning is structurally unreachable there, and no redundant check was added to that class. Because `POST /runs`'s RSS-004/DH-005 split-count guardrail (`runs.py`) computes `split_count` from `loaded.series.index` -- the same `LoadedSeries.series` this dedup step already mutated before returning -- the guardrail always sees the post-dedup row count, with no second wiring needed in `runs.py`.

**Same-timestamp-different-value conflict, hard-blocked (DH-003)**: `InlineOrLocalFileDatasetSource._build_series` runs a third check immediately after DH-002's dedup step and before constructing the returned `LoadedSeries` -- `series.index.duplicated(keep=False)`. By construction, any timestamp still repeated at this point must differ in value (an exact `(timestamp, value)` match would already have been dropped by DH-002), so this is a genuine data conflict, not a mechanical duplicate. Unlike DH-001/DH-002 (disclosed, non-fatal warnings), this is a **hard failure**: it raises the same `DatasetSourceError` every other malformed-input case in this module already raises, naming the conflicting timestamp and all distinct values found for it (e.g. `"conflicting values for timestamp 2022-01-01T01:00:00: 0.2 vs 999.0"`, or all N distinct values when more than two rows share the timestamp) -- never just a count. No `LoadedSeries` is ever constructed or returned for an input that reaches this branch. **No auto-resolution of any kind exists in this check** -- not "keep first," not "keep last," not "average": which of two contradictory readings for the same instant is correct is a genuine judgment call about the user's own data that this platform declines to make silently, per CLAUDE.md's no-silent-inference rule and the same reasoning behind DH-090/091/092's "Won't-fix" status. Because `ObjectStorageDatasetSource`/`IngestionServiceDatasetSource` both reuse `_build_series`, they inherit this check too, though `IngestionServiceDatasetSource`'s rows come from `ingestion-service`'s `(tenant_id, source, event_time)`-unique-keyed table, so it should never actually fire there (same reasoning as DH-002's own paragraph). `runs.py::create_run`'s existing `try: loaded = dataset_source.load(...) except Exception as exc:` branch (RSS-004/VS-012, unmodified by this ticket) already turns this `DatasetSourceError` into `status="failed"`, `failure_reason=str(exc)` -- no new error-handling path was added anywhere in `runs.py`.

`ObjectStorageDatasetSource` (VS-015) is the durable, remotely-backed implementation behind the same interface: `reference` is a dict with an `"object_key"` key (e.g. `{"object_key": "processed/{tenant_id}/{dataset_id}.csv"}`) naming a two-column CSV object in the `processed/{tenant_id}/...` object-storage zone (solution-design.md section 3.2), fetched via a `boto3` S3-compatible client against `INF-008`'s MinIO container and parsed by reusing `InlineOrLocalFileDatasetSource._read_csv`/`_build_series` directly (no second CSV-parsing implementation). It is read-only by construction -- no `put_object`/`upload_file`/`delete_object` method exists anywhere on the class. `CompositeDatasetSource` wraps both implementations behind the single `DatasetSource` interface and dispatches on `reference`'s keys at `load()` time (`"inline"`/`"path"` -> `InlineOrLocalFileDatasetSource`, `"object_key"` -> `ObjectStorageDatasetSource`, anything else -> the same `DatasetSourceError` as before); `src/app/dependencies/repositories.py`'s `get_dataset_source()` always returns a `CompositeDatasetSource` wrapping both, so `POST /runs`'s handler code is unaware of, and unchanged by, which underlying implementation actually serves a given call. New env vars (S3 client memoized by connection params, mirroring `_get_engine`'s memoized-by-URL pattern): `OBJECT_STORAGE_ENDPOINT_URL` (e.g. `http://minio:9000` inside Compose, `http://localhost:9000` for a local host run), `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY`, `OBJECT_STORAGE_BUCKET` (defaults to `naive-first` if unset).

**Non-negotiable care condition -- read this before assuming anything about real data**: this ticket makes the read-side *adapter* real (a genuine, tested `boto3` reader against the live `INF-008` MinIO container -- see `tests/test_dataset_source.py`'s real-MinIO integration test) but it does **not** mean a real, tenant-scoped `processed/{tenant_id}/...` zone is actually populated with real pilot data. That still depends on `ingestion-service` actually writing there, which is a separate, not-yet-confirmed fact this story does not assume into existence -- today, calling `CompositeDatasetSource.load` with an `"object_key"` reference against a real deployment will only succeed once something else has actually put an object at that key.

**Dataset access, fourth mode (VS-023, revised per ADR-0005)**: `IngestionServiceDatasetSource` reads a `{tenant_id, source}` continuous-table time-range slice by calling `ingestion-service`'s own `GET /datasets/{source}/series?start=&end=&field=` endpoint (`INGEST-009`) directly by Compose hostname (`http://ingestion-service:8003`) -- never through `gateway-api` (that hop is reserved for `dashboard-web`'s external calls) and never by importing `ingestion.*` tables/schema directly, matching this module's hard "no service reads another service's schema" rule (implementation-plan.md section 2) and the same direct-by-hostname precedent `reporting-service` already uses for its own call into `validation-service`. `reference` shape: `{"source": str, "start": "<iso8601, optional>", "end": "<iso8601, optional>", "field": "<optional>"}` -- a fourth, distinct dispatch key (`"source"`) alongside `"inline"`/`"path"`/`"object_key"`, reflecting the locked-in continuous-table dataset semantics (a dataset is `{tenant, source}` itself, not a discrete snapshot -- see `docs/adr/0005-dataset-is-a-continuous-tenant-source-table.md`). **Event publishing (VS-009, durable transport VS-014)**: `src/app/events.py` defines the `EventPublisher` Observer interface (`publish(event_name: str, payload: dict) -> None`), the interim `InProcessLogEventPublisher` (VS-009), and the durable `RedisStreamsEventPublisher` (VS-014). `POST /runs`' success path (`src/app/routers/runs.py`) calls `publish("run.completed", payload)` exactly once, after the run's status is persisted as `"completed"`, with `payload = {"run_id": ..., "tenant_id": ..., "status": "completed", "completed_at": <iso8601>}` — unchanged by which implementation is wired in.

- **`InProcessLogEventPublisher`** (VS-009, interim): logs a structured line and appends to an in-memory list (`.published`); does not deliver anywhere outside this process. Used whenever `REDIS_URL` is unset.
- **`RedisStreamsEventPublisher`** (VS-014, durable): calls `redis_client.xadd(event_name, fields)`. **Wire format (binding decision, grooming #9)**: the stream key *is* the event name (`XADD run.completed ...`), and the payload is flattened into individual string fields on the stream entry — **not** a nested JSON blob in a single field:
  ```
  XADD run.completed * run_id <uuid> tenant_id <tenant> status completed completed_at <ISO-8601 timestamp>
  ```
  All four fields (`run_id`, `tenant_id`, `status`, `completed_at`) are always present as strings; `completed_at` is ISO-8601 (`datetime.isoformat()`). This is the stable, documented contract `reporting-service`'s eventual consumer (`XRANGE`/`XREAD` against the `run.completed` stream) should be built against.

**Multi-source feature assembly (VS-030/MDF-003)**: `src/app/feature_dataset.py`, sibling to `dataset_source.py`, resolves a `POST /runs` request's optional `feature_references: list[{"source", "field"}]` into one aligned multi-column `pandas.DataFrame` handed to a candidate model's own inference path -- `run_validation_protocol`'s call site is unmodified: `Naive0`/`NaiveLast`/`dm_test.py` still only ever see the target `pd.Series`, unaffected by this feature except possibly seeing fewer rows if `missing_timestamp_policy` trimmed the target index. Built per `docs/adr/0008-multimodal-fusion-architecture-and-leakage-posture.md` and `docs/adr/0009-multimodal-timestamp-alignment-design.md` (both `status: accepted`) -- the join lives inside this service, calling the existing `CompositeDatasetSource.load()` once per reference (no new dispatch branches, no new service).

- **Request fields**: `feature_references` (optional, default `None`/`[]`, byte-identical response shape when omitted) and `missing_timestamp_policy` -- **required whenever `feature_references` is non-empty, no default**: `naive_first_common.contracts.RunRequest`'s own `model_validator` rejects a request with features but no policy with `422` before this handler body runs (`runs.py`'s own re-check is defense in depth, not the primary gate). One of `"drop_row"` (only an *exact* eligibility-instant match counts -- never bridges a gap, per ADR-0009's "or after gaps" clause), `"forward_fill_exhausted_as_null_then_drop"` (bridges any gap via backward `merge_asof`, drops only the genuinely-unfillable leading window), or `"exclude_source"` (drops the whole feature column, never rows, if it has any alignment gap).
- **Response fields**: `RunDetailResponse.feature_lineage` (`[]` for a single-series run) -- `{"source", "field", "lag_hours"}` per feature reference that composed the run, persisted on the `runs` row (`runs.feature_lineage`, nullable JSON, `server_default='[]'`, `migrations/versions/0009_add_runs_feature_lineage_column.py`, same column-type/migration precedent as `runs.warnings`/`0008`) and `RunDetailResponse.has_multimodal_features` -- derived, not a second independent flag: `bool(run.feature_lineage)`, computed in `runs.py::get_run`, same one-source-of-truth precedent VS-029 established for `has_client_model`.
- **Per-connector lag table** (ADR-0008(b), the exact dispatch table `feature_dataset.py`'s `FEATURE_SOURCE_LAG_HOURS` encodes):

  | Source prefix | Lag (hours) | Why |
  |---|---|---|
  | `blockchain_info_*` (on-chain) | 24 | Conservative floor -- this connector's revision risk is unverified/plausibly real (ADR-0008), sampling cadence is daily-or-coarser. |
  | `binance_price_*` | 0 | No additional lag beyond the run's own `purge_gap_hours` -- a closed exchange candle is not revised after the fact. |
  | `reddit_*` (sentiment) | 0 | No *separate* buffer -- substituting `fetched_at` for `created_utc` *is* the buffer; `fetched_at` already is the "known-at" instant. |
  | anything else | 0 | Same default as price/sentiment. |

- **Alignment ordering (leakage-critical, ADR-0009)**: `routers/runs.py::create_run` calls `FeatureDatasetAssembler.assemble` immediately after the primary `dataset_source.load(request.dataset_reference)` call and reassigns `series = series.loc[assembled.index]` -- strictly *before* the RSS-004/DH-005/MR-001 guardrails and `generate_splits`/`run_validation_protocol` run, so every downstream check and the protocol call itself see only the post-alignment series, never a superset of the original target index.
- **Per-fold preprocessing fit (`FeatureFoldScaler`)**: `fit(train_df) -> FittedScaler` computes per-column mean/std only over the rows passed in -- no function in `feature_dataset.py` computes a scaler parameter over the full, unsplit `feature_dataframe` (`tests/test_feature_dataset.py`'s hard-gate tests prove this both behaviorally, fold-to-fold divergence, and structurally, an AST scan of the module). Not yet wired into any candidate-model inference call -- no such consumer interface exists yet (MDF-004's explicit, deferred question) -- but directly callable against `generate_splits`'s own output today.
- **Read-only re-export (`GET /runs/{run_id}/features`, MR-007)**: a thin HTTP adapter, added to `routers/runs.py` alongside `create_run`/`get_run` (`create_run`'s own body is untouched by this ticket), that re-invokes `FeatureDatasetAssembler.assemble` for an already-executed run keyed by `run_id` (tenant-scoped via the same `X-Tenant-Id`/`Depends(get_tenant_context)` seam every other route in this router uses) and returns the assembled table as plain JSON -- `{"index": [...ISO8601 strings...], "columns": [...], "data": [[...], ...]}` (`pandas.DataFrame.to_dict(orient="split")`'s own shape, reused rather than hand-rolled). Returns `404` for a run that doesn't exist, belongs to a different tenant, or has no multimodal features (`feature_lineage == []`), same single-404 pattern `get_run` already establishes.

  **First-cut, disclosed-limitation implementation (MR-007's own backlog framing -- not a fully general re-assembly API)**: `runs.feature_lineage` only stores `{"source", "field", "lag_hours"}` per reference (`lag_hours` is dropped when rebuilding `feature_references` -- it is *derived* by `FEATURE_SOURCE_LAG_HOURS`, not an input), and neither the run's original `missing_timestamp_policy` nor its original `dataset_reference` dict is persisted anywhere (`runs` has no `missing_timestamp_policy` column at all, and adding one would force a line into `create_run`'s body, which this ticket's AC4 forbids). This route therefore:
  - Accepts `missing_timestamp_policy` as an **optional query parameter** (`?missing_timestamp_policy=...`), defaulting to `"drop_row"` (the strictest of the three) when omitted -- a caller passing a different policy than the run's original may legitimately get back a different row count than the original run's own target index; this is a known, disclosed limitation, not a bug.
  - Reconstructs the primary series via `dataset_source.load({"source": run.dataset_id})` (the `IngestionServiceDatasetSource` shape) -- the one dataset-loading shape reconstructable from a bare `dataset_id` string. This only works for runs whose original `dataset_reference` was ingestion-service-backed with `source == dataset_id`; a run originally loaded via `inline`/`path`/`object_key` cannot be re-loaded this way and the route returns `422` naming this limitation explicitly (never a silent empty/wrong table) on `DatasetSourceError`.
  - A future ticket to persist `missing_timestamp_policy`/the original `dataset_reference` properly (accepting a `create_run` diff at that point) is the correct follow-up if this proves to matter in practice -- not solved ad hoc here.
- **Disclosed gap, real, not fixed this ticket**: `ingestion-service`'s `GET /datasets/{source}/series` (`src/app/routers/datasets.py`) does not expose each row's `fetched_at` today, even though it is stored per-row in that service's own tables. Per ADR-0009 ("never use a value's nominal timestamp as a stand-in for when it became knowable") and CLAUDE.md's no-silent-inference rule, a feature reference that resolves to `IngestionServiceDatasetSource` therefore **always fails closed** with a disclosed `FeatureDatasetError` (AC5) -- it is never silently approximated using the series' own nominal index. Real per-row `fetched_at` alignment *is* fully implemented and tested for the two dataset shapes that can carry it today: inline payloads and object-storage CSVs, both extended with an optional third `fetched_at` column/key (opt-in, backward compatible -- absent for a plain 2-column payload, byte-identical to pre-VS-030 behavior). Extending `ingestion-service`'s series endpoint to expose `fetched_at` is a different module's change, out of this ticket's file scope, and not filed as a numbered ticket by this ticket itself -- flagged here for the Tech Lead/PM to pick up as a follow-up (`INGEST-*`).
- **Connector-status guardrail (AC6)**: a feature reference naming an ingestion-service source (`"source"` key) triggers `ConnectorStatusChecker.check` (real implementation: `IngestionServiceConnectorStatusChecker`, calling `GET /connectors/{source}/status`, reusing `IngestionServiceDatasetSource`'s own `httpx.Client`/`base_url`/`X-Tenant-Id` convention) *before* any loading/alignment is attempted -- any status other than `"completed"` (`"running"`/`"queued"`/`"failed"`) is rejected fail-closed, naming the concrete status.

**Fixed bug: `failure_reason` surfacing as the bare literal `"0"` (`UAT-006`)**: `POST /runs`'s three
`except Exception as exc` failure-handling blocks (dataset load, feature assembly, protocol execution/
split persistence -- `src/app/routers/runs.py`) previously persisted `failure_reason=str(exc)` directly.
**Root cause traced**: `str(exc)` alone is not reliably human-readable -- the concrete, reproducible
failure shape this ticket responds to is any exception whose `str()` collapses to a bare digit (the
textbook example: `str(KeyError(0)) == "0"`, since `BaseException.__str__` for a single-arg exception
just returns `str(args[0])`, with no surrounding context). An exhaustive trace of every `raise` reachable
from these three blocks -- `app/dataset_source.py`, `app/feature_dataset.py`, `app/level_detection.py`,
and `naive_first_engine`'s `splitting.py`/`baselines.py`/`metrics.py`/`dm_test.py`/`protocol.py` -- found
no first-party raise that constructs such an exception directly (every `DatasetSourceError`/
`FeatureDatasetError`/`ValueError` in this codebase already embeds a descriptive f-string), so the live
incident is a genuine but not locally reproducible exception (most plausibly a `KeyError` or similar
single-arg exception surfacing from a third-party/stdlib code path, e.g. pandas/numpy internals or a
downstream HTTP client) whose message happens to match this exact int-sentinel shape. **Fix**: a new
`_fail_run(run_repository, tenant, run, exc)` helper (`runs.py`), reused by all three failure blocks
(extract-on-second-duplication, implementation-plan.md section 9 -- previously three near-identical
inline blocks), never trusts `str(exc)` to already be descriptive: it wraps any non-empty, non-numeric
message with fixed context (`"Validation run failed: {exc}"`), and replaces an empty message or a
message that is purely digits (this exact `"0"` signature, or any other digits-only message from the
same exception family) outright with a fixed, descriptive fallback naming the exception's type and the
run id (`"Validation run failed with an unspecified internal error ({type}). ... run id {id} ..."`) --
never silently re-surfaced as a lone digit. A `try`/`except` around `str(exc)` itself is the blanket
safety net for the separate "never-`str()`-able exception" case (Implementation AC2). See
`tests/test_failure_reason_readability.py`: one test deterministically triggers the exact `KeyError(0)`
repro shape via a fake `DatasetSource` and asserts `failure_reason` is non-numeric/non-empty/descriptive;
a second re-asserts DH-003's pre-existing conflicting-timestamp failure path still produces a genuinely
descriptive (not merely non-crashing) message under the new wrapping. `gateway-api` is untouched -- it
only forwards `failure_reason` as-is, per its own README.
